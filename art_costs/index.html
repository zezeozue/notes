Where the costs are in ART: cheap until the GC, a lock or native code gets involved

This is a tour of the Android Runtime (ART) from the bottom up. It covers how objects are laid out and allocated, how the garbage collectors move them, what the compiler can and cannot remove, and what it costs to call native code. Most sections end with what it means for the code you write.

Code excerpts are from art/ and libcore/ in AOSP as of Android 17, arm64. Instruction sequences marked shape are simplified. The rest are quoted from the source files listed under Sources at the bottom. Cost tiers are rough orders of magnitude, not measurements.

At a glance

  • Plain Java is cheap. Field loads, array stores and inlined calls cost a few instructions each.
  • Allocation costs later. A new object is a quick pointer bump, but every byte brings the next garbage collection closer.
  • The compiler needs to see through calls. A call it cannot inline, a raw-memory write or a volatile field makes it assume all memory changed.
  • Locks are cheap until two threads fight. Contention turns a lock into a heavier one that stays heavy.
  • Native calls pay at the border. Each regular call into C swaps thread state twice, and strings and arrays usually get copied on the way.

Terms:

  • GC: the garbage collector. CC (Concurrent Copying) and CMC (Concurrent Mark-Compact) are ART’s two collectors that run alongside the app.
  • TLAB: a chunk of memory one thread allocates from on its own.
  • Card mark: the one-byte note (the write barrier) the GC needs after a reference store.
  • Read barrier: a check after each reference load; only the CC collector needs it.
  • Suspend check: the poll compiled code runs so the GC can stop the thread.
  • Deoptimize: drop from compiled code back to the interpreter when an assumption the compiler made stops holding.
  • JNI (Java Native Interface): the bridge between Java and C. @FastNative and @CriticalNative are annotations that make its calls cheaper.
  • Thread state: whether a thread is Runnable (may touch the heap) or, for example, Native (has promised not to). A regular JNI call switches it twice.
  • Userfault: a page fault the runtime handles itself while the GC compacts the heap.

The cost ladder: each step up costs roughly ten times more

Most of this page explains why things sit where they do on this ladder. Each step up is very roughly an order of magnitude.

Part I · Memory

1Every object pays a fixed header before its fields

Every Java object starts with a small header. The runtime needs two things from each object: what class it is, and a place for lock and GC state. So the header holds a pointer to the class and a lock word, 8 bytes in all. References are compressed to 32 bits to keep objects small. Objects are padded to a fixed alignment, and arrays add a length field before their elements. The exact sizes are in Numbers and method.

The lock word packs four jobs into one field

Locking, identity hashing and the GC all need a little state per object. A separate field for each would grow every object. So ART packs them into one 32-bit field in the header. Its top two bits say which of four meanings the rest has, and two more bits belong to the GC. Figure 3 shows the exact bit widths, which come from LockWord in lock_word.h.

  • A thin lock stores the owning thread’s id and a recursion count right in the word. An id of zero means unlocked.
  • A fat lock points to a separate native Monitor object. It is used when a thin lock is not enough, for example under contention or wait() (Section 14).
  • The hash state holds the object’s identity hash code.
  • The forwarding state holds the object’s new address while the CC collector moves it (Section 5).

The mark bit and the read-barrier (“gray”) bit are scratch bits the collectors use while tracing, that is, while walking the object graph to find live objects (Section 4). Taking a thin lock is a single compare-and-swap (CAS) on this word.

What it means for you Small objects are mostly header and padding: an Integer is 16 bytes for 4 bytes of payload. A lock and an identity hash cannot both fit in the lock word. If you take an object’s identity hash and later synchronized on it, ART must switch to a fat monitor (Section 14). The identity hash comes from System.identityHashCode, or from a hashCode() the class does not override.

2The heap is several spaces, each with its own rules

The “Java heap” is several address ranges, called spaces, with different rules for allocation, moving and sharing. Objects have different needs. Framework objects should be shared by every app. Most new objects should be cheap to allocate and free to move. A few must never move, because native code holds their address.

Two spaces come from outside the app. The boot image is a precompiled snapshot of framework classes, objects and code that every process maps. It is stored in .art and .oat files. The zygote is the process every app is forked from. Whatever it allocated before forking is shared with each app, copy-on-write: a page is copied only when one side writes to it.

The app’s own objects go to the other three spaces. Almost every new object goes to the moving space, whose layout depends on the collector (Sections 5 and 6). The non-moving space is collected in place by mark-sweep: the GC marks the live objects and frees the rest, and new objects come from a free list. Primitive arrays and strings of 12 KB or more go to the large object space.

3Allocation is a pointer bump; the cost comes later, in the GC

Each thread allocates from its own buffer, so a new object needs no lock and no atomic instruction. If every thread shared one “next free byte” pointer, each new would need one. Instead each thread owns a thread-local allocation buffer (TLAB): a chunk of the moving space that only it allocates from. Allocation is then a pointer bump. TLAB sizes differ by collector and are listed in Numbers and method.

quick_entrypoints_arm64.S// art_quick_alloc_object_resolved_tlab: fast path
ldr  x4, [xSELF, #THREAD_LOCAL_POS_OFFSET]
ldr  x5, [xSELF, #THREAD_LOCAL_END_OFFSET]
ldr  w7, [x0, #MIRROR_CLASS_OBJECT_SIZE_ALLOC_FAST_PATH_OFFSET]
add  x6, x4, x7        // pos + size
cmp  x6, x5            // fits?
b.hi .Lslow_path       // (classes not yet visibly initialized, and
                       //  finalizable classes, report a huge size)
str  x6, [xSELF, #THREAD_LOCAL_POS_OFFSET]
str  w0, [x4, #MIRROR_OBJECT_CLASS_OFFSET]
mov  x0, x4
ret
// what compiled code around new Point() looks like (shape)
ldr  lr, [tr, #pAllocObjectResolved]  // entrypoint in Thread
blr  lr                               // the fast path on the left
dmb  ishst                            // constructor fence
// ... inlined constructor stores ...

Allocation is not inlined into compiled code. It is a call into a hand-written stub of about ten instructions. After the call comes a StoreStore fence (dmb ishst), an instruction that makes earlier stores visible before later ones. It stops other threads from seeing the object before its class pointer and fields are written. The compiler drops the fence when it can prove the object does not escape to another thread before the next fence.

What it means for you A single allocation is cheap: about a call plus ten instructions. The real cost is indirect. Every byte allocated moves the heap toward its next GC, and objects that survive get traced and moved. Allocating in a hot loop is mostly paying for future GC work. Finalizable classes, which override finalize(), and classes still being initialized always take the slow path.

4A GC’s cost follows what survives, not how much garbage there is

ART’s collectors find live objects by tracing, so their work grows with the objects that survive. Java code never frees memory, so the runtime has to work out which objects the program can still reach. A tracing collector starts from roots: references held outside the heap, such as thread stacks, static fields and JNI global references held by native code. It follows every reference, marks what it reaches, and treats everything else as garbage.

To find roots on thread stacks, the GC must know which stack slots and registers hold references where each thread stopped. The compiler records this as stack maps at safepoints, the instructions where a thread is allowed to stop (Section 8).

Every collector has some short pauses, where all threads stop, and long concurrent phases, where the app keeps running alongside the GC. A common pause is the thread flip (ThreadList::FlipThreadRoots). The GC suspends every thread for a moment and gives each a “flip function” that updates its stack roots to the objects’ new addresses. After the threads resume, each flip function runs exactly once. It runs either on the thread itself, before it can run Java code again, or on the GC thread on its behalf.

5CC moves objects by checking every reference load

Freeing garbage in place leaves holes, so ART’s collectors also move live objects together. Moving an object while the app runs is the hard part. Every reference to it must be updated, and meanwhile the app must never use a stale address.

CC (Concurrent Copying) was the default from Android 8 until CMC. It splits the moving space into fixed-size regions. During a GC it picks the regions worth emptying, called from-space: every region allocated since the previous GC, plus older regions that are less than three-quarters live. It copies their live objects into fresh to-space regions and frees the old regions whole.

To keep the app from using a stale from-space address, CC adds a read barrier. This is a short check after every reference load that swaps a from-space pointer for its to-space copy. An object whose fields are still being scanned is gray, marked by the gray bit in its lock word (Section 1). Only loads from gray objects need the slow path. The region size and the live-share threshold are in Numbers and method.

The price is that read barrier on every reference load in compiled code (Section 7), plus a reserve of free regions to copy into. CC is still used where userfaultfd, the Linux feature CMC depends on (Section 6), is not available.

6CMC slides objects in place and uses page faults instead of read barriers

CMC (Concurrent Mark-Compact) is the newer collector. It solves the same problem as CC, moving objects while the app runs, but with no read barriers. Instead of copying objects to a separate to-space, it slides live objects down in address order inside the same space. It relies on userfaultfd, a Linux feature that lets a process handle page faults on a memory range itself. That stops the app from seeing a page before it has been compacted. CMC also has a generational mode: a young collection only processes objects allocated since the previous GC.

ART picks CMC at startup if the kernel has the userfaultfd features it needs and system settings allow it (the check is in mark_compact.cc, the CMC collector’s source). It is on by default up to Android 14. From Android 15, a system property or a device_config flag (a runtime-configurable system setting) turns it on.

Only two short pauses; the rest runs alongside the app

How userfaultfd keeps the app from seeing a half-built page

At the compaction pause, the GC moves the moving space’s contents to a separate from-space address with mremap(MREMAP_DONTUNMAP). That call moves the pages but leaves the original range reserved and empty, and the GC registers that range with userfaultfd. Each compacted page is then installed whole with UFFDIO_COPY, an ioctl (a control call on the userfaultfd file descriptor) that maps a fully written page atomically. Where the kernel allows it, UFFDIO_MOVE moves the page in instead. From then on:

Why it replaced CC

  • No read barriers: compiled code is smaller and every reference load is a plain ldr.
  • Less memory: sliding compaction doesn’t need a reserve of empty to-space regions, and preserves allocation order (good locality).
  • Generational: young collections only process recently allocated objects.

What it costs the app

  • A thread that touches a not-yet-compacted page during compaction takes a page fault. It then compacts that page itself, or waits if another thread is already on it. This happens once per page.
  • Kernel calls must not hit those faults, and native code may pass a heap pointer straight to a system call. So GetPrimitiveArrayCritical and GetStringCritical, the JNI calls that hand out a direct pointer into the heap (Sections 15 and 17), call EnsureObjectUserfaulted to touch the object’s pages before handing out the pointer.
  • Card marking (write barrier) is still needed for concurrent marking and generational GC.

7Barriers are the small tax that lets the GC run alongside the app

A barrier is extra code the compiler adds around reference loads or stores so the GC can run while the app does.

Write barrier: a one-byte note after each reference store

The write barrier stops the GC from missing references the app writes while marking. Without it, the app could store a reference to an unmarked object into an object the GC has already scanned, and the GC would free a live object. So the heap is divided into small cards, and a side array, the card table, holds one byte per card. After every reference store that may store a non-null value, compiled code marks the written object’s card as dirty.

code_generator_arm64.cc · MarkGCCard// after every reference store (when value may be non-null)
ldr  card, [tr, #card_table]   // biased base
lsr  temp, obj, #10            // kCardShift
strb card, [card, temp]        // low byte of base == kCardDirty

It takes three instructions. The card table base is chosen so its low byte equals the dirty value, so one register is both the address and the value. If the stored value might be null, a branch skips the mark. If it is known to be null, there is no barrier. Primitive stores never need it.

Read barrier: one untaken branch per load, CC only

GenerateFieldLoadWithBakerReadBarrier// every reference load under CC (shape)
cbnz mr, field_thunk   // mr (x20) = "GC is marking"
ldr  wRef, [obj, #off] // the real load
// field_thunk: is obj's lock word gray? if so, call
// the mark entrypoint to get the to-space ref

Outside a GC this is one extra branch that is not taken. It tests a dedicated marking register, which is reserved to hold “is the GC marking?”. During marking, loads from gray objects go through a shared thunk, a small out-of-line stub, that returns the to-space reference. Under CMC none of this is emitted, and reference loads are plain loads.

8Threads stop only at safepoints, and stack maps decide what stays alive

The GC can only stop a thread at points where the compiler wrote down which registers and stack slots hold references. Those points are safepoints. The GC often needs every thread stopped for a pause. Or it needs each thread to run a small job at a known point, called a checkpoint, such as a flip function or a stack dump for an ANR report. Every call is a safepoint. Compiled loops also get a suspend check on the jump back to the top of the loop, so a long loop cannot hold up a GC.

Suspension is cooperative. To stop a thread, the runtime sets a suspend or checkpoint request flag on the thread and waits. The thread notices at its next suspend check. It then blocks until resumed, or runs the checkpoint and carries on. A thread that is blocked, or inside a regular JNI call, does not touch the heap, so the GC counts it as already suspended (Section 16). @FastNative and @CriticalNative calls stay Runnable, so the GC has to wait for them to return. Because suspension is cooperative, every pause includes the time for the slowest running thread to reach its next safepoint.

GenerateSuspendCheck// explicit: test the thread's flags
ldr  w16, [tr, #thread_flags]
tst  w16, #SuspendOrCheckpointRequest
b.ne slow_path

// implicit (arm64, no SIMD in method): one load
ldr  x21, [x21]
// x21 = &thread->suspend_trigger, a word that normally
// points to itself, so the load changes nothing.
// To request a suspend, the runtime stores null there:
// the next check loads null into x21, the one after
// faults, and the SIGSEGV handler suspends the thread.

The same trick, making the common case free and letting a fault handle the rare case, serves two other checks. Null checks: a load from a null object faults, and the handler throws NullPointerException. Stack overflow checks: a probe below the stack pointer hits a guard page, an unmapped page kept below the stack so that running past it faults.

Stack maps also decide liveness: a reference that is not listed at a safepoint does not keep its object alive there. ART’s default is conservative. Dex bytecode keeps locals in numbered virtual registers. At each safepoint ART lists every reference still held in one of those registers, even after the code’s last use of it. The reference stays listed until the register is overwritten or the method returns. The rule is ShouldBeLiveForEnvironment in ssa_liveness_analysis.cc, the compiler’s liveness analysis.

Classes marked with the platform-internal @DeadReferenceSafe annotation opt out. Their dead references are dropped like dead primitives, so an object can be collected while a method that used it is still running. Methods that touch a @ReachabilitySensitive member keep the conservative rule. That annotation marks fields and methods whose owning object must stay reachable while they are in use.

What it means for you Once you turn an object into a raw address (a long), only the object reference keeps the memory alive. Do not rely on ART’s conservative default. The @DeadReferenceSafe javadoc notes that class-file and dex tools may not preserve it either. Keep the object reachable explicitly, with a field or a reachabilityFence after the last raw access. For raw access, also make sure the object cannot move, by putting it in the non-moving space.
Part II · Compiler

9Code gets faster as it gets hot

ART runs code in tiers and moves a method up as it gets hot. An app ships as dex bytecode, which the D8 and R8 tools build from Java and Kotlin. Compiling all of it up front would cost install time and storage, and most of it rarely runs.

The interpreter, nterp, is written in assembly. It runs bytecode directly and counts how often each method runs. A hot method is compiled by the JIT, the just-in-time compiler inside the app process. The first version is baseline code: compiled quickly with few optimizations. It records an inline cache at each virtual call site: the list of receiver classes seen there, that is, the classes of the objects the method was called on.

Hotter methods are recompiled by the optimized JIT, which uses those inline caches to inline calls (Section 11). A long-running loop in the interpreter can jump into compiled code mid-run. This is on-stack replacement (OSR).

The JIT also saves a profile of the hot methods and classes to disk. Later, during install or idle maintenance, dex2oat, the on-device ahead-of-time (AOT) compiler, compiles those methods with the speed-profile compiler filter, the setting that compiles only the methods in the profile. With this profile-guided compilation, the next launch starts with optimized code for the hot paths. Framework code is AOT-compiled into the boot image (Section 2).

10The compiler reuses a value only if it can prove nothing changed it

To remove a repeated load or move it out of a loop, the compiler must prove that nothing in between changed that memory. The optimizing compiler turns bytecode into an intermediate representation (IR) called an SSA graph, where every value is defined once. SSA stands for static single assignment, and ART’s class for it is HGraph. Each instruction records its side effects: which kinds of memory it may read or write, by field type and array element type, and whether it can trigger a GC. Every memory optimization asks the same question of these sets: “can anything between A and B have written what A read?”

Some library methods are intrinsics. The compiler recognizes them and emits a few instructions in place of a call, each with its own declared side effects. A volatile access is an ordering point the compiler cannot move other memory accesses across.

11Inlining matters most, and it needs a known call target

Inlining is the most important optimization. It removes the call and exposes the callee’s body, so the other optimizations can see across what used to be an opaque call. To inline a virtual call, the compiler first has to know which method it will actually reach.

Without that knowledge, the call is dispatched at runtime through a chain of loads. A virtual call loads the receiver’s class, then a method from the class’s vtable, then that method’s entry point. A vtable is an array of method pointers, one slot per overridable method.

Interface methods cannot have one slot that is the same in every implementing class. So each class also has an IMT (interface method table): a small fixed table indexed by a hash of the interface method. When two methods share a slot, the slot holds a conflict trampoline, a shared stub that searches a per-slot list for the right method.

The compiler avoids dispatch in three ways, shown at the bottom of Figure 14. Class hierarchy analysis (CHA) notices when only one loaded class implements a method. An inline cache (Section 9) says which classes a call site has actually seen. And sometimes the receiver’s type is known outright, for a final class or a freshly allocated object.

What it means for you Hot call sites that see one or two receiver classes cost about as much as direct calls. A hot interface call that sees five or more classes stays a real call, and everything after it is treated as unknown (Section 10). A typical case is a shared helper called with many List or listener implementations. Keep hot methods small enough to inline.

12Four passes remove repeated work once inlining exposes it

These four passes remove redundant work after inlining. All four rely on the side-effect sets from Section 10.

LSE · Load/Store Elimination

Reuses a loaded value instead of loading again, forwards a stored value to a later load, and deletes stores nobody reads. It can also remove an allocation entirely if the object never escapes, that is, if it is never stored to the heap, returned or passed to a call that isn’t inlined.

int p = this.pos; ... int q = this.pos; // q = p
this.pos = 5; this.pos = 6;              // first store dead
GVN · Global Value Numbering

Gives every computed value a number and reuses identical computations, including loads, as long as nothing in between wrote that memory.

long a = this.address + i;
long b = this.address + i;  // b = a
LICM · Loop-Invariant Code Motion

Moves computations that give the same result on every iteration out of the loop. A load can only move if nothing in the loop body may write it.

for (...) buf[i] = this.base;
// → int b = this.base; for (...) buf[i] = b;
BCE · Bounds-Check Elimination

Proves array indices are in range from loop bounds and the (immutable) array length. When it can’t prove it statically, it may add one guard before the loop that deoptimizes if the assumption fails, and drop the per-iteration checks.

for (int i = 0; i < a.length; i++) a[i] = 0;
// no checks: 0 ≤ i < a.length by construction

Intrinsics fill in the rest. Methods like Math.min, String.charAt, System.arraycopy and Integer.bitCount are recognized and replaced with a few instructions. Each declares its side effects in intrinsics_list.h, the compiler’s table of intrinsics. Math.min has none, and charAt only reads. When the compiler cannot be precise about what an intrinsic touches, it declares the broad kWriteSideEffects or kAllSideEffects, as for System.arraycopy.

14Uncontended locks are cheap; contended ones turn fat and stay fat

Every object can be a lock. ART keeps uncontended locking cheap by storing the owner directly in the lock word, as a thin lock. It only allocates a real Monitor, a fat lock, when it has to.

asm_support_arm64.S · LOCK_OBJECT_FAST_PATH (path without ARMv8.1 atomics, simplified)ldr   w9, [xSELF, #THREAD_MONITOR_ID_OFFSET]
cbz   x0, slow                // null → NPE path
add   x8, x0, #MIRROR_OBJECT_LOCK_WORD_OFFSET
1: ldaxr w10, [x8]            // load-acquire exclusive
eor   w11, w10, w9            // new word: our thread id, GC bits kept
tst   w10, #LOCK_WORD_GC_STATE_MASK_SHIFTED_TOGGLED  // unlocked?
b.ne  2f
stxr  w10, w11, [x8]          // try to claim it
cbnz  w10, 1b                 // lost the race → retry
ret
2: // same owner? count++ ; otherwise → slow path (inflate)
  • Uncontended: a call to this stub and one exclusive load/store pair (ldaxr/stxr, arm64’s way to update a word atomically). Cheap, but an ordering point. On CPUs with the ARMv8.1 atomics it is a single casa. ART’s code calls those atomics “LSE”, for Large System Extensions, which is unrelated to the compiler pass in Section 12.
  • Contended: the slow path (Monitor::MonitorEnter) spins a while, then yields the CPU up to 50 times with sched_yield, then inflates the lock. It allocates a fat Monitor, points the lock word at it, and blocks on a futex, the Linux primitive for sleeping until another thread wakes you. Now there are syscalls and context switches. The exact spin counts are in Numbers and method.
  • Fat locks stay fat. Idle monitors go back to thin locks only during a heap trim, the periodic housekeeping that returns free memory to the kernel. Even then, only while the app is in a state where pauses are not user-visible (Heap::Trim → DeflateMonitors).
  • Hash + lock: the lock word cannot hold both, so locking an object that has an identity hash goes straight to a fat monitor.
What it means for you Uncontended synchronized is a stub call and one atomic, which is fine outside the hottest loops. Contention is what hurts. Keep critical sections short and shard hot state. Lock on a dedicated private final Object. Never lock on an object that is also hashed by identity, because that forces a fat monitor that stays fat. Examples are a HashMap key whose class does not override hashCode, or anything passed to System.identityHashCode.

15Strings are compact, but short ones are mostly overhead

Strings are among the most common objects on an app’s heap, and ART treats them more specially than any other class. They have their own layout, compression, interning, compiler intrinsics, a fused concatenation path, and their own family of JNI functions.

One object, with characters stored inline

An ART String is a single object with its characters stored inline. There is no separate character array. After the object header come a length field and a cached hash code, so the characters always start at the same offset. If every character is ASCII, the string is compressed to one byte per character. Otherwise it uses two bytes per character (UTF-16). The exact fields and offsets are in Figure 17 and Numbers and method.

Characters start at offset 16, which suits both one- and two-byte loads, so charAt never pays for misalignment. The emoji row: a character outside the Basic Multilingual Plane is a surrogate pair, two units of UTF-16.

Equal literals share one object; everything else is a fresh copy

Two strings with the same contents are the same object when they are interned: looked up in a global table and deduplicated. The same literal appears in many classes, and building a new object each time it runs would waste memory and time. ART’s InternTable keeps a strong set and a weak set, and entries in the weak set can be collected. The table is guarded by a lock and keyed by the string’s hash. A literal is loaded by the dex instruction const-string.

MUTF-8 is the modified UTF-8 that dex files and JNI use (see below). The app image is the app’s counterpart of the boot image: objects dex2oat pre-builds for the app and maps at launch. Where the literal slot lives is in Table 3.

  • Literals (const-string) are interned when first resolved: strongly (never collected) by default, weakly (collectable once unused) behind the newer weak_const_string flag. So "a" == "a" holds across classes.
  • String.intern() is a @FastNative call into InternWeak: a hash, a locked table lookup, and possibly an insert. The result can be collected once nothing else references it.
  • Everything else is a fresh object: concatenation, substring, replace, toLowerCase, new String(bytes), valueOf. Each allocates and copies, unless the result would equal the input (a case change, trim or replace with nothing to change, or a full-length substring), in which case it returns this.
  • No substring sharing. Because characters are inline, a substring can’t point into its parent. That means it never keeps a huge parent alive (an old Java leak), but any substring shorter than its parent is a copy.
  • Interning to save memory pays off only for long-lived, highly duplicated strings (keys, enum-like values). Interning in a hot path adds a lock and a hash per call.
  • Compare with equals, not ==, unless both sides are known to be interned.

Reading a string is cheap; building one allocates

Most String methods are either intrinsics (Section 10) or plain Java that allocates a new string. The equals intrinsic shows how much the layout buys: strings of different length or encoding are rejected by a single compare of the length field.

JNI’s “UTF” functions do not produce standard UTF-8 The …UTF… JNI functions use modified UTF-8, which writes NUL and emoji differently. Passing that output to code that expects the standard form, such as protobuf, JSON or the kernel, can corrupt emoji. For the standard form, encode in Java with getBytes(StandardCharsets.UTF_8), or convert it yourself in native code. The exact byte forms are in Numbers and method.

Creating strings from native code always scans and allocates

  • NewStringUTF(const char*) scans and decodes modified UTF-8, counts UTF-16 units, decides compression, and allocates a managed string. It only lightly validates the input; CheckJNI, JNI’s debug checking mode, validates fully. Every call costs a full scan plus a Java allocation.
  • NewString(const jchar*, len) skips decoding but still scans for compressibility and copies.
  • For values that repeat, such as enum-like names and keys, create the jstring once and keep a global reference to it, a handle that stays valid across calls until you delete it, instead of recreating it per call.
What it means for you Short strings are mostly overhead, so avoid creating them in hot paths. Concatenating a log tag per call allocates every time. Keep text ASCII where you can, because one non-ASCII character doubles the size. Across JNI, prefer GetStringRegion or GetStringUTFRegion into a reused buffer over the Get…Chars family. And remember that the “UTF” functions do not produce standard UTF-8.
Part III · Native

16A regular JNI call swaps thread state twice and can absorb a GC pause

Every native call goes through a small generated stub that bridges two gaps between Java and C. The first gap is the calling convention, the rule for which registers carry which arguments. ART’s compiled code passes the method pointer and arguments in different registers from the standard Arm C convention (AAPCS64), and its references are 32-bit heap addresses. The second gap is the GC contract. A thread running Java code may hold raw object addresses, so the GC has to wait for it to reach a safepoint (Section 8). A C function can run as long as it likes without reaching one. The exact register assignments are in Numbers and method.

The JNI stub is generated per native method by ArtJniCompileMethodInternal in jni_compiler.cc, in dex2oat or the JIT. When a method has no compiled stub, a shared hand-written trampoline, art_quick_generic_jni_trampoline, does the same steps at runtime, more slowly.

Native code also needs a way to name Java objects that survives the GC moving them. JNI gives every native method a JNIEnv*, a per-thread pointer to the table of JNI functions. It refers to objects through handles (jobject) instead of addresses. Arguments and the objects JNI functions return are local references. They stay valid, and keep the object alive, until the native method returns. Steps 3 and 4 below show how the stub creates them.

The stub’s main job is the thread state transition. Each thread has a state-and-flags word that says whether it is running Java code, plus request flags that other threads set, such as “please suspend”. The mutator lock is a reader-writer lock (“mutator” is GC jargon for a thread running app code, which mutates the heap). Running Java threads hold it shared, and the GC takes it exclusively when it needs every thread stopped. So a Runnable thread holds the mutator lock in shared mode and may touch heap objects directly. Any other state, such as Native, is a promise not to touch the heap, so the GC treats that thread as already suspended. The word’s layout is in Numbers and method.

What each step does

The step numbers match the comments in ArtJniCompileMethodInternal. The arm64 instructions come from jni_macro_assembler_arm64.cc. Each step below is in plain words. Table 2, after the list, gives the registers, fields and functions behind each one.

  1. Build and publish the frame (regular and @FastNative). The stub pushes a frame and stores the method pointer at its bottom. The frame saves the callee-save registers, the ones a function must hand back unchanged. It then copies every reference argument that arrived in a register, including this, to that argument’s stack slot. Finally it records the stack pointer in the thread. From then on the GC can walk this thread’s stack while C code runs, find those references, and update them if it moves the objects. @CriticalNative stubs skip all of this, because the GC cannot run during the call.
  2. Leave Runnable (regular only). Synchronized methods take the monitor first. Then the stub changes the thread state from “Runnable, no flags” to “Native, no flags” in one atomic compare-and-swap, and clears the thread’s record that it holds the mutator lock: 
    // TryToTransitionFromRunnableToNative, LSE (ARMv8.1 atomics) path
// (VIXL assembler calls shown as assembly, register names simplified)
mov  w16, #0                      // expected: kRunnable (0), no flags
mov  w17, #kNativeStateValue      // new: kNative, no flags
casl w16, w17, [x19]              // state_and_flags is at offset 0 of Thread
cbnz w16, slow_path               // any flag set → pJniMethodStart
str  xzr, [x19, #held_mutexes[kMutatorLock]]
    The comparison includes the flag bits. If the GC has already asked this thread to suspend or run a checkpoint, the swap fails, and a slow path handles the request first. Once the swap succeeds, the GC no longer waits for this thread. @FastNative and @CriticalNative skip this step and stay Runnable for the whole native call. That saves both swaps. But any GC pause, thread flip or checkpoint that needs this thread now waits until the native function returns. Their javadoc says it plainly: do not do I/O, take long-held native locks, or do unbounded work in them.
  3. Push a local reference frame (regular and @FastNative). A local reference is an entry in a per-thread table that keeps an object alive and gives native code a stable handle to it. Every JNI call that returns an object, such as NewStringUTF, adds one. JNI frees them all when the native method returns, and this step makes that cheap. The stub saves the table’s current top position and keeps it in callee-save registers, so it can roll the table back after the call.
  4. Build the native arguments and call (all flavours, differently). For regular and @FastNative methods:
    • The first argument is the JNIEnv*.
    • The second is the class, for a static method, or this, for an instance method. Both are passed as handles.
    • Each reference argument becomes a handle that is the address of its stack slot from step 1, or null. Native code never sees a heap address. If the GC moves the object, it updates the slot, and the handle still leads to the object.
    • Primitives are passed unchanged, following the C convention.
    The call goes through the method’s JNI entry point. RegisterNatives fills it in, or else the runtime looks up the native symbol by name on the first call. Afterwards the stub extends small integer results, because C only guarantees their low bits.
    @CriticalNative methods must be static and take and return only primitives, so there is nothing to wrap. The C function gets no JNIEnv* and no class. For example: 
    // Java declaration
@CriticalNative static native long write(long ptr, int len);
// binds to
jlong Java_..._write(jlong ptr, jint len)
    Optimized code goes one step further and calls the native function directly, skipping the stub. Debuggable apps do not get this.
  5. Return to Runnable (regular only). After the C function returns, the thread is still Native and may not touch the heap, not even to turn a returned handle into a reference. The stub does the reverse swap, “Native, no flags” to “Runnable, no flags”, and records the mutator lock as held again. If any flag was set while the thread was in native code, the swap fails. That flag can be a suspend request for a GC pause, a checkpoint, or a pending thread flip. A slow path then waits until the request is done. That wait is charged to the end of the JNI call.
    @FastNative never left Runnable, so instead it does a suspend check: it tests the suspend and checkpoint flags and calls into the runtime if any is set. Without it, a thread making many short @FastNative calls could hold off a GC indefinitely. For methods that return an object, the stub checks for a pending exception first, then turns the returned handle back into a reference.
  6. Pop the local reference frame (regular and @FastNative). The stub writes back the table position it saved in step 3. Every local reference the native code created is dropped at once, without visiting them.
  7. Unlock, check for an exception, return (regular and @FastNative). Synchronized methods release the monitor. Then the stub checks whether the thread has a pending exception. C code has no way to throw into Java: env->ThrowNew(…) only records the pending exception in the thread and returns normally. This check is where it is actually thrown, and the Java stack unwinds. Otherwise the stub restores the saved registers, pops its frame and returns.

What it means for you A regular JNI call costs one atomic swap each way plus the frame and local-reference bookkeeping, and it can absorb a GC pause on its way back. The annotated kinds are several times cheaper (Figure 24). Batch work so each crossing does more. Use @FastNative and @CriticalNative only for short, bounded functions, since they hold up the GC while they run.
