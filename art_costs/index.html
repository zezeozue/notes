Where the costs are in ART: cheap until the GC, a lock or native code gets involved

On Android, ordinary Java and Kotlin code compiles to tight machine instructions: reading a field, writing an array element, or calling an inlined helper costs little more than C. Performance cliffs appear where managed code meets the runtime: relocating live objects concurrently, proving safety across opaque calls, contending on locks, or crossing JNI. This note walks the Android Runtime (ART) from object headers through GC, compilation, strings, and JNI to show why each boundary exists.

Code excerpts are from art/ and libcore/ in AOSP as of Android 17, arm64. Instruction sequences marked shape are simplified. The rest are quoted from the source files listed under Sources at the bottom. Cost tiers are rough orders of magnitude, not measurements.

At a glance

  • Straight-line Java compiles down to single loads and stores. Once ART’s compiler inlines a hot path, local variables live in CPU registers, field accesses take one instruction, and most array bounds checks disappear.
  • Allocation is cheap up front and paid back in GC work. Creating a small object bumps a thread-local pointer in roughly ten instructions, but every allocated byte pulls the next collection closer, and surviving objects must be traced and relocated.
  • Optimizations stop where the compiler loses visibility. Uninlined virtual calls, volatile accesses, and raw-memory intrinsics force the compiler to assume heap fields changed and reload them from memory.
  • Locks stay lightweight only while uncontended. An uncontended synchronized block updates the object’s header word with one atomic instruction; contention or an identity hash code inflates the lock into a native monitor backed by kernel waits.
  • Crossing into C/C++ pays at the border and on the data. A regular JNI call performs two atomic thread-state transitions so the GC does not wait on native code, and passing Java strings or movable arrays usually copies their bytes.

How ART got here: compilation and GC evolved under mobile limits

Desktop and server JVMs can spend gigabytes of RAM on generous heap headroom and background compilation threads. Phones cannot: flash storage, RAM, battery, and 16 ms frame budgets pull against one another, and ART’s Android 17 design is the product of two multi-release trade-offs.

From full AOT to profile-guided tiers. Android originally ran apps on Dalvik, an interpreter paired with a small trace JIT that saved RAM and storage at the cost of CPU speed. Android 5 replaced Dalvik with ART and ran dex2oat at install time to compile the entire APK ahead of time (AOT), boosting steady-state speed while stalling installs and bloating flash with cold methods.

Android 7 restored balance with tiered execution (Section 9): apps start immediately on a fast assembly interpreter (nterp) while an in-process JIT compiles warm methods and records which concrete classes appear at each virtual call site. Background dex2oat then reads that profile to AOT-compile only proven hot paths, devirtualizing and inlining calls that static analysis alone could never resolve (Section 10 and Section 11).

From mark-sweep to read barriers to page-fault compaction. Early non-moving mark-sweep collectors freed dead objects in place, leaving scattered holes that fragmented RAM and forced allocations onto free lists. Android 8 introduced Concurrent Copying (CC) (Section 5), evacuating sparse 256 KB regions while the app runs; that unlocked bump-pointer allocation at the cost of a reserve of empty to-space regions and a read barrier on every reference load.

Concurrent Mark-Compact (CMC) (Section 6) drops that per-load tax: using Linux userfaultfd, it slides live objects in place with zero read barriers on loads. In exchange, touching an uncompacted heap page during compaction triggers a page fault that compacts that one page on the spot, and JNI helpers that expose raw heap pointers pre-touch pages before returning so kernel syscalls never trip a user-space fault.

Terms on the ladder below. A TLAB (thread-local allocation buffer) is a private slice of the moving heap that one thread bumps through without locks. A card mark is the one-byte write barrier emitted after storing a reference, a read barrier is CC’s per-load check during marking, and a suspend check is the poll at calls and loop back-edges where ART pauses threads for GC.

JNI (Java Native Interface) bridges Java and C/C++: regular JNI calls switch a thread’s state from Runnable to Native and back so GC never waits on C code, whereas @FastNative and @CriticalNative stay Runnable to make short, non-blocking C calls cheaper.

The cost ladder: each step up costs roughly ten times more

Most of this page explains why things sit where they do on this ladder. Each step up is very roughly an order of magnitude.

Part I · Memory

1Every object pays a fixed header before its fields

In C, a struct’s type disappears once compiled; at run time it is just raw fields in memory. Java cannot do that: every heap object must support virtual dispatch, runtime type checks (instanceof and casts), synchronized locking, identity hashing, and GC graph traversal. ART therefore prefixes every object with an 8-byte header: a 4-byte class pointer (klass_) and a state word (monitor_).

Even on 64-bit arm64, ART places the entire managed heap inside a four-gigabyte virtual address window so every Java reference, including klass_, fits in a 32-bit compressed HeapReference. That halves reference-field memory and cache footprint while native code keeps full pointers. Objects are padded to eight-byte alignment, and arrays add a length field before their elements; exact sizes are in Numbers and method.

The lock word packs four jobs into one field

Locking, System.identityHashCode, and moving GC each need per-object state, yet almost no object uses all of them at once. Giving each subsystem its own header word would add 12 bytes to every object in RAM, so ART multiplexes all four onto the single 32-bit monitor_ word (LockWord in lock_word.h). Its top two bits select which state the word currently holds, and two bits belong to the GC:

  • A thin lock stores the owning thread’s id and a recursion count right in the word. An id of zero means unlocked.
  • A fat lock holds a MonitorId indexing a separately allocated native Monitor struct when a thin lock is not enough: under thread contention, Object.wait(), or when an already-hashed object is locked (Section 14).
  • The hash state holds the object’s 28-bit identity hash code once computed.
  • The forwarding state holds the object’s new address while the CC collector evacuates it (Section 5).

The mark bit and the read-barrier (“gray”) bit are scratch bits the collectors use while tracing the object graph (Section 4). Taking an uncontended thin lock is a single atomic compare-and-swap (CAS) on this word.

What it means for you Small objects are mostly header and padding: an Integer is 16 bytes for 4 bytes of payload. A lock and an identity hash cannot both fit in the lock word. If you take an object’s identity hash and later synchronized on it, ART must inflate it to a fat monitor (Section 14). The identity hash comes from System.identityHashCode, or from a hashCode() the class does not override.

2The heap is several spaces, each with its own rules

One uniform memory region cannot satisfy everything Android asks of a managed heap: framework classes should share physical RAM pages across every app, short-lived objects should allocate by pointer bump and compact freely, multi-page buffers should not be copied on every GC, and buffers shared with C must never move.

ART therefore splits its virtual heap window into distinct spaces, each with its own allocator and compaction rules. Reserving a space’s virtual address range (such as 64 MB for the non-moving space) does not consume physical RAM up front; physical pages fault in on allocation and return to the kernel via madvise when freed.

Two spaces are inherited rather than allocated by the app. The boot image maps pre-initialized framework classes and strings from .art files (paired with compiled code in .oat files) into every process. The zygote space holds heap objects allocated by the zygote process before it forks each app; child processes share those physical RAM pages copy-on-write until a write, such as locking or mutating a shared object, dirties a private copy of that 4 KB page.

The app’s own allocations land in three spaces. Almost every new object goes to the moving space, compacted in place by CMC or across regions by CC (Section 5 and Section 6). The non-moving space uses mark-sweep and a free list for pinned addresses such as Class objects and VMRuntime.newNonMovableArray buffers.

Primitive arrays and strings of 12 KB or more go straight to the page-granular large object space. Copying a 64 KB byte[] during compaction would burn memory bandwidth without helping small-object fragmentation, and reclaiming whole OS pages avoids free-list holes.

3Allocation is a pointer bump; the cost comes later, in the GC

Because the collector compacts the moving space into contiguous free ranges, allocating a small object never searches a free list. Still, if every thread bumped one shared heap cursor, every new on a multicore phone would contend on the same cache line with atomic compare-and-swaps.

ART avoids that contention by giving each thread its own thread-local allocation buffer (TLAB), a private slice of the moving space stored on its Thread struct. Within a TLAB, allocation is an unsynchronized pointer bump; only refilling an exhausted TLAB touches shared heap state. TLAB sizes differ by collector (see Numbers and method).

quick_entrypoints_arm64.S// art_quick_alloc_object_resolved_tlab: fast path
ldr  x4, [xSELF, #THREAD_LOCAL_POS_OFFSET]
ldr  x5, [xSELF, #THREAD_LOCAL_END_OFFSET]
ldr  w7, [x0, #MIRROR_CLASS_OBJECT_SIZE_ALLOC_FAST_PATH_OFFSET]
add  x6, x4, x7        // pos + size
cmp  x6, x5            // fits?
b.hi .Lslow_path       // (classes not yet visibly initialized, and
                       //  finalizable classes, report a huge size)
str  x6, [xSELF, #THREAD_LOCAL_POS_OFFSET]
str  w0, [x4, #MIRROR_OBJECT_CLASS_OFFSET]
mov  x0, x4
ret
// what compiled code around new Point() looks like (shape)
ldr  lr, [tr, #pAllocObjectResolved]  // entrypoint in Thread
blr  lr                               // the fast path on the left
dmb  ishst                            // constructor fence
// ... inlined constructor stores ...

To keep compiled code compact, ART does not inline the bump sequence at every new site; instead it calls a shared ten-instruction assembly entrypoint on Thread. After the call comes a StoreStore fence (dmb ishst), ordering the header and constructor stores before any reference store that publishes the new object to another thread. The compiler omits that fence when escape analysis proves the object stays thread-local until a later barrier.

What it means for you A single allocation is cheap: about a call plus ten instructions. The real cost is indirect. Every byte allocated moves the heap toward its next GC, and objects that survive get traced and moved. Allocating in a hot loop is mostly paying for future GC work. Finalizable classes, which override finalize(), and classes still being initialized always take the slow path.

4A GC’s cost follows what survives, not how much garbage there is

Managed runtimes reclaim memory either by counting references on every pointer store or by periodically tracing live objects from roots. Reference counting pays an atomic increment and decrement on every pointer write and leaks reference cycles without backup cycle detection. ART instead uses tracing garbage collectors: pointer stores stay fast, cycles are reclaimed automatically, and collection work scales with the live objects that survive rather than the dead objects left behind. Dead memory is never visited.

A tracing cycle starts from GC roots: references outside heap objects that are reachable by definition. Roots include thread stacks and registers, static reference fields, interned strings, JNI local references in active native frames, and JNI global references from NewGlobalRef (weak globals from NewWeakGlobalRef do not keep objects alive). From those roots, the collector marks reachable objects and reclaims the rest.

To find roots on thread stacks, the GC must know which stack slots and registers hold references where each thread stopped. The compiler records this as stack maps at safepoints, the instructions where a thread is allowed to stop (Section 8).

Every collector combines short pauses, where all threads stop, with long concurrent phases alongside the app. A key pause is the thread flip (ThreadList::FlipThreadRoots): the GC briefly suspends threads and installs a flip function on each to update its stack roots to new object addresses. Once resumed, each thread’s flip runs once, either on the thread itself before Java resumes or on the GC thread’s behalf.

5CC moves objects by checking every reference load

Compacting live objects while the app is frozen is straightforward; compacting them while UI threads keep reading and writing fields is where concurrent GC gets hard. Once an object is copied, heap fields briefly mix old and new pointers, and writing to the stale copy loses updates. CC (Concurrent Copying), Android’s default collector from Android 8 until CMC, prevents that with a to-space invariant: app threads never observe an old address.

CC divides the moving space into fixed 256 KB regions. During a collection it selects sparse regions to evacuate as from-space (every region allocated since the previous GC plus older regions that are less than three-quarters live), copies their surviving objects into fresh to-space regions, installs a forwarding address in each old lock word (Section 1), and reclaims the emptied regions whole.

To uphold the to-space invariant while evacuation is running, the compiler emits a read barrier after every reference load. An object whose reference fields have not all been updated yet carries the gray bit in its lock word; only loads from gray objects take the barrier’s slow path to copy or look up the forwarding address and return the to-space reference. Region sizes and evacuation thresholds are in Numbers and method.

The price is that read barrier on every reference load in compiled code (Section 7), plus a reserve of free regions to copy into. CC is still used where userfaultfd, the Linux feature CMC depends on (Section 6), is not available.

6CMC slides objects in place and uses page faults instead of read barriers

Every reference load in a Java app runs far more often than GC compaction does, so paying CC’s read barrier on every dereference and holding empty to-space regions in reserve is a steep tax. CMC (Concurrent Mark-Compact) compacts concurrently with zero read barriers and no separate to-space reserve.

Instead of evacuating into empty regions, CMC computes each survivor’s destination address from its mark bitmaps, rewrites references to those post-compaction addresses, and slides live objects down in address order inside the same virtual range. Linux’s userfaultfd intercepts any thread that touches an uncompacted page, and generational mode compacts only young objects allocated since the previous cycle.

ART selects CMC at process startup when the kernel supports the required userfaultfd features and system configuration enables it (ShouldUseUserfaultfd in mark_compact.cc). It is on by default through Android 14, and controlled from Android 15 onward by ro.dalvik.vm.enable_uffd_gc or a runtime device_config flag.

Only two short pauses; the rest runs alongside the app

How userfaultfd keeps the app from seeing a half-built page

Once the compaction pause flips thread roots to post-compaction virtual addresses, the moving space’s virtual range cannot keep pointing at uncompacted physical pages, or threads would read stale bytes at new offsets. During that pause, mremap(MREMAP_DONTUNMAP) moves the old page-table mappings to a separate from-space virtual range while leaving the original virtual range reserved, unmapped, and registered with userfaultfd.

As the GC assembles each compacted page from from-space survivors (rewriting their internal references to post-compaction addresses), it maps the finished physical page into the original virtual range atomically via UFFDIO_COPY, or moves it without copying via UFFDIO_MOVE when supported:

Why it replaced CC

  • No read barriers: compiled code is smaller and every reference load is a plain ldr.
  • Less memory: sliding compaction doesn’t need a reserve of empty to-space regions, and preserves allocation order (good locality).
  • Generational: young collections only process recently allocated objects.

What it costs the app

  • A thread that touches a not-yet-compacted page during compaction takes a page fault. It then compacts that page itself, or waits if another thread is already on it. This happens once per page.
  • Kernel calls must not hit those faults, and native code may pass a heap pointer straight to a system call. So GetPrimitiveArrayCritical and GetStringCritical, the JNI calls that hand out a direct pointer into the heap (Sections 15 and 17), call EnsureObjectUserfaulted to touch the object’s pages before handing out the pointer.
  • Card marking (write barrier) is still needed for concurrent marking and generational GC.

7Barriers are the small tax that lets the GC run alongside the app

If the app mutates the object graph while a collector is walking it, or stores a pointer from an old object to a newly allocated young object, the collector needs a lightweight record of what changed. A barrier is the short inline instruction sequence the compiler emits around reference stores or loads to maintain that invariant.

Write barrier: a one-byte note after each reference store

The write barrier solves two problems at once: during concurrent marking, it catches references stored into already-scanned objects so live targets are not missed; during generational GC, it records which older objects point to young objects so young collections skip scanning the whole heap.

Logging every pointer store into a per-thread queue would cost bounds checks and flushes. ART instead coarsens tracking to 1 KB heap slices called cards: a flat side byte array, the card table, holds one byte per 1 KB of virtual heap, and every non-null reference store unconditionally marks that slice’s byte dirty with no atomic instruction or branch.

code_generator_arm64.cc · MarkGCCard// after every reference store (when value may be non-null)
ldr  card, [tr, #card_table]   // biased base
lsr  temp, obj, #10            // kCardShift
strb card, [card, temp]        // low byte of base == kCardDirty

It takes three instructions. ART biases the card table’s base address so its low byte equals the dirty marker (0x70), letting one register supply both the base pointer and the byte value to store. If the stored reference may be null, MaybeMarkGCCard wraps these three instructions in a zero check; known-null and primitive stores emit no barrier.

Read barrier: one untaken branch per load, CC only

Under CC, checking a thread-local memory flag on every reference load would double the memory traffic of pointer chasing. On arm64, ART avoids that extra load under CC by dedicating one general-purpose register (x20) as the marking register across managed code, so normal execution outside a GC cycle pays only a single predicted-not-taken branch:

GenerateFieldLoadWithBakerReadBarrier// every reference load under CC (shape)
cbnz mr, field_thunk   // mr (x20) = "GC is marking"
ldr  wRef, [obj, #off] // the real load
// field_thunk: is obj's lock word gray? if so, call
// the mark entrypoint to get the to-space ref

While CC is not marking, mr holds zero and execution falls straight through to ldr. During marking, loads from gray objects branch to a shared out-of-line thunk that copies or forwards the target and returns its to-space address. Under CMC none of this is emitted, freeing x20 and leaving reference loads as plain ldr instructions.

8Threads stop only at safepoints, and stack maps decide what stays alive

Why can’t the GC pause threads instantly with a POSIX signal wherever they happen to be running? Mid-sequence, a CPU register may hold an unboxed interior pointer (such as array base plus offset), and recording exact register-type metadata for every machine instruction would bloat .oat files severalfold. Instead, threads stop only at designated safepoints (calls and loop back-edges), where compact stack maps list which registers and stack slots hold heap references.

Stopping is cooperative, whether for a full stop-the-world pause or a per-thread checkpoint (a short self-service task such as flipping stack roots or dumping a stack for ANR). The runtime sets a request flag on Thread, and running Java code polls it at the next safepoint suspend check.

Threads blocked in the kernel or inside a regular JNI call have already promised not to touch the heap, so the GC treats them as suspended immediately (Section 16). @FastNative and @CriticalNative calls remain Runnable without safepoints inside C code, so every pause waits until they return and every other Runnable thread reaches a safepoint.

Because loop back-edges run constantly in hot code, even a three-instruction flag test adds measurable overhead. On arm64 methods without SIMD registers to spill, ART reduces the suspend check to a single self-referential load that faults only when suspension is requested:

GenerateSuspendCheck// explicit: test the thread's flags
ldr  w16, [tr, #thread_flags]
tst  w16, #SuspendOrCheckpointRequest
b.ne slow_path

// implicit (arm64, no SIMD in method): one load
ldr  x21, [x21]
// x21 = &thread->suspend_trigger, a word that normally
// points to itself, so the load changes nothing.
// To request a suspend, the runtime stores null there:
// the next check loads null into x21, the one after
// faults, and the SIGSEGV handler suspends the thread.

The same trick, making the common case free and letting a fault handle the rare case, serves two other checks. Null checks: a load from a null object faults, and the handler throws NullPointerException. Stack overflow checks: a probe below the stack pointer hits a guard page, an unmapped page kept below the stack so that running past it faults.

Stack maps also decide liveness: a reference that is not listed at a safepoint does not keep its object alive there. ART’s default is conservative. Dex bytecode keeps locals in numbered virtual registers. At each safepoint ART lists every reference still held in one of those registers, even after the code’s last use of it. The reference stays listed until the register is overwritten or the method returns. The rule is ShouldBeLiveForEnvironment in ssa_liveness_analysis.cc, the compiler’s liveness analysis.

Classes marked with the platform-internal @DeadReferenceSafe annotation opt out. Their dead references are dropped like dead primitives, so an object can be collected while a method that used it is still running. Methods that touch a @ReachabilitySensitive member keep the conservative rule. That annotation marks fields and methods whose owning object must stay reachable while they are in use.

What it means for you Once you turn an object into a raw address (a long), only the object reference keeps the memory alive. Do not rely on ART’s conservative default. The @DeadReferenceSafe javadoc notes that class-file and dex tools may not preserve it either. Keep the object reachable explicitly, with a field or a reachabilityFence after the last raw access. For raw access, also make sure the object cannot move, by putting it in the non-moving space.
Part II · Compiler

9Code gets faster as it gets hot

Java permits classes to be loaded dynamically and ships apps as portable dex bytecode built by D8 and R8. Compiling every method in an APK ahead of time wastes flash storage on cold error paths and still lacks runtime knowledge of which concrete subclasses actually show up at virtual call sites. ART therefore executes code in tiers, promoting methods only after they prove they are hot.

Cold code starts in nterp, a hand-written assembly interpreter that runs dex bytecode directly while incrementing per-method hotness counters. Once a method crosses the warm threshold, the in-process JIT compiles a fast baseline version with minimal optimization whose job is both to run faster and to populate an inline cache at each virtual call site: a short list of the receiver classes actually observed there.

Methods that stay hot are recompiled by the optimizing JIT, which reads those inline caches to guard and inline virtual calls (Section 11). If a method is stuck inside a long-running loop in the interpreter, on-stack replacement (OSR) transfers execution into freshly compiled loop code mid-iteration.

To avoid repeating that warm-up on every app launch, the runtime flushes hot method and inline-cache records to a profile file on disk. During idle maintenance (or using cloud profiles at install), dex2oat runs ahead-of-time compilation with the speed-profile filter, compiling only profiled methods and pre-populating an app image of hot classes and literals. Framework code in the boot image is AOT-compiled up front (Section 2).

10The compiler reuses a value only if it can prove nothing changed it

Keeping a heap field in a CPU register instead of reloading it on every loop iteration requires proving non-aliasing: nothing between the first load and the second use could have written that memory. Whole-program pointer analysis is too slow for an on-device JIT, so ART leans on Java’s type safety: writing a byte[] element can never overwrite an int field.

Inside the optimizing compiler, bytecode becomes a static single assignment (SSA) graph (HGraph) where every instruction carries a side-effects bitset listing which field and array types it may read or write, plus whether it can trigger GC. Every memory optimization asks those bitsets whether anything between A and B could have written the memory category A read.

Known library methods marked as intrinsics are lowered directly into inline IR or machine instructions with custom side-effect declarations, whereas a volatile field access acts as a memory-ordering barrier that surrounding heap accesses cannot be reordered across.

11Inlining matters most, and it needs a known call target

Inlining is the highest-leverage pass in ART’s compiler: removing the call instruction itself saves a little work, and splicing the callee’s graph into the caller’s removes the black box that would otherwise force register spills and heap reloads. That requires knowing which concrete method a virtual or interface call will actually invoke.

When the target is unknown at compile time, the CPU resolves it dynamically through dependent pointer loads. Because Java has single class inheritance, each overridable method occupies a fixed slot index in every subclass’s embedded vtable: a virtual call loads obj.klass_, loads vtable[i], and branches to that ArtMethod’s compiled entry point.

Interfaces break fixed indexing: a class implementing two unrelated interfaces I and J cannot place both interfaces’ first method at slot 0. Each class therefore carries a fixed 43-slot IMT (interface method table) indexed by a hash of the interface method. Uncollided slots jump straight to the implementing ArtMethod; slots shared by two or more methods point to a conflict trampoline that scans a short per-slot dispatch list.

To avoid dynamic dispatch and unlock inlining, the compiler resolves targets in three ways (bottom of Figure 14): exact type knowledge (final classes/methods or a freshly constructed receiver), class hierarchy analysis (CHA) when only one currently loaded class implements the method, and inline caches (Section 9) when runtime profiling saw one to four receiver types at that site.

What it means for you Hot call sites that see one or two receiver classes cost about as much as direct calls. A hot interface call that sees five or more classes stays a real call, and everything after it is treated as unknown (Section 10). A typical case is a shared helper called with many List or listener implementations. Keep hot methods small enough to inline.

12Four passes remove repeated work once inlining exposes it

Once inlining merges small helpers and getters into a single SSA graph, redundant loads, temporary wrapper objects, and repeated bounds checks sit side by side in one method. Four optimization passes clean them up, all gated on the side-effect bitsets from Section 10.

LSE · Load/Store Elimination

Reuses a loaded value instead of loading again, forwards a stored value to a later load, and deletes stores nobody reads. It can also remove an allocation entirely if the object never escapes, that is, if it is never stored to the heap, returned or passed to a call that isn’t inlined.

int p = this.pos; ... int q = this.pos; // q = p
this.pos = 5; this.pos = 6;              // first store dead
GVN · Global Value Numbering

Gives every computed value a number and reuses identical computations, including loads, as long as nothing in between wrote that memory.

long a = this.address + i;
long b = this.address + i;  // b = a
LICM · Loop-Invariant Code Motion

Moves computations that give the same result on every iteration out of the loop. A load can only move if nothing in the loop body may write it.

for (...) buf[i] = this.base;
// → int b = this.base; for (...) buf[i] = b;
BCE · Bounds-Check Elimination

Proves array indices are in range from loop bounds and the (immutable) array length. When it can’t prove it statically, it may add one guard before the loop that deoptimizes if the assumption fails, and drop the per-iteration checks.

for (int i = 0; i < a.length; i++) a[i] = 0;
// no checks: 0 ≤ i < a.length by construction

Intrinsics fill in the rest. Methods like Math.min, String.charAt, System.arraycopy and Integer.bitCount are recognized and replaced with a few instructions. Each declares its side effects in intrinsics_list.h, the compiler’s table of intrinsics. Math.min has none, and charAt only reads. When the compiler cannot be precise about what an intrinsic touches, it declares the broad kWriteSideEffects or kAllSideEffects, as for System.arraycopy.

14Uncontended locks are cheap; contended ones turn fat and stay fat

Java lets code synchronized on any object, yet most locks are taken by one thread at a time and never call Object.wait(). Pre-allocating an OS mutex and wait queue on every object would waste dozens of bytes per instance. ART instead keeps uncontended locks inline inside the 32-bit header word as a thin lock, inflating to a native Monitor (fat lock) only on contention, wait(), count overflow, or a stored identity hash.

2: // same owner? count++ ; otherwise → slow path (inflate)
  • Uncontended: a call to this stub and one exclusive load/store pair (ldaxr/stxr, arm64’s way to update a word atomically). Cheap, but an ordering point. On CPUs with the ARMv8.1 atomics it is a single casa. ART’s code calls those atomics “LSE”, for Large System Extensions, which is unrelated to the compiler pass in Section 12.
  • Contended: the slow path (Monitor::MonitorEnter) spins a while, then yields the CPU up to 50 times with sched_yield, then inflates the lock. It allocates a fat Monitor, points the lock word at it, and blocks on a futex, the Linux primitive for sleeping until another thread wakes you. Now there are syscalls and context switches. The exact spin counts are in Numbers and method.
  • Fat locks stay fat. Idle monitors go back to thin locks only during a heap trim, the periodic housekeeping that returns free memory to the kernel. Even then, only while the app is in a state where pauses are not user-visible (Heap::Trim → DeflateMonitors).
  • Hash + lock: the lock word cannot hold both, so locking an object that has an identity hash goes straight to a fat monitor.
What it means for you Uncontended synchronized is a stub call and one atomic, which is fine outside the hottest loops. Contention is what hurts. Keep critical sections short and shard hot state. Lock on a dedicated private final Object. Never lock on an object that is also hashed by identity, because that forces a fat monitor that stays fat. Examples are a HashMap key whose class does not override hashCode, or anything passed to System.identityHashCode.

15Strings are compact, but short ones are mostly overhead

Strings are among the most common objects on an app’s heap, and ART treats them more specially than any other class. They have their own layout, compression, interning, compiler intrinsics, a fused concatenation path, and their own family of JNI functions.

One object, with characters stored inline

On a standard desktop JVM, a String is two heap objects: a wrapper holding metadata plus a reference to a separate byte[] or char[]. On mobile heaps packed with UI labels, JSON keys, and class names, that second object wastes an extra array header, a reference field, padding, and a dependent pointer load on every read.

ART instead gives java.lang.String a custom variable-size VM layout: a single object whose characters follow inline right after its header, count_, and cached hash_code_. Strings containing only ASCII characters (code points below 128) use one byte per character; all others use two-byte UTF-16 units. Exact offsets are in Figure 17 and Numbers and method.

Equal literals share one object; everything else is a fresh copy

Two strings with identical contents become the same object when interned in a global deduplication table. Because string literals repeat across many classes, allocating a fresh object each time bytecode runs would waste RAM and CPU. ART’s locked, hash-keyed InternTable maintains a strong set and a collectable weak set, populated lazily when bytecode executes const-string.

MUTF-8 is the modified UTF-8 that dex files and JNI use (see below). The app image is the app’s counterpart of the boot image: objects dex2oat pre-builds for the app and maps at launch. Where the literal slot lives is in Table 3.

  • Literals (const-string) are interned when first resolved: strongly (never collected) by default, weakly (collectable once unused) behind the newer weak_const_string flag. So "a" == "a" holds across classes.
  • String.intern() is a @FastNative call into InternWeak: a hash, a locked table lookup, and possibly an insert. The result can be collected once nothing else references it.
  • Everything else is a fresh object: concatenation, substring, replace, toLowerCase, new String(bytes), valueOf. Each allocates and copies, unless the result would equal the input (a case change, trim or replace with nothing to change, or a full-length substring), in which case it returns this.
  • No substring sharing. Because characters are inline, a substring can’t point into its parent. That means it never keeps a huge parent alive (an old Java leak), but any substring shorter than its parent is a copy.
  • Interning to save memory pays off only for long-lived, highly duplicated strings (keys, enum-like values). Interning in a hot path adds a lock and a hash per call.
  • Compare with equals, not ==, unless both sides are known to be interned.

Creating strings from native code always scans and allocates

  • NewString(const jchar*, len) skips decoding but still scans for compressibility and copies.
  • For values that repeat, such as enum-like names and keys, create the jstring once and keep a global reference to it, a handle that stays valid across calls until you delete it, instead of recreating it per call.
What it means for you Short strings are mostly overhead, so avoid creating them in hot paths. Concatenating a log tag per call allocates every time. Keep text ASCII where you can, because one non-ASCII character doubles the size. Across JNI, prefer GetStringRegion or GetStringUTFRegion into a reused buffer over the Get…Chars family. And remember that the “UTF” functions do not produce standard UTF-8.

16A regular JNI call swaps thread state twice and can absorb a GC pause

Calling a C function from Java cannot be a plain branch because Java and C disagree on calling conventions and GC safety. ART’s managed ABI passes ArtMethod* in x0, shifts arguments up from x1, and uses 32-bit heap references, whereas C expects Arm AAPCS64 arguments starting in x0. Java threads also poll cooperative safepoints (Section 8), whereas C code can block in syscalls indefinitely.

ART bridges both mismatches with a per-method JNI stub compiled by ArtJniCompileMethodInternal in jni_compiler.cc (or handled by art_quick_generic_jni_trampoline until compiled). Because the GC may move objects while C runs, native code never sees raw heap pointers; it receives a JNIEnv* table and indirect jobject handles pointing to root slots ART updates.

Reference arguments and JNI return values are local references: GC roots scoped to the active JNI frame and freed in bulk on return. To retain an object across calls or threads, native code creates a NewGlobalRef (strong root until DeleteGlobalRef) or NewWeakGlobalRef (updated on move, collected when unreachable).

To let GC proceed while C runs, a regular JNI stub performs a thread state transition on entry and exit. Runnable threads hold ART’s reader-writer mutator lock in shared mode; switching from kRunnable to kNative releases it and promises not to touch the heap, letting GC pauses, flips, and checkpoints proceed without waiting. Exact layouts are in Numbers and method.

The seven steps inside a compiled JNI stub

The step numbers match ArtJniCompileMethodInternal, with arm64 code emitted by jni_macro_assembler_arm64.cc. Notice how packing the thread’s state and its suspend/checkpoint request bits into a single 32-bit state_and_flags word at offset 0 of Thread lets one atomic compare-and-swap both switch state and verify that no GC request is pending. Table 2, after the list, gives the registers, fields, and runtime entrypoints behind each step.

  1. Build and publish the frame (regular and @FastNative). The stub pushes a frame, stores the ArtMethod* at its bottom, saves callee-save registers, and spills every register-passed reference argument (including this) into its stack slot.

    Finally it records the stack pointer in Thread so the GC can walk the stack while C runs, find those references, and update them if objects move. @CriticalNative stubs skip all of this because the GC cannot run during the call.

  2. Leave Runnable (regular only). Synchronized methods lock first; then one atomic CAS flips state_and_flags from “Runnable, no flags” to “Native, no flags” and clears the mutator-lock record: 
    // TryToTransitionFromRunnableToNative, LSE (ARMv8.1 atomics) path
// (VIXL assembler calls shown as assembly, register names simplified)
mov  w16, #0                      // expected: kRunnable (0), no flags
mov  w17, #kNativeStateValue      // new: kNative, no flags
casl w16, w17, [x19]              // state_and_flags is at offset 0 of Thread
cbnz w16, slow_path               // any flag set → pJniMethodStart
str  xzr, [x19, #held_mutexes[kMutatorLock]]
    Pending GC flags make the CAS fail into a slow path; once it succeeds, GC no longer waits for this thread. @FastNative and @CriticalNative stay Runnable, saving both swaps while making GC pauses wait for C to return, so never block or loop unboundedly in them.
  3. Push a local reference frame (regular and @FastNative). A local reference is a slot in a per-thread table that keeps an object alive and gives native code a stable handle; calls like NewStringUTF add entries to it. The stub snapshots the table’s current top index in callee-save registers so all local references created during the call can be rolled back in one write on return.
  4. Build the native arguments and call (all flavours). Regular and @FastNative calls pass JNIEnv*, a class or this handle, stack-slot addresses from step 1 for reference arguments (so GC moves stay transparent), and primitives per AAPCS64, then call the JNI entry point (from RegisterNatives or lazy symbol lookup) and extend narrow integer results. @CriticalNative methods must be static with primitive-only signatures and receive no JNIEnv* or jclass: 
    // Java declaration
@CriticalNative static native long write(long ptr, int len);
// binds to
jlong Java_..._write(jlong ptr, jint len)
    Optimized callers jump straight to the C function pointer without a stub (except in debuggable apps).
  5. Return to Runnable (regular only). When C returns, the thread is still Native and cannot touch the heap, even to decode a returned jobject. A reverse CAS flips back to “Runnable, no flags” and re-records the mutator lock; if a suspend, checkpoint, or flip flag arrived in C, the CAS fails and waits in a slow path charged to the end of the JNI call. @FastNative instead polls the flags explicitly before decoding any reference result after an exception check.
  6. Pop the local reference frame (regular and @FastNative). The stub writes back the table position saved in step 3, dropping every local reference created during the call in O(1) time without scanning them.
  7. Unlock, check for an exception, return (regular and @FastNative). Synchronized methods release the monitor, and the stub checks Thread::exception. Because C cannot throw across frames into Java, env->ThrowNew(…) simply records a pending exception and returns normally; this check unwinds the Java stack if one is set, or else restores registers and returns.

17Arrays reach native code by copying, by blocking the GC, or by never moving

Passing bulk binary data between Java and C hits the core tension of a moving runtime: C functions want a contiguous uint8_t* that stays valid for the duration of the call, whereas ART’s moving space can relocate an ordinary primitive array at any GC flip. Every array-crossing API picks one of three ways out: copy the bytes across the border, block GC flips until C finishes, or allocate the array in a non-moving space up front.
