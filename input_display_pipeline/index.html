How a touch becomes pixels, and how Android decides a frame was late

A touch passes through the kernel, two threads in system_server, the app's two drawing threads, the GPU, SurfaceFlinger and the display hardware before it reaches the screen. Every stage works to a deadline set by the display's refresh. This note follows one frame through each stage, then shows how FrameTimeline decides which frames were janky. Each section ends with what it means when you read a trace.

Code is from AOSP as of Android 17: frameworks/native, frameworks/base and external/perfetto. Excerpts marked shape are simplified. Timelines assume a fixed refresh rate and omit the small phase offsets unless stated.

At a glance

  • Input. The kernel reads the touch, system_server picks the window under the finger, and a socket carries the event to the app.
  • Making a frame. Once per refresh, the app runs input, animation and layout, then a second thread and the GPU draw the image.
  • Showing it. SurfaceFlinger collects every app's finished image, and the display hardware combines them on the next refresh.
  • Jank. A stage that misses its deadline leaves the old image on screen for one more refresh. The user sees a stutter.
  • Reading a trace. FrameTimeline marks each frame as on time, late because of the app, late because of the system, or queued behind a late frame.

Terms. A panel does not redraw continuously. It reads a finished image out of memory line by line, top to bottom. This read-out is scanout, and the number of scanouts per second is the refresh rate. The display can switch images only between two scanouts, at a VSYNC (vertical sync) signal. At 60 Hz that is every 16.7 ms. A frame's deadline is the latest time its work can finish and still make its VSYNC. A late or repeated frame is jank. SurfaceFlinger is the system process that combines every app's images and the system UI into the one image the panel shows. A buffer is one image in memory (Section 8). A fence is a kernel object that signals when the GPU or display is done with a buffer (Section 9). Latching is SurfaceFlinger taking a new buffer for the frame it is building. HWC, the hardware composer, is the display hardware's driver interface (Section 10). doFrame and DrawFrames are the per-frame trace slices on the app's UI thread and on its RenderThread, the second thread that issues GPU commands (Sections 6 and 7).

A frame takes about two refresh periods from the app's start to the screen

The app gets one refresh period to draw a frame, and SurfaceFlinger gets the next one to put it on screen. That holds with the default scheduling durations (Section 5). The work is spread across several threads and two processes, the app and SurfaceFlinger. Everything in this note exists to have the right image fully rendered at the right VSYNC.

Part I · Input

1The kernel reports each touch as a short run of small fixed-size records

Linux gives Android one generic format for every input device, so Android needs no driver protocol per vendor. The touch controller is a small processor on the panel. It scans its capacitive grid at its own rate, independent of the display refresh. When it has new contacts, it interrupts the phone's main chip, the SoC. The kernel touch driver then publishes the contacts on a device file, /dev/input/eventN. This interface is evdev (event device), and Android reads it with ordinary read() calls.

evdev is a stream of fixed-size records. Each record holds a timestamp, a type, a code and a value. The type says key, absolute axis or sync. The code says which key or axis. On a 64-bit kernel each record is 24 bytes.

A touch needs several values for several fingers at once, so the kernel groups records into packets. The reader must know which values belong together and which finger is which. The kernel's multi-touch protocol B answers both:

  • Each finger lives in a numbered slot.
  • A tracking id names the contact for as long as the finger is down.
  • The driver sends only values that changed.
  • A SYN_REPORT record closes one atomic packet.

The older protocol A re-sent every contact anonymously on each report. One finger going down looks like this (example values):

// one packet from /dev/input/eventN (example)
EV_ABS  ABS_MT_SLOT         0      // talk about slot 0
EV_ABS  ABS_MT_TRACKING_ID  42     // new contact id; -1 later means "lifted"
EV_ABS  ABS_MT_POSITION_X   540
EV_ABS  ABS_MT_POSITION_Y   1280
EV_KEY  BTN_TOUCH           1
EV_SYN  SYN_REPORT          0      // end of packet: now it is consistent

Touch timestamps come from the kernel, not from the moment Android read the event. EventHub, the input reader's wrapper around the device files (Section 2), asks the kernel to stamp events with CLOCK_MONOTONIC, a clock that never jumps and pauses while the device is suspended. It does this with ioctl(EVIOCSCLOCKID), a control call on the device file. That kernel time is what MotionEvent.getEventTime() returns. A MotionEvent is the Java object an app receives for each touch or pointer event. It holds an action, such as DOWN, MOVE or UP, plus the coordinates of every pointer.

2system_server turns raw records into screen coordinates on one thread and routes them on another

Raw records are in panel units, unrotated, and know nothing about windows, so system_server converts and routes them. The code is inputflinger, native code inside system_server, the process that hosts the window manager and most system services. It has two main threads. The InputReader thread turns raw records into Android events. The InputDispatcher thread decides which window gets each event and delivers it.

EventHub sleeps until any input device has data, then reads a batch of records. The kernel holds a wakelock from the interrupt until the reader has picked the events up. A wakelock keeps the device from suspending. The exact limits are in Section 14.

InputReader hands each device's records to a mapper. For a touchscreen that is MultiTouchInputMapper, a kind of TouchInputMapper. It collects axis values until SYN_REPORT. Then it applies rotation and scaling to get display coordinates and emits one motion record, a NotifyMotionArgs in inputflinger's terms.

// TouchInputMapper, on SYN_REPORT
TouchInputMapper::sync → processRawTouches → cookAndDispatch → dispatchTouches
// raw panel units → display coordinates → NotifyMotionArgs

The filter stages are a chain of InputListener stages built in InputManager.cpp. Each stage can change, drop or annotate an event before passing it on. In order, they include palm rejection (UnwantedInteractionBlocker), accessibility key filters such as bounce and sticky keys (InputFilter), the mouse and stylus pointer icons (PointerChoreographer) and motion classification (InputProcessor), plus a few more.

3The dispatcher picks the window under the finger and sends the event over a socket, not Binder

The dispatcher has two jobs: find the window under the finger, and deliver the event without letting a stuck app block everyone else. SurfaceFlinger pushes the current window list to the dispatcher whenever it changes. For a touch down, the dispatcher walks that list front to back and picks the first touchable window under the point. Spy windows, such as system gesture monitors, also receive the stream without being the target.

InputDispatcher::onWindowInfosChanged            // SurfaceFlinger pushes the latest WindowInfo list
DispatcherTouchState::findTouchedWindowTargets   // on touch down
  findTouchedWindowAt                            // front to back: first touchable window under the point

Each window has an InputChannel: one end of a pair of already-connected local sockets, created in one call. The socket type keeps message boundaries, so one send is exactly one input message. The app gets its end when the window is added, and the main thread's event loop (its Looper) watches it. The dispatcher's end stays in system_server. The same socket carries the app's finished signal back.

An input ANR fires when the oldest event sent to a window stays unfinished too long

If an app stops reading its socket, the system must notice and tell the user. That is an ANR (Application Not Responding): the dialog and bug report that system_server raises when an app has not handled input, a broadcast or a service call in time. For input, each connection keeps two queues. The outbound queue holds events not yet written to the socket. Once an event is sent, it moves to the wait queue and an ANR deadline is armed. It leaves the wait queue only when the app's finished signal for it arrives. If the socket is full (WOULD_BLOCK), events wait in the outbound queue until the app catches up.

The default timeout is 5 seconds. Slow emulators stretch it, and a window or application can carry its own. When an event is sent, the dispatcher records its timeout time in an ANR tracker. The oldest overdue connection gets the ANR. Key events have a second ANR path: no focused window to receive them. Only that path can warn early: behind a feature flag, the dispatcher sends a pre-ANR notice at half the timeout, or a fixed window before the deadline, whichever is earlier.

        HwTimeoutMultiplier());   // 5000 ms × 1 on real hardware; larger on slow emulators

What it means for you An input ANR is not "the app was slow for 5 s". It is "the oldest event sent to this window was not finished for 5 s". A single long main-thread task blocks every event behind it, including ones the app would have handled instantly.

4The app collects touch moves and handles them once per frame

The touch panel and the display run on unrelated clocks, so the app batches moves and handles them once per frame. Delivering every MOVE the moment it arrives would make the app lay out several times per frame and throw away all but the last result. Instead the app side batches moves: it collects them without delivering them. It consumes them once per frame, in the input step of Choreographer, the per-thread object that runs an app's work once per VSYNC (Section 6).

The rule is simple: only moves (ACTION_MOVE and ACTION_HOVER_MOVE) wait, and anything else goes out at once. The batching code is InputConsumer::consume in libs/input/InputConsumer.cpp. Figure 5 shows the three cases.

When a batch is waiting, ViewRootImpl asks Choreographer for an input callback, and the next frame drains the batch.

frameworks/base/core/java/android/view/ViewRootImpl.java// called by NativeInputEventReceiver when a batch is pending
public void onBatchedInputEventPending(int source) {
    final boolean unbuffered = mUnbufferedInputDispatch
            || (source & mUnbufferedInputSource) != SOURCE_CLASS_NONE;
    if (unbuffered) { ... consumeBatchedInputEvents(-1); return; }
    scheduleConsumeBatchedInput();   // postVsyncCallback(CALLBACK_INPUT, ...)
}
// at the next frame: doConsumeBatchedInput(frameTimeNanos) drains the batch

View.requestUnbufferedDispatch opts out, and moves are delivered as they arrive. Drawing and stylus apps use it when they want every sample with minimal delay.

Resampling evens out the uneven number of samples per frame

Batching makes per-frame steps uneven, and resampling evens them out. With a 240 Hz panel and a 60 Hz display, some frames get four new samples and some get five. A finger moving at constant speed would then jump by uneven steps. So the app synthesizes the pointer position at a fixed offset before the frame time. The real samples are not lost. They travel in the same MotionEvent as its history, readable with getHistoricalX/Y.

RESAMPLE_MAX_PREDICTION8 msExtrapolation limit, further bounded by half the last sample gap.

Resampling applies only to pointer moves from a finger, mouse, stylus or unknown tool. It is on by default and controlled by the ro.input.resampling property. Resampler.cpp carries the same constants for the newer InputConsumerNoResampling path.

What it means for you A MOVE you see in onTouchEvent is usually a synthetic position 5 ms before the frame. The real samples are in getHistoricalX/Y. If you need every raw sample, for ink or drawing, read the history or request unbuffered dispatch.
Part II · Producing a frame

5SurfaceFlinger predicts VSYNC in software and wakes the app and itself at different times

SurfaceFlinger does not wake everyone on the hardware VSYNC. It predicts VSYNC in software and wakes each client a set time before the VSYNC that client targets. Keeping the hardware VSYNC interrupt on all the time costs power. Waking the app and SurfaceFlinger at the same moment would waste a period.

The prediction is a straight-line fit of VSYNC times, kept honest by the frames that actually reach the screen. The model learns from hardware VSYNC, then turns the interrupt off. After that, the times of present fences (Section 9) keep it calibrated. If a present fence disagrees with the model, SurfaceFlinger turns hardware VSYNC back on.

Two clients are scheduled from the model:

  • VSYNC-app wakes every Choreographer that asked for a frame. It fires early enough to cover both the app's work and SurfaceFlinger's.
  • VSYNC-sf wakes SurfaceFlinger itself, leaving just its own work time before the target VSYNC. It runs commit and composite (Section 10).
// how the two clients are registered (shape)
// VSYNC-app: the EventThread named "app", SurfaceFlinger's thread that sends VSYNC events to subscribers over a socket
workDuration  = appWorkDuration;
readyDuration = sfWorkDuration;     // fires appWorkDuration + sfWorkDuration before the target VSYNC
// VSYNC-sf: SurfaceFlinger's own MessageQueue callback, registered as "sf"
workDuration  = sfWorkDuration;     // fires sfWorkDuration before the target VSYNC

Older documentation and properties describe the same schedule as a phase offset: how long after a hardware VSYNC each client wakes. AOSP still configures offsets by default and converts them into durations. A device can instead set the durations directly.

Each VSYNC-app event offers several candidate frame timelines, one period apart. Each has a vsync id, a deadline and an expected presentation time, and Choreographer uses the preferred one. The vsync id is the number you see in Choreographer#doFrame 123456 and in DrawFrames 123456 on RenderThread. It is also the name of the FrameTimeline slices (Section 12). The candidates travel in VsyncEventData, and the cap is in Section 14.

What it means for you Your frame budget is not "16.7 ms from doFrame". It is "from VSYNC-app to the deadline", roughly one period with default durations. It covers the UI thread, RenderThread and the GPU together.

6Choreographer runs each frame's work in a fixed order: input, animation, layout, draw

Choreographer turns each VSYNC-app event into one ordered pass of work, so a frame is never drawn from half-updated state. An app has many sources of per-frame work: input, animators, layout, drawing. If each ran whenever its message reached the front of the main thread's queue, a frame could mix old and new state, or lay out the same views twice. There is one Choreographer per Looper thread. Code that wants to run on the next frame posts a callback into one of five queues. Choreographer asks for a VSYNC only when some queue has work.

The public form is a frame callback, a Choreographer.FrameCallback posted with postFrameCallback. It runs once in the next frame, in the animation queue after input, and receives that frame's VSYNC time.

TypeValueTrace sliceTypical users
CALLBACK_INPUT0inputBatched input from ViewRootImpl (Section 4)
CALLBACK_ANIMATION1animationpostFrameCallback, postVsyncCallback, animators
CALLBACK_INSETS_ANIMATION2insets_animationWindow inset animations, combined into one update
CALLBACK_TRAVERSAL3traversalViewRootImpl.doTraversal: measure, layout, draw
CALLBACK_COMMIT4commitPost-draw work; frame time may be adjusted for delays during traversal

The order is the point. Input and animations change state first, so that one traversal measures, lays out and records the whole frame once.

If the UI thread starts a frame a full period late or more, Choreographer snaps the frame time forward to the latest VSYNC. The trace then shows a "resynced" doFrame slice. When many frames were skipped, it also logs the familiar "Skipped N frames!" warning.

// Choreographer.doFrame (shape)
if (jitterNanos >= frameIntervalNanos)   // started a full period late or more
    // snap the frame time to the latest VSYNC; slice "Choreographer#doFrame - resynced to …"
if (skippedFrames >= SKIPPED_FRAME_WARNING_LIMIT)   // 30 by default, debug.choreographer.skipwarning
    // logs "Skipped N frames!  The application may be doing too much work on its main thread."
What it means for you Work posted with Handler.post runs between frames and competes with them. Work posted to Choreographer runs inside the frame in a known order. A resynced doFrame means the main thread was busy past a whole VSYNC before the frame could even start.

7The UI thread records what to draw, and RenderThread turns it into GPU commands

Since Android 5.0, drawing is split across two threads so the main thread can get back to input sooner. Drawing has two very different halves. One decides what to draw: it walks the view tree and runs app code. The other tells the GPU how to draw it: it builds command buffers and uploads textures. hwui, Android's native UI renderer, gives each half its own thread.

The UI thread only records. Each View has a native RenderNode holding a display list: a recorded list of drawing operations, such as "draw this text here", that can be replayed later. A RenderNode also holds properties such as translation, alpha and clip. The RenderThread, one per app process, turns those display lists into GPU commands.

Each RenderNode keeps two copies of its state so the two threads never touch the same data. The UI thread writes the staging copy (mStagingProperties and mStagingDisplayList), and RenderThread reads the live one. A simple property change, such as setTranslationY, marks a staging field dirty without re-recording the display list.

At the end of draw, the UI thread hands the frame to RenderThread and waits. RenderThread copies the staging state into the live tree and uploads new bitmaps. Then it normally releases the UI thread before it starts drawing.

frameworks/base/libs/hwui/renderthread/DrawFrameTask.cpp// UI thread: ThreadedRenderer.syncAndDrawFrame → DrawFrameTask::postAndWait (blocks on a condition variable)
void DrawFrameTask::run() {
    ATRACE_FORMAT("DrawFrames %" PRId64, vsyncId);
    ...
    canUnblockUiThread = syncFrameState(info);   // prepareTree: staging → live, upload bitmaps
    ...
    if (canUnblockUiThread) unblockUiThread();
    if (CC_LIKELY(canDrawThisFrame)) context->draw(solelyTextureViewUpdates);
    ...
    if (!canUnblockUiThread) unblockUiThread();   // texture cache full: UI waits for the draw
}

If the texture cache, the GPU memory where hwui keeps uploaded bitmaps, runs out of space, the UI thread stays blocked through the whole draw. In code, syncFrameState returns info.prepareTextures, which is false in that case.

What it means for you When the UI thread looks stuck in syncAndDrawFrame, look at RenderThread at the same moment, not at your view code. The cause is almost always on RenderThread or downstream of it.
Part III · Buffers & composition

8Buffers pass between the app and SurfaceFlinger through a small shared pool, without copies

The app and SurfaceFlinger share a small pool of image buffers, so frames change hands without copying. The app draws in one process and SurfaceFlinger shows the result in another, at different times. The app must also never draw into an image that is still on screen. A BufferQueue solves both. It is a small pool of graphics buffers in shared memory, between a producer that draws and a consumer that displays.

A buffer cycles through four steps. The producer dequeues a free buffer, draws into it, and queues it. The consumer acquires it, uses it, and releases it once it is no longer needed.

dequeueBuffer → draw → queueBuffer → acquireBuffer → use → releaseBuffer   // producer: first three; consumer: last three

SurfaceFlinger composes layers, one per surface. Each layer has a buffer and geometry: position, size, crop and transform. Layer changes arrive as a transaction (SurfaceControl.Transaction), a batch that SurfaceFlinger applies atomically, all in the same display frame. Latching is SurfaceFlinger taking a layer's newest ready buffer for the frame it is about to compose.

Since Android 12, BLAST lets an app window's buffer and geometry change land in the same frame. BLAST stands for buffer as layer state. Before it, SurfaceFlinger owned each window's queue consumer, while window geometry travelled separately in transactions. A new buffer and a new size could therefore land on different frames, the "bounce" below. With BLAST, BLASTBufferQueue runs the consumer side inside the app. It acquires each queued buffer and sends it to SurfaceFlinger as one more field of a transaction.

frameworks/native/libs/gui/BLASTBufferQueue.cpp · acquireNextBufferLockedt->setBuffer(mSurfaceControl, buffer, fence, bufferItem.mFrameNumber, mProducerId,
             releaseBufferCallback, dequeueTime);     // fence = the acquire fence
t->setDataspace(...); t->setBufferCrop(mSurfaceControl, crop); t->setTransform(...);
...
t->addTransactionCompletedCallback(makeTransactionCallbackThunk(), nullptr);

Two BLAST settings matter for jank. First, BLAST sets an infinite dequeue timeout, so dequeueBuffer blocks when no buffer is free. Second, BLAST layers turn on backpressure (eEnableBackpressure), so one layer advances at most one buffer per SurfaceFlinger frame. If SurfaceFlinger already has a ready buffer for that layer in the current frame, the next buffer transaction waits. The trace shows this as hasPendingBuffer <layer> on SurfaceFlinger's main thread. In the app process, the counter QueuedBuffer - <name>BLAST#<id> shows how many buffers are in flight.

What it means for you A RenderThread stuck in dequeueBuffer is waiting for SurfaceFlinger to release a buffer. The queue is full because the app is ahead of the display, not because the app is slow at that moment.

BLAST fixed the resize bounce by applying the new buffer and the new size together

Before BLAST, a resized window could briefly show old content inside its new bounds. Two owners decide what a window shows. The window manager (WM) in system_server decides where the window is and how big. The app decides what is drawn inside, and needs a frame or more to lay out and render at a new size. Before BLAST these travelled on two channels. WM changed the layer's size and crop with a transaction. The app's buffers reached SurfaceFlinger's own queue consumer, which latched them whenever they were ready.

The two rarely landed on the same display frame. For a frame or two, SurfaceFlinger showed the old-size buffer inside the new bounds: stretched, cropped, or with a strip of background. Then the new-size buffer arrived and the content snapped into place. During a resize animation this repeats every frame, so the content visibly wobbles against its own window edge. That artefact is the bounce. The BLAST code still spells out the hazard. In freeze scaling mode (below) it refuses to move the destination bounds before a matching buffer exists:

frameworks/native/libs/gui/BLASTBufferQueue.cpp · acquireNextBufferLocked// Only update mSize for destination bounds if the incoming buffer matches the requested size.
// Otherwise, it could cause stretching since the destination bounds will update before the
// buffer with the new size is acquired.
if (mRequestedSize == getBufferSize(bufferItem) ||
    bufferItem.mScalingMode != NATIVE_WINDOW_SCALING_MODE_FREEZE) {
    mSize = mRequestedSize;
}

BLAST makes this fix possible because a buffer is now a transaction field, so it can be merged with any other transaction. The protocol that uses it is BLAST sync, run by BLASTSyncEngine in WM and described in services/core/java/com/android/server/wm/BLASTSync.md. Figure 13 shows the three steps.

Separately, hwui sets freeze scaling mode on its surfaces (NATIVE_WINDOW_SCALING_MODE_FREEZE). In that mode, BLASTBufferQueue keeps the destination size at the old value until a buffer of the requested size arrives. It also rejects buffers whose size matches neither (rejectBuffer), so a stale buffer is never stretched into new bounds.

What it means for you A resize, rotation or window transition now waits for your first frame at the new size. A slow performTraversals after a configuration change shows up as a delayed transition, not as a stretched frame. With the view trace category on, the <window>-reportDrawFinished seqId=N instant on the main thread marks when your synced frame was handed back.

9Fences let each stage hand work on before the hardware has finished it

Every hand-off carries a fence, so CPU threads wait for the GPU or the display only when they need the data. A fence is a kernel sync_file: a file descriptor (fd) that signals once some hardware work is done. Without fences, RenderThread would wait for the GPU before handing over a buffer, and SurfaceFlinger would wait for the panel before releasing one. The pipeline would run one step at a time. An fd can be passed to another process cheaply. The receiver waits only when it actually needs the data, often on the GPU rather than the CPU.

SurfaceFlinger normally skips a buffer whose GPU work is not done, so one slow layer cannot make it miss its deadline for every layer. The trace then shows fence unsignaled <layer>, and the transaction waits for a later frame. The default exception is AutoSingleLayer. If a single layer is updating with a simple buffer-only change, SurfaceFlinger may latch it anyway and let HWC wait on the fence. Perfetto records the outcome for each frame in latched_fence_state. The setting and the three outcome values are in Section 14.

What it means for you RenderThread finishing on time is not enough. The frame is ready when the GPU finishes, which is when the acquire fence signals. GPU-heavy frames miss deadlines with an idle CPU.

10The display hardware blends most layers itself, and SurfaceFlinger uses the GPU only for the rest

Phones blend most layers in the display controller while scanning out, and SurfaceFlinger uses the GPU only for layers the hardware cannot handle. The panel shows one image, but the screen is made of many layers: the app, the status bar, the navigation bar, the wallpaper, perhaps a dialog. Combining them is composition. Doing it on the GPU every frame costs power and GPU time.

On VSYNC-sf, SurfaceFlinger's main thread runs two steps. Commit applies ready transactions: it latches buffers, updates geometry and works out what changed. Composite builds the frame for each display and hands it to the Hardware Composer (HWC). HWC is the display's hardware abstraction layer (HAL), the vendor-implemented interface to the display controller.

HWC picks a composition type for each layer. With DEVICE, the display hardware reads the layer's buffer directly into an overlay plane, a hardware layer it blends on the fly during scanout. With CLIENT, SurfaceFlinger's RenderEngine first draws the layer on the GPU into a single client target buffer, which HWC then shows. A few rarer types exist (Section 14).

Client composition costs GPU time and memory bandwidth inside SurfaceFlinger's budget. FrameTimeline marks such frames with gpu_composition = 1. Slow GPU composition shows up as SurfaceFlinger GPU Deadline Missed.

Each frame, SurfaceFlinger and HWC exchange two commands. Validate sends the layer list and gets back HWC's choice for each layer. Present queues the frame for the next scanout and hands back the fences (Section 9).

What it means for you Effects that the display controller cannot do push layers to CLIENT composition: blur, unusual blending or scaling, more layers than planes. That moves cost onto the GPU inside SurfaceFlinger. In a trace, frames with gpu_composition = 1 or long RenderEngine work on SurfaceFlinger point there, not at the app's draw.
Part IV · Jank

11One late frame can leave every later frame a period behind: buffer stuffing

Buffer stuffing is when the app has more finished buffers queued than the display can take on schedule. It usually starts with one late frame. Figure 17 follows four frames at 60 Hz, using the simple schedule from Section 5. Frame k starts at Vk, must be ready one VSYNC later, and is expected on screen one VSYNC after that.

Once stuffed, the queue stays one buffer deep until the app pauses for a frame. The animation looks smooth, but every frame carries one extra period of touch-to-display latency. If another frame is late while stuffed, all buffers are in use and RenderThread blocks in dequeueBuffer.

As of Android 17, Choreographer can recover from stuffing on its own. When RenderThread waits too long for a buffer release, Choreographer skips one VSYNC to drain a buffer. It then shifts animation time back by one frame until the animation goes idle. The trace shows a Buffer stuffing recovery track.

What it means for you Do not optimize the frames tagged Buffer Stuffing. They were on time. Find the first late frame before the run, here f1, and fix that. Then decide whether the extra period of latency matters for your interaction.

12FrameTimeline compares each frame's plan with what happened, and says whose fault a late frame was

FrameTimeline records, for every frame, what the scheduler planned and what actually happened. That tells you which frames the user saw stutter, and who caused it. A long doFrame does not prove the user saw a stutter. A stutter may also have nothing to do with the app. FrameTimeline is a SurfaceFlinger module in Android 12 and later. It records a SurfaceFrame for each app buffer or transaction, and a DisplayFrame for each SurfaceFlinger frame. Perfetto shows them as each process's Expected Timeline and Actual Timeline tracks, from the tables expected_frame_timeline_slice and actual_frame_timeline_slice.

An app's actual slice ends when its buffer is ready, not when it is shown

For an app frame, neither slice runs from start to present. Present time is an attribute of the slice instead.

  • Expected runs from the predicted start, the VSYNC-app wake-up, to the predicted deadline (mPredictions.endTime).
  • Actual runs from the start of Choreographer#doFrame to the moment the buffer was both queued and finished on the GPU. In code that is max(acquire fence time, queue time), set in SurfaceFrame::setAcquireFenceTime. Dropped frames end at the drop time.

The legacy rules sort late frames by whether the app finished late

A frame counts as presented on time if it is within 2 ms of the prediction. It finished late if it finished any time after its deadline. The deadline-based logic, now called the legacy classification, is Figure 20. The exact thresholds are in Section 14.

Version note Android 17 adds a second, cadence-based classification behind a SurfaceFlinger feature flag (use_experimental_jank_classification). With the flag on, SurfaceFlinger writes the new result into jank_type and moves the legacy result into the Jank type (experimental) arg. With the flag off, it is the other way round. The new one judges presentation cadence: the rhythm at which frames reach the screen. A frame is on cadence if the gap since the previous frame's present matches the expected gap, and the expected gap is short enough to be an animation. An on-cadence frame with more than 2 ms of present delay is Buffer Stuffing. The app deadline check subtracts time spent in dequeueBuffer. Frames that fit neither pattern become Non Animating. In the stuffing example both classifications agree. The cadence limits are in Section 14.

jank_type lists every reason, and jank_tag sums them up for the slice colour

jank_type is a comma-separated list of reasons, and jank_tag is one summary used for the slice colour. The strings come from JankTypeBitmaskToStringId in Perfetto's frame_timeline_event_parser.cc. For app frames:

Only late frames during motion count as perceptible jank

A late frame matters only if the user was watching something move. During a scroll or an animation the eye expects a new image every period, so one repeated frame breaks the rhythm and is seen. Some frames have no rhythm to break: the first frame after the screen was idle, content that changes once, or a frame while the display is off. Counting those as jank would bury the real stutters, so both SurfaceFlinger and Perfetto separate them.

With that flag on, SurfaceFlinger judges a frame by cadence (the version note above). It compares the gap since the previous frame's present with the gap that was planned. Some frames get the type Non Animating instead of late:

  • The frame has no usable previous frame, as on the first frame of an animation.
  • The gap is off, but the frames are too far apart to form an animation.
  • The frame carries a negative system content priority (mSystemContentPriority). This check sits behind a further flag.

While the display is off or changing power mode, the type is Display not ON or PowerModeChange in progress.

When one of those three types is a frame's only type, Perfetto tags it Non-perceivable Jank (CalculateSurfaceFrameJankTag). Everything tagged Self Jank or Other Jank is perceptible: it fell inside an animation and changed what the user saw. Buffer Stuffing and SurfaceFlinger Stuffing sit in between. The cadence held, but latency grew.

SurfaceFlinger also rates how bad each janky frame was, in the jank_severity_type column. The value is None, Partial, Full, or Unknown when there is too little information (calculateJankSeverity). The score is computed only for the jank reasons. It measures how far the actual present gap was from the expected one, relative to the frame interval.

-- perceptible jank only, with severity, for one app
SELECT jank_type, jank_severity_type, COUNT(*) AS frames
FROM actual_frame_timeline_slice
JOIN process USING (upid)
WHERE process.name = 'com.example.app'
  AND jank_tag IN ('Self Jank', 'Other Jank')
GROUP BY jank_type, jank_severity_type
ORDER BY frames DESC;
What it means for you Count Self Jank for the app, Other Jank for the system, and treat Buffer Stuffing as latency. Leave Non-perceivable Jank out of user-facing numbers. Read present_type and on_time_finish together. A late present with an on-time finish is never the app's CPU budget.

13Three queries cover frames by tag, per-thread time and input latency

Summary of frames by tag and type for one process. The actual_frame_timeline_slice table needs no INCLUDE: it is in the prelude, the set of tables Trace Processor always provides.

SELECT jank_tag, jank_type, present_type, COUNT(*) AS frames,
       ROUND(AVG(dur) / 1e6, 2) AS avg_actual_ms
FROM actual_frame_timeline_slice
JOIN process USING (upid)
WHERE process.name = 'com.example.app'
GROUP BY jank_tag, jank_type, present_type
ORDER BY frames DESC;

Per-frame breakdown of Self Jank into UI thread and RenderThread time. The android_frames table, from Perfetto's standard SQL library (stdlib), already joins Choreographer#doFrame, DrawFrames and the timeline slices by vsync id.

INCLUDE PERFETTO MODULE android.frames.timeline;

SELECT f.frame_id,
       a.jank_type,
       ROUND(a.dur / 1e6, 2)  AS actual_ms,
       ROUND(ui.dur / 1e6, 2) AS do_frame_ms,
       ROUND(rt.dur / 1e6, 2) AS draw_frames_ms
FROM android_frames f
JOIN actual_frame_timeline_slice a ON a.id = f.actual_frame_timeline_id
JOIN slice ui ON ui.id = f.do_frame_id
JOIN slice rt ON rt.id = f.draw_frame_id
WHERE f.process_name = 'com.example.app'
  AND a.jank_tag = 'Self Jank'
ORDER BY f.ts;

Input latency per event. The android_input_events table splits each event's latency into dispatch, handling and ack. Dispatch runs from the dispatcher to the app. Handling runs from the app receiving the event to sending finished. The table also links each event to the frame it landed in, and end_to_end_latency_dur runs from read time to that frame's present.

INCLUDE PERFETTO MODULE android.input;

SELECT event_action, dispatch_latency_dur, handling_latency_dur,
       ack_latency_dur, end_to_end_latency_dur, frame_id
FROM android_input_events
WHERE process_name = 'com.example.app'
ORDER BY read_time;
