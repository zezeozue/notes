How a touch becomes pixels, and how Android decides a frame was late

Turning a finger drag into lit pixels crosses privilege, process and hardware boundaries: kernel input drivers, window routing in system_server, two rendering threads in the app, an asynchronous GPU, SurfaceFlinger and the display controller. Running all of those stages end-to-end inside a single refresh interval (16.7 ms at 60 Hz, 8.3 ms at 120 Hz) would leave almost no budget for layout or shading, so Android pipelines frame production across two refresh periods synchronized by predicted VSYNC deadlines and kernel fences. This note explains why each stage in that pipeline exists, how Android's input and graphics architecture evolved to its current form, and how FrameTimeline separates real stutters from queue backlogs in a Perfetto trace.

Checked against AOSP as of Android 17: frameworks/native, frameworks/base and external/perfetto. Excerpts marked shape are simplified. Timelines assume a fixed refresh rate and omit small phase offsets unless stated.

At a glance

  • Input. Touch controllers sample asynchronously; system_server maps raw kernel records into display coordinates, hit-tests the global window stack, and streams events over a per-window socket to the app.
  • Making a frame. Once per predicted VSYNC, Choreographer batches input, animations and layout into a single UI-thread pass that records lightweight display lists for RenderThread and the GPU.
  • Showing it. App buffers travel as SurfaceControl.Transaction state (BLAST) synchronized by kernel fences; SurfaceFlinger latches ready buffers and hands layers to the display hardware on the next period.
  • Buffer stuffing vs jank. One slow frame repeats the old image for a refresh (a visible hitch) and leaves a backlog in the queue so later on-time frames arrive a period late despite smooth motion.
  • Reading a trace. FrameTimeline tracks each frame's predicted deadline and presentation token end-to-end, distinguishing app misses (Self Jank), compositor misses (Other Jank), and Buffer Stuffing.

Terms.

  • Scanout, refresh rate and VSYNC: a display panel reads a finished image out of memory line by line (scanout) at its refresh rate (every 16.7 ms at 60 Hz, 8.3 ms at 120 Hz) and switches images only between scanouts at vertical sync (VSYNC).
  • Deadline and jank: a frame's deadline is the latest moment its CPU and GPU work can finish and still make its target VSYNC; missing that deadline repeats the prior image on screen, causing a visible stutter (jank).
  • Looper and Binder: Looper is a thread's epoll-backed event loop; Binder is Android's general inter-process RPC mechanism, whereas high-rate input events use dedicated Unix-domain sockets.
  • SurfaceFlinger and HWC: SurfaceFlinger is the system compositor process that collects layer buffers from apps and system UI and hands them to the Hardware Composer (HWC), the vendor display-controller HAL (§10).
  • Buffer, fence and latching: a buffer is a shared-memory graphics surface (§8); a fence is a kernel file descriptor that signals when asynchronous GPU or display hardware finishes using a buffer (§9); latching is SurfaceFlinger acquiring a layer's newest ready buffer for composition.
  • doFrame and DrawFrames: the per-frame trace slices on the app's main UI thread (Choreographer#doFrame) and on its RenderThread, which submits GPU commands (§§6–7).

A frame takes about two refresh periods from the app's start to the screen

Under default scheduling durations (§5), the pipeline budgets one refresh period for the app's CPU and GPU work and the next refresh period for SurfaceFlinger and the display hardware. In steady state those two periods overlap like an assembly line: while SurfaceFlinger composes frame N, the app is already recording and rendering frame N+1. Every mechanism below exists to get the right buffer rendered, synchronized and latched before its VSYNC deadline.

Part I · Input

1The kernel reports each touch as a short run of small fixed-size records

Touch controllers are dedicated microcontrollers on the display assembly that scan their capacitive grid on their own hardware clock — typically 120–240 Hz or higher — completely asynchronous to display VSYNC. Rather than inventing a custom driver ABI per touch vendor, Android builds directly on Linux evdev (event device): when the controller detects new contacts and interrupts the SoC, the kernel driver publishes fixed-size records on /dev/input/eventN that user space reads with ordinary read() calls.

Each evdev record carries a timestamp, a type (key, absolute axis, or sync), a code (which key or axis), and a 32-bit signed value. On a 64-bit kernel each struct input_event is 24 bytes.

Reporting multiple fingers requires grouping individual axis updates into atomic snapshots and tracking finger identity across frames. The kernel's multi-touch protocol B solves both:

  • Each active contact occupies a numbered slot (ABS_MT_SLOT).
  • A tracking ID (ABS_MT_TRACKING_ID) identifies that contact for as long as the finger stays down.
  • The driver emits only axes whose values changed since the last report, reducing bus and syscall traffic.
  • An EV_SYN / SYN_REPORT record closes one atomic multi-finger packet.

The older protocol A re-sent every contact anonymously on every scan. One finger touching down under protocol B looks like this:

// one packet from /dev/input/eventN (example)
EV_ABS  ABS_MT_SLOT         0      // talk about slot 0
EV_ABS  ABS_MT_TRACKING_ID  42     // new contact id; -1 later means "lifted"
EV_ABS  ABS_MT_POSITION_X   540
EV_ABS  ABS_MT_POSITION_Y   1280
EV_KEY  BTN_TOUCH           1
EV_SYN  SYN_REPORT          0      // end of packet: now it is consistent

Touch timestamps come from the kernel interrupt path rather than when user space happens to wake up. EventHub, the reader's wrapper around /dev/input (§2), configures each device node via ioctl(EVIOCSCLOCKID) to stamp records with CLOCK_MONOTONIC — a monotonic clock that never jumps on wall-clock adjustments and pauses during system suspend. That kernel timestamp flows all the way to MotionEvent.getEventTime() on the Java MotionEvent delivered to the app (alongside actions such as ACTION_DOWN, ACTION_MOVE and ACTION_UP, and per-pointer coordinates).

2system_server turns raw records into screen coordinates on one thread and routes them on another

At first glance, routing every touch through system_server looks like an unnecessary hop between the kernel and the foreground app. Two system invariants require it. First, untrusted apps cannot read /dev/input/event* directly without being able to snoop touches and keystrokes meant for every other app. Second, raw panel coordinates know nothing about windows: only the system knows the live window Z-order, split-screen and floating bounds, non-touchable regions, system-wide gesture monitors (such as back-swipe or status-bar shade), and which process to blame with an ANR if input stalls.

Inside system_server, native inputflinger splits that work across two dedicated threads so window-routing policy never delays draining kernel buffers: InputReader converts raw device records into display-space events, and InputDispatcher resolves window targets and manages per-window delivery.

EventHub blocks in epoll_wait across all input device descriptors registered with EPOLLWAKEUP, so the kernel holds a wakeup source from the hardware interrupt until InputReader reads the batch of records (§14). InputReader feeds each device's stream into a mapper — MultiTouchInputMapper (a subclass of TouchInputMapper) for touchscreens — which accumulates slot state until SYN_REPORT, applies display rotation and panel-to-pixel scaling, and emits a NotifyMotionArgs packet:

// TouchInputMapper, on SYN_REPORT
TouchInputMapper::sync → processRawTouches → cookAndDispatch → dispatchTouches
// raw panel units → display coordinates → NotifyMotionArgs

Between InputReader and InputDispatcher sits a chain of InputListener filter stages assembled in InputManager.cpp. Each stage can transform, drop or annotate events in order — including palm rejection (UnwantedInteractionBlocker), accessibility key filters such as bounce and sticky keys (InputFilter), mouse and stylus cursor choreography (PointerChoreographer), and motion classification (InputProcessor).

3The dispatcher picks the window under the finger and sends the event over a socket, not Binder

InputDispatcher has two jobs: resolve the right target window from what is actually visible on screen, and stream events to that window without letting one hung app stall input for the rest of the system. Because window animations and transforms run in SurfaceFlinger, SurfaceFlinger pushes authoritative WindowInfo snapshots back to InputDispatcher whenever layer geometry changes. On ACTION_DOWN, the dispatcher walks that list front to back and selects the first touchable window containing the contact point, while also copying the stream to spy windows such as system navigation gesture monitors.

InputDispatcher::onWindowInfosChanged            // SurfaceFlinger pushes the latest WindowInfo list
DispatcherTouchState::findTouchedWindowTargets   // on touch down
  findTouchedWindowAt                            // front to back: first touchable window under the point

Why deliver events over a socket instead of Binder? During a high-rate swipe, touch samples arrive every few milliseconds and fan out to both the target window and system gesture spies. Sending each sample as a Binder transaction would wake Binder pool threads (which then still have to hop onto the main UI thread) or contend on a process-wide async Binder buffer. Instead, each window receives an InputChannel backed by a dedicated AF_UNIX SOCK_SEQPACKET socketpair: the app registers its descriptor directly on the main thread's Looper epoll set, SOCK_SEQPACKET preserves exact InputMessage packet boundaries without framing overhead, and the same bidirectional socket carries compact completion acknowledgements back to InputDispatcher.

An input ANR fires when the oldest event sent to a window stays unfinished too long

Per-window sockets also isolate backpressure and fault attribution when an app's UI thread wedges. If an app stops draining its InputChannel, system_server raises an ANR (Application Not Responding) dialog and captures stack traces. Each connection maintains two user-space queues around its 32 KB kernel socket buffer: events wait in outboundQueue before being written, move into waitQueue with an armed ANR deadline once send() succeeds, and leave waitQueue only when the app writes back a FINISHED reply for that sequence number. If the 32 KB socket fills and returns WOULD_BLOCK, newer events back up inside that connection's outboundQueue while other windows keep receiving input normally.

The default timeout is 5 seconds. Slow emulators stretch it, and a window or application can carry its own. When an event is sent, the dispatcher records its timeout time in an ANR tracker. The oldest overdue connection gets the ANR. Key events have a second ANR path: no focused window to receive them. Only that path can warn early: behind a feature flag, the dispatcher sends a pre-ANR notice at half the timeout, or a fixed window before the deadline, whichever is earlier.

What it means for you Input ANR timers measure how long the oldest dispatched event in waitQueue has waited for its FINISHED reply (5 seconds by default), rather than how long any single touch handler took. One long main-thread Binder call or lock stall delays every input event queued behind it — even events the app's own touch code would process in microseconds.

4The app collects touch moves and handles them once per frame

Because the touch controller (often 120–240 Hz) and the display panel (60 or 120 Hz) run on independent clocks, dispatching every ACTION_MOVE the instant it arrives on the socket would cause two problems: the UI thread would measure and lay out views multiple times per refresh only to overwrite all but the last pass, and beat frequencies between the two clocks would deliver a varying number of raw samples from one frame to the next. Android solves the redundant-work problem with batching and the uneven-cadence problem with resampling.

On the app side, InputConsumer::consume (in libs/input/InputConsumer.cpp) buffers pointer move events (ACTION_MOVE and ACTION_HOVER_MOVE) until Choreographer runs its per-frame input callback (§6), while delivering discrete state changes such as ACTION_DOWN, ACTION_UP and key events immediately (flushing any pending moves first so event ordering stays intact; Figure 5).

When a batch is waiting, ViewRootImpl schedules an input callback on Choreographer, and the next frame drains the batch:

frameworks/base/core/java/android/view/ViewRootImpl.java// called by NativeInputEventReceiver when a batch is pending
public void onBatchedInputEventPending(int source) {
    final boolean unbuffered = mUnbufferedInputDispatch
            || (source & mUnbufferedInputSource) != SOURCE_CLASS_NONE;
    if (unbuffered) { ... consumeBatchedInputEvents(-1); return; }
    scheduleConsumeBatchedInput();   // postVsyncCallback(CALLBACK_INPUT, ...)
}
// at the next frame: doConsumeBatchedInput(frameTimeNanos) drains the batch

Calling View.requestUnbufferedDispatch opts out so move events dispatch immediately as they arrive — useful for low-latency stylus inking or drawing canvases that predict strokes themselves.

Resampling evens out the uneven number of samples per frame

Batching alone still suffers from clock-ratio beat jitter: when a touch sensor scans at a non-integer or phase-drifting multiple of the display refresh, one VSYNC interval might collect three raw samples and the next four, making a finger moving at constant velocity appear to lurch forward by alternating distances. Resampling restores uniform temporal spacing by evaluating the pointer position at a fixed offset before the frame timestamp (frameTime − 5 ms): when a newer raw sample already sits in the buffer past that sample point, InputConsumer linearly interpolates between the bracketing samples; otherwise it extrapolates boundedly from the last two. None of the raw hardware readings are discarded — they ride along inside the same MotionEvent as historical coordinates accessible via getHistoricalX and getHistoricalY.

What it means for you The coordinates returned by MotionEvent.getX() and getY() on an ACTION_MOVE in onTouchEvent are normally resampled at frameTime − 5 ms, while the raw touch-controller samples sit in getHistoricalX and getHistoricalY. Ink and drawing apps that fit curves to raw hardware samples should read the history array or call requestUnbufferedDispatch.
Part II · Producing a frame

5SurfaceFlinger predicts VSYNC in software and wakes the app and itself at different times

Before Android 4.1 (Project Butter), apps drew whenever an invalidation or Handler timer reached the front of the main Looper: two frames could render back-to-back inside one refresh period while the next period missed its scanout completely. Project Butter aligned both app rendering and composition to VSYNC, and modern SurfaceFlinger goes one step further: rather than keeping the display hardware's VSYNC interrupt enabled continuously (which burns power) or waking every stage at the hardware edge (which wastes pipeline headroom), SurfaceFlinger predicts VSYNC timestamps in software and wakes each client a configured work duration before the target scanout.

The software clock, VSyncPredictor, fits a linear regression over recent hardware VSYNC timestamps and then disables the hardware interrupt. From that point on, actual display present fences (§9) fed through VSyncReactor keep the phase and period calibrated; if a present fence drifts outside tolerance, SurfaceFlinger re-enables hardware VSYNC interrupts to retrain.

Two distinct wake-up streams are scheduled from that model:

  • VSYNC-app (driven by SurfaceFlinger's EventThread named "app") wakes every Choreographer that requested a frame, firing early enough to cover both the app's work and SurfaceFlinger's composition pass.
  • VSYNC-sf wakes SurfaceFlinger's own main-thread MessageQueue just sfWorkDuration before the target scanout to run commit and composite (§10).
// how the two clients are registered (shape)
// VSYNC-app: the EventThread named "app", SurfaceFlinger's thread that sends VSYNC events to subscribers over a socket
workDuration  = appWorkDuration;
readyDuration = sfWorkDuration;     // fires appWorkDuration + sfWorkDuration before the target VSYNC
// VSYNC-sf: SurfaceFlinger's own MessageQueue callback, registered as "sf"
workDuration  = sfWorkDuration;     // fires sfWorkDuration before the target VSYNC

Older documentation and properties describe the same schedule as a phase offset: how long after a hardware VSYNC each client wakes. AOSP still configures offsets by default and converts them into durations. A device can instead set the durations directly.

Each VSYNC-app pulse carries up to seven candidate frame timelines in VsyncEventData (§14), spaced one period apart. Each candidate bundles a token (vsyncId), a buffer-ready deadline, and an expected presentation timestamp; Choreographer selects the preferred candidate. That vsyncId is the correlation key printed on Choreographer#doFrame 123456, on DrawFrames 123456 on RenderThread, and on the matching FrameTimeline slices in SurfaceFlinger (§12).

What it means for you An app's frame budget runs from the predicted VSYNC-app wake-up to deadline (appWorkDuration, roughly one refresh period under AOSP defaults) — and the UI thread, RenderThread and GPU shader execution all share that single budget. If the main thread wakes late because of earlier Looper work, the time lost comes straight out of what remains before the deadline.

6Choreographer runs each frame's work in a fixed order: input, animation, layout, draw

Aligning wake-ups to VSYNC-app solves pacing only if everything that mutates UI state for one frame runs in a deterministic order. During an interactive scroll, batched touch events, property animators, window-inset transitions and view invalidations all want to update the hierarchy. Running each on an independent Handler message would either measure and lay out views multiple times per refresh or draw half-updated state. Choreographer (one instance per Looper thread) coalesces all per-frame work into five ordered callback queues and requests a VSYNC-app pulse from EventThread only while at least one queue is non-empty.

App and library code schedules frame-aligned work with Choreographer.postFrameCallback (or postVsyncCallback), which runs once in the next frame's CALLBACK_ANIMATION phase — after batched input has been delivered and before layout begins.

The order is the point. Input and animations change state first, so that one traversal measures, lays out and records the whole frame once.

If the UI thread starts a frame a full period late or more, Choreographer snaps the frame time forward to the latest VSYNC. The trace then shows a "resynced" doFrame slice. When many frames were skipped, it also logs the familiar "Skipped N frames!" warning.

// Choreographer.doFrame (shape)
if (jitterNanos >= frameIntervalNanos)   // started a full period late or more
    // snap the frame time to the latest VSYNC; slice "Choreographer#doFrame - resynced to …"

    // logs "Skipped N frames!  The application may be doing too much work on its main thread."
What it means for you Messages posted via Handler.post execute at arbitrary times on the Looper and can delay the next VSYNC callback, whereas callbacks registered with Choreographer execute inside doFrame in causal order. Seeing Choreographer#doFrame - resynced to … in a trace means earlier main-thread work kept doFrame from even starting until at least one full VSYNC interval had already elapsed.

7The UI thread records what to draw, and RenderThread turns it into GPU commands

When Android 3.0 introduced hardware-accelerated 2D rendering (hwui), a single main thread walked the View hierarchy, translated canvas calls into OpenGL commands, waited in dequeueBuffer, and submitted work to the GPU driver. Any driver hiccup — compiling a shader, uploading a large bitmap, or waiting on a busy buffer — froze the UI thread and blocked touch dispatch for the following frame. Android 5.0 solved that coupling by splitting hwui across two threads: the UI thread records lightweight scene instructions, and a per-process RenderThread owns the GPU context and buffer queue.

During draw, the UI thread never talks to the GPU driver. Instead, each View records drawing operations into a native RenderNode holding a display list (replayable commands such as text runs, rounded rects and child RenderNode references) alongside transform properties such as translation, alpha, elevation and clip. Because RenderNode double-buffers its fields — the UI thread mutates mStagingProperties and mStagingDisplayList while RenderThread reads the live tree — changing a view property such as setTranslationY marks a staging property dirty without re-recording the display list, and allows RenderThread-driven animations (such as ripples) to keep animating smoothly even if the UI thread stalls on a later frame.

At the end of draw, the UI thread calls ThreadedRenderer.syncAndDrawFrame (DrawFrameTask::postAndWait) and blocks briefly on a condition variable while RenderThread runs syncFrameState to copy staging changes into the live tree and upload bitmaps. As soon as that sync finishes, RenderThread unblocks the UI thread so it can return to Looper input while RenderThread dequeues a buffer and issues Skia/Vulkan/GL commands in parallel:

frameworks/base/libs/hwui/renderthread/DrawFrameTask.cpp// UI thread: ThreadedRenderer.syncAndDrawFrame → DrawFrameTask::postAndWait (blocks on a condition variable)
void DrawFrameTask::run() {
    ATRACE_FORMAT("DrawFrames %" PRId64, vsyncId);
    ...
    canUnblockUiThread = syncFrameState(info);   // prepareTree: staging → live, upload bitmaps
    ...
    if (canUnblockUiThread) unblockUiThread();
    if (CC_LIKELY(canDrawThisFrame)) context->draw(solelyTextureViewUpdates);
    ...
    if (!canUnblockUiThread) unblockUiThread();   // texture cache full: UI waits for the draw
}

If hwui's GPU texture cache runs out of space to stage bitmap uploads during syncFrameState (info.prepareTextures == false), canUnblockUiThread turns false and the UI thread must stay blocked until RenderThread finishes drawing the frame and frees texture memory.

What it means for you When the UI thread looks stuck inside syncAndDrawFrame, inspect RenderThread at that exact timestamp rather than profiling your View.onDraw code: the UI thread is almost always waiting for RenderThread to finish the previous frame's draw or dequeueBuffer wait.
Part III · Buffers & composition

8Buffers pass between the app and SurfaceFlinger through a small shared pool, without copies

Copying a multi-megabyte screen-sized bitmap across processes on every refresh would saturate memory bandwidth, while drawing into a buffer currently scanning out to the panel would tear visibly on screen. Android solves both with a BufferQueue: a small ring of gralloc DMA-BUF allocations shared zero-copy between a producer (such as an app's RenderThread or camera HAL) and a consumer, guarded by kernel fences (§9) so CPU threads pipeline buffers without waiting in user space for pixels to finish rendering.

Each buffer slot cycles through four states: the producer calls dequeueBuffer to claim a free slot, submits GPU rendering into it, and calls queueBuffer; the consumer calls acquireBuffer, presents or composites it, and returns it via releaseBuffer once a newer buffer replaces it on screen.

dequeueBuffer → draw → queueBuffer → acquireBuffer → use → releaseBuffer   // producer: first three; consumer: last three

SurfaceFlinger composes layers, one per surface, combining each layer's pixel buffer with its geometry (position, size, crop, transform and alpha). Geometry updates arrive in SurfaceControl.Transaction batches applied atomically on the same display frame, and latching is SurfaceFlinger adopting a layer's newest ready buffer for composition.

Historically, pixels and geometry crossed two uncoordinated IPC channels: SurfaceFlinger hosted each app window's BufferQueue consumer directly, while window size and position traveled over Binder through WindowManagerService into separate SurfaceControl.Transactions. Whenever a window resized, the new bounds and the newly sized pixel buffer raced each other into SurfaceFlinger, causing the visible resize tearing described below. Android 12 unified the two channels with BLAST (Buffer as Layer State): BLASTBufferQueue moves the BufferQueue consumer into the app process itself, acquires each queued buffer locally, and packages it via setBuffer as just another atomic field inside a SurfaceControl.Transaction:

             releaseBufferCallback, dequeueTime);     // fence = the acquire fence
t->setDataspace(...); t->setBufferCrop(mSurfaceControl, crop); t->setTransform(...);
...
t->addTransactionCompletedCallback(makeTransactionCallbackThunk(), nullptr);

Two BLASTBufferQueue settings shape how traces look under load. First, BLAST configures an infinite producer dequeue timeout, so dequeueBuffer blocks when all slots in the pool are in flight. Second, BLAST layers set eEnableBackpressure, telling SurfaceFlinger to latch at most one buffer per layer on each VSYNC: if a second buffer transaction arrives before the first has been latched, it waits in pending transaction state (visible as hasPendingBuffer <layer> on SurfaceFlinger's main thread, while QueuedBuffer - <name>BLAST#<id> in the app process tracks buffers in flight).

What it means for you A RenderThread blocked in dequeueBuffer is waiting for SurfaceFlinger to release an older slot: all pool buffers are already queued or on screen, either because the queue is stuffed (§11) or because composition fell behind downstream.

BLAST fixed the resize bounce by applying the new buffer and the new size together

Two different processes own what a resized window displays: WindowManagerService (WM) in system_server owns the window's screen bounds and crop, whereas the app owns the pixels drawn inside those bounds and needs at least one layout-and-draw pass to render at the new dimensions. Before Android 12, WM sent updated layer bounds directly to SurfaceFlinger in a transaction while the app's old-size buffers kept arriving independently on SurfaceFlinger's BufferQueue consumer.

Because those two updates rarely landed on the same VSYNC, SurfaceFlinger routinely composited one or two frames with an old-size buffer inside new window bounds — visibly stretching the image, clipping an edge, or exposing a black gutter until the resized buffer caught up. During interactive split-screen drags or Picture-in-Picture transitions, that mismatch repeated every frame as a jittery resize bounce. BLASTBufferQueue.cpp still documents the exact invariant when handling NATIVE_WINDOW_SCALING_MODE_FREEZE:

frameworks/native/libs/gui/BLASTBufferQueue.cpp · acquireNextBufferLocked// Only update mSize for destination bounds if the incoming buffer matches the requested size.
// Otherwise, it could cause stretching since the destination bounds will update before the
// buffer with the new size is acquired.
if (mRequestedSize == getBufferSize(bufferItem) ||
    bufferItem.mScalingMode != NATIVE_WINDOW_SCALING_MODE_FREEZE) {
    mSize = mRequestedSize;
}

Turning pixel buffers into transaction state makes atomic resize synchronization straightforward: instead of sending the resized frame's transaction straight to SurfaceFlinger, the app routes that SurfaceControl.Transaction back to WM via SurfaceSyncGroup, and BLASTSyncEngine in WM merges the app's buffer transaction with WM's geometry transaction before committing both together (documented in services/core/java/com/android/server/wm/BLASTSync.md; Figure 13).

Separately, hwui sets freeze scaling mode on its surfaces (NATIVE_WINDOW_SCALING_MODE_FREEZE). In that mode, BLASTBufferQueue holds the destination size at the old value until a buffer matching the requested size arrives and drops stale intermediate-size buffers (rejectBuffer), preventing mismatched dimensions from ever stretching on screen.

What it means for you Resizes, rotations and coordinated window transitions wait for your first rendered frame at the new dimensions. A slow performTraversals after a configuration change therefore delays the transition start rather than flashing a stretched frame. With the view trace category enabled, the <window>-reportDrawFinished seqId=N instant on the main thread marks when your synced frame transaction was handed back to WM.

9Fences let each stage hand work on before the hardware has finished it

If RenderThread had to wait on the CPU until the GPU finished shading every pixel before calling queueBuffer, and SurfaceFlinger had to wait until scanout finished before returning a replaced buffer, the pipeline would serialize into lockstep. Instead, every buffer hand-off carries a kernel sync_file fence: a lightweight file descriptor (fd) passed across Binder or sockets that signals asynchronously when hardware work completes. Consumers pass that fd straight into the next hardware queue (GPU driver or display controller) so CPU threads stay unblocked until pixels are actually read.

SurfaceFlinger normally skips any transaction whose buffer acquire fence has not signaled yet, preventing one slow app's GPU work from making composition miss scanout for every other visible layer (recorded as fence unsignaled <layer> on SurfaceFlinger's main thread). The default exception is LatchUnsignaledConfig::AutoSingleLayer: when only a single layer updates with a simple buffer-only transaction, SurfaceFlinger may latch it unsignaled and hand the acquire fence down to HWC. Perfetto records each frame's latch result in latched_fence_state (§14).

What it means for you Finishing doFrame and DrawFrames early on the CPU guarantees an on-time frame only if the GPU also finishes before SurfaceFlinger's latch check. Heavy fragment shaders or overdraw keep the acquire fence unsignaled past VSYNC even while every CPU thread sits idle.

10The display hardware blends most layers itself, and SurfaceFlinger uses the GPU only for the rest

A typical phone screen stacks half a dozen surfaces at once — wallpaper, app content, status bar, navigation bar, floating picture-in-picture or a dialog. Blending all of those full-screen buffers on the GPU every 8.3 or 16.7 ms would keep the GPU awake continuously and burn DRAM bandwidth reading and writing pixels twice. Dedicated display controllers therefore include hardware overlay planes that fetch multiple layer buffers directly out of memory and composite them on the fly during scanout, leaving the GPU idle whenever hardware planes suffice.

On each VSYNC-sf wake-up, SurfaceFlinger's main thread runs two phases: commit applies ready transactions, latches signaled buffers and updates layer geometry, and composite negotiates how each visible layer will be blended with the vendor Hardware Composer (HWC) HAL:

  • DEVICE composition: the display controller reads the layer's DMA-BUF directly into a hardware overlay plane during scanout with zero GPU work.
  • CLIENT composition: when layers exceed available hardware planes or request effects the display block cannot execute (such as background blur or complex color/geometry transforms), SurfaceFlinger's RenderEngine composites those layers on the GPU into a single client target buffer, which HWC then scans out alongside any remaining DEVICE planes (§14 lists rarer composition types).

CLIENT composition consumes GPU cycles and memory bandwidth inside SurfaceFlinger's own sfWorkDuration budget. FrameTimeline flags any frame involving RenderEngine with gpu_composition = 1, and overruns appear as SurfaceFlinger GPU Deadline Missed.

Across the Composer AIDL interface (DisplayCommand.aidl), SurfaceFlinger and HWC exchange two logical operations each refresh: validateDisplay submits the layer list so HWC returns its DEVICE vs CLIENT assignments, and presentDisplay commits the final buffers (including any RenderEngine client target) for scanout and returns the display's present and release fences (§9; presentOrValidateDisplay folds both into a single HAL call when no fallback is needed).

What it means for you Cross-window blurs, unsupported blend modes or scaling ratios, and stacking more visible surfaces than the SoC has hardware overlay planes push layers onto CLIENT composition. In a trace, frames with gpu_composition = 1 and long RenderEngine slices inside SurfaceFlinger point to layer-stack cost rather than slow app rendering.
Part IV · Jank

11One late frame can leave every later frame a period behind: buffer stuffing

Multi-slot buffer queues (§8) prevent a brief hiccup from stalling the app's threads immediately, yet combined with one-buffer-per-VSYNC backpressure they introduce a subtle queuing effect that defeated early jank metrics: buffer stuffing. Once a single slow frame misses its latch deadline and remains queued, every subsequent frame — even if rendered well inside its budget — sits behind that backlog in the queue and reaches the panel one refresh period later than originally scheduled.

Figure 17 traces four frames at 60 Hz under the two-period schedule from §5: frame fk wakes at Vk, must finish GPU work by V(k+1), and is expected on screen at V(k+2).

Once stuffed, the queue stays one buffer deep until the app stops requesting frames for a refresh. Visually, motion after f1 is completely smooth — a new frame scans out on every single VSYNC (V4, V5, V6) — yet every frame carries one extra refresh period of touch-to-display latency, and zero slack remains in the pool: if a second frame runs late while stuffed, all slots are busy and RenderThread blocks in dequeueBuffer.

As of Android 17, Choreographer can drain a stuffed queue automatically: when hwui reports via onWaitForBufferRelease that RenderThread waited longer than half a frame interval for a buffer release, Choreographer intentionally skips one VSYNC (DELAY_FRAME) to let SurfaceFlinger consume the backlog, and shifts animation timestamps back by one frame (OFFSET) until the animation goes idle (visible on the Buffer stuffing recovery track).

What it means for you Frames tagged Buffer Stuffing finished their own CPU and GPU work on time — optimizing them changes nothing. Walk backward to the first frame that missed its deadline at the start of the stuffed run (f1 in Figure 17) and fix that root cause.

12FrameTimeline compares each frame's plan with what happened, and says whose fault a late frame was

Historically, Android developers hunted jank by checking whether Choreographer#doFrame took longer than 16.7 ms (or watching Skipped N frames! logcat lines). Across a multi-process, GPU-pipelined, triple-buffered architecture, that single-thread duration fails in every direction:

  • False negatives on GPU and compositor stalls. A 4 ms doFrame whose fragment shaders miss the acquire-fence deadline, or a fast app frame delayed by slow RenderEngine GPU composition in SurfaceFlinger, causes a visible screen hitch while the app's UI thread looks effortless.
  • False positives on buffer stuffing and non-animating frames. Measuring raw start-to-present latency flags every single frame inside a buffer-stuffed scroll (§11) as "one VSYNC late" even though 59 of 60 frames presented at a rock-steady cadence, and penalizes slow one-off draws when nothing on screen was animating.

Android 12 introduced FrameTimeline inside SurfaceFlinger to judge frames by end-to-end schedule tokens rather than main-thread wall time. Using the vsyncId token chosen from VsyncEventData (§5), FrameTimeline records a SurfaceFrame for each app buffer or transaction and a DisplayFrame for each SurfaceFlinger composition pass, emitting paired Expected Timeline and Actual Timeline tracks per process into Perfetto's expected_frame_timeline_slice and actual_frame_timeline_slice tables.

An app's actual slice ends when its buffer is ready, not when it is shown

For an app SurfaceFrame, neither timeline slice spans all the way to scanout; presentation timing is recorded as slice attributes instead:

  • Expected runs from the predicted VSYNC-app start to the predicted buffer-ready deadline (mPredictions.endTime).
  • Actual runs from the start of Choreographer#doFrame to the moment the buffer was both queued and finished on the GPU — max(acquireFenceTime, queueTime) in SurfaceFrame::setAcquireFenceTime (or drop time if replaced before latch).

The legacy rules sort late frames by whether the app finished late

A frame counts as presented on time if it is within 2 ms of the prediction. It finished late if it finished any time after its deadline. The deadline-based logic, now called the legacy classification, is Figure 20. The exact thresholds are in Section 14.

Version note Android 17 adds a second, cadence-based classification behind a SurfaceFlinger feature flag (use_experimental_jank_classification). With the flag on, SurfaceFlinger writes the cadence result into jank_type and moves the legacy deadline result into the Jank type (experimental) slice argument; with the flag off, those roles reverse. Cadence mode evaluates presentation rhythm directly: a frame is on cadence if the elapsed gap since the previous frame's present matches the expected gap (within 30%) and the expected gap is short enough to constitute an animation (< 50 ms). An on-cadence frame with more than 2 ms of present delay is classified as Buffer Stuffing, the app-deadline check subtracts time spent blocked in dequeueBuffer, and isolated non-periodic updates become Non Animating (§14).

jank_type lists every reason, and jank_tag sums them up for the slice colour

jank_type holds a comma-separated bitmask of fault reasons, while jank_tag collapses them into a single summary label that colors the Perfetto slice (mapped via JankTypeBitmaskToStringId in frame_timeline_event_parser.cc). For app SurfaceFrame rows:

Only late frames during motion count as perceptible jank

A late frame is visible to a human eye only when it interrupts ongoing motion. During a scroll or transition, the visual system anticipates a new image at each VSYNC, so repeating a frame breaks continuity; conversely, the first frame after an idle screen, a one-off state toggle, or a draw while the panel is off has no established rhythm to break. Counting those isolated frames as jank would drown out real stutters, so SurfaceFlinger and Perfetto separate them explicitly.

With use_experimental_jank_classification enabled, SurfaceFlinger evaluates presentation cadence (the version note above), comparing the actual present-to-present interval against the expected interval and classifying non-periodic updates as Non Animating rather than late:

  • The frame has no usable predecessor, such as the opening frame of an animation after idle.
  • The interval missed expectations, yet adjacent frames sit too far apart (≥ 50 ms) to form continuous motion.
  • The frame carries a negative system content priority (mSystemContentPriority, gated behind an additional flag).

Frames rendered while the panel is off or switching power states receive Display not ON or PowerModeChange in progress.

Whenever one of those three reasons is a frame's sole reason, Perfetto's CalculateSurfaceFrameJankTag assigns Non-perceivable Jank. Frames tagged Self Jank or Other Jank are perceptible: they broke active motion on screen. Buffer Stuffing and SurfaceFlinger Stuffing sit between the two — cadence stayed smooth, at the cost of an extra period of latency.

For perceptible jank reasons, SurfaceFlinger also computes a severity bucket in jank_severity_type (calculateJankSeverity): None (score of 0), Partial (missed by less than roughly one frame interval, score below 0.9), Full (0.9 and above), or Unknown when timing data is insufficient.

-- perceptible jank only, with severity, for one app
SELECT jank_type, jank_severity_type, COUNT(*) AS frames
FROM actual_frame_timeline_slice
JOIN process USING (upid)
WHERE process.name = 'com.example.app'
  AND jank_tag IN ('Self Jank', 'Other Jank')
GROUP BY jank_type, jank_severity_type
ORDER BY frames DESC;
What it means for you Attribute Self Jank to app CPU/GPU work, Other Jank to compositor or display scheduling, and Buffer Stuffing to queue latency rather than stutter; exclude Non-perceivable Jank from user-visible smoothness metrics. Always inspect present_type alongside on_time_finish: a late presentation paired with on_time_finish = 1 cannot be fixed by trimming app CPU work.

13Three queries cover frames by tag, per-thread time and input latency

Summary of frames by tag and reason for one process (actual_frame_timeline_slice lives in Trace Processor's prelude and needs no INCLUDE):

SELECT jank_tag, jank_type, present_type, COUNT(*) AS frames,
       ROUND(AVG(dur) / 1e6, 2) AS avg_actual_ms
FROM actual_frame_timeline_slice
JOIN process USING (upid)
WHERE process.name = 'com.example.app'
GROUP BY jank_tag, jank_type, present_type
ORDER BY frames DESC;

Per-frame breakdown of Self Jank into UI-thread and RenderThread duration using Perfetto stdlib's android_frames table, which joins Choreographer#doFrame, DrawFrames and the timeline slices by vsyncId:

INCLUDE PERFETTO MODULE android.frames.timeline;

SELECT f.frame_id,
       a.jank_type,
       ROUND(a.dur / 1e6, 2)  AS actual_ms,
       ROUND(ui.dur / 1e6, 2) AS do_frame_ms,
       ROUND(rt.dur / 1e6, 2) AS draw_frames_ms
FROM android_frames f
JOIN actual_frame_timeline_slice a ON a.id = f.actual_frame_timeline_id
JOIN slice ui ON ui.id = f.do_frame_id
JOIN slice rt ON rt.id = f.draw_frame_id
WHERE f.process_name = 'com.example.app'
  AND a.jank_tag = 'Self Jank'
ORDER BY f.ts;

End-to-end input latency per event: android_input_events decomposes each event into dispatch_latency_dur (InputDispatcher to app), handling_latency_dur (app receipt to FINISHED ack), and end_to_end_latency_dur (kernel read timestamp to presentation of the frame frame_id that consumed the event):

INCLUDE PERFETTO MODULE android.input;

SELECT event_action, dispatch_latency_dur, handling_latency_dur,
       ack_latency_dur, end_to_end_latency_dur, frame_id
FROM android_input_events
WHERE process_name = 'com.example.app'
ORDER BY read_time;
