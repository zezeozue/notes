How trace processor turns an out-of-order trace file into fast SQL tables

Recording millions of kernel and app events per second without slowing a phone down produces a trace file whose timestamps jump backwards and forwards. Trace processor sorts those events into monotonic time, reconstructs intervals and tracks into dense column-oriented tables, and exposes those columns to SQLite through a thin virtual-table adapter. Understanding those two boundaries — sorting at ingestion and column storage behind SQLite — explains why some tables and queries are cheap and others are not.

Code is from the upstream Perfetto repository, main as of late October 2026, and paths are relative to its root. Excerpts marked shape are simplified. The rest are quoted or closely paraphrased from the files under Sources.

At a glance

  • Why the file is disordered. Kernel per-CPU ring buffers and per-thread app writers flush asynchronously without a global lock, so packets land on disk out of timestamp order.
  • The ingestion split. Code before the sorter runs in file order and only frames packets and normalizes clocks. Only code after the sorter sees monotonic timestamps and may reconstruct slices, scheduling intervals or thread lifetimes.
  • Columnar storage. Instead of inserting rows into SQLite B-trees, every table keeps one typed array per column, with string pooling and null-compression layouts chosen from Python schema flags.
  • Pushed-down queries. SQLite parses and plans the SQL, while single-table filters and sorts run as register bytecode directly over columns before surviving rows step back into SQLite.
  • What to do in practice. Record long traces in streaming mode (write_into_file, §2), filter strings with GLOB rather than LIKE, and join on id, utid/upid or sorted columns.

Terms. Trace processor is Perfetto’s C++ analysis engine: it ingests a trace file and answers SQL queries over it. The embedder is the host program driving it, such as the Perfetto UI, the Python API or the trace_processor shell. traced is Perfetto’s system tracing daemon, and ftrace is the Linux kernel’s built-in per-CPU event tracer. A packet is one length-prefixed protobuf message (TracePacket) in the trace, and a sequence is the ordered stream of packets from one writer, tagged by trusted_packet_sequence_id. A slice is a named time interval with a begin and an end, such as a function call or a frame. A track is the timeline a slice or counter series lives on, such as one thread, one CPU’s frequency or one async lane of an app. A dataframe is trace processor’s in-memory columnar table, and a vtab (virtual table) is SQLite’s C callback interface for querying external storage as if it were a SQL table.

Two design splits shape the engine: sorting at ingestion and columns behind SQLite

Trace processor’s architecture is a direct response to two physical constraints: how a low-overhead tracer writes bytes on a live device, and how an analytical engine scans tens of millions of events in memory.

Why trace files arrive out of timestamp order. Capturing every kernel context switch, Binder transaction and app slice on a multi-core phone leaves only a few hundred nanoseconds of budget per event. Writers cannot contend on a shared lock or serialize into one clock-ordered buffer. Instead, ftrace writes into separate per-CPU kernel ring buffers, while each user-space thread writes into its own shared-memory chunks under a distinct trusted_packet_sequence_id. Whenever a buffer fills, a periodic flush fires or tracing stops, traced copies chunks into the output file in whatever order it drains them. Order and compression state hold within a single sequence, but across sequences a packet near the end of the file can carry an earlier timestamp than one near the start.

Why downstream analysis needs monotonic order. Engineers rarely query raw point events in isolation. Pairing a slice’s begin marker with its matching end marker on a call stack, or turning point sched_switch events into continuous thread-state durations, requires seeing events in non-decreasing timestamp order. Trace processor therefore splits ingestion down the middle. Code before the sorter sees packets in arbitrary file order: it may frame bytes, maintain per-sequence wire compression tables and translate device clocks into one shared trace time, but it cannot depend on prior events from other sequences. Only after the sorter merges streams into monotonic trace time do stateful trackers pair intervals, resolve recycled thread IDs and append table rows.

Why tables live in custom columnar dataframes instead of SQLite B-trees. Once events become rows, SQL is an ideal query language for both interactive debugging and Perfetto’s modular standard library, and SQLite supplies a battle-tested SQL parser and query planner in a small embeddable footprint. Storing trace rows inside native SQLite tables, however, fails at trace scale. A 500 MB trace routinely expands into tens of millions of slice, scheduler and counter rows. SQLite’s native storage is row-oriented B-trees (balanced tree pages of variable-length records): inserting tens of millions of rows inflates memory several-fold with page and record headers, and filtering on a single column such as dur > 16000000 drags every column of every row through CPU caches.

Trace processor keeps SQLite’s front end while replacing its storage. Trackers write into custom columnar dataframes — one dense typed array per column, backed by a trace-wide string pool, compact null bitmaps and declared sort invariants — frozen read-only at end of file. Each dataframe registers with SQLite through a virtual table adapter (DataframeModule). Single-table filters and sorts push down into a register bytecode interpreter that scans contiguous column arrays, returning only surviving row indices for SQLite to step one row at a time. An experimental |> pipe engine goes further and keeps whole multi-stage interval queries in columnar batches until the final output.

Figure 1 maps these two boundaries onto the C++ classes that implement them. On the file-order side sit ForwardingTraceParser, ChunkedTraceReader and format tokenizers. TraceSorter forms the ordering boundary. On the timestamp-order side, stateless format parsers and stateful trackers populate Dataframes, which DataframeModule and the experimental pipe executor read at query time. (“Intern ids” in the figure means replacing repeated strings and track descriptions with compact integer IDs, covered in Sections 1, 3 and 6. The repository’s own overview is in docs/design-docs/trace-processor-architecture.md.)

Part I · Ingestion

1Readers cut bytes into timestamped events and stop there

Part I follows an event from raw input bytes to table rows (Sections 1 to 4). The ingestion pipeline has to accept multi-gigabyte traces in arbitrary byte chunks, normalize several wire formats onto one clock, sort disordered streams without holding the whole file in memory when streaming, and reconstruct intervals and entity identities.

The first stage — the reader and its tokenizer — handles everything that must happen in file order and stops before building any cross-event state. Three constraints keep this stage narrow: a streamed packet may split across two input chunks, wire-level compression tables belong to a single writer sequence, and timestamps from different clocks cannot be compared until they are translated into global trace time.

Trace processor accepts many formats, including Perfetto protobuf, JSON, perf and systrace text. It must accept them in pieces, because the embedder may be streaming a multi-gigabyte file. Bytes arrive through TraceProcessorStorageImpl::Parse(TraceBlobView) in chunks of any size the caller chooses. A TraceBlobView is a reference-counted view of a byte buffer.

The first call creates a ForwardingTraceParser. It looks at the first bytes, guesses the format, and creates the matching reader from the TraceReaderRegistry. Every reader implements ChunkedTraceReader, so it must cope with a packet split across two chunks.

The tokenizer is the part of a reader that runs before sorting. For Perfetto protobuf traces it is ProtoTraceReader. It splits the stream into packets and keeps each sequence’s interned data.

Interning is a size trick used by writers. A repeated string, such as an event name, is sent once with a small integer id. Later packets on the same sequence carry only the id. The tokenizer stores these tables per sequence so the parser can resolve ids later.

The tokenizer also converts each timestamp into trace time, the single clock all tables use. ClockTracker::ToTraceTime does this with clock snapshots that the service writes into the trace. The snapshots relate clocks such as BOOTTIME and MONOTONIC. The tokenizer then pushes the timestamp and payload into a sorter stream.

One missing clock snapshot can change the memory profile of a whole import. If the snapshot that relates two clocks has not been seen yet, conversion fails. Before end of file, the reader then tries to switch the sorter into SortingMode::kFullSort and parks the packet until the end. Full sort releases nothing until the end of the file. Ftrace events are the exception. They arrive in a bundle, one packet holding a batch of events from one CPU, and the ftrace tokenizer converts them one by one and drops any it cannot convert instead (Trace merging §9).

What it means for you If you write an importer, the tokenizer is where you extract a timestamp and stop. Anything that depends on the previous event belongs in the parser, after the sorter.

2The sorter merges nearly sorted queues instead of sorting everything

Once timestamps are in trace time, events from dozens of sequences and CPUs have to merge into one monotonic stream. Two obvious designs perform poorly at trace scale. Buffering the whole trace in an array and calling std::sort at end of file holds gigabytes of packets in RAM and copies variable-sized payloads on every swap. Pushing every incoming event into a binary min-heap avoids waiting for end of file, but pays heap-maintenance branches on tens of millions of events even when almost every stream is already ordered.

TraceSorter avoids both costs by exploiting two properties of real traces noted at the top of src/trace_processor/sorter/trace_sorter.h: most high-rate events come from kernel ftrace, and ftrace events from a single CPU arrive almost completely in timestamp order already. The sorter keeps variable-sized payloads out of the sort array, sorts only the out-of-order tail of each stream, and drains old events incrementally behind periodic flush barriers.

Each stream gets its own queue of small 16-byte entries

Each importer asks the sorter for typed streams. A stream is one input lane of the sorter, and its events share one payload type. Its sink is the object that gets them back, in order, after sorting. Each CreateStream(sink) call appends a new Queue and returns a Stream<T> bound to it.

ProtoTraceReader creates one stream for generic trace packets and one for track events. It also has factories that create ftrace, ETW and inline sched_switch/sched_waking streams lazily, one per CPU. So a typical Android trace has a queue per CPU per ftrace encoding, plus a few shared queues. The header comment still describes the original fixed “N+1 queues” layout, but the code now has a queue per stream.

The queue holds only a small pointer to each event, not the event itself. When a tokenizer calls Stream::Push(ts, data), the payload goes into a TraceTokenBuffer. This is a bump allocator: it hands out memory by advancing a pointer through 64 KB chunks, and frees whole chunks at once. The queue receives only a 16-byte TimestampedEvent that points at the payload. Negative timestamps are dropped here and counted in the trace_sorter_negative_timestamp_dropped stat.

A queue sorts only the part that arrived late. It remembers its largest timestamp so far. The first time an older one arrives, it marks where order broke and starts tracking the oldest late timestamp. The code below shows the fields.

trace_sorter.h · Queue::Appendif (PERFETTO_LIKELY(ts > max_ts_ || (!use_slow_sorting && ts == max_ts_))) {
  max_ts_ = ts;                         // common case: still in order
} else {
  if (sort_start_idx_ == 0) {           // first out-of-order event
    sort_start_idx_ = events_.size() - 1;
    sort_min_ts_ = ts;
  } else {
    sort_min_ts_ = std::min(sort_min_ts_, ts);
  }
}

When the queue is needed, Queue::Sort binary-searches the sorted prefix for sort_min_ts_ with std::lower_bound. It then runs std::sort only from there to the end. A queue that never went out of order is never sorted at all.

Events are released in time order, one flush window behind the newest data

Extraction merges queues that are each already sorted. SortAndExtractEventsUntilAllocId finds the queue with the oldest head, and the second-oldest head among the others. It drains the first queue until its next event is newer than that second head, then looks again. A comment in trace_sorter.cc puts this loop at a few percent of CPU time. That is why it rescans the queue heads directly rather than keeping them in a heap (a priority queue), which would add bookkeeping to every event.

An event older than the last one already released to the parser can no longer be placed. It is discarded at extraction and counted in sorter_push_event_out_of_order. A non-zero count means the window described next was too small for that trace.

In streaming mode, the sorter must decide when no future packet can be older than what it holds. It measures arrival order for this, not timestamps. Its yardstick is the token-buffer allocation id, which only grows as packets arrive. The signal comes from the tracing service. Every so often the service asks every data source to flush, that is, to write out whatever it has buffered. Then it reads its buffers into the file. It records both events in TracingServiceEvent packets, which call into the sorter:

So at each qualifying read the sorter releases events in timestamp order until the oldest remaining one arrived after the previous mark. It keeps the rest. After each drain it calls token_buffer_.FreeMemory().

The header notes that the window only helps traces recorded with write_into_file, where the service streams buffers into the file throughout the session. A ring-buffer trace keeps its buffers in memory, overwriting the oldest data, and writes them out once when tracing stops. It has a single read at the end, so it is sorted entirely in memory.

The window is a protobuf feature. Most other formats, and TAR and ZIP archives, declare TraceSortPolicy::kFullSort in their descriptor. ForwardingTraceParser::Init then switches the sorter to full sort before parsing. So a merged archive is always sorted in memory as a whole (Trace merging §6). At end of file, ExtractEventsForced() drains everything.

What it means for you Peak import memory is roughly everything between two extraction points. For ring-buffer traces and full-sort imports, that is the whole trace. If sorter_push_event_out_of_order is non-zero, events were lost to ordering, not by the producer.

3Parsers decode events, and trackers keep the state and write rows

Events leaving the sorter arrive in non-decreasing trace time, so downstream code can safely maintain call stacks, open intervals and thread lifecycles. Trace processor splits that work into two layers so format details do not leak into domain state machines.

Each sorted event reaches its stream’s sink, which calls the format’s parser. A parser knows one wire encoding — such as how a kernel sched_switch bundle or an SDK TrackEvent protobuf message is laid out — and keeps no state across events. It decodes fields and calls trackers: format-agnostic state machines that own one relational concept each and write rows into dataframes. Because of that boundary, a slice from a Chrome JSON trace and a slice from a Perfetto protobuf trace pass through the same SliceTracker and produce identical table rows.

A slice row is written at its begin and patched at its end

A slice arrives as two separate events — begin and end — yet queries almost always filter the slice table by start timestamp (ts). If SliceTracker waited until the end event to insert a completed row, any nested child slice would finish before its parent and land earlier in the table, leaving slice.ts unsorted and forcing either a full table re-sort or linear scans on time ranges. Writing each row at begin time keeps slice.ts monotonically non-decreasing, fulfilling its ColumnFlag.SORTED promise so queries can binary-search it (Section 7).

SliceTracker::Begin therefore inserts the row immediately with duration set to kPendingDuration (−1), depth set to the current stack size, and parent_id pointing to the open slice on top of the track’s stack. Because events arrive from the sorter in timestamp order, rows are appended in start-time order across all tracks. Stacks are maintained per track, and nesting deeper than kMaxDepth (512) is dropped with an import log.

End searches the stack from the top for the first open slice whose name and category match. A null name or category matches anything. It calls set_dur(ts - start) on that row, runs the end-event args callback, and pops the entry if it was on top. An end with no matching open slice is ignored, for example when its begin came before tracing started.

Begin args and end args land in the same arg set, the group of key/value pairs attached to one row (Section 4). They collect in the slice’s stack entry and are written when the slice is popped. At end of file, open slices get their args written but stay open. The holder and flush function names are in Numbers and method.

Threads, processes and tracks get stable ids

Raw kernel identifiers and repeated timeline descriptions create two hazards for relational tables: Linux recycles a numeric tid or pid once a thread or process exits, and millions of slice or counter events repeat the same logical timeline metadata.

ProcessTracker solves ID reuse by mapping active kernel thread and process IDs to monotonic row numbers in the thread and process tables: UniqueTid and UniquePid, written utid and upid in SQL. The main entry points:

  • GetOrCreateThread(tid) finds or creates the current thread for a tid.
  • StartNewThread, called on task_newtask, forces a new utid so a recycled tid does not merge with its predecessor.
  • UpdateThread(tid, pid) attaches a thread to its process.
  • UpdateThreadName only replaces a name with one of higher priority.

TrackTracker creates each track row once and finds it again cheaply. Every slice and counter value lives on a track, and thousands of events name the same one, so tracks are interned. A caller first describes a track type once, as a constexpr blueprint. A blueprint is the track’s kind plus the names of its dimensions, such as utid or cpu, which tell its instances apart. The caller then interns a track with concrete dimension values:

track_tracker.h (shape)tracks::SliceBlueprint("type", tracks::DimensionBlueprints(...))   // once, constexpr
InternTrack(blueprint, tracks::Dimensions(...))                    // returns a TrackId

The first InternTrack call for a set of values creates a row in the track table. Later calls return the same TrackId, which slices and counters then reference. The intern map belongs to one trace file. When an archive holds several files, each has its own TrackTracker, so the same thread can get two tracks (Trace merging §11).

What it means for you dur = -1 means the slice never ended in this trace. It is not a parse error. Join threads and processes on utid and upid, never on raw tid or pid.

4Args live in one shared table, deduplicated and written once per row

Trace events carry open-ended key/value annotations: SDK debug arguments, protobuf extensions and per-event ftrace fields. Giving every distinct key its own table column would create thousands of nearly empty columns, while packing annotations into a JSON string per row would force queries to reparse text on every row. Instead, tables store a single nullable arg_set_id integer that points into one shared key/value dataframe, __intrinsic_args (exposed in SQL as the args view), laid out so that identical sets are stored once and lookups jump straight to the first matching row without a binary search.

Args are buffered in memory, then committed in one step

An inserter collects a row’s args and writes them only when it goes away. A tracker asks for an ArgsInserter bound to one row’s arg_set_id cell. Adding an arg only appends to a pooled buffer. A repeated key either keeps its first value or takes the last, as the caller chooses. Duplicate detection is a linear scan until the buffer reaches 32 args, then a hash map.

When the inserter is destroyed, Commit() runs:

Two properties follow. Identical arg sets are stored once and shared, keyed by a hash of their contents. And every new set starts at the current row count and is written contiguously. So the first row whose arg_set_id is k is row k.

This layout makes looking up an arg set a jump, not a search. The args table declares arg_set_id as ColumnFlag.SORTED | ColumnFlag.SET_ID, which the generator turns into the SetIdSorted sort state. The query interpreter (Section 10) has a dedicated instruction for equality on it, Uint32SetIdSortedEq. It jumps to row k, clamped into the current row range, and scans forward while the value equals k. An arg set is a handful of rows, so this is a jump plus a few comparisons in one or two cache lines.

How cheap the commit is depends on the target column’s null layout (Section 6). The commit turns a NULL cell into a value, and ArgsInserter::Commit handles every layout: NonNull, DenseNull or either sparse layout with popcount. Six tables declare arg_set_id as CppAccess.READ_AND_HIGH_PERF_WRITE: slice, thread, process, cpu, gpu and the generic __intrinsic_state table. That makes the column DenseNull, so the write takes constant time.

Most other tables, including counter, use READ_AND_LOW_PERF_WRITE. There the column is sparse with a popcount, and each commit is a memmove whose cost grows with the column (Section 7).

What it means for you EXTRACT_ARG(arg_set_id, 'key') and joins on args.arg_set_id are cheap. Equal arg_set_ids on two rows mean equal args, not the same event. During import, an arg set exists only once its inserter goes out of scope. That is usually the end of the parser call that created the row. For a slice it is when the slice is popped, at its end event or at end of file. Tracker code that reads arg_set_id earlier sees NULL.
Part II · Storage

5Storing columns instead of rows makes scans cheap

Part II explains how trace processor holds tens of millions of imported rows in memory (Sections 5 to 8). Storage has to satisfy two competing phases: during import, trackers append rows and patch cells such as dur and arg_set_id out of order; once import ends, analytical queries scan a few columns across millions of rows and never mutate them again.

Analytical trace queries read narrow slices of wide tables, such as “all slices longer than 16 ms” or “total duration per track”. In a row layout — the B-tree record format SQLite’s native tables use — all fields of one row sit side by side, so scanning durations drags timestamps, names, depths and parent IDs through CPU caches too. In column storage, each column is its own contiguous typed array, so every 64-byte cache line fetched during a scan carries eight int64_t durations and nothing else.

Columns also allow metadata per column. If a column is known to be sorted, a range filter becomes two binary searches. If it is the implicit id, the value is the row number and needs no storage at all. The rest of this part covers that metadata and what it costs to keep.

6Each column carries metadata the planner can rely on

Plain arrays make full-column scans fast, but avoiding scans altogether requires knowing what invariants a column obeys — whether its values are unique, sorted or dense, and how its missing values are packed. A table is a dataframe::Dataframe: column names, a vector of shared columns, and a row count. Strings are stored not as variable-length byte runs inside the column, which would break fixed-stride indexing, but as 32-bit StringPool::Id handles into a trace-wide StringPool that interns each distinct slice or thread name once and turns string equality into a 32-bit integer comparison. Each column records five structural properties that the query planner reads directly (src/trace_processor/core/dataframe/types.h):

Five NULL layouts trade memory against write speed

Many trace columns are mostly NULL, and the layout decides what that costs. Top-level slices have no parent, and events without args have no arg set. Storing a full value slot for every NULL row wastes memory. Not storing it makes row r’s value hard to find.

A nullable column has a null bitmap, with one bit per row that is set when the row has a value. A dense layout also keeps a value slot for every row, so row r’s value is at index r. A sparse layout packs only the non-NULL values. Row r’s value is then at the index equal to the number of set bits before r.

Counting set bits is called popcount, one CPU instruction per 64-bit word. To make that lookup constant-time instead of a scan, a layout can add a prefix-popcount array: the running count of set bits at the start of each 64-row word.

The layouts are the NullStorage variants in types.h, and the writes are in Dataframe::SetCellUncheckedInternal in dataframe.h. A comment on prefix_popcount_for_cell_get says the popcount exists only to serve single-cell reads (GetCell) on sparse columns. Columns that need writes should use DenseNull.

7Python flags declare intent, and a generator picks the layout

Choosing among five NULL layouts by hand across more than a hundred built-in tables would be error-prone: picking a sparse layout on a column that a tracker patches after insertion silently turns import into a quadratic memmove bottleneck, while picking DenseNull everywhere wastes hundreds of megabytes on rarely populated columns. Instead, table authors declare usage intent in Python schemas under src/trace_processor/tables/*.py, and a code generator selects the tightest layout that satisfies those access guarantees.

The generator in python/generators/trace_processor_table/serialize.py turns each column into a dataframe::ColumnSpec: storage type, nullability, sort state and duplicate state. It also generates typed row references, cursors and setters. A column declaration looks like this:

Besides flags, three knobs drive the choice:

  • cpp_access: whether C++ code may read or write the column through generated row references and cursors, and whether writes are on a hot path. The levels are NONE (the default, SQL only), READ, READ_AND_LOW_PERF_WRITE and READ_AND_HIGH_PERF_WRITE.
  • cpp_access_duration: whether that C++ access is needed only during import (PRE_FINALIZATION_ONLY, the default) or also after the tables are frozen at end of file (POST_FINALIZATION). Finalization is covered in Section 8.
  • sql_access: HIGH_PERF asks for the layout that is fastest to filter from SQL, at the cost of memory.

8At end of file the tables are shrunk and frozen

Import and querying want opposite data structures: import needs growable buffers with spare capacity, temporary prefix-popcount arrays for C++ cell lookups and live tracker maps; queries want minimal resident memory, fixed column addresses that never reallocate under an open SQLite cursor, cardinality statistics and pre-built indexes. Finalization is the one-way transition between those two worlds. When the last byte chunk has been fed in, TraceProcessorImpl::NotifyEndOfFile runs four ordered stages.

Dataframe::Finalize does four things:

  • It shrinks every value array and bit vector to fit.
  • It frees the popcount array of SparseNullWithPopcountUntilFinalization columns, which then become scan-only like SparseNull.
  • It estimates the number of distinct values of each HasDuplicates integer or string column, into estimated_distinct. The planner uses it to estimate equality selectivity as roughly rows divided by distinct values.
  • It bumps the table’s mutation counter, a count of changes, so cursors holding raw pointers into the columns know to refresh them.

Indexes declared for a table at registration time are built right after, with BuildIndex and AddIndex. From then on the tables are read-only. AddIndex returns a new Dataframe that shares the columns rather than changing the old one.

Trace bounds come from the data, not from trace metadata

Trace files rarely carry trustworthy start and end timestamps in a header: text formats have no header at all, ring buffers overwrite their earliest packets, and slices left open with dur = -1 have no end timestamp. Yet almost every UI timeline and utilization query needs accurate trace bounds to clip unfinished intervals or compute time fractions. Trace processor therefore derives the trace start and end directly from the rows it imported. Each plugin may report GetTimestampBounds(), and AggregatePluginTimestampBounds takes the earliest start and latest end across all plugins, returning (0, 0) when no plugin has data and widening a zero-length span to one nanosecond.

Most of the bounds come from the storage_tables plugin. It scans ts in a fixed list of tables: ftrace events, sched, counters, slices, thread state, logs, heap profiles and graphs, smaps, profiler samples and __intrinsic_state. For interval tables it uses ts + max(dur, 0) as the end. So a slice left open with dur = -1 contributes only its start.

The result becomes the trace_bounds view and the trace_start(), trace_end() and trace_dur() functions.

The bounds are cached and recomputed only when some table has changed, because the scan is not free. CacheBoundsAndBuildTable sums the tables’ mutation counters, as reported by each plugin, and recomputes only if the sum changed. It runs at end of file, in the tracker stage, and on every Flush(). Before either, trace_bounds is (0, 0).

What it means for you Use trace_start() and trace_end() rather than MIN(ts) over one table, because they cover all the main event tables at once. If you add a table whose timestamps should extend the trace, add it to both GetTimestampBounds and GetBoundsMutationCount in its plugin. The code comment insists the two lists match.
Part III · Queries

9SQLite plans the query and reads the columns through a virtual table

Part III follows how SQL queries read finalized dataframes (Sections 9 to 15). Building a full SQL parser, join reorderer, window-function engine and expression evaluator from scratch would duplicate years of database engineering, whereas storing trace rows in SQLite’s own row-oriented B-trees would forfeit Part II’s memory density and cache-line scan speed.

Trace processor gets both by embedding SQLite for SQL planning and expression evaluation while keeping all trace rows in dataframes behind SQLite’s virtual table (vtab) interface. A virtual-table module registers C callbacks that SQLite invokes in place of B-tree page reads. Every finalized dataframe is exposed through DataframeModule (src/trace_processor/perfetto_sql/engine/dataframe_module.cc). The callbacks that define the boundary:

  • xBestIndex, at prepare time. SQLite lists the WHERE constraints on this table, the ORDER BY and the columns used. It asks which ones the table can handle itself, and at what cost. Taking a filter here is constraint push-down: the filter runs inside the table, on columns, instead of in SQLite on every row.
  • xFilter, at execution: start a scan with the chosen plan and the actual constraint values.
  • xNext / xEof: advance to the next result row, or report the end.
  • xColumn: hand SQLite the value of one column of the current row.

xBestIndex takes every filter the table understands and leaves the rest to SQLite

DataframeModule::BestIndex walks aConstraint, SQLite’s array of constraints, and maps SQLite operators to dataframe operators. Figure 12 shows which operators are taken. An equality that SQLite can pass as a whole list, through sqlite3_vtab_in, becomes In. Constant LIMIT and OFFSET are taken too, unless some other constraint was not understood.

The rest of the plan is reported back to SQLite:

  • SQLite does not recheck what the table handles, including ORDER BY (omit, orderByConsumed). The dataframe either sorts itself or knows it is already sorted.
  • DISTINCT is pushed down for the columns the query reads (colUsed).
  • The plan’s estimated cost and row count go back to SQLite. A plan that returns at most one row says so (SQLITE_INDEX_SCAN_UNIQUE).
  • The chosen plan travels to xFilter as a string stored with the prepared statement (idxStr).

xFilter runs the plan, and xNext and xColumn hand rows over one at a time

Filter deserializes the plan only when idxStr differs from the last one this cursor saw. It copies the argv pointers into a value fetcher and runs the bytecode. The result is a span of row indices. Next advances a pointer and Eof compares two pointers. Column reads one cell and hands it to SQLite with the matching sqlite3_result_* call.

What it means for you Filters in the supported list run in the dataframe. Others run in SQLite on every returned row. name GLOB 'foo*' is pushed down, and name LIKE 'foo%' is not.

10A small bytecode interpreter runs each filter over many rows at once

Pushing filters down through xBestIndex only pays off if the dataframe evaluates them far faster than SQLite’s per-row loop would. A naive C++ loop that inspected a column’s data type, null representation and comparison operator on every row would spend more CPU cycles on branches than on the comparisons themselves.

Instead, trace processor compiles a table’s pushed-down constraints once at prepare time into a short program for a specialized bytecode interpreter. Each instruction is monomorphized for one exact combination of storage type, null layout and operator, and processes a whole contiguous range or index list in a tight inner loop. Instruction dispatch — a single switch in Interpreter::Execute — runs once per filter stage rather than once per row.

It is a register interpreter: instructions read and write numbered slots that hold intermediate results, rather than pushing them on a stack. Registers hold a Range (a begin and end pair), a span of row indices, slabs, cast filter values, or storage pointers. A slab is an owned scratch buffer that spans point into.

Planning has two stages. LogicalPlanner::Plan (core/dataframe/logical_plan.cc) decides what to do. It picks the filter order and a strategy for each filter: binary search, set-id search, small-value lookup, range scan or index-list scan. It also decides whether an index helps and whether a sort can be skipped.

BytecodeLowering::Lower decides how. It assigns registers and emits instructions specialized for each column’s storage type, nullability and sort state. Each instruction is a small, fixed-size, trivially copyable Bytecode (core/interpreter/bytecode_core.h). Its exact size is in Numbers and method.

Cheap filters run first, while the candidate rows are still one range

Filters are ordered so the cheapest ones run while the candidates are still a contiguous range. The order comes from FilterPreference: id equality, then set-id equality, id inequality, sorted numeric equality and inequality, sorted string equality and inequality, then everything else. The sorted cases require a NonNull column.

While only these have run, the candidates are a Range, which is two integers and costs nothing to represent. The first filter that cannot keep a range forces the rows to be listed. AllocateIndices plus Iota writes the surviving row numbers into a slab, and the remaining filters compact that list in place.

Ordering, distinct and limit are bytecode too. ORDER BY on a column already sorted in the requested direction costs nothing, or a Reverse. Otherwise the interpreter copies the sort keys into a row-layout buffer and runs a stable sort, using AllocateRowLayoutBuffer, CopyToRowLayout and SortRowLayout. DISTINCT uses the same buffer. An ORDER BY x LIMIT 1 becomes FindMinMaxIndex.

The costs each instruction reports to SQLite are rough rankings, not measurements. FixedCost, LogPerRowCost and LinearPerRowCost carry a TODO in bytecode_instructions.h saying they are not yet backed by benchmarks. They rank “binary search” against “scan” well, and should not be read as more than that.

11Indexes speed up equality on columns that are not sorted

Binary search works out of the box on id and ts, but trace queries routinely join or filter on unsorted columns such as track_id, utid, upid or keys in materialized helper tables. Because SQLite executes joins as nested loops, an unsorted inner join column triggers a full linear scan of the inner dataframe for every outer row. Building a traditional B-tree or hash table per column would bring back pointer-heavy memory overhead on read-only data.

Trace processor instead uses two compact structures tailored to immutable columns. First, an index (dataframe::Index) is a plain 4-byte-per-row permutation vector holding the table’s row numbers sorted by one or more target columns. With it, equality on an unsorted column becomes a binary search over the permutation vector. The planner uses an index for a prefix of = or IN filters matching the index’s leading columns; an IN filter ends the prefix because its matches are no longer contiguous in the permutation.

Only tables created from SQL can get an index from SQL. CREATE PERFETTO INDEX works only on tables the SQL engine owns, that is, CREATE PERFETTO TABLE results. On a built-in table it fails with “indexes on intrinsic table … must be declared at compile time, not via SQL”. Those indexes are attached at registration and built after finalization (Section 8).

SmallValueEq gives constant-time equality on some sorted, unique, non-null Uint32 columns. It is a bit vector indexed by value plus a prefix popcount, so col = k is one bit test and one popcount.

Finalize does not build it. AdhocDataframeBuilder does, which backs tables created at runtime from SQL results and several table functions. The builder adds it when the maximum value is below 16 times the row count, and the column is not already IdSorted or SetIdSorted.

What it means for you When you materialize an intermediate result with CREATE PERFETTO TABLE, the builder infers sort state and may add SmallValueEq. If you then join on a column that is neither sorted nor SmallValueEq, add CREATE PERFETTO INDEX on it.

12Pipe syntax keeps multi-stage interval work out of SQLite

The virtual-table contract has a structural ceiling: xBestIndex plans one table scan in isolation. As soon as a query joins tables, groups rows, evaluates expressions or chains multi-step interval operations — intersecting scheduling spans with app slices, flattening nested call stacks, or summing durations up a slice tree — every intermediate row must step out through xNext and xColumn into SQLite’s row-at-a-time bytecode engine, the VDBE (Virtual Database Engine), and back again.

PerfettoSQL’s experimental pipe syntax removes that per-stage row boundary by compiling whole multi-stage pipelines onto a C++ columnar batch executor and crossing into SQLite only once at the end. Documented in docs/analysis/perfetto-sql-pipe-syntax.md, a pipeline starts from a table or subquery source and chains stages left-to-right with |>, each stage consuming the table produced by the previous one. PERFETTO PRAGMA pipelines = 1 enables it for user queries (implementation notes warn that syntax and execution details may still change).

docs/analysis/perfetto-sql-pipe-getting-started.md (PRAGMA line from its intro)PERFETTO PRAGMA pipelines = 1;
FROM (SELECT ts, dur, track_id FROM slice WHERE dur > 0)
|> INTERVAL FLATTEN PER track_id AGGREGATE COUNT(*) AS active;

A pipe query compiles to a plan of columnar operations, which runs inside one table function. The compiler (perfetto_sql/pipeline/compiler.h) produces a pipeline logical plan of operations: scan, order_by, interval_intersect, interval_flatten and tree_accumulate, found in perfetto_sql/pipeline/operations/. Projection stages such as SELECT, DROP and RENAME only rename or drop columns, and add no plan node.

The plan is serialized into ordinary SQL that calls a table function, __intrinsic_pipeline(X'…'), implemented by PipelineModule. A table function is a vtab used like a function in FROM. Relations the pipeline reads from SQL, such as views and subqueries, are first built into dataframes by __intrinsic_dataframe_agg and passed in as arguments.

The operators are written for trace-shaped work. INTERVAL INTERSECTION OF, for example, partitions each operand by its PER columns and sorts the intervals in each partition. When no operand has overlaps it takes a single multi-way sweep. Otherwise it falls back to pairwise narrowing with a linear sweep, binary search or interval tree (docs/design-docs/perfetto-sql-pipelines.md).

Before running, a backward liveness pass drops unused columns. It walks from the last stage to the first and keeps only columns that some later stage reads. It can also remove a whole TREE ACCUMULATE stage whose output is never read.

What it means for you Pipe stages pay off for multi-stage interval work over large tables. Where you can, start a pipeline from a table rather than a view or subquery. A finalized dataframe has its columns shared in place (Scan::FindDirectDataframe). A SQL source is first run through SQLite and copied into a new dataframe.

13Plugins package each feature and declare what it depends on

As trace processor grew from core scheduling and slice tables to dozens of domain subsystems — heap profilers, Android Binder and Winscope analyzers, Linux perf importers, and structural table functions such as ancestor_slice and descendant_slice — wiring every importer, dataframe and SQL function inside one central startup file became brittle. Features depend on one another’s tables and helpers, and some hooks run once when trace processor starts while others run per SQL connection.

Trace processor isolates each feature into a plugin that declares its compile-time and runtime dependencies explicitly, letting the engine topologically sort and initialize them in a valid order. Several dozen plugins live under src/trace_processor/plugins/, from span_join_operator and interval_intersect to storage_tables, which registers the core built-in tables. The base contract lives in src/trace_processor/core/plugin/plugin.h.

}
  • Identity: Plugin<Self, Deps...> uses CRTP, the curiously recurring template pattern. A class passes itself as a template argument to its base, so the base can generate per-class code at compile time. The base gives each class a unique id, the address of a per-type static, plus the ids of its dependencies.
  • Registration: a PluginRegistration links itself into a global list. The intended form is the PERFETTO_TP_REGISTER_PLUGIN macro, a global constructor. A TODO in the TraceProcessorImpl constructor says that is disabled for build reasons. So each plugin exposes RegisterPlugin() with a function-local static, and the constructor calls them all before GetPluginSet(). The call count is in Numbers and method.
  • Order: GetPluginSet() runs Kahn’s topological sort once, which orders the plugins so each comes after everything it depends on. It CHECK-fails on a missing dependency or a cycle, and caches the result.
  • Access: dependency<T>() indexes a vector of resolved dependency pointers by T’s position in Deps....

Every hook on PluginBase defaults to a no-op, so a plugin overrides only what it needs:

What it means for you New tables and SQL functions live in a plugin. Return your dataframes from RegisterDataframes, and they will be finalized and indexed at end of file. Declare dependencies in Deps.... Until static registration is restored, you also add one RegisterPlugin() call to the TraceProcessorImpl constructor.
