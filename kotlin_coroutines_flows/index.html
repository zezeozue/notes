Kotlin coroutines and flows: how async work outlives the UI

Coroutines, reactive flows and Jetpack Compose do not change how Android’s garbage collector finds live memory. Where classic View code held references through explicit Handler messages, listener lists and background tasks, modern Android UI code builds chains of ordinary heap objects: compiler-generated continuation frames, parent-child job trees, flow collectors and composition slot arrays. Tracing which object points to which on the heap, and which lifecycle event severs that link, explains every async UI leak.

Code excerpts are from kotlinx.coroutines, the Kotlin 2.2.0 compiler and standard library, published AndroidX sources (Compose runtime, RecyclerView, ViewPager, ViewPager2) and AOSP frameworks/base (android16-qpr2-release). Excerpts marked shape are simplified; full source paths are listed in Versions and method.

At a glance

  • Async abstractions still compile down to heap reference graphs. A suspended coroutine, an active flow collector or a remembered Compose value stays in memory as long as a garbage-collection root can reach it.
  • Structured concurrency replaces manual teardown with a job tree. View callbacks, posted messages and executor tasks each had to be cancelled by hand; coroutines group work under a parent job so cancelling a scope tears down every child at once.
  • Scope mismatches recreate the View-era leak. Collecting UI state in an application or singleton scope, or in a window-attach scope while a View sits hidden, pins captured UI references and upstream producers in memory.
  • Stream operators hold state and subscriptions of their own. Hot flows retain their latest value even with zero collectors, while combine keeps every input stream active and caches each input’s last emission until collection ends.
  • The fixes align object lifetimes with UI visibility. Collect in a lifecycle-aware scope, share upstream work lazily with WhileSubscribed, gate conditional streams with flatMapLatest or collectLatest, cancel timers on teardown, and key what you remember.

Terms:

  • GC root: a starting reference the garbage collector always treats as live, such as a running thread’s stack, a static field or a JNI global reference held by native Binder code.
  • Looper and Handler: a thread’s message-processing loop and the handle used to post Runnable tasks or delayed messages into its queue.
  • Continuation: the compiler-generated heap object that stores a paused suspend function’s resume point, local variables and caller link across suspension points.
  • Job and CoroutineScope: the lifecycle handle for a coroutine and the container that attaches newly launched coroutines as children of a parent job.
  • Cold vs hot flow: a cold Flow runs its producer fresh for each collector and stops when cancelled; a hot StateFlow or SharedFlow lives independently and shares emissions across subscribers.
  • Slot table: Compose’s per-composition array that caches remember values and effect observers by call-site position across recompositions.

Part I shows why imperative View callbacks and recycled rows leak memory or overwrite fresh state. Parts II, III and IV trace the heap structures created by suspend functions, Flow operators and Compose’s remember, and Part V distils those mechanics into eight recurring leak shapes and their fixes.

Part I · The View-era problem

1View code ends every async lifetime by hand

Android confines all View measurement, layout, drawing and widget mutation to a single UI thread. Making a stateful widget tree thread-safe would require locking across parent-child layout passes and frame draws, risking deadlocks and torn frames. Instead, the main thread runs a Looper that pulls messages one by one from a MessageQueue, while slow work—Binder IPC (cross-process calls into system_server or another app), disk I/O and bitmap decoding—runs on background threads.

Early Android apps bridged those threads with listener interfaces, Handler posts, background Executor pools and AsyncTask (deprecated in Android 11 because inner-class tasks routinely captured an Activity or View across configuration changes). Look at the four independent lifetimes created by one typical View-era setup:

// The View-era pattern (shape)
userManager.registerCallback(callback)                // 1. must be unregistered later
bgExecutor.execute {
    val bmp = decodeAvatar(user)                       // 2. no way to cancel this
    mainHandler.post { imageView.setImageBitmap(bmp) } // 3. the view may be gone by now
}
mainHandler.postDelayed(expireRunnable, 30_000)        // 4. must be removed on teardown

Each numbered line starts async work whose lifetime must be ended by hand in a matching teardown callback such as onDetachedFromWindow or onDestroyView. Nothing in the type system ties those four registrations to the View’s lifecycle. Handler.postDelayed shows the retention path directly: the main thread’s MessageQueue holds the pending Message, the Message holds the Runnable, and any lambda that touches a View captures a strong reference to that View.

Garbage collection frees an object only when no path from any GC root (live thread stacks, static fields or JNI global references) reaches it. The collector cannot tell whether a detached View will ever be drawn again; as long as a queued message or registered listener points to the View, the View and its entire drawable and child subtree stay resident on the heap.

What it means for you In View code, every listener registration, posted message and executor task is a lifetime you must end yourself. In a heap dump, look for a Message, a listener list or a singleton sitting between a GC root and a detached View.

2Recycled Views outlive the data they were bound to

Scrolling lists and swipeable pagers cannot inflate fresh XML layouts on every frame without missing VSYNC deadlines. Instead, RecyclerView allocates enough row Views to fill the viewport plus a small margin, and rebinds those same View instances as items scroll on and off screen.

Rows that scroll off screen enter a small scrap cache or a shared RecycledViewPool (Table 1). Later, onBindViewHolder(holder, position) points the existing ViewHolder (the wrapper around one row View and its child references) at a new item. A ViewHolder therefore has a longer lifetime than any single item binding: it represents whichever position was bound most recently.

Pagers go further by attaching and laying out neighbour pages before the user swipes to them. The older ViewPager asks its PagerAdapter to instantiateItem every page within offscreenPageLimit of the current page, adds them to the View hierarchy, and lays them out immediately past the screen edge; pages further away receive destroyItem.

ViewPager2 builds on an internal RecyclerView (mRecyclerView) in which each page is a ViewHolder. By default it leaves offscreen retention to RecyclerView’s cache, while a positive limit pre-lays out that many neighbour pages on each side.

Recycling and pre-layout create two distinct async traps. First, an offscreen pager page is already attached to a visible window (onAttachedToWindow has run), so any work gated only on window attachment runs for pages the user cannot see. Second, background work started during onBindViewHolder has no built-in tie to that binding—if the user scrolls quickly, a slow load for an old item finishes late and overwrites the row’s new data while retaining the row View until completion:

What it means for you Any result that arrives after a rebind, a page change or a detach must be dropped or cancelled. Inside a pager, “attached” does not mean “visible”. Coroutines make the cancel cheap to write. They do not make it automatic unless the work runs in a scope that ends at the right moment.
Part II · Coroutines

3A suspend function becomes a state machine whose frame lives on the heap

Sequential code on a dedicated OS thread keeps its local variables on the call stack, where they disappear as soon as the method returns. On Android’s main thread, however, blocking on I/O freezes frame rendering, while parking a dedicated OS thread per waiting UI task ties up roughly a megabyte of virtual stack space. View callbacks avoid blocking threads by making the programmer split one logical operation into hand-wired heap closures.

A coroutine lets you write sequential code that pauses partway through without holding a thread, and resumes later on the same or another thread. A suspend function marks where that pause can happen, and may only be called from a coroutine or another suspend function.

An engineer debugging memory leaks or lifecycle bugs needs to know where that paused execution state lives. Because the main thread returns to Looper while a coroutine waits, the coroutine cannot leave its locals on the thread stack. Instead, the Kotlin compiler rewrites every suspend function into a heap-allocated state machine object: whoever holds that object while it waits—a dispatcher queue, a registered callback, a delay timer or a flow slot—keeps its entire chain of caller frames and local references alive.

Compare a five-line Kotlin suspend method on the left with the state machine produced by the Kotlin 2.2.0 compiler (inspected with javap, the JDK bytecode disassembler) on the right, watching how this and live locals move into fields on Cache$load$1:

// Demo.kt
class Cache {
    val map = HashMap<Int, String>()

    suspend fun load(id: Int): String {
        val cached = map[id]
        if (cached != null) return cached
        val v = fetch(id)      // suspension point
        map[id] = v
        return v
    }
    suspend fun fetch(id: Int): String = ...
}

The compiler adds a hidden trailing parameter, a Continuation with one method, resumeWith(result), meaning “here is the result you were waiting for, carry on”. The return type becomes Object so the function can return either a finished value or the sentinel COROUTINE_SUSPENDED.

// javap of Cache.load, written back as Java (shape)
Object load(int id, Continuation cont) {
  Cache$load$1 sm;
  if (cont instanceof Cache$load$1
      && (((Cache$load$1) cont).label & 0x80000000) != 0) {
    sm = (Cache$load$1) cont;     // resuming: reuse my frame
    sm.label -= 0x80000000;
  } else {
    sm = new Cache$load$1(this, cont); // fresh call
  }
  Object result = sm.result;
  switch (sm.label) {
    case 0:
      String cached = map.get(id);
      if (cached != null) return cached;
      sm.L$0 = cached; sm.I$0 = id;  // spill
      sm.label = 1;
      result = fetch(id, sm);     // sm is fetch's continuation
      if (result == COROUTINE_SUSPENDED) return result;
      break;
    case 1:
      id = sm.I$0;                   // restore
      throwOnFailure(result);
      break;
    default: throw new IllegalStateException(...);
  }
  String v = (String) result;
  map.put(id, v);
  return v;
}

When fetch suspends, Cache$load$1 acts as its heap stack frame: label records which switch branch runs next, completion points up to the caller’s continuation frame, and this$0 holds the receiver this. Live locals needed after the suspension point are spilled into fields (L$n for object references, I$n for ints), keeping referenced objects strongly reachable, while dead in-scope locals such as cached still get an L$n slot cleared via SpillingKt.nullOutSpilledVariable for debugger visibility without retaining memory.

When the awaited operation finishes, calling invokeSuspend(result) on Cache$load$1 stores the outcome, sets the sign bit of label, and re-enters load(0, this). That top bit distinguishes resuming an existing frame from a fresh recursive call whose caller happens to be another load instance.

Unwinding a completed call chain uses an iterative loop in BaseContinuationImpl.resumeWith rather than recursive Java calls, so a deep chain of synchronously completing frames never overflows the thread stack. Each iteration calls invokeSuspend; if the callee suspends again it returns immediately, and otherwise it passes the outcome straight up to completion:

kotlin/coroutines/jvm/internal/ContinuationImpl.kt · BaseContinuationImpl.resumeWith (excerpt)while (true) {

        val completion = completion!!
        val outcome: Result<Any?> =
            try {

            } catch (exception: Throwable) { Result.failure(exception) }

What it means for you In a heap dump, a generated class named Outer$method$1 or …Kt$fn$2 with label, this$0 and L$n fields is a suspended stack frame on the heap. It is not a GC root itself, so trace who holds the leaf continuation to see why the chain and its captured UI objects stay alive.

4Dispatchers move a coroutine between threads, through the main Handler on Android

State-machine frames explain how a function pauses, while a dispatcher (CoroutineDispatcher) replaces the manual Executor and Handler.post plumbing from Section 1. Each coroutine carries its settings—dispatcher, job and optional name—in an immutable map called its CoroutineContext, and stays on its current thread until a suspension point switches dispatchers.

On Android, Dispatchers.Main is a HandlerContext backed by a Handler on the main Looper (its Dispatchers.Main.immediate variant, used by lifecycleScope and viewModelScope, skips the initial post when already on the main thread). Notice in HandlerContext how delay posts to the same main MessageQueue as Figure 1, yet registers an automatic removeCallbacks hook on cancellation:

    if (!handler.post(block)) { cancelOnRejection(context, block) }
}

        continuation.invokeOnCancellation { handler.removeCallbacks(block) }
    } else { cancelOnRejection(continuation.context, block) }

A CancellableContinuation extends Continuation with cancellation listeners. Calling invokeOnCancellation wires teardown once inside the dispatcher, so cancelling a sleeping coroutine pulls its Runnable out of MessageQueue immediately instead of pinning captured Views until the timer expires.

withContext(dispatcher) { … } switches threads for a single block, suspends the caller, and posts the result back to the caller’s original dispatcher when done. Because the main thread is released during that gap, other messages and coroutines run on Looper before the caller resumes:

One call, end to end

Tracing scope.launch(Dispatchers.Main) { text.text = cache.load(7) } shows which heap object holds the continuation chain at every stage, where fetch runs on Dispatchers.IO (the shared thread pool for blocking disk and Binder work):

  1. Start. launch creates a StandaloneCoroutine (both the coroutine’s job handle and the top of its completion chain), wraps the lambda’s continuation frame in a DispatchedContinuation (which implements Runnable), and calls handler.post on plain Dispatchers.Main. While queued, the main MessageQueue keeps the chain reachable.
  2. First slice on main. Looper runs that Runnable, entering the lambda and calling load(7, frame). On a cache miss, load spills its live locals into Cache$load$1, sets label = 1, and calls fetch.
  3. Suspend. withContext(Dispatchers.IO) creates a DispatchedCoroutine holding a reference to Cache$load$1, submits the task to the IO pool, and returns COROUTINE_SUSPENDED all the way back to Looper. Nothing on the main thread’s stack points to this coroutine any more; the IO worker queue (alongside the parent scope’s job tree, Section 5) keeps the chain and its captured text View reachable.
  4. Background. An IO worker runs the block and finishes in DispatchedCoroutine.afterResume, which calls uCont.intercepted().resumeCancellableWith(value). Because uCont belongs to Dispatchers.Main, HandlerContext.dispatch posts a fresh resumption Runnable back to the main MessageQueue.
  5. Resume on main. Looper runs DispatchedTask.run. If the job was cancelled in the meantime, it resumes the frame with CancellationException; otherwise BaseContinuationImpl.resumeWith re-enters load at label 1, updates map, sets text.text, and marks StandaloneCoroutine complete, dropping the chain.
What it means for you Running on Dispatchers.Main prevents data races on a single instruction, but does not make a multi-step read-modify-write atomic across a suspension point. Guard shared cache updates across withContext with a kotlinx.coroutines.sync.Mutex, which suspends contenders without blocking the main thread.

5Jobs make lifetimes objects, and cancelling a parent cancels the whole tree

Unstructured async APIs—AsyncTask, bare Executor.execute calls and fire-and-forget threads—failed at scale on Android because starting background work took one line while cancelling every child task and listener on teardown required bespoke bookkeeping. Coroutines solve this with structured concurrency: every coroutine runs inside a CoroutineScope whose context carries a parent Job.

Both coroutine builders are extensions on CoroutineScope: launch starts fire-and-forget work and returns a Job, while async returns a Deferred<T> (a Job carrying a result). Each attaches its new job as a child of the scope’s job. As Job.kt states, cancelling a parent immediately cancels all of its children recursively, and a parent never completes until every child finishes.

Cancellation is cooperative rather than preemptive: job.cancel() transitions the job’s state, and the coroutine observes it at its next cancellable suspension point—any call built on suspendCancellableCoroutine, such as delay, withContext or channel and flow reads. That call throws CancellationException, unwinding the heap state machine through its finally blocks so cleanup hooks run reliably; tight CPU loops that never suspend must poll ensureActive() explicitly.

Structured concurrency guarantees cleanup only when the parent scope ends, so picking a scope with the wrong lifetime recreates the View-era leak in coroutine clothes. Launching UI collection in an application or singleton scope pins captured Views for the life of the process; launching it in a ViewModel’s viewModelScope survives Activity rotation and leaks destroyed Views across configuration changes.

AndroidX (Android’s Jetpack libraries) bridges UI lifetimes to scopes through LifecycleOwner (INITIALIZED, CREATED, STARTED, RESUMED, DESTROYED). An Activity’s lifecycleScope (or a Fragment’s viewLifecycleOwner.lifecycleScope) cancels at DESTROYED, while repeatOnLifecycle(Lifecycle.State.STARTED) launches a fresh child job each time the UI enters STARTED and cancels it when stopped. Notice in this status-indicator view binder how three parallel collect loops (each suspending forever on a UI flow, Section 6) share one lifecycle block—and where one gap still remains:

A view binder for a status indicator (shape)view.repeatWhenAttached {
    repeatOnLifecycle(Lifecycle.State.STARTED) {
        launch { viewModel.isShown.collect { shown -> view.isVisible = shown } }
        launch { viewModel.label.collect { label -> view.text.text = label } }
        launch { viewModel.icon.collect { icon -> view.icon.setImageDrawable(icon) } }
        bindClicks(view, viewModel)
    }
}

repeatWhenAttached follows the window, not the View

System surfaces such as the status bar, notification shade and keyguard (lockscreen) live in windows added directly to WindowManager rather than inside an Activity, so they have no Activity lifecycle to observe. SystemUI bridges that gap with View.repeatWhenAttached (SystemUI/src/com/android/systemui/lifecycle/RepeatWhenAttached.kt).

Each time the View attaches to a window, repeatWhenAttached creates a ViewLifecycleOwner and runs the block in its lifecycleScope; detaching moves that owner to DESTROYED and cancels the tree. While attached, however, its state tracks the enclosing window, not the individual child View:

RepeatWhenAttached.kt · ViewLifecycleOwner.updateStateregistry.currentState =
    when {
        view.windowVisibility != View.VISIBLE -> Lifecycle.State.CREATED
        !view.hasWindowFocus() -> Lifecycle.State.STARTED
        else -> Lifecycle.State.RESUMED

Because the status bar window stays visible whenever the screen is on, a child indicator set to View.GONE inside it remains STARTED, keeping its icon collector active and its drawable pinned. An offscreen pager page (Section 2) hits the identical case: attached to a visible window, yet invisible to the user.

What it means for you A coroutine scope cancels only on the signal wired into it: window detach, Activity stop or dialog dismissal. Whenever a View can remain attached while hidden (View.GONE, collapsed panels or offscreen pages), gate expensive collections explicitly on a visibility boolean with collectLatest or flatMapLatest.
Part III · Flows

6A cold flow does its work once per collector, and only while collected

A suspend function models a one-shot request, whereas UI state—the user’s avatar, whether an indicator is visible, the list of installed apps—changes continuously over time. Earlier Android stacks observed streams through raw listener lists, RxJava Observables (whose Disposable handles still had to be gathered and cleared in teardown callbacks) or LiveData (lifecycle-aware, yet main-thread-bound and awkward to compose). Kotlin’s Flow<T> ties multi-value streams directly to structured concurrency.

Its entire contract is one suspending method, suspend fun collect(collector: FlowCollector<T>), where FlowCollector exposes suspend fun emit(value: T). Because collect is a normal suspend call, a stream subscription has no separate Disposable handle: the collecting coroutine’s Job is the subscription, and cancelling that scope unwinds the entire pipeline from downstream (the collector) back to upstream (the source).

Flows come in two kinds, cold and hot, because UI pipelines have two opposite sharing needs. A flow is cold when the Flow instance is an inert blueprint—like a lambda waiting to be called—that allocates no resources at rest. Every call to collect runs the producer block from scratch for that collector alone, and most operators (map, filter, combine, flatMapLatest) return cold wrapper objects around their upstream flow.

Cold flows are ideal for bridging imperative Android listener APIs on demand. The library’s callbackFlow launches a producer block inside a ProducerScope backed by a Channel—a coroutine queue whose buffer holds values sent with non-blocking trySend until the collector receives them. Trace in the two columns below how SystemUI’s conflatedCallbackFlow pairs callbackFlow with awaitClose so cancelling the collector automatically unregisters the framework callback:

Chaining conflate() applies conflation: when the producer emits faster than a slow collector reads, queued intermediate values are overwritten so the collector always wakes to the newest app list.

What it means for you A cold flow allocates nothing at rest and keeps its producer resources alive for the duration of each collect call. When a cold-flow callback leaks in a heap dump, trace the collecting coroutine’s job to see which scope failed to cancel it.

7A hot flow holds one shared value, whether or not anyone collects it

Running a fresh producer per collector breaks down when five UI widgets observe the same repository state—each would register its own Binder listener and repeat the same query—or when newly bound UI needs the current state immediately without waiting for an async reload. That need is why hot flows exist alongside cold ones.

A hot flow lives and holds state independently of whether any collector is subscribed, multicasting emissions from a single source to every current listener. kotlinx.coroutines provides two hot types: SharedFlow, a general broadcast stream with a configurable replay cache, and its specialized subtype StateFlow, which models a single observable state cell that always holds one current value.

StateFlow

MutableStateFlow(initial) allocates a StateFlowImpl containing an atomic _state reference, a change counter sequence, and a slots array inherited from AbstractSharedFlow. Notice two distinct heap edges in Figure 7: _state retains the latest value even when slots is empty, while each occupied StateFlowSlot points directly to its suspended collector’s continuation:

In StateFlowImpl.collect, each subscriber claims a slot, checks its job for cancellation, emits the latest state when unequal to what it last saw, and parks its continuation in slot.awaitPending() until a writer wakes it:

kotlinx-coroutines-core/common/src/flow/StateFlow.kt · StateFlowImpl.collect (excerpt)val slot = allocateSlot()
try {
    var oldState: Any? = null
    while (true) {
        val newState = _state.value
        collectorJob?.ensureActive()
        if (oldState == null || oldState != newState) {     // conflation by equals()
            collector.emit(NULL.unbox(newState))
            oldState = newState
        }
        if (!slot.takePending()) { slot.awaitPending() }
    }
} finally { freeSlot(slot) }

Because each iteration reads _state.value directly, slow collectors skip intermediate updates (built-in conflation). Three memory and lifecycle rules follow:

  • Never completes: StateFlow.collect loops forever and exits only when the collecting job is cancelled, running freeSlot(slot) in finally. Until cancelled, StateFlowImpl.slots roots the collector’s continuation.
  • Equality deduplication: both updateState and the collector loop compare with equals(), so adding distinctUntilChanged() onto a StateFlow is a no-op.
  • Unconditional retention: whatever object sits in _state stays strongly reachable for as long as the StateFlowImpl itself is reachable, even with zero subscribers.

SharedFlow, stateIn and shareIn

MutableSharedFlow(replay = 0, extraBufferCapacity = 0, onBufferOverflow = SUSPEND) backs general event multicasting with a circular buffer array. It retains the last replay emissions (how many historical values a newly attached collector receives upfront; StateFlow acts like replay = 1) plus any unconsumed items still queued for slow active collectors.

To avoid duplicate work without hand-managing a MutableStateFlow, repositories and view-models convert a cold upstream flow into a shared hot flow with stateIn(scope, started, initial) or shareIn. Both launch one upstream collector coroutine in scope governed by a SharingStarted policy:

  • Eagerly: starts collecting upstream immediately and never stops until scope is cancelled.
  • Lazily: waits for the first subscriber, then keeps collecting upstream until scope is cancelled.
  • WhileSubscribed(stopTimeoutMillis = 0, replayExpirationMillis = Long.MAX_VALUE): cancels the upstream collector stopTimeoutMillis after the last subscriber disappears (for example 5_000 ms to ride out Activity rotation), yet leaves the last value in _state unless replayExpirationMillis = 0 also resets it to initial.
What it means for you Store large payloads in a StateFlow only when their lifetime matches the StateFlow’s owner. Calling stateIn(applicationScope, Eagerly, …) keeps the upstream callback registered forever; switching to WhileSubscribed(5_000) stops the upstream producer when idle, and adding replayExpirationMillis = 0 drops the cached value back to initial as well.

8combine keeps every input collected, all the time

Real screens derive state from several asynchronous sources at once. Rendering those sources through independent callbacks meant mutating separate fields on a controller and re-running a manual refresh method without knowing whether all inputs had loaded yet. combine(a, b) { x, y -> … } solves that cleanly: it waits until every input emits at least once, caches each input’s latest emission, and recomputes whenever any input changes.

The memory trap appears when engineers use combine to gate an expensive flow behind a cheap state flag—such as an overlay that needs the installed-apps list from Section 6 only while open. Look at combineInternal to see why returning null inside the transform lambda does not stop the unused input:

When a downstream coroutine collects the combined flow, combineInternal sets up five pieces of state:

  1. flowScope opens a child scope for this collection (like coroutineScope, except a failure or cancellation in any child cancels the whole group).
  2. It allocates latestValues filled with the sentinel UNINITIALIZED, plus a bounded Channel<Update>(size) buffered with one slot per input.
  3. It immediately launches one child coroutine per input flow; each child collects its upstream, sends Update(index, value) into the channel, and calls yield() so sibling inputs get a fair turn.
  4. The parent loop reads updates from the channel into latestValues[index], waits until no slot holds UNINITIALIZED, and invokes transform on the full array for every subsequent update.
  5. The loop exits on its own only if every upstream flow completes; for infinite UI streams it runs until the downstream collector cancels flowScope.

Now trace what happens when the overlay combines its open/closed state with installedApps and returns null while closed:

Overlay app category, first version (illustrative shape)val categories: Flow<List<Category>?> =
    overlayState.combine(installedApps) { state, apps ->
        if (state is OverlayState.Closed) { null }
        else { listOf(Category(apps)) }
    }

Suppose a controller collects categories in a long-lived scope via launchIn(scope) (shorthand for scope.launch { collect() }) to watch when categories should appear. Because combine cannot inspect the opaque transform lambda, it launches both input children right away.

Child 1 starts the cold installedApps flow, registering a LauncherApps.Callback and storing the full List<AppModel> in latestValues[1]. Even though the overlay stays closed for hours and transform emits null, the callback re-queries on every package install and the list remains pinned inside CombineKt$combineInternal$2.

What it means for you Reach for combine only when every input should stay subscribed simultaneously. When one upstream signal decides whether another flow is needed at all, switch streams with flatMapLatest: a combine lambda that returns null still keeps every input subscribed and every last emission cached on the heap.

9flatMapLatest and collectLatest stop the old work when a new value arrives

Two UI problems need an operator that tears down previous async work whenever an upstream value changes: rebinding a row or screen to a new key (the stale-result race from Section 2), and turning off an expensive subscription while a piece of UI is hidden or closed (Sections 5 and 8). Without automatic cancellation on new emissions, old collectors stay subscribed or slow loads overwrite newer UI state.

flatMapLatest, mapLatest and collectLatest solve both problems through a single engine, ChannelFlowTransformLatest. Watch in the right-hand column how each upstream emission cancels and waits for the previous child job before launching the new one:

flow/operators/Merge.kt, flow/terminal/Collect.kt (signatures shortened)fun <T, R> Flow<T>.flatMapLatest(transform) =
    transformLatest { emitAll(transform(it)) }
fun <T, R> Flow<T>.mapLatest(transform) =
    transformLatest { emit(transform(it)) }
suspend fun <T> Flow<T>.collectLatest(action) {
    mapLatest(action).buffer(0).collect()
}
flow/internal/Merge.kt · ChannelFlowTransformLatest.flowCollectcoroutineScope {
    var previousFlow: Job? = null
    flow.collect { value ->
        previousFlow?.apply {
            cancel(ChildCancelledException())
            join()
        }
        previousFlow = launch(start = CoroutineStart.UNDISPATCHED) {
            collector.transform(value)
        }
    }
}

Calling join() right after cancel() is what makes resource handoff clean: the outer collector suspends until the old child job finishes running its finally and awaitClose blocks (unregistering any Binder callback) before starting the replacement block with CoroutineStart.UNDISPATCHED on the current thread.

In flatMapLatest, the transform returns an inner flow whose values are flattened into the single downstream output. Returning flowOf(null) when closed emits one null and completes without subscribing to anything, so rewriting Section 8’s overlay keeps installedApps completely unsubscribed while closed:

Overlay app category, fixed (illustrative shape)val categories: Flow<List<Category>?> =
    overlayState
        .map { it is OverlayState.Open }
        .distinctUntilChanged()
        .flatMapLatest { isOpen ->
            if (!isOpen) flowOf(null)
            else installedApps.map { apps -> listOf(Category(apps)) }
        }
  • map { it is Open } projects the rich state down to the boolean that governs subscription lifetime.
  • distinctUntilChanged() prevents an Open → Open state update from cancelling and re-registering the callback.
  • flatMapLatest subscribes to installedApps only while open; closing the overlay cancels and joins the inner job, running awaitClose to unregister the callback and making the cached app list eligible for GC.

collectLatest applies the identical cancel-and-join pattern at the terminal collector: writing isShown.collectLatest { shown -> if (shown) collectIcon() } cancels the inner icon collection as soon as an attached View flips to View.GONE (closing the visibility gap from Section 5 and pattern 1 in Section 11).

What it means for you flatMapLatest and collectLatest turn an upstream boolean (“shown”, “open”, “active”) into a dynamic child scope. Whenever the upstream flow is not already a StateFlow, precede them with distinctUntilChanged() so equal emissions do not tear down and restart the inner subscription.
Part IV · Compose

10In Compose, remember and LaunchedEffect tie values and work to the composition

A View is a stateful heap object whose fields persist across frames while callers mutate it through setters. A Compose UI (@Composable fun Screen(…)) is a function that the runtime calls again (recomposes) whenever snapshot state it read has changed. Ordinary local variables vanish as soon as the function returns and would be rebuilt on every recomposition, whereas a view-model, animation object, or running coroutine must survive across calls without outliving that UI branch.

Compose solves this with positional memoization: each piece of Compose UI owns a composition backed by a slot table (SlotTable) indexed by call-site position in execution order. Per composition, the table pairs group metadata (groups: IntArray) with remembered values (slots: Array<Any?>) in a gap buffer, an array keeping unused space at the active cursor so insertions do not shift trailing elements. Anything stored without the right key or cleanup observer stays pinned in slots until that branch leaves composition.

Below, remember (Composer.cache) reads or populates the next slot when it sees Composer.Empty, and SystemUI’s rememberActivated pairs remember(key) with LaunchedEffect to bind an object’s active work to that slot’s lifetime:

compose/runtime/Composables.kt, Composer.kt (annotations dropped)inline fun <T> remember(crossinline calculation: () -> T): T =
    currentComposer.cache(false, calculation)

inline fun <T> Composer.cache(invalid: Boolean, block: () -> T): T {
    return rememberedValue().let {
        if (invalid || it === Composer.Empty) {
            val value = block()
            updateRememberedValue(value)
            value
        } else it
    } as T
}
SystemUI/src/…/lifecycle/Activatable.kt@Composable
fun <T : Activatable> rememberActivated(
    traceName: String, key: Any = Unit, factory: () -> T,
): T {
    val instance = remember(key) { factory() }
    LaunchedEffect(instance) {
        traceCoroutine(traceName) { instance.activate() }
    }
    return instance
}

LaunchedEffect(key) { … } stores a LaunchedEffectImpl in a slot and restarts its coroutine whenever key changes. LaunchedEffectImpl implements RememberObserver, the lifecycle interface for slot-table entries: the runtime calls onRemembered() when the value enters the composition, onForgotten() when its group leaves, and onAbandoned() if composition aborts before apply. onRemembered() launches the coroutine; the other two cancel its job with ExitedCompositionCancellationException.

SystemUI uses this pattern to scope view-models to a composable subtree rather than to an entire Activity. An Activatable exposes suspend fun activate(), which runs active work until cancelled, and rememberActivated invokes it inside LaunchedEffect(instance). View-models built on HydratedActivatable implement onActivated(): activate() opens a coroutineScope, runs onActivated(), and suspends in awaitCancellation() with onDeactivated() in a finally block, so every child collector launched there is cancelled as soon as the composable leaves composition.

What it means for you In Compose, work inside LaunchedEffect or rememberActivated cancels automatically when its branch leaves the composition. Retention bugs move to two places: omitting a key on remember when inputs change (pinning stale state in SlotTable.slots), or writing UI references into a longer-lived MutableStateFlow or singleton.
Part V · Leak patterns

11Common leak patterns: each is a lifetime that runs too long

Across Views, coroutines, flows, and Compose, every leak reduces to one shape: a reference chain from a GC root outlives the UI that needed it. The anchor on that chain may be a queued Message, a suspended Continuation, a child Job in a long-lived scope, a StateFlowImpl._state or StateFlowSlot, combine’s latestValues, or an unkeyed entry in SlotTable.slots.

To isolate one in a heap dump, start from the dead View, Activity, or model and trace shortest paths back to GC roots (Section 1). Object X dominates object Y when every path from a GC root to Y passes through X. X’s retained size is the total shallow size of everything X dominates: what the GC would free if X alone became unreachable. The first object on that path with no reason to remain alive is the bug.
