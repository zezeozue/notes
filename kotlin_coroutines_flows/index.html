Kotlin coroutines and flows: how async work outlives the UI

This note is for an engineer who knows Android Views but finds the coroutine vocabulary opaque. It starts with the problems of View callbacks and Handlers. It then shows what suspend functions, jobs, cold and hot flows, combine, flatMapLatest and Compose’s remember keep alive on the heap. Last, it lists the common leak patterns, each as a rule with a small code shape.

At a glance

  • Every leak pattern in Part V has one shape: some work, or some value, outlives the piece of UI that needed it.
  • In View code, each callback, posted message and background task is a lifetime you must end by hand.
  • Coroutines make that lifetime an object, a job, which is cancelled together with its parent.
  • The mistake moves rather than disappears: a flow collected in a scope that lives too long keeps its inputs alive.
  • The main fixes are: collect in a scope that ends with the UI, share lazily, switch inputs with flatMapLatest, remove timers, and key what you remember.

Some examples of the shape. A View is detached, but a queued message still points at it. A dialog is closed, but a callback is still registered. A View is hidden, but a collector still sets a large picture on it.

To spot these patterns in coroutine and flow code, you need to know what the operators actually keep alive. That is what Parts II and III are about. Exact sources and versions are listed in Versions and method.

Part I · The View-era problem

1View code ends every async lifetime by hand

All View work happens on one thread, so slow work must leave it and its result must come back as a message. Views are not thread-safe. Measuring, layout, drawing and mutation all happen on the main thread. That thread runs a Looper: a loop that takes the next message from a queue and runs it. Slow work happens elsewhere: Binder calls (Android’s cross-process calls into system_server or another app), disk, decoding.

The classic shape is a callback that hops to an executor (a background thread pool), then back through a Handler. A Handler is an object that posts a Runnable into one specific Looper’s queue:

// The View-era pattern (shape)
userManager.registerCallback(callback)                // 1. must be unregistered later
bgExecutor.execute {
    val bmp = decodeAvatar(user)                       // 2. no way to cancel this
    mainHandler.post { imageView.setImageBitmap(bmp) } // 3. the view may be gone by now
}
mainHandler.postDelayed(expireRunnable, 30_000)        // 4. must be removed on teardown

Each numbered line is a lifetime that the code has to end by hand. Nothing in the types connects them to the View’s attach and detach. A Handler.postDelayed is the clearest case. The queued message holds the Runnable, and a lambda that touches the View holds the View.

Why that matters for memory: the garbage collector frees an object only when nothing reachable points at it. It starts from GC roots, objects that are live by definition (thread stacks, static fields, and JNI global references, which native code holds on Java objects), and follows references. Anything on a path from a root stays, whether or not the app will use it again.

What it means for you In View code, every register, post and executor task is a lifetime you must end yourself. In a heap dump, look for a Message, a listener list or a singleton between a GC root and a detached View.

2Recycled Views outlive the data they were bound to

Lists and pagers reuse a few Views for many items, so a View is not tied to one item. RecyclerView keeps a small set of row Views and rebinds them as you scroll. A row that scrolls off goes into a small cache or a shared pool (Table 1). The adapter later calls onBindViewHolder(holder, position) to point the same View objects at different data. A ViewHolder wraps one row View and its child references. So a ViewHolder is not “row 0”. It is “whatever position was bound last”.

Pagers go further: they build pages the user cannot see yet. A swipe has to reveal the next page without a pause to inflate it. The older ViewPager asks its PagerAdapter to instantiateItem every page within offscreenPageLimit of the current one. It adds those pages to the view hierarchy, then measures and lays them out beside the visible page, past the edge of the screen. Pages further away get destroyItem. ViewPager2 is built on a RecyclerView, mRecyclerView, in which each page is a ViewHolder. A positive limit makes it lay out that many extra pages on each side.

Part II · Coroutines

3A suspend function becomes a state machine whose frame lives on the heap

Coroutines let you write async code as one function and have the compiler split it into resumable pieces. The code in Part I needs three things. It must wait for slow work without blocking the main thread. It must come back to the main thread afterwards. And it must cancel the whole thing when the UI goes away. Callbacks provide the first two by splitting one function into pieces by hand.

A coroutine is a computation that can stop partway through without holding a thread, and continue later, possibly on another thread. A suspend function is a function marked with the suspend keyword. It may pause (suspend) at a call to another suspend function. It can only be called from a coroutine or from another suspend function. The compiler makes pausing possible by turning every suspend function into a state machine: a function that can be re-entered at any of its suspension points.

A small example, compiled with the Kotlin 2.2.0 compiler and read back with javap, the JDK tool that prints what a compiled class contains:

// Demo.kt
class Cache {
    val map = HashMap<Int, String>()

    suspend fun load(id: Int): String {
        val cached = map[id]
        if (cached != null) return cached
        val v = fetch(id)      // suspension point
        map[id] = v
        return v
    }
    suspend fun fetch(id: Int): String = ...
}

The compiler adds a hidden last parameter, a Continuation. It is an object with one method, resumeWith(result), meaning “here is the value you were waiting for, carry on”. The return type becomes Object. The function now returns either its real result or the marker COROUTINE_SUSPENDED.

// javap of Cache.load, written back as Java (shape)
Object load(int id, Continuation cont) {
  Cache$load$1 sm;
  if (cont instanceof Cache$load$1
      && (((Cache$load$1) cont).label & 0x80000000) != 0) {
    sm = (Cache$load$1) cont;     // resuming: reuse my frame
    sm.label -= 0x80000000;
  } else {
    sm = new Cache$load$1(this, cont); // fresh call
  }
  Object result = sm.result;
  switch (sm.label) {
    case 0:
      String cached = map.get(id);
      if (cached != null) return cached;
      sm.L$0 = cached; sm.I$0 = id;  // spill
      sm.label = 1;
      result = fetch(id, sm);     // sm is fetch's continuation
      if (result == COROUTINE_SUSPENDED) return result;
      break;
    case 1:
      id = sm.I$0;                   // restore
      throwOnFailure(result);
      break;
    default: throw new IllegalStateException(...);
  }
  String v = (String) result;
  map.put(id, v);
  return v;
}

The compiler turns the function’s local frame into a heap object, Cache$load$1. A label field records where to resume. Locals still needed later are copied into fields (spilled): L$n for references, I$n for ints, and this$0 captured once for this.

To resume, the frame’s invokeSuspend(result) stores the result, sets the top bit of label and calls load(0, this) again. That bit is how load tells “I am being resumed” apart from “a new call whose caller happens to be another load frame”.

Resuming is a loop, not recursion. BaseContinuationImpl.resumeWith calls invokeSuspend. If that returns COROUTINE_SUSPENDED, it stops. Otherwise it feeds the value to completion, the caller’s frame, and continues up the chain:

kotlin/coroutines/jvm/internal/ContinuationImpl.kt · BaseContinuationImpl.resumeWith (excerpt)while (true) {
    with(current) {
        val completion = completion!!
        val outcome: Result<Any?> =
            try {
                val outcome = invokeSuspend(param)
                if (outcome === COROUTINE_SUSPENDED) return
                Result.success(outcome)
            } catch (exception: Throwable) { Result.failure(exception) }
        releaseIntercepted()
        if (completion is BaseContinuationImpl) { current = completion; param = outcome }
        else { completion.resumeWith(outcome); return }
    }
}
What it means for you In a heap dump, a class named like Outer$method$1 or …Kt$fn$2, with fields label, L$0 and L$1, is a suspended frame. Whatever its L$n fields point to is retained while that coroutine stays suspended. For a collect loop, that can be the life of the process.

4Dispatchers move a coroutine between threads, through the main Handler on Android

A suspend function runs on whatever thread called it, and moves only when it asks to. The object that decides which thread a coroutine runs on is its dispatcher. It is stored in the coroutine’s CoroutineContext, a small map of per-coroutine settings: dispatcher, job, name.

On Android, Dispatchers.Main is a HandlerContext wrapping a Handler on the main Looper. Dispatching a resumption is a handler.post. A delay is a postDelayed. If the coroutine is cancelled while waiting, the Runnable is removed:

ui/kotlinx-coroutines-android/src/HandlerDispatcher.kt · HandlerContextoverride fun dispatch(context: CoroutineContext, block: Runnable) {
    if (!handler.post(block)) { cancelOnRejection(context, block) }
}
override fun scheduleResumeAfterDelay(timeMillis: Long, continuation: CancellableContinuation<Unit>) {
    val block = Runnable { with(continuation) { resumeUndispatched(Unit) } }
    if (handler.postDelayed(block, timeMillis.coerceAtMost(MAX_DELAY))) {
        continuation.invokeOnCancellation { handler.removeCallbacks(block) }
    } else { cancelOnRejection(continuation.context, block) }
}

That highlighted line is the removeCallbacks that View code has to remember (Section 1), done once in the library. A CancellableContinuation is a continuation that is also told when its coroutine is cancelled, and invokeOnCancellation registers what to do then.

withContext(dispatcher) { … } runs a block on another dispatcher and suspends the caller until it finishes. Then it posts the caller back to its own dispatcher. For a main-thread caller, that is another handler.post.

One call, end to end

Putting Sections 3 and 4 together, here is every step of one call. It starts a coroutine on the main thread and ends when the result lands back there. Assume scope.launch(Dispatchers.Main) { text.text = cache.load(7) }. launch starts a new coroutine and returns its job (Section 5). The body of fetch is withContext(Dispatchers.IO) { … }, where Dispatchers.IO is the library’s shared thread pool for blocking work such as disk and Binder calls.

  1. Start. launch creates a StandaloneCoroutine. It is both the new coroutine’s job and the last continuation in the chain. It creates a frame for the lambda and calls intercepted().resumeCancellableWith(…) on it. intercepted() wraps the frame in a DispatchedContinuation, which is a Runnable. The main dispatcher says a dispatch is needed, so this is a handler.post. launch returns before any of the body runs.
  2. First slice on main. The Looper runs that Runnable. It resumes the lambda’s frame, which calls load(7, frame). On a cache miss, load spills its locals, sets label = 1 and calls fetch.
  3. Suspend. withContext sees a different dispatcher. It creates a DispatchedCoroutine, dispatches the block to the IO pool, and returns COROUTINE_SUSPENDED. Every frame above it returns the same marker. The Runnable returns, and the Looper moves on to the next message. Nothing on the main thread’s stack refers to this call any more. Only heap objects do.
  4. Background. An IO thread runs the block. When it returns, DispatchedCoroutine.afterResume calls uCont.intercepted().resumeCancellableWith(value). That is the waiting frame, wrapped by its dispatcher, so HandlerContext.dispatch does another handler.post.
  5. Resume on main. The Looper runs that Runnable. DispatchedTask.run first checks the job. If the coroutine was cancelled meanwhile, the frame is resumed with a CancellationException instead of the value. Otherwise BaseContinuationImpl.resumeWith runs the loop from Section 3. load re-enters at label 1, writes the map and returns v. The lambda sets the text and returns. Its completion is the StandaloneCoroutine, which marks the job complete.
What it means for you “Single-threaded” does not mean “no races” once there is a suspension point in the middle. Guard check-then-act across withContext with a kotlinx.coroutines.sync.Mutex, which suspends waiters instead of blocking the thread.

5Jobs make lifetimes objects, and cancelling a parent cancels the whole tree

Coroutines turn each lifetime into an object and arrange those objects in a tree, so ending one ends everything under it. In Section 1, every piece of async work was a lifetime the code had to end by hand, and nothing grouped them.

A Job is the handle for a running coroutine’s lifetime: active, cancelling, or complete. A CoroutineScope is an object that carries a context with a job in it. There are two ways to start a coroutine, and both are extension functions on a scope. launch is fire and forget and returns a job. async returns a Deferred, which is a job with a result. Each creates a child job of the scope’s job.

Job.kt states the rule: “cancellation of a parent leads to immediate cancellation of all its children recursively”. A parent also does not complete until its children do. This parent and child discipline is called structured concurrency.

Cancellation is cooperative. cancel() only marks the job. The coroutine notices at its next suspension point, which throws CancellationException inside it.

“Suspension point” here means any suspending call built on suspendCancellableCoroutine, the library primitive that pauses a coroutine and hands its continuation to whoever will resume it. delay, withContext, and channel and flow operations are all built on it. The exception unwinds the state machine like any other, so finally blocks run. Code that never suspends never sees the cancel, unless it checks itself with ensureActive(), as StateFlowImpl.collect does in Section 7.

coroutineScope { … } creates a child scope and waits for every launch inside it. Calling collect on a flow (a stream of values, Section 6) suspends for as long as the stream runs. For UI state, that is forever. So to collect three flows at once, you launch three children.

The UI decides when those children should stop. AndroidX (Android’s Jetpack support libraries) models that with a lifecycle: a small state machine (INITIALIZED, CREATED, STARTED, RESUMED, DESTROYED). It is exposed by a LifecycleOwner such as an Activity or Fragment. Its lifecycleScope is a scope that is cancelled when the state reaches DESTROYED. repeatOnLifecycle(state) runs a block each time the state rises to state, and cancels it each time the state falls below.

Take a view binder for a small status indicator that shows a label and an icon. It uses both. viewModel is its view-model: the object that holds the indicator’s state as flows, so the View code only has to display them:

A view binder for a status indicator (shape)view.repeatWhenAttached {
    repeatOnLifecycle(Lifecycle.State.STARTED) {
        launch { viewModel.isShown.collect { shown -> view.isVisible = shown } }
        launch { viewModel.label.collect { label -> view.text.text = label } }
        launch { viewModel.icon.collect { icon -> view.icon.setImageDrawable(icon) } }
        bindClicks(view, viewModel)
    }
}

repeatWhenAttached follows the window, not the View

Most SystemUI Views (status bar, notification shade, keyguard, which is the lockscreen) live in windows that SystemUI adds directly, not in an Activity. So there is no Activity lifecycle to borrow. SystemUI gives each View one with View.repeatWhenAttached, a helper in SystemUI’s lifecycle library (SystemUI/src/com/android/systemui/lifecycle/RepeatWhenAttached.kt).

On each attach, it creates a fresh ViewLifecycleOwner and launches the block in its lifecycleScope. On detach, it calls onDestroy(), which moves the lifecycle to DESTROYED and cancels that scope. Between those, the state follows the window, not the View:

RepeatWhenAttached.kt · ViewLifecycleOwner.updateStateregistry.currentState =
    when {
        view.windowVisibility != View.VISIBLE -> Lifecycle.State.CREATED
        !view.hasWindowFocus() -> Lifecycle.State.STARTED
        else -> Lifecycle.State.RESUMED
    }

So a repeatOnLifecycle(STARTED) block keeps running for as long as the window is visible. The status bar window is visible whenever the status bar is. So a View inside it that is GONE is still STARTED. The same holds for an offscreen pager page (Section 2): attached, in a visible window, not on screen.

What it means for you A scope only ends when something you chose ends: detach, window hidden, a dialog closing. If the UI can be hidden by other means, such as View.GONE or an inactive state, gate the collection on that signal yourself. Usually that means collectLatest or flatMapLatest.
Part III · Flows

6A cold flow does its work once per collector, and only while collected

A flow is a stream of values over time that is tied to a coroutine’s lifetime. UI state changes over time: the user’s avatar, whether a chip is visible, the list of installed apps. A suspend function returns one value. A callback delivers many values but has no lifetime of its own. A Flow<T> gives you both.

Its interface has one method, suspend fun collect(collector). The collector is an object with one method, suspend fun emit(value), supplied by whoever wants the values. The flow’s producer code calls emit once per value. collect suspends the caller until the producer finishes or the caller is cancelled. An operator such as map or filter is a function that takes a flow and returns a new flow wrapping it. In a chain a.map { … }.filter { … }, values travel from upstream (the source, a) to downstream (towards the final collector).

A flow is cold when it is only a description, like a function that has not been called. Building it runs nothing. Each call to collect runs the producer code from the start, for that collector alone, until that collection ends. Most operators (map, filter, combine, flatMapLatest) return cold flows that wrap their inputs.

SystemUI wraps Android callback APIs this way. The library’s callbackFlow turns a callback into a cold flow. It runs a producer block in a ProducerScope, a scope that owns a Channel.

A channel is a queue between coroutines: send suspends when the queue is full, and receive suspends when it is empty. The callback pushes values into the channel with trySend, which does not suspend and is safe from any thread. The collector receives them. The channel’s queue is a buffer: room for values the producer has sent but the collector has not taken yet. SystemUI’s conflatedCallbackFlow is a one-liner over callbackFlow:

SystemUI/utils/…/coroutines/flow/FlowConflated.ktfun <T> conflatedCallbackFlow(
    @BuilderInference block: suspend ProducerScope<T>.() -> Unit
): Flow<T> = callbackFlow(block).conflate()

LauncherApps is the framework service that lists launchable apps; its callback fires when an app is installed, updated or removed. The callback exists only while someone is collecting. When the collecting coroutine is cancelled, the producer’s suspension in awaitClose throws CancellationException, and the finally runs the unregister.

conflate() applies conflation. When the collector is slower than the producer, values it has not taken yet are replaced by newer ones. So it sees only the latest list, not every intermediate one.

What it means for you A cold flow costs nothing until collected and costs its full price for as long as the collection lasts. To find who keeps it alive, find the collector and the scope it was launched in.

7A hot flow holds one shared value, whether or not anyone collects it

A hot flow shares one producer among all collectors. A cold flow runs its producer once per collector, which is wrong for two common needs. Several pieces of UI want the same value without each registering its own callback. And some values, such as the current user or whether the shade is open, should exist before anyone looks.

A flow is hot when it exists independently of its collectors. Values are produced whether or not anyone listens, and collectors attach to an ongoing stream. Cold is a function call that each caller makes for itself. Hot is a broadcast already on air. The two hot types in kotlinx.coroutines are SharedFlow, a broadcast with an optional replay buffer, and its special case StateFlow, which always has exactly one current value.

StateFlow

MutableStateFlow(initial) returns a StateFlowImpl. Its state is one atomic reference _state, an int sequence, and an array of collector slots inherited from AbstractSharedFlow:

kotlinx-coroutines-core/common/src/flow/StateFlow.kt · StateFlowImpl.collect (excerpt)val slot = allocateSlot()
try {
    var oldState: Any? = null
    while (true) {
        val newState = _state.value
        collectorJob?.ensureActive()
        if (oldState == null || oldState != newState) {     // conflation by equals()
            collector.emit(NULL.unbox(newState))
            oldState = newState
        }
        if (!slot.takePending()) { slot.awaitPending() }
    }
} finally { freeSlot(slot) }

Each pass of the loop reads only the current _state, so a slow collector skips intermediate values. A StateFlow is always conflated. Three further consequences follow.

  • A StateFlow never completes, so collecting it only ends by cancellation.
  • Equal consecutive values are dropped. updateState returns early on oldState == newState, and the loop compares again. So distinctUntilChanged() on a StateFlow does nothing.
  • Whatever is in _state stays reachable as long as the StateFlowImpl is, whether or not anyone collects.

SharedFlow, stateIn and shareIn

MutableSharedFlow(replay = 0, extraBufferCapacity = 0, onBufferOverflow = SUSPEND) keeps a circular buffer. It holds the last replay values plus any values slow collectors have not consumed yet. Replay is how many past values a new collector receives first, before live ones. A StateFlow behaves like replay 1. With the defaults, emit suspends until every current collector has taken the value.

stateIn(scope, started, initial) and shareIn turn a cold flow into a hot one. They launch one collection of it in scope and publish what it emits. The started argument is a SharingStarted policy that decides when that collection runs:

  • Eagerly: now, until the scope ends.
  • Lazily: on the first subscriber, then until the scope ends.
  • WhileSubscribed(stopTimeoutMillis = 0, …): stops the upstream once the last subscriber is gone.
What it means for you Put large objects in a StateFlow only if they should live as long as its owner. A stateIn(applicationScope, Eagerly, …) keeps its upstream running and its value alive for the life of the process.

8combine keeps every input collected, all the time

combine must know every input’s latest value at all times, so it collects all of them for as long as it is collected. UI often depends on several flows at once. Take an overlay that shows a list of apps only while it is open: its app category needs both the overlay’s state and the list of installed apps from Section 6. combine(a, b) { x, y -> … } produces a value whenever any input changes, computed from the latest value of each.

    combineInternal(arrayOf(this@combine, flow), nullArrayFactory(), { emit(transform(it[0] as T1, it[1] as T2)) })
}

Step by step, when someone collects a combined flow:

  1. flowScope opens a scope for this one collection. It is a coroutineScope that is also cancelled if any child is.
  2. It fills latestValues with the marker UNINITIALIZED. It creates a channel with room for one update per input.
  3. It launches one child coroutine per input. Each child collects its input. For every value, it sends (index, value) into the channel, then yields so the other children get a turn.
  4. The parent loops on the channel. Each update overwrites latestValues[index]. Nothing is emitted until every input has produced at least one value. After that, every update, or small batch of updates, calls transform on the whole array, which emits downstream.
  5. The loop ends on its own only when every input has completed. Otherwise it runs until the collector is cancelled. That cancels the scope and with it every child.

Now apply that to the overlay. A first version combines the two inputs and returns null while the overlay is closed:

Overlay app category, first version (illustrative shape)val categories: Flow<List<Category>?> =
    overlayState.combine(installedApps) { state, apps ->
        if (state is OverlayState.Closed) { null }
        else { listOf(Category(apps)) }
    }

If something collects categories in a long-lived scope, for example a launchIn(scope) (shorthand for scope.launch { collect() }) that decides when to show the overlay, combine starts both children at once. Child 1 collects the cold installedApps flow. That registers a LauncherApps.Callback and sends the full app list, which lands in latestValues[1]. The transform returns null because the overlay is closed. But the child keeps collecting and the array keeps the list, for as long as that collection lives. The callback also re-queries on every package install or update.

What it means for you Use combine when you need every input live at once. When one input decides whether another is needed at all, use flatMapLatest. combine will keep the unneeded input collected and its last value in memory: a transform that returns null still pays for every input.

9flatMapLatest and collectLatest stop the old work when a new value arrives

The rebind problem from Section 2 comes back in flow form. When a new value arrives (a new position, “now hidden”, “now inactive”), the work started for the old value should stop. The …Latest operators run a block per upstream value and cancel the previous block when a new value arrives. They are all one implementation:

flow/operators/Merge.kt, flow/terminal/Collect.kt (signatures shortened)fun <T, R> Flow<T>.flatMapLatest(transform) =
    transformLatest { emitAll(transform(it)) }
fun <T, R> Flow<T>.mapLatest(transform) =
    transformLatest { emit(transform(it)) }
suspend fun <T> Flow<T>.collectLatest(action) {
    mapLatest(action).buffer(0).collect()
}
flow/internal/Merge.kt · ChannelFlowTransformLatest.flowCollectcoroutineScope {

The previous block is cancelled and joined before the next one starts. join() suspends until that job has fully finished. So any finally or awaitClose in the old inner flow has run, and its callback is unregistered, before the new one begins. CoroutineStart.UNDISPATCHED starts the new block immediately on the current thread instead of posting it.

flatMapLatest’s transform returns a flow, the inner flow. The values of the current inner flow are emitted downstream. It is “flat” because a flow of flows becomes one flow. The inner flow for “closed” can be flowOf(null), which emits one null and collects nothing. For the overlay of Section 8, the state now decides whether the app list is collected at all:

Overlay app category, fixed (illustrative shape)val categories: Flow<List<Category>?> =
    overlayState
        .map { it is OverlayState.Open }
        .distinctUntilChanged()
        .flatMapLatest { isOpen ->
            if (!isOpen) flowOf(null)
            else installedApps.map { apps -> listOf(Category(apps)) }
        }
  • map { it is Open } reduces the state to a boolean.
  • distinctUntilChanged() stops an Open → Open update from cancelling and re-registering.
  • flatMapLatest collects installedApps only while open. When the overlay closes, it cancels and joins that collection. So awaitClose unregisters the callback, and the list becomes garbage.

collectLatest is the terminal version: isVisible.collectLatest { if (it) collectStuff() } stops collectStuff each time visibility changes. This is how a View that is hidden but still attached stops its work (Section 5, and pattern 1 in Section 11).

What it means for you flatMapLatest and collectLatest turn a boolean (“shown”, “active”, “visible”) into a scope. When the upstream is not a StateFlow, put distinctUntilChanged() before them. Then equal values do not tear down and rebuild the inner collection.
Part IV · Compose

10In Compose, remember and LaunchedEffect tie values and work to the composition

A Compose UI is a function that runs again and again, so anything that must last has to be stored outside the call. A View is a long-lived object: its fields are its state, and you change the screen by calling setters on it. A Compose UI is a function, @Composable fun Screen(…), that the runtime calls again (recomposes) whenever state it read has changed. A local variable inside that function is recreated on every call. An animation object, a view-model or a running job must survive across calls, so it has to live somewhere else.

The runtime keeps a composition for each piece of Compose UI. It records which composables were called, in what order, with what remembered values. That storage is the slot table. Per composition, it is an array of groups (groups: IntArray) and an array of values (slots: Array<Any?>), laid out in call order. It is kept as a gap buffer: an array with an empty stretch kept at the current editing position, so inserting there does not shift the rest. remember reads and writes the next slot:

compose/runtime/Composables.kt, Composer.kt (annotations dropped)inline fun <T> remember(crossinline calculation: () -> T): T =
    currentComposer.cache(false, calculation)

inline fun <T> Composer.cache(invalid: Boolean, block: () -> T): T {
    return rememberedValue().let {
        if (invalid || it === Composer.Empty) {
            val value = block()
            updateRememberedValue(value)
            value
        } else it
    } as T
}
SystemUI/src/…/lifecycle/Activatable.kt@Composable
fun <T : Activatable> rememberActivated(
    traceName: String, key: Any = Unit, factory: () -> T,
): T {
    val instance = remember(key) { factory() }
    LaunchedEffect(instance) {
        traceCoroutine(traceName) { instance.activate() }
    }
    return instance
}

LaunchedEffect(key) { … } runs a coroutine while it stays in the composition, and restarts it when key changes. It stores a LaunchedEffectImpl in a slot. That class is a RememberObserver: an interface for remembered values that want to know their own lifetime. The runtime calls onRemembered() when the value enters the composition and onForgotten() when it leaves. It calls onAbandoned() if the composition was discarded before it was applied. LaunchedEffectImpl launches the block in onRemembered(). The other two cancel it with ExitedCompositionCancellationException.

SystemUI uses this to scope view-models to the UI. An Activatable is an object with a suspend fun activate() that does its work until cancelled. rememberActivated, above, remembers one and activates it in a LaunchedEffect. View-models built on HydratedActivatable do their work in onActivated(). activate() runs it inside a coroutineScope, then awaitCancellation(), which suspends until the coroutine is cancelled, with onDeactivated() in a finally.

So everything launched in onActivated() lives as long as the composable that remembered the view-model.

What it means for you In Compose, “scoped to the UI” is the default when work runs in a LaunchedEffect or an activated view-model. What it keeps alive is whatever those coroutines write into longer-lived objects, such as a MutableStateFlow field.
Part V · Leak patterns

11Common leak patterns: each is a lifetime that runs too long

Every pattern below is one mistake in a different place: some work, or some value, outlives the piece of UI that needed it. To find one in a heap dump, start from the object that should be gone and follow the references back to a GC root (Section 1). Object X dominates object Y if every path from a GC root to Y passes through X. X’s retained size is the total size of everything it dominates: what the GC would free if X alone became unreachable. The first object on the path that has no reason to be alive is usually the bug.

What it means for you For every coroutine, callback, timer and cached value, name the moment it should end, and make that moment cancel or release it. In a heap dump, the leak is the first object on the path to a GC root that is still alive after that moment.
