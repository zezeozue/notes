PerfettoSQL: every statement goes through a generated parser, and pipe queries run on Perfetto's own executor

Trace Processor embeds SQLite, yet stock SQLite alone hit two architectural ceilings as Perfetto grew: SQLite exposes no syntax tree for modules or macros, and its virtual-table boundary steps multi-stage queries one row at a time. This note explains why Perfetto put a generated LALR(1) parser in front of SQLite and built a columnar batch executor for |> pipe queries, then traces one query from raw bytes to output rows.

Code is from the upstream Perfetto repository, main as of late October 2026, and code marked shape is simplified. Pipe syntax is experimental and changes quickly, so treat the names as a snapshot. Its status is in the design doc docs/design-docs/perfetto-sql-pipelines.md in the Perfetto repository.

At a glance

  • One generated parser in front of SQLite. Stock SQLite compiles SQL straight to bytecode without exposing a syntax tree, so Perfetto parses every statement first with a Lemon parser built from SQLite's grammar plus PerfettoSQL rules.
  • Three execution routes from one AST. Plain SQL forwards to SQLite, catalog extensions (CREATE PERFETTO …, INCLUDE) run in C++, and |> pipe queries compile onto Perfetto's batch executor.
  • Token-level macros keep accurate tracebacks. Macros expand inside the tokenizer as numbered token layers while recording byte-range rewrites, so SQLite errors still point back to the line you wrote.
  • Pipelines bypass row-at-a-time interpretation. Multi-stage |> queries run in C++ over columnar batches of up to 2,048 rows, crossing into SQLite only once to stream final rows out.
  • Modular operator registration. Adding a new pipe stage touches roughly five files; the real design work is declaring which columns it reads and what row order it preserves.

Terms. Trace Processor is Perfetto's C++ query engine: it ingests a trace into in-memory columnar tables called dataframes and exposes them to SQLite as virtual tables (vtabs) backed by C++ callbacks. SQLite executes queries by compiling SQL into bytecode for its scalar interpreter, the VDBE (Virtual Database Engine). The standard library (stdlib) is the collection of reusable PerfettoSQL modules shipped with Trace Processor and loaded via INCLUDE PERFETTO MODULE. Names starting with __intrinsic_ are intrinsics: internal tables and functions Trace Processor registers for its own plumbing rather than public queries.

On the compiler side, a token is the smallest meaningful slice of text (such as a keyword, identifier, or operator), and a grammar is the set of rules defining valid token sequences. An AST (abstract syntax tree) is the tree representing a statement's structure without redundant punctuation. Lemon is SQLite's LALR(1) parser generator, syntaqlite is the toolchain that builds Perfetto's AST-producing dialect parser on top of Lemon, and a pipeline is a dataflow query written with |> stages.

Overview: why Perfetto parses SQL itself, then routes each statement one of three ways

Why build a custom SQL parser and execution engine inside a system that already embeds SQLite? Two concrete bottlenecks forced the design.

First, scaling a reusable SQL standard library broke text-level preprocessing. Perfetto's standard library grew to hundreds of SQL modules that needed module imports (INCLUDE PERFETTO MODULE), typed materialized tables and functions (CREATE PERFETTO TABLE, CREATE PERFETTO FUNCTION), and parameterized macros (CREATE PERFETTO MACRO) because SQL functions cannot accept tables or expressions as arguments. Early versions split statements and expanded macros with ad-hoc text scanning before handing the result to SQLite. That brittle preprocessing tripped over comments, string literals, and nested subqueries, and macro substitution shifted character offsets so SQLite errors pointed into generated text instead of the author's file and line. Calling SQLite's internal parser was not an option either: SQLite emits VDBE bytecode directly inside grammar actions and never exposes a syntax tree. Generating a full AST parser from SQLite's grammar plus PerfettoSQL extensions solved syntax extensions and multi-layer error tracebacks cleanly.

Second, multi-stage analytical queries hit SQLite's row-at-a-time virtual-table wall. As Trace Processor internals covers, trace data lives in dense columnar dataframes rather than SQLite B-trees. SQLite's virtual-table API pushes single-table filters down into a dataframe cleanly, so simple scans are fast. Multi-step analysis is different: joins, expressions across views, hierarchical slice rollups, and sorts pull intermediate rows across virtual-table callbacks one row and one column cell at a time through the VDBE interpreter. Standard SQL also forces multi-step queries to read inside-out as nested subqueries. Adding GoogleSQL-style |> pipe syntax (gated for user queries behind PERFETTO PRAGMA pipelines = 1) lets analysts write top-to-bottom dataflow queries while Trace Processor compiles the whole multi-stage pipeline onto its own C++ columnar executor, processing up to 2,048 rows per batch.

Because every statement passes through Perfetto's parser first, the root node of its AST cleanly selects one of three execution routes (Figure 1): plain SQL forwards to SQLite, PerfettoSQL catalog statements execute in C++, and |> pipelines compile into a C++ batch plan wrapped in a single bridge virtual-table call.

Part I · Parsing

1The tokenizer reuses SQLite's lexical rules and cuts text into typed byte spans

Part I explains how Perfetto turns raw SQL text into a compact syntax tree without breaking compatibility with SQLite's dialect or allocating thousands of tiny heap objects per script. Parsing starts with lexical analysis because any mismatch in quoting, identifier rules, or numeric literals between Perfetto's front-end and SQLite's own parser would cause plain SQL queries to parse one way in Perfetto and fail inside SQLite.

A tokenizer (or lexer) scans raw bytes into flat tokens: keywords, identifiers, numbers, string literals, operators, whitespace, and comments. Each token carries a small integer type ID plus the half-open byte range it came from. The tokenizer checks zero grammar structure—it will happily emit FROM FROM FROM and leave structural validation to the parser.

To match SQLite byte for byte, syntaqlite reuses SQLite's hand-written tokenizer directly. A generated header defines one constant per token type. The Perfetto dialect (SQLite's base grammar plus PerfettoSQL's additions, Section 3) defines 207 token types, twenty more than stock SQLite (exact counts are in What Lemon generates).

Keywords are found by looking up words that look like names. A word like TREE is a keyword in this dialect. It can still be used as a column name, thanks to the parser's fallback rule (Section 4).

2A Lemon grammar defines valid syntax, and an LALR(1) state machine parses it bottom-up

Hand-writing a recursive-descent parser for SQL is a trap: SQLite's dialect has hundreds of productions with subtle precedence interactions across NOT, BETWEEN, CASE, joins, and bitwise operators, and SQLite already maintains its authoritative grammar in a Lemon file (parse.y). Layering PerfettoSQL onto that same Lemon grammar guarantees identical operator precedence and forces the parser generator to prove at build time—not when a user runs a query—that new rules introduce no ambiguities.

A grammar specifies which token sequences form valid statements and how they group into phrases. Each rule (or production) has a left-hand nonterminal—a composite phrase such as perfetto_pipe_stage—and a right-hand sequence of nonterminals and terminals (leaf token types such as ORDER). In Lemon syntax:

perfetto.y// a pipe stage can be ORDER BY followed by an order list
perfetto_pipe_stage(A) ::= ORDER BY perfetto_pipe_order_list(L). {
    A = synq_parse_perfetto_pipe_order_by(pCtx, L);
}

The letters in parentheses bind each symbol's semantic value, the C value carried on the parser stack. The C block is the rule's action: it runs as soon as the rule matches and computes the left-hand nonterminal's value—here the integer handle of a newly constructed AST node.

Because each action chooses what to record, the AST keeps semantic meaning and discards syntactic scaffolding. A raw parse tree would allocate a node for every intermediate grammar rule and keep every keyword token as a leaf. Downstream compilers only care about "an ORDER BY stage with this list of sort terms". The action above allocates one PerfettoPipeOrderBy node and drops both keywords, while the rule matching |> allocates no node at all (Section 4).

How does the generated parser match rules in a single left-to-right pass without backtracking? Lemon builds a bottom-up LR parser that maintains an explicit stack of symbols it has partially matched. At each step it chooses between two moves:

  • Shift: push the next input token onto the stack because the current phrase is not complete yet.
  • Reduce: when the symbols at the top of the stack match a rule's right-hand side, pop them off, execute the rule's C action, and push the resulting left-hand nonterminal in their place. Because inner phrases reduce before outer phrases, children always exist before their parent node is built.

A precomputed finite state machine picks between shifting and reducing in constant time. Each state encodes the set of grammar rules that remain viable given the stack prefix so far. To choose its move, the state machine inspects the current state and one unconsumed lookahead token—the "(1)" in LALR(1). LALR (Look-Ahead LR) keeps the table compact by merging parser states that track the exact same grammar positions and differ only in which lookahead tokens can follow. Full canonical LR tables can explode to tens of thousands of states on SQL; LALR compresses Perfetto's entire dialect into under eight hundred states (Figure 5) while still accepting SQLite's grammar cleanly.

If one token of lookahead cannot distinguish two valid parses for the same state—either shifting vs reducing, or reducing by two different rules—Lemon reports a conflict when generating the parser, never at query run time. Standard expression ambiguities (such as whether a + b * c reduces + first or shifts *) are resolved declaratively via precedence directives (%left, %right).

Lemon turns the grammar into tables and a small C driver

Nobody builds these state machines by hand: SQLite's has several hundred states. A parser generator reads a grammar and writes the parser for it. Lemon is SQLite's own parser generator, and SQLite's grammar lives in parse.y. Lemon computes the LALR states and reports conflicts. It then writes one C file with the parse tables, which are the state machine as compressed arrays, plus a driver function that walks them. The generated syntaqlite_perfetto.c has the usual Lemon pieces:

Two Lemon directives matter later. %fallback ID A B C. says: if token A cannot be shifted here, retry it as an ID. %wildcard ANY. declares a symbol that matches any token. It sits in SQLite's base grammar, and Perfetto uses it to swallow macro bodies (Section 4). Every action also receives a context argument, pCtx, a SynqParseCtx*. It owns the node storage (the arena, Section 3) and the parse flags.

What it means for you A grammar change is a table change. Adding one rule can shift every state number. That is why nobody edits the generated C by hand, and why it is checked in whole. If Lemon reports a conflict, the new rule is ambiguous with an existing one under one token of lookahead. Fix the grammar, not the action code.

3syntaqlite replaces SQLite's inline bytecode actions with a typed syntax tree

Why couldn't Trace Processor simply call SQLite's own parser? Inside stock SQLite, grammar actions in parse.y never materialize a standalone AST: they populate internal symbol tables attached to a Parse struct and emit VDBE opcodes on the fly. Trace Processor needs an explicit tree to dispatch PerfettoSQL statements, compile pipelines, track macro spans for error tracebacks, infer query schemas statically, and auto-format SQL files. syntaqlite fills that gap: it pairs SQLite's base tokenizer and grammar with generated C actions that construct typed AST nodes, and lets projects layer a custom dialect—extra rules, node types, and keywords—on top.

Perfetto's dialect lives in two hand-written files under src/perfetto_sql/syntaqlite/. The syntaqlite generator merges them with its bundled SQLite base grammar and emits one self-contained C file plus a header, both checked into the repository so normal builds need no external tool.

Build details: the BUILD.gn next to these files compiles the pair into the syntaqlite source set (GN's name for a group of compiled sources). Standalone builds also make perfetto_fmt_dialect, a shared library that the syntaqlite fmt --dialect tool loads to format .sql files. inline_dispatch.h replaces the dialect's function pointers with direct calls on the hot path.

Each node in the .synq file declares its fields and how to print them. An index field holds the ID of another node. An inline field holds a value directly, usually an enum or a byte range into the source. The matching grammar rule calls the generated builder for that node, synq_parse_<node>():

For example, abstract PerfettoPipeStage lists the eleven stage nodes: PerfettoTreeAccumulate, PerfettoIntervalFlatten, PerfettoIntervalFillGaps, PerfettoPipeOrderBy, PerfettoPipeAggregate and six projections. semantic { … } blocks feed syntaqlite's own analysis. For example, define_table on CreatePerfettoTableStmt tells that analysis the statement defines a table.

Tree nodes pack into a per-statement arena, avoiding per-node heap allocations

Loading the standard library parses hundreds of SQL statements in sequence, each producing dozens of short-lived AST nodes that become garbage the moment the statement finishes. Heap-allocating every node individually would thrash the allocator and waste memory on 64-bit pointers. Instead, syntaqlite appends all nodes for the current statement into one contiguous buffer—an arena—and resets the write cursor before parsing the next statement. Nodes reference children by 32-bit node ID within the arena rather than raw pointers, using SYNTAQLITE_NULL_NODE (0xFFFFFFFF) for absent optional fields. Lists are flat arena nodes too (a tag, a count, and a trailing array of child IDs), and identifiers stay as zero-copy byte spans (SyntaqliteTextSpan) pointing straight into the input buffer.

Resetting the arena after every statement bounds parser memory by the largest single statement rather than the length of a multi-thousand-line script. The lifetime rule is strict: any pointer returned by syntaqlite_parser_node(p, id) is invalidated as soon as syntaqlite_parser_next() advances.

What it means for you C++ code reads the tree by casting. Node<SyntaqlitePerfettoPipeOrderBy>(parser, id) in pipeline/compiler.h is a static_cast of syntaqlite_parser_node(). Anything that needs the tree, such as pipeline compilation, must finish before the parser moves on to the next statement.

4Four grammar techniques add keywords and pipes without breaking existing SQL

Extending a production SQL dialect carries a sharp backwards-compatibility hazard: reserving twenty new keywords or repurposing | and > would immediately break existing queries that name columns per, up, or tree, or compute bitwise OR in expressions. Four targeted techniques in perfetto.y keep existing SQL working without forking SQLite's tokenizer.

New keywords still work as names

perfetto.y// Allow extension keywords to be used as regular identifiers.
%fallback ID PERFETTO FUNCTION MODULE RETURNS MACRO DELEGATES INCLUDE
          TREE ACCUMULATE UP DOWN INTERVAL INTERSECTION PER EXTEND FLATTEN
          AGGREGATE FILL GAPS.

Every new keyword risks breaking queries that use the word as a name, like a column called per or up. Fallback makes Lemon retry such a token as a plain name whenever the current state has no action for it. So the word acts as a keyword only where a rule expects it.

The pipe is two tokens that must touch

perfetto.yperfetto_pipe(A) ::= BITOR(B) GT(G). {
    if (B.layer_id != G.layer_id || B.offset + B.n != G.offset) {
        pCtx->error = 1;
    }
    A = 0;
}

The tokenizer has no |> token, so the grammar accepts BITOR followed by GT. The action then rejects the pair unless the two characters are next to each other and come from the same layer. A layer is one piece of source text or one macro expansion (Section 5).

Reusing the bitwise OR character has a cost, as the comment above the rule says. An expression may end in |, so nothing that ends in a bare expression may come right before a pipe. That is why a pipeline's FROM source is only a table or a subquery in parentheses. A join's ON expression would be ambiguous: in a JOIN b ON a.x = b.y |> …, the | could continue the expression as a bitwise OR. It is also why an ORDER BY term gets the precedence of BITNOT, the ~ operator, which binds tighter than |. So a term ends at |.

Empty rules mark exact positions

An empty rule (X ::= .) matches nothing, but Lemon must reduce it at one exact point in the input. That makes it a hook for running code at that point.

perfetto.yselect_body_start(A) ::= . { A = pCtx->cur_shift_start; }
select_body_end(A)   ::= . { A = pCtx->last_shifted_end; }

cmd(A) ::= CREATE perfetto_or_replace(R) PERFETTO TABLE nm(N)
           perfetto_table_impl(I) perfetto_table_schema(S)
           AS select_body_start(BS) select(E) select_body_end(BE). {
    SyntaqliteTextSpan select_span = {
        .offset = BS, .length = BE - BS, };
    ...
}

select_body_start/end bracket the body of CREATE PERFETTO TABLE/VIEW/FUNCTION. They record its exact source span, without leading whitespace.

before_macro_body sits just before AS in CREATE PERFETTO MACRO. Reducing it increments pCtx->in_macro_def_body. While that is set, the tokenizer does not expand nested macro calls. So the body is captured as written, through the ANY wildcard. The macro's cmd action decrements the counter again.

Aliases always need AS

A pipe alias (perfetto_pipe_alias) is either empty or AS nmorerr, meaning a name or Lemon's built-in error symbol. The error symbol lets the parser recover from a bad name. A bare alias would let a fallback keyword be read as a name. In FROM t PER cpu, PER would become the alias of t. The AliasNeedsAs test in perfetto_sql_connection_unittest.cc checks that FROM t x |> … is a syntax error.

What it means for you Write |> without a space, and alias with AS. Wrap a join in a subquery before piping it. A top-level a | b in an ORDER BY term needs parentheses.
Part II · PerfettoSQL statements

5Token-layer macros parameterize SQL queries while keeping source-line tracebacks

Part II explains how PerfettoSQL scales reusable SQL libraries with macros, module imports, and typed catalog objects while preserving exact error locations. Standard SQL hits a composition wall in a large standard library: views take zero arguments, and scalar or table-valued functions accept runtime values—never a table name, a subquery, or an arbitrary SQL expression. Trace modules repeatedly need structural templates such as "compute cumulative callstack counts over whichever table of sample callsites the caller supplies".

PerfettoSQL solves this with macros whose parameters carry syntactic kinds such as Expr or TableOrSubquery. Calls use Rust's name!(arg, …) syntax (selected via --macro-style rust) so macro invocations never collide with SQL function calls, and each $param in the body expands to the argument's token stream:

stdlib/stacks/cpu_profiling.sqlCREATE PERFETTO TABLE _cpu_profiling_callstacks AS
FROM _callstacks_for_callsites!((SELECT callsite_id FROM cpu_profiling_samples))
|> TREE ACCUMULATE UP SUM(self_count) AS cumulative_count;

Why not run a C-style text preprocessor over the script before parsing? Whole-file text substitution loses token boundaries and scrambles byte offsets: a column typo inside a caller's argument ends up reported deep inside generated macro text. Instead, syntaqlite expands macros inside the tokenizer during the single parse pass. Whenever the tokenizer sees name!(…), it invokes Perfetto's callback (PerfettoSqlParser::Impl::LookupMacro, Figure 9) and pushes the expanded tokens onto the input stream as a numbered layer: layer 0 is the author's original text, and macro expansions get layers 1 and up.

Step 3 leaves alone any $name that is not one of the macro's parameters. SQLite then sees it as a bind variable, a placeholder whose value is supplied when the statement runs. That is how a CREATE PERFETTO FUNCTION body receives its arguments.

Errors map back through every expansion to the text you wrote

SQLite only ever sees the expanded text, so its error offsets point into text the user never wrote. For example, it may report "no such column" at some byte offset of the expansion. Perfetto's SqlSource solves this. It is a string that remembers where each part came from. SqlSource::Rewriter builds a new one by replacing byte ranges with other sources, and keeps the originals as a tree. AsTraceback(offset) walks that tree back to file, line and column. The result is a traceback: the list of locations from the error, through each macro call, to the text you wrote.

RewriteTree, a class in perfetto_sql_parser.cc, rebuilds that tree from the rewrite records syntaqlite kept for the statement (syntaqlite_result_rewrite_at). Each record is one replacement. It points at its parent: the index of the record it sits inside, or SYNTAQLITE_REWRITE_PARENT_SOURCE if it sits directly in the original source.

Two details keep this cheap. NodeSource returns the source text of one AST node. If a statement had no rewrites at all, it returns a plain substring. Otherwise it asks syntaqlite_node_is_macro_free() for each node, and builds the tree only for nodes that span an expansion. Calls that arrive through an argument are tagged SYNTAQLITE_MACRO_BODY_CALL_ARG_INTERNAL and handled by BuildForArg.

6Root-tag dispatch routes each statement to SQLite, C++ catalog handlers, or the pipe compiler

SQLite understands SELECT, CREATE VIEW, and virtual-table queries, whereas module imports (INCLUDE PERFETTO MODULE), materialized dataframe tables (CREATE PERFETTO TABLE), runtime column indexes, macros, and |> pipelines exist only in Trace Processor. Rather than regex-matching statement prefixes—which breaks on leading comments, CTEs, or macros—Trace Processor dispatches off the AST's root node.

PerfettoSqlParser drives the syntaqlite parser one statement at a time. Each call to Next() advances syntaqlite_parser_next() past comment-only empty statements until a root node appears, reconstructs the macro rewrite tree, and materializes statement_sql() as the expanded SQL string.

ParseStatement then switches on the root node's tag (its leading enum field) and returns a PerfettoSqlParser::Statement—a std::variant with one alternative per route. Any standard SQLite root tag falls through to SqliteSql{}.

PerfettoSqlConnection::ProcessFrame runs the loop, with one branch per route. Plain SQL is prepared directly, in the branch marked PERFETTO_LIKELY, a compiler hint that this is the common case. A pipeline has its own branch: its plan, compiled during parsing, goes to PreparePipeline (Section 10). The running example takes this route, because its root tag is SYNTAQLITE_NODE_PERFETTO_PIPELINE. Other extension statements go through ResolveExtensionStatement, which runs them in C++. It then returns a dummy statement, because the rest of the loop always expects "the current prepared statement".

The check is SetPipelinesAllowed(builtin || pipelines_enabled_), called on each frame's parser before every statement. builtin is true for a standard library module, and pipelines_enabled_ is set by the pragma.

What it means for you Syntax errors in any statement come from syntaqlite, with a traceback into your text. Name and type errors in plain SQL, such as "no such column", come from SQLite's second parse of the expanded text. They are mapped back through the SqlSource tree. Statements take effect one at a time, in order, so a macro or module is visible only to the statements after it.
Part III · Pipelines

7Pipe syntax aligns queries with dataflow and unlocks multi-stage batch execution

Part III follows |> pipelines from syntax to execution. Pipelines exist to fix two mismatches at once: how multi-step analytical queries are written, and how Trace Processor executes them.

First, plain SQL writes multi-step transformations inside-out: FROM sits in the middle, and each subsequent step wraps the previous query in another subquery or CTE. Trace analysis also leans heavily on hierarchical and interval operations—rolling durations up a parent-child slice tree or intersecting time intervals per CPU—that plain SQL expresses awkwardly or not at all. Second, even when a multi-stage query can be written in SQL, SQLite executes joins, views, and aggregations row by row through VDBE bytecode, crossing virtual-table callbacks once per cell. A pipeline writes a source followed by top-to-bottom |> stages in dataflow order, giving Trace Processor a self-contained multi-stage plan it can execute end to end on columnar batches in C++.

A stage is also called a pipe operator. Three layers below use similar words for it, so Figure 13 keeps them apart.

A pipeline is either a statement on its own (cmd ::= perfetto_pipeline) or the body of CREATE PERFETTO TABLE … AS. It cannot appear inside a SELECT. User SQL must first run PERFETTO PRAGMA pipelines = 1;, or compilation fails with "Pipelines are not enabled". Standard library modules may always use pipes (builtin || pipelines_enabled_).

The compiler is deliberately narrow today:

  • Every place that takes an expression accepts only a column reference. ResolveColumnExpr rejects "an expression other than a column".
  • SELECT and EXTEND items are columns or stars. There are no computed columns yet.
  • TREE ACCUMULATE supports only SUM (ResolveSum). INTERVAL FLATTEN also allows COUNT(*).
  • ORDER BY rejects string columns.
  • A pipeline outputs at most 256 columns (kMaxPipelineColumns).

8The compiler separates mutable column names from immutable dataflow values

As rows move down a pipeline, the visible schema keeps mutating: SELECT drops columns, RENAME and AS rebind names, TREE ACCUMULATE appends new columns, and interval intersections expose operand columns only under table aliases (x.ts vs bare region ts). If every rename or column projection emitted a physical copy step, readable pipelines would pay runtime overhead just for tidying up names. The pipeline compiler solves that at compile time by resolving every mutable name into a stable numeric value ID once, before any execution plan runs.

pipeline::Compile(parser, pipeline_node, source_fn, catalog) runs inside ParseStatement while the arena AST is still alive, so invalid column names or unsupported constructs fail immediately at parse time with an exact source traceback. The catalog lets it look up registered relations (tables and views) and finalized dataframes.

Compilation emits a logical plan (LogicalPlan): a tree describing what relational work to perform, independent of physical executor operators. Each PlanNode wraps one PlanOperation plus the IDs of its child nodes, with the final stage at the root and sources at the leaves. For our running example, the logical plan has just two nodes: Scan(slice) feeding OrderBy(ts).

As the Compiler class comment states, "adding a plan node does not change the visible row, and changing the row does not add execution work". The compiler enforces that split with two distinct structures:

  • Immutable values live in the plan: AddColumn(name, type) allocates a monotonic ColumnId that never changes, and every PlanOperation references inputs and outputs solely by ColumnId.
  • Mutable names live in Scope: an ordered list of currently visible columns (name + ColumnId), plus frozen snapshots of that list saved whenever AS alias binds a relation alias.
compiler.h (shape)// Scope::row, one entry per visible column
RowColumn{NamedColumn{name, id}, operation, node, qualified_only}
// Scope::aliases, a snapshot of row per alias

So RENAME, DROP and SELECT edit the row and add nothing to the plan. That is why their registrations have no encoding: they never appear in the plan's byte form (Section 10). qualified_only exists for intersections. Operand columns are reachable as x.ts but not as a bare ts, so a bare ts always means the region.

The registry of operations is a flat array in operation_registry.cc:

operation_registry.ccconst OperationRegistration* const kOperations[] = {

The tag comments are added here. Each tag is the first argument of OperationRegistration::Encoding{…} in the operation's .cc file. An encoding tag is the number that identifies the operation when the plan is written out as bytes (Section 10).

A table source is read straight from its dataframe only in one case. The name must be unqualified and found in the catalog, and the dataframe must be finalized, meaning complete and no longer being built (Scan::FindDirectDataframe). Anything else, including views and subqueries, becomes a SQL scan. Its columns and types come from analysis::RelationAnalyzer in src/perfetto_sql/analysis, without running the SQL. The running example is a SQL scan, because slice is a CREATE PERFETTO VIEW over __intrinsic_slice (stdlib/prelude/after_eof/views.sql).

9Backward liveness pruning drops unread columns and dead stages before execution

Trace views are wide while analytical answers are narrow: slice exposes fifteen columns, yet a query often keeps only two or three. Carrying every source column through a pipeline wastes memory bandwidth in every batch, sort, and hash table—and when a source is a SQL view, SQLite would first have to copy every unread column cell by cell into a temporary dataframe (Section 10). Column pruning eliminates dead columns—and any stage whose outputs nobody reads—via a backward liveness pass right after compilation.

Immediately after building the plan, Compile runs PruneColumns(plan). It seeds a needed bitvector from plan.output() and walks backwards from the root toward the leaves. Each operation's Prune(needed) drops any outputs that are unmarked, marks all input ColumnIds required to compute its surviving outputs, and returns either nullopt ("keep this stage") or a child index ("all my outputs are dead; splice me out and replace me with that child").

The running example prunes nothing, because it has no SELECT and every slice column is output. Figure 15 uses the tree query from Section 8 instead, whose SELECT id, t keeps two columns.

column_pruning.ccPlanNodeId PruneNode(LogicalPlan& plan, PlanNodeId id, std::vector<bool>& needed) {
  PlanNode& node = plan.nodes()[id];
  if (std::optional<uint32_t> child = node.operation().Prune(&needed)) {
    return PruneNode(plan, node.children()[*child], needed);
  }
  for (auto& child : node.children()) child = PruneNode(plan, child, needed);
  return id;
}

10A synthetic table-valued function bridges compiled pipelines back into SQLite

Why route a compiled C++ pipeline back through SQLite at all instead of returning batches directly? Every external caller—the Perfetto UI, Python bindings, trace_processor_shell, and CREATE PERFETTO TABLE … AS pipeline—consumes query results through SQLite's prepared-statement cursor API, and pipelines can read SQLite views or subqueries that only SQLite knows how to evaluate in the current scope. Wrapping the compiled plan in one synthetic SELECT over __intrinsic_pipeline preserves full SQLite composability while keeping multi-stage execution inside C++.

__intrinsic_pipeline is an eponymous virtual table: SQLite lets queries call it directly as a table-valued function in a FROM clause without a prior CREATE VIRTUAL TABLE statement. SelectPipelineSql(plan) constructs the bridge query in three steps:

  1. SQL scans become arguments. Each one becomes a numbered argument: a small query that collects its rows into a dataframe. The dataframe reaches the pipeline as a tagged C pointer that only the pipeline can read. The query runs where the pipeline was written, so it sees the views in scope there. Code: MoveSqlSourcesToDataframeArgs (leaves Scan::DataframeArg{i}), DataframeAgg, sqlite3_result_pointer with tag "PIPELINE_DATAFRAME".
  2. The plan becomes bytes. SerializePlan writes each source and stage as its encoding tag plus a payload. Columns are referred to by position. The bytes become a hex blob literal, X'…'.
  3. Both go into one SELECT. The result is SELECT c0 AS "id", c1 AS "t" FROM __intrinsic_pipeline(X'…' [, (SELECT __intrinsic_dataframes(…))]). The inner SELECT makes SQLite build the dataframe list once. Otherwise it would be rebuilt on every call to the virtual table's Filter callback, which starts a scan.

For the running example, with the column lists shortened, SQLite actually prepares this statement:

shape, simplified: output of SelectPipelineSql for FROM slice |> ORDER BY tsSELECT c0 AS "id", c1 AS "ts", c2 AS "dur", …
FROM __intrinsic_pipeline(
  X'…',                                  -- serialized plan: Scan(argument 0), OrderBy(ts)
  (SELECT __intrinsic_dataframes(
     (SELECT __intrinsic_dataframe_agg('id,ts,dur,…', "id", "ts", "dur", …) FROM slice))))

11Lowering translates logical operations into physical batch steps and elides redundant work

In compiler design, lowering translates a high-level logical plan ("what result is required") into a concrete physical execution plan ("which operators run on which buffer slots"). Separating the two pays off at run time because physical properties of the input data—whether a dataframe column is already sorted, whether tree topology columns have already been computed, and what runtime types a SQL view actually produced—are only known once dataframes are bound. Tracking those properties lets lowering skip redundant sorts, share tree-preparation passes across adjacent stages, and fuse stateless steps in place.

pipeline::Lower(plan) produces a PhysicalPlan: a batch source (core::exec::Source), a sequence of execution steps, and the final batch-column slot for each output column. As Lowering walks the tree bottom-up, it assigns batch column slots (Define(id)) and maintains three physical invariants:

  • Order: which columns the rows are grouped by, and which ascend within a group. Scan::Lower marks every dataframe column whose sort state is not Unsorted as ascending. SortRows then skips the sort for a single ascending key, with no grouping, that is already ascending.
  • Tree columns (TreeColumns): PrepareTree adds TreeNumberNodes once. It adds TreeChildFirst (UP) or TreeParentFirst (DOWN), which reorder rows so children come before parents or the reverse, only when the direction changes. So back-to-back TREE ACCUMULATE stages share them.
  • Types: RequireInt64 adds an AssertType step only when a column's type is unknown and not yet checked.

The executor, in src/trace_processor/core/exec/, is pull-based. The consumer asks for the next batch, and each step asks the one before it. It has three kinds of node:

Source

Produces batches: DataframeScan, IntervalIntersect, and Pipeline itself.

Transform

Changes a batch in place and never holds rows back, so nothing is copied or buffered: AssertType, TreeNumberNodes, TreeAccumulateUp/Down.

Operator

Reads an input batch into a separate output batch. So it may keep rows, which Finish emits after the last input, or emit several outputs per input. Examples: TreeParentFirst, IntervalFlatten, and the breakers below.

A breaker, short for pipeline breaker, is an Operator that must read all of its input before it can emit anything. Sort, GroupBy and TreeChildFirst are breakers. Everything before a breaker streams. Nothing after it starts until its input runs out.

A Pipeline is a list of steps, and each step is a Transform or an Operator. It cuts the list into segments at each Operator, and a segment's Transforms run on the batch in place. Batches hold at most 2048 rows (kMaxBatchRows in core/exec/selection.h). Figure 17 shows segments and breakers together in a longer query.

core/exec/pipeline.h (shape)std::vector<Step>  // Step = std::variant<std::unique_ptr<Transform>, std::unique_ptr<Operator>>

The running example sorts its whole input before SQLite sees the first row

The running example pays for a full sort, because its input comes through a view and arrives unsorted. When SQLite starts the generated statement, it first evaluates the argument subquery. There DataframeAgg reads every row of the slice view into a temporary dataframe. PipelineModule::Filter then calls LoadPipeline. That decodes the blob, binds the dataframe to the scan, and lowers the plan to DataframeScan → Sort(ts).

The sort is not skipped, because DataframeAgg builds with analyze = false: it does not inspect the columns it copies, so it marks none as sorted. Reading __intrinsic_slice directly would skip it, since its ts column is declared SORTED in tables/slice_tables.py.

Still inside Filter, the RowCursor opens and pulls its first batch. Sort pulls every batch from the scan, sorts, and serves its first output batch. So the whole sort happens before SQLite sees row one. Each SQLite step then calls PipelineModule::Next, which moves the cursor one row and pulls a new batch when needed. Column reads the value of output column cN from the current batch. The outer SELECT c0 AS "id", … returns it to the caller as an ordinary result row.

What it means for you Put ORDER BY where the data is already in that order, or last. Only a table read directly keeps its sort information. A view or subquery arrives unsorted, so ordering it costs a full sort. Put TREE ACCUMULATE stages of the same direction next to each other, so they share one numbering and one tree sort. Select only the columns you need, because pruning reaches all the way to the scan.
Part IV · Extending

12Self-contained operator registrations keep new pipe stages to roughly five files

Part IV walks through extending the pipeline engine. If adding a domain-specific trace operator required editing central switch statements across the compiler, pruner, wire serializer, and physical planner, the experimental pipe engine would quickly ossify. Instead, every stage implements one PlanOperation interface and plugs into a flat registry via a static OperationRegistration struct—confining a new operator to roughly five files of focused work.

Every stage touches the same seven checkpoints: AST declaration, grammar production, plan operation, registry entry, lowering, batch execution, and tests. ORDER BY is the smallest end-to-end stage that exercises all seven, while TREE ACCUMULATE is the reference template for a stage that appends new columns.

1–2 · Syntax

Add a node to perfetto.synq with its fields and fmt block, and list it in abstract PerfettoPipeStage. In perfetto.y, add a perfetto_pipe_stage(A) ::= … rule that calls the generated synq_parse_… builder. Put any new keyword in the %fallback ID … line, so existing queries that use the word as a name keep parsing. Remember Section 4: a stage that ends in an expression must not let it swallow the next |. Then run tools/gen_syntaqlite_parser and commit the regenerated syntaqlite_perfetto.{c,h}. It needs the prebuilt tool from tools/install-build-deps --syntaqlite.

3 · The plan operation

Subclass PlanOperation and give it a static registration. The registration ties together the AST tag, the builder and the wire encoding:

    SYNTAQLITE_NODE_PERFETTO_PIPE_ORDER_BY, &BuildPlan,
    OperationRegistration::Encoding{4, /*is_source=*/false, &DecodePlan}};

base::Status OrderBy::BuildPlan(Compiler* c, uint32_t stage) {
  c->SetOperation("ORDER BY");                     // label for error messages
  const auto* n = Node<SyntaqlitePerfettoPipeOrderBy>(c->parser(), stage);
  const auto* terms = Node<SyntaqlitePerfettoPipeOrderTermList>(c->parser(), n->terms);
  OrderBy order;
  for (uint32_t i = 0; i < syntaqlite_list_count(terms); ++i) {
    const auto* term = Node<SyntaqlitePerfettoPipeOrderTerm>(
        c->parser(), syntaqlite_list_child_id(terms, i));
    ASSIGN_OR_RETURN(ColumnId id, c->ResolveColumnExpr(term->expr));
    const auto& type = c->plan().columns()[id].type;
    if (type && type->Is<core::String>())
      return c->Unsupported(term->expr, "ordering by a string column");
    order.keys_.push_back({id, term->sort_order == SYNTAQLITE_SORT_ORDER_DESC});
  }
  c->AddNode(std::move(order), {c->plan().root()});   // new root, reads the old root
  return base::OkStatus();
}

A stage that produces values follows TreeAccumulate::BuildPlan, in this order:

  1. Resolve all inputs against the incoming row.
  2. Allocate each output with c->AddColumn(name, type).
  3. Add each output to the row with c->Append(NamedColumn{name, id}, ast_node).
  4. Only then call AddNode.

Report problems with c->Unsupported, c->Expected or c->Err, so they carry a traceback to the AST node. The remaining virtual methods, as OrderBy implements them:

4 · Registration and encoding

Add the files to operations/BUILD.gn, and add &MyOp::kRegistration to kOperations[]. Pick an unused encoding tag (Section 8), because tags 0 to 4 are taken. The comment in operation_registry.h says the tag is "independent of registration order", so array order does not matter. But if two tags are equal, FindOperationByTag returns the first. A stage that only renames or drops columns needs no plan node and no encoding. Register it with std::nullopt, like projection::kDrop.

Land syntax and compiler together A stage that parses but has no registration and no special case crashes Trace Processor, as Figure 20 shows. In this revision PerfettoPipeAggregate is in the grammar with neither a registration nor a special case. So a well-formed |> AGGREGATE … reaches the fatal path. If the grammar lands first, add an Unsupported case next to the FILL GAPS one.

5–6 · Lowering and the executor

Reuse the Lowering helpers before writing an executor:

  • SortRows for ordering.
  • PrepareGroups(keys, ascending) for per-partition work, as IntervalFlatten does.
  • PrepareTree for tree work, and RequireInt64 for type checks.

Then call AddOperator(std::make_unique<ex::MyStep>(spec)) with batch positions from Position(id). Call Define(output_id) for each appended column, in append order. If the step reorders or replaces rows, update what Lowering knows. Either call SetOrder, or call ResetLayout and re-Define the surviving columns, as IntervalFlatten::Lower does.

A new executor goes in src/trace_processor/core/exec/. Pick the base class by how the step treats rows:

Keep the node const, and put run state in an OperatorState from MakeState(). As operator.h says, "a plan can be run more than once or concurrently".
