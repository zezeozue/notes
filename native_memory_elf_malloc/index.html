Native memory on Android: where each page in smaps comes from

This note explains native memory on Android from the page up. It covers how the kernel hands out memory and how a shared library is laid out. It follows linker64, Android’s dynamic linker, from dlopen() to your first call. It then shows how Scudo, the default allocator in bionic (Android’s C library), turns pages into malloc blocks. After reading it you should be able to look at a line in /proc/pid/smaps and say where it came from and why it costs what it does.

Code excerpts and constants are from AOSP as of Android 17 (bionic/, external/scudo/ and frameworks/base/). ELF numbers are illustrative: they come from readelf on the arm64 libhwui.so of one platform build (“this build” below), and exact sizes and counts vary from build to build. Excerpts marked shape are simplified. Cost tiers are rough orders of magnitude, not measurements.

At a glance

  • Reserving address space is free. RAM is used only when a page is first touched.
  • Shared pages stay shared until someone writes to them. Writing one byte costs a whole private page.
  • Loading a library writes addresses into its pointer tables. Those pages become private memory in every process, unless the zygote or WebView shares them.
  • On Android, malloc is Scudo. It groups small blocks by size, checks every free, and fences large blocks with guard pages.
  • Freeing memory lowers RSS only when a whole page is empty, and Scudo waits a moment before giving pages back.

Terms used throughout, defined once:

  • VMA (virtual memory area): one address range in a process, with permissions and a backing, either a file or nothing.
  • Page fault: the trap into the kernel when a process touches a page that has no RAM behind it yet.
  • Clean pages still match their file and can be dropped. Dirty pages were written and cannot.
  • RSS: every page of a process that is currently in RAM, with shared pages counted in full.
  • PSS: a process’s memory with each shared page split between the processes that map it.
  • Zygote: the pre-initialised process that every app is forked from, so apps start with its memory already set up.
  • Relocation: a note telling the dynamic linker to write an address into a library once it knows where the library landed.
  • RELRO: the part of a library the linker writes during loading and then makes read-only.

Three layers explain almost every native-memory question

Native memory has three layers. Each layer builds on the one below.

  1. Virtual address space. Each process has a list of VMAs. Creating one is cheap and uses no RAM.
  2. Pages. The kernel hands out RAM one page at a time, on first touch. Pages backed by the same file are shared between processes until someone writes to them.
  3. User-space sub-allocators. The kernel only deals in whole pages. linker64 maps page-aligned slices of library files. malloc carves anonymous pages, which have no file behind them, into small blocks. It gives empty pages back with madvise, a syscall that tells the kernel it may take them away.

Staying in user space is cheap. Entering the kernel or touching a new page is far slower. Figure 1 puts the operations this note covers side by side.

Part I · Pages

1Reserving address space is free, touching it costs RAM

Virtual memory lets the kernel do three things at once. It keeps processes out of each other’s memory. It lets them ask for far more memory than they will touch. And it shares one copy of common code between all of them.

Every load and store uses a virtual address. The CPU’s MMU (memory management unit, the hardware that does the translation) maps it to a physical address through per-process page tables. The user address space runs to hundreds of gigabytes or more, depending on how the kernel is configured (Figure 3). The hardware also ignores the top byte of a pointer (TBI, top-byte ignore). That is what lets Android store tags there (Section 10).

Translation works one page at a time. A page is 4 KiB, or 16 KiB on devices built for larger pages. The low bits of an address pass through unchanged. The rest select a page-table entry (PTE), which either points at a physical page or is not present.

Asking for memory only creates a VMA. mmap(NULL, 1 GiB, PROT_READ|PROT_WRITE, MAP_PRIVATE|MAP_ANONYMOUS, -1, 0) does not allocate a gigabyte. It records one VMA saying “this range is valid, read-write, anonymous” and returns. The PTEs stay empty.

The first store to a page traps into the kernel. This trap is a page fault. The kernel finds the VMA, takes one zeroed physical page, fills in the PTE and resumes the store.

That is a minor page fault: no I/O, only kernel work. A major fault has to read the page from storage first. A read of untouched anonymous memory is cheaper still. The kernel can map its single shared, read-only zero page, and allocates a real page only on the first write.

Pages come in two kinds. File-backed pages hold file contents and live in the page cache, the kernel’s in-RAM cache of file data. Every process that maps the same file shares those pages, and a clean one can be dropped and read back later.

Anonymous memory has no file behind it: heap, stacks, and globals once written. Android has no swap partition. So the only way to reclaim it without killing the process is zram, a compressed swap device that lives in RAM.

This is why VSZ (virtual size) in top is huge on 64-bit Android and means nothing. Scudo reserves one range per size class (Section 10). The zygote, the pre-initialised process that every app is forked from, reserves a range for WebView (Section 7). linker64 can leave PROT_NONE (no-access) gaps inside and between libraries (Section 6). None of that is RAM until it is touched.

What it means for you Reserving address space is free. Touching pages is not. Measure memory in resident pages (RSS and PSS, Section 3), never in virtual size.

2A write to a shared page makes a private copy

mmap is how a process gets any memory from the kernel, whether it wants a file’s contents or fresh scratch space. Every mapping has a backing, a file or nothing (anonymous). It also has a sharing mode, MAP_PRIVATE or MAP_SHARED. The combination decides what a write does.

fork() adds a second kind of copy-on-write. Parent and child share every private page after the fork, and the first write by either side copies it. The zygote relies on this: framework code, preloaded classes and native libraries relocated in the zygote are shared by every app forked from it until an app writes to one of those pages.

What it means for you A write to a file-backed or inherited page costs a full private page, even if you changed one byte. Data that every process only reads should stay read-only, and anything you want shared across apps is best set up in the zygote, before the fork.

3PSS splits shared pages fairly, so it is the number to sum

Once pages are shared, “how much memory does this process use” has three answers.

  • RSS (resident set size): every page mapped into the process, shared pages counted in full.
  • PSS (proportional set size): private pages in full, plus each shared page divided by the number of processes that map it. Summing PSS over all processes gives the RAM actually used, which is why Android’s tools report it.
  • USS (unique set size): private pages only. Roughly what killing the process gives back.

/proc/pid/smaps breaks each VMA into Shared_Clean, Shared_Dirty, Private_Clean, Private_Dirty, plus Rss and Pss. Clean pages match their file and can be dropped and re-read. Dirty pages cannot: they are anonymous or copy-on-write copies.

What it means for you Private dirty memory is the expensive kind. Clean file pages are cheap to reclaim, and shared pages are split between everyone who maps them.
Part II · ELF & linker64

4A library is mapped by permission, so its sections are grouped into segments

An ELF file describes the same bytes twice, because it has two readers. The static linker combines object files and wants fine-grained named pieces. The loader only wants to know what to map where, and with which permissions.

The section header table (readelf -S) lists named pieces such as .text, .rodata, .data and .bss. It exists for the static linker and for debuggers. The program header table (readelf -l) lists segments: page-aligned ranges with one set of permissions each. The loader only reads program headers.

The split exists because the MMU enforces permissions per page. Page-aligning thirty sections would waste a page of padding for each. So the static linker, lld, groups sections with the same runtime permissions into one loadable (PT_LOAD) segment. The one exception is read-write data: the RELRO part gets a segment of its own.

A relocation is needed wherever the library holds an address that is only known once the library’s load address is. GNU_RELRO (“relocation read-only”) marks the range that holds those written addresses. The linker writes it during loading and then makes it read-only (Section 6). Here is what lld produced for libhwui.so in this build:

A table of pointers is never read-only data

A table of string pointers never lands in .rodata, however many consts it has. Each element holds an address, and the address depends on where the library is loaded. So the linker must write it at load time. The compiler puts the table in .data.rel.ro, and every page of it becomes dirty in every process that relocates it.

// 8-byte pointer per entry, one relocation each:
// lives in .data.rel.ro, dirtied at load
const char* const kEventNames[] = {
  "ACTION_DOWN", "ACTION_UP", "ACTION_MOVE",
  // ...
};
// no pointers: lives in .rodata, shared clean
constexpr char kEventBlob[] =
  "ACTION_DOWN\0ACTION_UP\0ACTION_MOVE\0";
constexpr uint16_t kEventOffsets[] = {
  0, 12, 22,
};
What it means for you Big tables of pointers, and classes with many virtual methods, cost dirty memory per process. An offset table into one string blob costs nothing beyond its clean file pages.

5Code reaches other libraries through a table, so code pages are never patched

A shared library loads at a different address in different processes. One reason is ASLR (address space layout randomisation): the kernel and linker pick random base addresses so an attacker cannot predict where code lives. Another is that each process loads a different set of libraries.

If code contained absolute addresses, the linker would have to patch .text. Every patched page would become private dirty, and the code segment would have to be writable. Bionic refuses such text relocations: it rejects any library with DT_TEXTREL or DF_TEXTREL. Executables must be position-independent too. Support for non-PIE executables was dropped in API 21.

Position-independent code (PIC) relies on one invariant. All segments of a library move together by the same load bias: the difference between the address the library was linked at and the address it was actually loaded at. So the distance between any instruction and any byte of the same library is a link-time constant. Code reaches its own data with PC-relative instructions (adrp + add/ldr) and needs no relocation.

Anything in another library is reached through a table of addresses inside this library. The GOT (global offset table) holds addresses of imported globals and functions, and the linker fills it in at load time. A call to an imported function goes to a small stub in the PLT (procedure linkage table, the .plt section). The stub loads the target from its GOT slot and branches. Figure 6 shows libhwui.so calling malloc.

Bionic resolves every slot up front, never lazily. Desktop glibc can instead resolve each PLT slot the first time it is called (lazy binding), which means the GOT stays writable for the life of the process. Bionic’s dynamic-section parser ignores DT_PLTGOT with the comment “Ignored (because RTLD_LAZY is not supported)”. Every slot is resolved during dlopen, and then the whole RELRO range is made read-only. Platform libraries are also linked with -z now, the static-linker flag that marks a library for eager binding: libhwui.so carries FLAGS BIND_NOW and FLAGS_1 NOW.

6linker64 loads a library in five steps

Everything so far is a static description in a file. Something has to turn it into a running library. It must pick an address, map the segments, fill in the GOT and pointer tables, and run initialisation code. On Android that is /system/bin/linker64, the dynamic linker.

The kernel maps linker64 into every dynamically linked process, because the executable’s PT_INTERP header names it. The kernel jumps to it before main. It is also what runs when you call dlopen.

The linker finds its inputs through the .dynamic section, a list of tagged entries (DT_*). They say where the symbol and relocation tables are, and which libraries this one needs (DT_NEEDED). Figure 7 shows the main steps, with the bionic functions that do them. Many are methods of soinfo, the linker’s record of one loaded library.

Reserve one range, then map each segment into it

The linker reserves the whole library’s range first, so that all segments keep their distances. If linker64 mapped each segment with mmap(nullptr, …), the kernel could put them anywhere and the PIC invariant would break. So ElfReader::ReserveAddressSpace computes the span of all PT_LOAD segments and reserves it with one anonymous PROT_NONE mapping. ElfReader::MapSegment then maps each segment over its slice of the reservation:

// Mark segments as huge page eligible if they meet the requirements

Details that show up in /proc/pid/maps:

  • Gaps between segments stay inaccessible. For a library with large segment alignment, like libhwui.so, the space between segments is never mapped over. It stays PROT_NONE (---p), and a stray pointer into it faults. Libraries with smaller alignment and a segment-padding note can instead have each segment extended to meet the next.
  • The reservation lands at a random place. It is aligned for bionic’s Control Flow Integrity (CFI) shadow, a table that maps each code address to its library’s indirect-call checker. It is placed at a random offset inside a larger temporary mapping. On 64-bit, a library that crosses a 2 MiB boundary also gets a random inaccessible gap after it, which makes libraries harder to find by probing.
  • The .bss gets its own anonymous line. For a writable segment, the linker zeroes the rest of the last file-backed page. It maps any further .bss pages anonymously and names the range [anon:.bss].
  • Libraries can map straight out of an APK. Segments are MAP_PRIVATE file mappings, so a library stored uncompressed and page-aligned in an APK needs no extraction.
  • Page size must match. On 16 KiB-page devices, a library whose segments are aligned only for smaller pages fails with “program alignment … cannot be smaller than system page size”. The exception is 16 KiB app-compat mode, which lets an app whose libraries are aligned only for 4 KiB pages still run. There the linker reads the file into an anonymous read-write reservation instead of mapping it.

A Bloom filter rejects libraries that do not define a symbol

Resolving an import means finding a symbol name in the libraries of the lookup scope: the ordered list of loaded libraries the linker is allowed to search for this library. Most of those libraries do not define the name, so the fast path is rejecting them. .gnu.hash has a Bloom filter for that. It is a small bit array that can answer “definitely not here” with one or two bit tests, at the price of an occasional false “maybe”.

The name is hashed with the DJB hash (h = h*33 + c), which is NEON-accelerated (arm SIMD) on arm and arm64. Two bits derived from the hash are then tested in one 64-bit filter word:

bionic/linker/linker_soinfo.cpp · soinfo::gnu_lookupconstexpr uint32_t kBloomMaskBits = sizeof(ElfW(Addr)) * 8;
const uint32_t word_num = (hash / kBloomMaskBits) & gnu_maskwords_;
const ElfW(Addr) bloom_word = gnu_bloom_filter_[word_num];
const uint32_t h1 = hash % kBloomMaskBits;
const uint32_t h2 = (hash >> gnu_shift2_) % kBloomMaskBits;
// test against bloom filter
if ((1 & (bloom_word >> h1) & (bloom_word >> h2)) == 0) {
  return nullptr;
}
// bloom test says "probably yes"...
uint32_t n = gnu_bucket_[hash % gnu_nbucket_];

Only on a Bloom hit does it walk the hash chain. It then compares 31 bits of the stored hash, checks the symbol version, and finally runs strcmp on the name. A library that does not define the symbol usually costs one load and two shifts.

RELR shrinks relocation records, but dirties the same pages

Section 4 introduced relocations as “write this address here” records. The linker has to apply thousands of them per library, so their encoding matters. There are two kinds.

  • Relative (R_AARCH64_RELATIVE): add the load bias to a pointer to something inside the same library. Vtables and pointer tables in .data.rel.ro produce thousands of them. No symbol lookup is needed.
  • Symbolic (JUMP_SLOT, GLOB_DAT, ABS64): look up a symbol (previous section) and write its address. These fill the GOT and any data pointer to another library’s symbol.

Relative relocations mostly hit consecutive 8-byte words, so a full record for each is wasteful. A standard Elf64_Rela record is 24 bytes. RELR encodes the same information as a bitmap, and the saving is large (Figure 9).

The format works like this. An even entry is an address to relocate, and base becomes the word after it. The odd entries that follow are bitmaps. Each set bit after bit 0 means “also relocate the word at that position after base”. Each bitmap then moves base on by 63 words:

bionic/linker/linker.cpp · relocate_relrif ((entry&1) == 0) {
  // Even entry: encodes the offset for next relocation.
  offset = static_cast<ElfW(Addr)>(entry);
  apply_relr_reloc(offset, load_bias, has_memtag_globals);
  // Set base offset for subsequent bitmap entries.
  base = offset + wordsize;
  continue;
}
// Odd entry: encodes bitmap for relocations starting at base.
offset = base;
while (entry != 0) {
  entry >>= 1;
  if ((entry&1) != 0) {
    apply_relr_reloc(offset, load_bias, has_memtag_globals);
  }
  offset += wordsize;
}
// Advance base offset by 63 words for 64-bit platforms,
// or 31 words for 32-bit platforms.
base += (8*wordsize - 1) * wordsize;

RELR is now a standard format. It was proposed on the generic-ABI (gABI) mailing list, where the ELF standard is discussed, and became DT_RELR. Bionic treats DT_RELR and the older DT_ANDROID_RELR tag the same way. The platform libhwui.so in this build uses DT_ANDROID_RELR. Its symbolic relocations live in other tables (Figure 8).

Compact encoding shrinks the file and the time spent reading relocation records. It does not change how many pages get written: every page of .data.rel.ro that holds a pointer still becomes dirty.

RELRO is sealed read-only, but its pages stay dirty

The tables the linker writes must not stay writable. The GOT, vtables and constructor arrays must be writable while the linker fills them in. But if they stayed writable, a memory-safety bug could overwrite a function pointer and redirect execution. PT_GNU_RELRO marks the part of a writable segment that only needs to be writable during relocation.

After soinfo::relocate, soinfo::protect_relro calls phdr_table_protect_gnu_relro. That mprotects every page the range touches to PROT_READ. From then on those tables can no longer be overwritten.

Sealing does not make the pages clean. They were written, so they are copy-on-write copies. In smaps the RELRO line is r--p, but its pages are Private_Dirty, or Shared_Dirty if inherited from the zygote. For this build’s libhwui.so that is up to 264 KiB per process that relocates it itself.

Then call_constructors runs the library’s static constructors: C++ constructors of global objects, and functions marked __attribute__((constructor)). It goes children first: DT_INIT, then every function in DT_INIT_ARRAY. Static constructors run on the thread that called dlopen, before it returns.

What it means for you A library’s load cost is mostly page faults on its segments, relocation writes into RELRO, and its static constructors. Fewer pointers in const data and less work in global constructors make both dlopen and memory cheaper. In a trace, look for dlopen: … and calling constructors: … slices.

7Only the zygote and WebView share RELRO between processes

Libraries the zygote loads before forking are relocated once, in the zygote. Examples are libandroid_runtime.so and its dependency libhwui.so. Children inherit the relocated, sealed pages copy-on-write and never write to them, so the pages stay shared. Libraries loaded after the fork are relocated privately in each process.

WebView’s native library is large and is loaded after the fork, in every app that uses WebView. So each app would pay for its own relocated RELRO copy. Android shares it with two flags to android_dlopen_ext, bionic’s dlopen variant that takes extra options (Figure 11).

The comparison is a page-by-page memcmp. Each run of equal pages is then replaced with mmap(…, PROT_READ, MAP_PRIVATE|MAP_FIXED, fd, …):

bionic/linker/linker_phdr.cpp · phdr_table_map_gnu_relrowhile (match_offset < size) {
  // Skip over dissimilar pages.

    match_offset += page_size();

    mismatch_offset += page_size();

  // Map over similar pages.

    void* map = mmap(mem_base + match_offset, mismatch_offset - match_offset,
                     PROT_READ, MAP_PRIVATE|MAP_FIXED, fd, *file_offset + match_offset);

The private dirty copies made during relocation are dropped when the file is mapped over them. The order in soinfo::link_image is: relocate, seal RELRO, then serialize (WRITE_RELRO) or map (USE_RELRO).

What it means for you RELRO is shared only when it is relocated before the fork (zygote-preloaded libraries) or matched against a RELRO file (WebView). Any other library you dlopen pays for every RELRO page the linker writes, as private dirty memory in every process. For this build’s libhwui.so that would be up to 264 KiB.

8Namespaces decide which libraries an app may load

A device carries hundreds of platform libraries whose ABI is not stable and may change in any update. If apps could link against them, every platform change could break apps, and vendor code could depend on system internals. Namespaces are how the linker enforces which libraries a caller may see.

Bionic does not keep one global list of loaded libraries. Each library belongs to a namespace with its own search paths. In code, the linker’s record of one loaded library is a soinfo, and a namespace is an android_namespace_t (bionic/linker/linker_namespaces.h). Namespaces are connected by links. Each link carries an allow-list of library names (shared_lib_sonames) that may be resolved through it.

The system namespaces are default, vendor, and one for each APEX module, the separately updatable parts of the platform. They are described in /linkerconfig/ld.config.txt, which the linkerconfig tool generates at boot. For apps, libnativeloader creates one namespace per app class loader, named with the clns prefix. An app namespace can see its own APK’s libraries and the public NDK libraries. Private platform libraries live in other namespaces.

What it means for you An app’s dlopen of a private system library fails with “not accessible for the namespace” even though the file exists. Ship the library in your APK or use a public NDK API instead.
Part III · malloc

9malloc is a thin dispatcher in front of Scudo

malloc(48) is not a system call. The kernel hands out whole pages, and each mmap costs a syscall and a VMA. So an allocator gets large anonymous ranges from the kernel and carves them into small blocks in user space. A good allocator has a lock-free fast path for the common sizes, keeps per-block overhead low, and gives empty pages back.

In bionic, malloc checks one atomic pointer, the current dispatch table. If it is null, malloc calls the native allocator directly. If not, it calls through the table:

bionic/libc/bionic/malloc_common.cppextern "C" void* malloc(size_t bytes) {
  auto dispatch_table = GetDispatchTable();
  void *result;
  if (__predict_false(dispatch_table != nullptr)) {
    result = dispatch_table->malloc(bytes);
  } else {
    result = Malloc(malloc)(bytes);
  }
  ...
  return MaybeTagPointer(result);
}

The table exists so tools can intercept every allocation without relinking the program. The tools are malloc debug and malloc hooks (libc_malloc_debug.so, libc_malloc_hooks.so), heapprofd (Perfetto’s native heap profiler), and GWP-ASan. GWP-ASan sends a small random sample of allocations to guarded pages to catch memory bugs on users’ devices.

Two process-wide settings shape the behaviour. Apps started with MALLOC_USE_APP_DEFAULTS get zero-initialisation of new blocks turned off. They also get mallopt(M_DECAY_TIME, 1), which on Android selects the longest page-release interval (Section 11).

10Scudo balances speed, small overhead and safety

A phone allocator has three jobs that pull against each other. It must be fast, because malloc is on every hot path. It must keep per-process overhead small, because hundreds of processes each have their own heap. And it should make heap bugs hard to exploit, because overflows and use-after-free in native code are a common attack route.

Scudo is the default native allocator in bionic and is built for that balance. It comes from LLVM’s hardened allocator project (external/scudo/standalone), tuned with an Android configuration for normal phones. It has three parts:

TSD caches

TSD stands for thread-specific data. Each cache holds free blocks per size class. A group of threads shares it under its own lock, which is normally uncontended. Up to 8 shared caches, 2 by default. This is the fast path.

Primary

One region per size class, for blocks up to 64 KiB of user data.

Secondary

One mapping per allocation, fenced with guard pages, for anything bigger. A small cache of freed mappings avoids repeated mmap.

Small blocks of one size share a region

A request is rounded up to a size class, one of a fixed list of block sizes. Each class gets its own region. So blocks of one size sit side by side, and a freed block can be reused by any request of the same class. Android uses a fixed table of 32 classes on 64-bit.

Every class size includes Scudo’s 16-byte header (SizeDelta = 16). That is why so many of them end in 0x10: malloc(4096) plus its header is 0x1010, with no waste.

The primary reserves all its regions up front, in one PROT_NONE mapping named scudo:primary_reserve. Each region is 256 MiB (RegionSizeLog = 28). Add the internal batch class, whose blocks hold Scudo’s own free-list bookkeeping, and that is a little over 8 GiB of address space (Figure 3).

Pages are committed, meaning remapped read-write so they can be used, lazily at the front of each region. Scudo commits 256 KiB at a time (MapSizeIncrement) and renames that part scudo:primary.

A malloc that hits a TSD cache pops a block and writes its header. That costs one uncontended lock and no syscall. When the cache for a class is empty, it refills a batch from the region’s free list. When the region’s committed space runs out, Scudo commits another 256 KiB.

A checksummed header in front of every block catches bad frees

free(p) gets only a pointer. Scudo needs to know which size class the block belongs to, whether it is really an allocated block, and whether anyone has scribbled over its bookkeeping. It keeps that in a header in front of every block.

Every block starts with a 16-byte header area: the 8-byte header, rounded up to the minimum alignment. The pointer you get is immediately after it. The header itself is a packed bitfield:

external/scudo/standalone/chunk.hstruct UnpackedHeader {
  uptr ClassId : 8;
  u8 State : 2;
  // Origin if State == Allocated, or WasZeroed otherwise.
  u8 OriginOrWasZeroed : 2;
  uptr SizeOrUnusedBytes : 20;
  uptr Offset : 16;
  uptr Checksum : 16;
  ...
};
inline AtomicPackedHeader *getAtomicHeader(void *Ptr) {
  return reinterpret_cast<AtomicPackedHeader *>(reinterpret_cast<uptr>(Ptr) -
                                                getHeaderSize());
}

The header is what lets Scudo catch misuse on free:

  • Checksum. computeHeaderChecksum runs CRC32 over the cookie, the address and the header. It uses hardware CRC32 instructions where available, and a BSD checksum otherwise. An overflow that clobbers the next block’s header fails the check, and so does a pointer that malloc never returned. Both abort with “corrupted chunk header”.
  • State. Available, Allocated or Quarantined. Freeing a block that is not Allocated, such as a double free, aborts with “invalid chunk state”.
  • Origin. Malloc, New, NewArray or Memalign. Scudo can abort on a mismatched free/delete/delete[], but Android’s config turns that off (AbortOnDeallocTypeMismatch = false).

The Quarantined state belongs to an optional quarantine. It is a holding area where freed blocks wait for a while before reuse, so a use-after-free touches dead memory instead of someone else’s new object. It costs memory, and Android’s config compiles it out (QuarantineDisabled = true).

Large blocks get their own mapping, fenced by guard pages

Big blocks are rare, would waste a lot of space if rounded to a size class, and should go back to the kernel as soon as they are freed. So larger requests get their own mapping, fenced by guard pages: PROT_NONE pages next to the block that fault on any access.

MapAllocator::allocate reserves the rounded size plus one guard page on each side. It commits the middle, and places the block at the end of the committed range:

external/scudo/standalone/secondary.h · MapAllocator::allocateconst uptr MapSize = RoundedSize + 2 * getGuardPageSize();
...
uptr CommitBase = MapBase + getGuardPageSize();
...
const uptr CommitSize = MapEnd - getGuardPageSize() - CommitBase;
const uptr AllocPos = roundDown(CommitBase + CommitSize - Size, Alignment);

Pointer tags catch a bad access when it happens

Header checks catch corruption only when the block is freed, long after the bad write. Catching the bad access itself needs help from the pointer. arm64 ignores the top byte of an address (TBI, Section 1), so allocators can store a tag there.

On hardware with MTE (Memory Tagging Extension, an Armv8.5 feature), memory carries tags too. Every 16-byte granule has a 4-bit tag, and the CPU compares it with the pointer’s tag on every load and store (Figure 17).

  • Without MTE, bionic tags every heap pointer with a fixed top byte, POINTER_TAG = 0xB4 (malloc_tagged_pointers.h), and checks it on free. Code that truncates or rewrites the top byte of a heap pointer aborts with “Pointer tag for %p was truncated”.
  • With MTE, in a process where heap tagging is enabled, Scudo gives each block a random tag in the low half of the top byte. It stores the same tag on every granule of the block, using the MTE instructions irg (pick a random tag) and stg (store a tag to memory), in memtag.h. A load or store through a pointer with the wrong tag faults. On free, a primary block is retagged with a different random tag (retagBlock excludes the previous one), so a stale pointer faults on use.
What it means for you A Scudo abort on free is almost always a bug in the caller: overflow into a neighbour’s header, double free, or freeing a pointer that did not come from malloc. The abort happens at the free, not where memory was corrupted. MTE or HWASan move the report to the bad access. HWASan is hardware-assisted AddressSanitizer, a debug build that checks top-byte tags in software.

11free() lowers RSS only when a whole page is empty

A C/C++ allocator can never move a live block, because the program holds raw pointers to it. A page can go back to the kernel only when every block on it is free. One long-lived 64-byte object keeps its whole page resident.

Release is also rate-limited on purpose. Giving a page back and faulting it in again costs a syscall, a TLB flush (the TLB is the CPU’s cache of recent address translations) and a page fault. Doing that on every free would be slower than keeping a few pages around. M_DECAY_TIME chooses the trade-off. On Android, Scudo accepts only three values, and the highest one picks the longest interval its config allows. The exact values are in Section 15.

What it means for you Allocate long-lived objects separately from short-lived bursts. For example, build a result, then copy it out and free the scratch. A spike of small allocations with a few survivors leaves RSS high until those survivors are freed. After a large one-off job, mallopt(M_PURGE, 0) (API 28+) returns free pages immediately instead of waiting for the release interval. M_PURGE_ALL (API 34+) is slower and more thorough.

12Scudo replaced dlmalloc and jemalloc for its safety checks

Every general-purpose allocator answers the same questions differently. Where does per-block metadata live? How do threads avoid contending on one lock? When do empty pages go back to the kernel? Bionic has used three allocators.

Early releases used dlmalloc: one heap of variable-size chunks under a global lock. Each chunk carries inline boundary tags, size fields stored right before and after the chunk. A freed chunk stores its free-list pointers in itself. Inline metadata made heap overflows easy to turn into arbitrary writes.

jemalloc replaced it, with per-thread caches, several independent heaps (arenas), and size-segregated runs whose metadata sits out of line. It is still in the tree for low-memory builds (external/jemalloc_new, libjemalloc5). Scudo replaced jemalloc as the default in Android 11, per the source.android.com Scudo page. It won for its checks and randomisation at a similar memory cost.

TCMalloc is Google’s server allocator and is not part of the Android tree. TCMalloc’s design document (docs/design.md in the TCMalloc repository) describes a front end of per-CPU caches or per-thread caches.

Per-CPU caches rely on rseq, Linux restartable sequences: short code sequences that the kernel restarts if the thread is preempted or migrated mid-way. That lets a thread update the current CPU’s data without locks or atomics. Behind that sit a middle end of transfer caches and central free lists. Then comes a page heap, whose hugepage-aware version (Temeraire) packs allocations into huge pages. Size-class information lives in a page map rather than in per-object headers.

14Cheat sheet

QuestionShort answer
Why does mmap of 1 GiB cost nothing?It creates a VMA with empty page-table entries. RAM is allocated one page at a time on first touch (minor faults).
Sections vs segments?Sections are the static linker’s view. Segments are what linker64 maps: one per permission set, except that RELRO gets its own. Current lld emits four PT_LOADs: R, RX, RW (RELRO), RW (data, bss).
Why are there two r--p lines per library?The first is the read-only segment (clean). The second is RELRO, mapped writable, relocated, and then sealed read-only. It is dirty.
Why is my const char* const table dirty?Pointers need relocation, so it lives in .data.rel.ro. Use offsets into a string blob.
How does a library call malloc without patching code?PC-relative branch to a PLT stub, which loads the target from a GOT slot the linker filled at load time.
Does Android resolve symbols lazily?No. Bionic does not support lazy binding. All slots are resolved during dlopen and RELRO is sealed.
What is RELR?A bitmap encoding of relative relocations: one 8-byte word covers 63 pointers. Smaller files, same number of dirty pages.
Why is dlopen slow?Page faults on segments, relocation writes, dependency loading, and static constructors. Split it with the dlopen: … and calling constructors: … slices.
Why didn’t free() lower RSS?A page is released only when every block on it is free, and Scudo rate-limits release (1 s on Android). M_PURGE forces it.
Why do Scudo classes end in 0x10?Class sizes include the 16-byte header, so malloc(4096) fits 0x1010 exactly.
Where does a large allocation go?Above the 64 KiB primary limit: its own scudo:secondary mapping, right-aligned against a guard page.
