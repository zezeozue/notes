How Parcel holds native memory: its buffers, the copy a Binder call makes, and what keeps that copy alive in system_server

Data that apps send to system_server over Binder arrives in a temporary kernel buffer, yet copies of it made by Parcel::appendFrom can stay on system_server's native heap for hours while looking like 48-byte objects to ART's garbage collector and Java heap dumps. This note builds Parcel up from first principles, traces how Bundle copies and retains app payloads across processes, and shows how Parcel's native-memory accounting evolved from 2009 to 2021.

Checked against AOSP as of Android 17 (frameworks/base, frameworks/native/libs/binder, libcore) and the Android common kernel’s Binder driver.

New to Parcel? Start at §0, Parcel from the ground up—seven visual steps that build the mental model before the internals below.

At a glance

  1. Incoming Binder buffers die with the call, so kept Bundles copy into malloc. Transactions arrive in a shared ~1 MiB /dev/binder kernel mapping freed before the reply is sent; when system_server reads a Bundle (Intent or Notification extras, saved state), Parcel::appendFrom copies its slice into malloc and duplicates every embedded file descriptor (§2).
  2. One unread entry pins the entire copied Bundle. Reading even one primitive or string key leaves larger entries (such as a notification Bitmap or custom app Parcelable) wrapped in Parcel.LazyValue placeholders that keep the whole copied buffer and its duplicated ashmem/memfd descriptors alive (§2).
  3. Most system_server holders outlive the app that sent them. Notifications, PendingIntents, saved activity state, widgets, jobs, alarms, sticky broadcasts, and clipboard entries keep their Bundle copies until cancelled or replaced—only media sessions release theirs when the app dies (§3). Meanwhile, Parcel.recycle() frees buffers immediately and pools only 32 empty 120 B shells, so pooling is not the cause (§1).
  4. Java tools see 48 B instead of the native buffer. Parcel cleans up via finalize() rather than NativeAllocationRegistry, reporting 0 native bytes to ART's GC and Java heap dumps; from 2015 to 2020 it reported open ashmem sizes (never malloc buffers), and even that was removed for a 3% microbenchmark gain (§4).
Details: exact classes and functions behind each step
  • Pool (§1). recycle() calls Parcel::freeData(), freeing mData and mObjects back to Scudo. The 32-entry sOwnedPool caches only the Java object and its empty 120-byte C++ Parcel.
  • Copy on read (§2). IPCThreadState frees the ~1 MiB driver mmap slice before sending the reply. BaseBundle.readFromParcelInner() copies the Bundle's byte range into a heap Parcel via appendFrom(), duplicating FDs and incrementing Binder strong refs.
  • LazyValue (§2). Top-level unparcelling wraps length-prefixed Parcelable entries in Parcel.LazyValue; LazyValue.mSource retains the entire copied Parcel.
  • Holders (§3). NotificationRecord, PendingIntentRecord.Key, ActivityRecord.mIcicle, AppWidgetServiceImpl.Widget, JobStatus, AlarmManagerService.Alarm (via its PendingIntent), StickyBroadcast, and ClipboardService survive app death; MediaSessionRecord uses linkToDeath.
  • mNativeSize (§4). Parcel.java still declares private long mNativeSize, left over from the 2015–2020 ashmem accounting; nothing reads or writes it.
Glossary of terms (Binder, Owned vs Borrowed Parcel, LazyValue, NAR, Scudo, ashmem/memfd)
  • Binder (/dev/binder): Android's kernel IPC driver; moves messages across processes with a single copy while translating Binder handles and file descriptors.
  • Owned Parcel: a Parcel whose bytes live in its own malloc buffer and are freed with free() (C++ android::Parcel with mOwner == nullptr; mData holds bytes and mObjects holds kernel-object offsets on the native heap).
  • Borrowed Parcel: a Parcel pointing into the read-only ~1 MiB /dev/binder kernel buffer of an incoming call, released via BC_FREE_BUFFER rather than free() (ipcSetDataReference(); mOwner != nullptr).
  • LazyValue: a placeholder in BaseBundle.mMap for an unparsed length-prefixed entry (Parcelable, List, Map, array, Serializable); its mSource field keeps the backing Parcel alive until read.
  • NativeAllocationRegistry (NAR): a libcore helper pairing a Java object with a Cleaner so native memory is freed on GC and sized in heap dumps. Parcel does not use it.
  • Scudo: Android's native heap allocator in bionic (malloc / realloc / free).
  • ashmem / memfd: kernel shared-memory files passed via file descriptors; pages stay allocated while any process holds an open fd.
  • BC_* / BR_*: Binder driver commands sent from user space (BC_FREE_BUFFER, BC_REPLY) and returned by the driver (BR_TRANSACTION).
Part 0 · Ground-up primer

0Parcel from the ground up: what it is, how one Binder call moves it, and where its memory lives

Read this first if Parcel is new to you. It assumes no knowledge of Binder internals; §1 to §3 each zoom into one box of these figures.

The problem: a pointer means nothing in another process

Every Android app runs in its own process, and every process has its own private address space. When an app calls NotificationManager.notify(id, notification), the code that actually shows the notification runs in a different process, system_server. The app cannot hand over a pointer to its Notification object: address 0x7f3a10 in the app is unrelated memory, or no memory at all, in system_server. The only thing that can write into both address spaces is the kernel, through the Binder driver (/dev/binder).

So every cross-process call does three things: flatten the arguments into a run of plain bytes, have the kernel copy those bytes into the other process, and rebuild values from the bytes there. A Parcel is the container that holds those bytes. It is not a general file format: it has no field names, no versioning, and the docs warn against storing it on disk. It exists to move one call's arguments, or one reply, across one Binder transaction.

Writing and reading: a byte stream with a cursor and no labels

A Parcel is a growable byte array plus a cursor, a position that says where the next value goes. Each write*() call appends at the cursor and moves it forward; each read*() call reads at the cursor and moves it forward. Everything is aligned to 4 bytes: an int takes 4 bytes, a boolean is widened to 4, and a string is written as its length, then its UTF-16 characters, then a terminator, padded up to the next multiple of 4.

Nothing in the bytes says "this is an int" or "this field is called id". The only structure is order. The receiver must read exactly the same types in exactly the same sequence the sender wrote them. That is why nobody hand-writes Binder calls: the AIDL (Android Interface Definition Language) compiler generates the sending half (the proxy) and the receiving half (the stub) from one interface definition, so the two orders cannot drift apart.

Objects travel the same way. A class that implements Parcelable has a writeToParcel() method that writes its fields one by one, and a CREATOR that reads them back in the same order to build a new object on the other side. A Bundle (the key/value map inside Intent extras, Notification extras and saved state) is itself Parcelable: it writes its total length first, then each key and value. The length prefix matters later, because it lets a receiver copy or skip the whole Bundle without understanding what is inside.

Two halves: a small Java object and a native buffer

The Java class android.os.Parcel holds almost nothing. Its key field is mNativePtr, a pointer to a C++ android::Parcel in libbinder, the native Binder library. The C++ object is a fixed 120-byte header. It points at two separately allocated buffers on the native heap (malloc): mData, the bytes themselves, which grow by about 1.5× whenever a write runs out of room; and mObjects, a short list of offsets explained in the next subsection. Parcel.obtain() hands out a Java wrapper (from a small pool of 32), and recycle() frees the native buffers.

The two things that cannot be copied as bytes: Binder objects and file descriptors

Most values are just numbers and characters, and copying their bytes is enough. Two kinds of value are not:

  • A file descriptor is a small integer that indexes the sending process's table of open files. "fd 42" in the app means nothing in system_server; that process's fd 42 is some other file, or nothing.
  • A Binder object (an IBinder, such as a callback the server should call later) is a live reference to an object in some process. Its address is as meaningless across processes as any other pointer.

For these, Parcel writes a fixed 24-byte placeholder record (flat_binder_object) into the byte stream, and also appends that record's offset to mObjects. During the transaction the kernel does not try to understand the bytes; it walks the mObjects list, visits each record, and rewrites it for the receiver: it opens the same file in the receiver and writes the receiver's new fd number, or it converts the object reference into a handle, a small number that the receiver can use to call back into the original object. It also keeps reference counts so the object or file stays alive while anyone holds it.

One complete Binder call, step by step

Each process that uses Binder has a Binder buffer: about 1 MiB of memory that the kernel manages and maps read-only into the process. Incoming transactions land there. Here is what happens, and where the bytes are, during a synchronous call such as notify():

  1. Client writes. The AIDL proxy takes a Parcel from Parcel.obtain() and writes the arguments. The bytes are in the client's malloc heap.
  2. Client calls transact(). libbinder hands the kernel a pointer to those bytes and to the mObjects list, and the client thread blocks.
  3. Kernel copies once. The driver reserves a slice of the server's Binder buffer, copies the bytes straight from the client's memory into it, and rewrites any fd and Binder records. This is the only copy of the request.
  4. Server reads in place. A server Binder thread wakes up, wraps the slice in a Parcel that borrows the memory (no second copy), and the stub's onTransact() reads the arguments in order.
  5. Server replies and frees. The server writes its reply into a new Parcel (server malloc), and before sending it, tells the kernel to free the request slice (BC_FREE_BUFFER).
  6. Kernel copies the reply into the client's Binder buffer the same way.
  7. Client reads the reply, frees that slice, and recycle()s its request Parcel, which frees the client-side malloc bytes.

Big payloads go through shared memory, not through the Parcel

The Binder buffer is small and shared by every transaction in flight to that process, so a call whose Parcel is too big fails with TransactionTooLargeException. Large payloads therefore travel beside the Parcel: the sender puts them in a shared-memory region (ashmem or memfd) and writes only that region's file descriptor into the Parcel. The kernel rewrites the fd as in Figure P4, and the receiver maps the same physical pages. A Bitmap does this above about 12 KiB of pixels, and Parcel.writeBlob() above 16 KiB.

Where memory gets stuck: a Bundle that must outlive the call

Figure P5 frees everything when the call returns. That breaks the moment the server needs to keep part of the request. system_server keeps a lot: the extras Bundle of every posted notification, the Intent inside every PendingIntent, saved activity state, queued broadcasts, widget views. It cannot keep pointing into its Binder buffer: that slice is freed at step 5, and the buffer is a shared 1 MiB that would fill up in seconds.

So when a Bundle is read from an incoming Parcel, it uses its length prefix to copy its own bytes into a brand-new Parcel on the malloc heap (Parcel::appendFrom()), duplicating every file descriptor and taking a reference on every Binder object inside it. It also parses lazily: simple values are decoded when the Bundle is first touched, but bigger values (nested Parcelables such as a notification's Bitmap, lists, arrays) stay as undecoded bytes, each one a placeholder (LazyValue) that points back at the whole copied Parcel. As long as the Bundle is alive and even one such value has not been read, the entire copy, and every fd it duplicated, stays alive in system_server.

Part I · How Parcel Allocates, Copies, and Stays Alive Across Processes

1Inside a Parcel: who frees it, what is in it, how it grows

Every Binder call, Intent and Notification travels in an android::Parcel. This section opens one up and answers three questions in order: who frees its memory, how its bytes are laid out, and how its buffer grows and shrinks. Each answer decides how much native memory a Parcel costs and when that memory comes back.

The code is split across three files: Parcel.java (the Java wrapper), Parcel.h (the C++ class) and Parcel.cpp (its implementation). Most methods in Parcel.cpp first check three facts about the instance: does the Java wrapper own the C++ object, are the bytes in malloc or in the kernel's Binder buffer, and is this kernel Binder or socket-based RPC Binder. The first two are the ownership questions below. The third only changes the object bookkeeping and is covered in the layout subsection.

Who frees what: two ownership questions, four real cases

The problem. A Parcel has three pieces (Figure P3): the Java wrapper, the 120-byte C++ android::Parcel struct, and the payload bytes (mData and mObjects). If you made the Parcel with Parcel.obtain(), you made all three, and recycle() frees them.

Binder also hands you Parcels you did not make. Freeing those the normal way would be a bug:

  • The bytes may belong to the kernel. An incoming request is read where the kernel put it, in your process's Binder buffer (Figure P5); copying it into malloc first would add a second copy to every call. Those bytes go back to the kernel with BC_FREE_BUFFER. Passing them to free() would corrupt the heap.
  • The C++ struct may be someone else's local variable. For an incoming call, libbinder declares Parcel data, reply; as locals in IPCThreadState::executeCommand(), on the Binder thread's stack. They vanish when the call ends. Deleting them from Java would crash the process.

The solution: one switch at each seam (Figure 1a). Because the struct and the bytes can have different owners, Parcel records each choice right at the boundary it controls:

  1. Java → C++ struct (mOwnsNativeParcelObject on Parcel.java). true when Java allocated a heap struct (nativeCreate() → new Parcel()) and must delete it; false when Java is temporarily viewing a C++ stack variable.
  2. C++ struct → bytes (mOwner on android::Parcel). nullptr when the bytes live in malloc and release via free(); otherwise a callback (IPCThreadState::freeBuffer) that sends BC_FREE_BUFFER to the kernel instead.

Because the two switches sit at different seams, all four combinations occur in one ordinary Binder call (Figure 1b). Even a single Parcel can flip one switch mid-life: your client reply starts with mOwner = nullptr at obtain(), then flips mOwner to freeBuffer when transact() points it at the server's answer inside your Binder buffer (Figure 1a, bottom).

Two pools of spare wrappers. Every Binder call needs wrappers on both sides, so Parcel.java keeps up to 32 spares of each kind instead of allocating Java objects per call. One pool cannot serve both kinds, because what a spare wrapper carries differs (Figure 1c).

What this means for memory. Only the top row of Figure 1b is native heap that can linger. B, C and D are released within one call. A is short-lived for ordinary requests, but it is also where a Bundle's private copy lives (Figure P7), and that copy can stay in system_server for hours. Sections 2 and 3 follow cell A.

In code: recycle() on an owned Parcel calls freeBuffer() → nativeFreeBuffer() → Parcel::freeData(), which frees mData and mObjects at once, then offers the wrapper to sOwnedPool. If the pool already holds 32, the wrapper is not kept and only its empty struct waits for the GC. A Parcel dropped without recycle() keeps its bytes until the GC runs Parcel.finalize() → destroy() → delete parcel.

What is in the 120-byte header, and how the object list points into the bytes

The problem. Take an app calling NotificationManager.notify() with a notification that has a title, a PendingIntent for the tap action, and a 2 MB Bitmap as its large icon. The Parcel that carries it holds three kinds of value. The title is plain bytes: copy them and you are done. The PendingIntent is a Binder object, which the kernel must translate into a handle the receiver can use (Figure P4). The Bitmap's pixels are too big to copy, so they go into a shared-memory file and the Parcel carries only its file descriptor (Figure P6), which the kernel must also translate. The kernel cannot parse the Parcel format, so something has to tell it where the Binder objects and file descriptors are. libbinder needs the same information for itself: when the Parcel is freed, it must drop the Binder references and close the file descriptors it holds.

The answer is one byte stream plus a list of offsets into it, both reached from a fixed-size C++ header (Figure 2).

The header. On 64-bit Android, sizeof(android::Parcel) is 120 bytes, pinned by a static_assert in Parcel.cpp. It is mostly pointers and sizes: where the byte stream is and three numbers about it, where the offset list is, mOwner (the release function from Figure 1), and a few flags. It never holds payload, so its size does not depend on what you write.

The byte stream, mData. Values are written back to back, each padded to a multiple of 4 bytes: a bool, byte or char16_t takes 4 bytes, and strings and byte arrays get trailing zeros. The padding keeps the kernel's records aligned, and because it is zeroed, leftover heap bytes never leak to another process. Three numbers describe the stream:

  • mDataPos: the cursor, where the next read or write happens.
  • mDataSize: the end of the valid bytes. It moves up whenever the cursor passes it.
  • mDataCapacity: how many bytes are allocated. The gap between size and capacity is slack, the subject of the next subsection.

The offset list, mObjects. Writing an IBinder or a file descriptor goes through writeObject(). It writes a 24-byte flat_binder_object record into the stream at the cursor and appends that byte offset to mObjects, an array of 8-byte offsets. The kernel walks this list during the transaction and rewrites each record for the receiver (Figure P4). libbinder walks the same list for its own bookkeeping:

  • Keeping objects alive. Writing a record calls acquire_object(): a strong reference on the IBinder (incStrong), and an fdsan ownership tag on file descriptors the Parcel owns. Freeing or truncating the Parcel walks mObjects backwards calling release_object(): decStrong for Binders, and FdTagClose for a file descriptor only when the record's cookie field is non-zero, which marks the fd as owned by this Parcel.
  • Guarding the records. Before reading primitives or appending bytes, validateReadData checks mObjects (starting from mNextObjectHint, a cached position in the list) so that a plain read or write cannot straddle a record or forge one.

Why it is built this way. The kernel sees the bytes and the offset list together and never has to understand the format. Plain values cost nothing extra; only the few special records pay 8 bytes each in the list. Large payloads stay out of the stream altogether: Parcel::writeBlob() writes byte arrays up to BLOB_INPLACE_LIMIT (16 KiB) inline, and above that puts them in an ashmem region named "Parcel Blob" and writes only a BINDER_TYPE_FD record. Bitmap.cpp does the same for pixels above 12 KiB, using a sealed memfd.

What this means for memory. A Parcel costs the 120-byte header, plus mDataCapacity bytes of stream, plus 8 bytes per Binder or fd in mObjects. Payloads passed by file descriptor appear in none of these. In the notify() example, the 2 MB of pixels live in a memfd and are accounted there; the Parcel itself holds a few hundred bytes.

How the buffer grows, and why it rarely shrinks

The problem. A Parcel does not know in advance how much will be written into it. Take the simplest loop:

Parcel p = Parcel.obtain();
for (int i = 0; i < 50; i++) p.writeInt(i);   // 200 bytes in total

Each writeInt checks whether 4 more bytes fit within mDataCapacity. When they do not, the Parcel must get a bigger buffer. Allocating exactly 4 more bytes each time would mean 50 realloc calls, each of which may copy everything written so far.

The mechanism. When a write does not fit, growData(len) asks for 1.5× the size the Parcel will have after the write, with a floor of 128 bytes: max((pos + len) * 3 / 2, 128). It passes that number to continueWrite(), the one function that actually resizes, which calls realloc. In the loop, the first write allocates 128 bytes. The 33rd write needs byte 132, so the buffer grows to 132 × 1.5 = 198. The 50th needs byte 200 and gets 300. Three allocations for 50 writes, ending with 100 bytes unused.

Why it is built that way. Each realloc may copy the whole buffer. Growing by a constant factor keeps the total copying proportional to the final size no matter how many writes there are, and the 128-byte floor skips the many tiny reallocations a fresh Parcel would otherwise make. The price is slack: right after a growth, a third of the capacity is unused.

Why a Bundle copy has no slack. When system_server reads a notification whose extras Bundle is 64 KiB, BaseBundle.readFromParcelInner() takes a fresh Parcel from Parcel.obtain() and calls appendFrom(source, offset, 64 KiB) to copy the Bundle's bytes into it. Because the target is empty (capacity 0, cursor 0), appendFrom() skips growData() and asks continueWrite() for exactly the length. The copy is 64 KiB, not up to 96 KiB. This matters because these copies are cell A of Figure 1, the ones that stay in system_server for hours. Two limits: an appendFrom() into a non-empty Parcel goes through growData() like any write, and the mObjects list still grows by 1.5× inside appendFrom().

The second problem: truncation keeps the memory. Now take a Parcel that holds 64 KiB, and code that calls setDataSize(0) to empty it and fill it again. dumpsys meminfo still counts 64 KiB for it, and keeps doing so for as long as the Parcel lives.

The mechanism. setDataSize(n) calls continueWrite(n). On a Parcel that already owns a heap buffer, that function does two things when n is smaller than the current size. It releases every object recorded past the cut (Binder references dropped, owned file descriptors closed) and shrinks mObjects with realloc. Then, because n is not larger than the capacity, it only lowers mDataSize and mDataPos. It never calls realloc to shrink mData.

Why it is built that way. Truncation is how code reuses a Parcel: empty it, write again. Keeping the buffer means those writes land in memory that is already allocated, with no realloc and no copy, until they pass the old capacity. The cost comes when the Parcel is kept but not refilled to the same size: a long-lived Parcel that once carried a large payload keeps the whole buffer.

Only three paths shrink or release mData:

  • restartWrite(n), reached from Parcel::setData() (Java unmarshall()). It releases all objects, then calls realloc(mData, n) even when n is below the capacity, so it can shrink.
  • freeData(), reached from Java recycle().
  • ~Parcel(), reached from destroy(), including the one run by finalize().

What this means for memory accounting. The Parcel memory line in dumpsys meminfo comes from the counter gParcelGlobalAllocSize, which adds up mDataCapacity of Parcels that own their bytes. So it includes growth slack and truncated-but-kept capacity. It leaves out the 120-byte headers, the mObjects lists, borrowed Binder buffer pages, and ashmem/memfd regions; the 2 MB Bitmap from the notify() example is invisible to it. Long-lived Bundle copies, the main source of Parcel memory in system_server, are counted at exactly their size, because they carry no slack.

Details: continueWrite's three branches, realloc in Scudo, and a per-method table

Almost every write, resize or copy funnels into continueWrite(desired). If desired is below mDataSize, it first sorts mObjects and finds the objects past desired so their references and fds can be released. Then it branches on where the bytes are:

  1. mOwner != nullptr (bytes borrowed from the kernel's Binder buffer). If desired == 0 it calls freeData(). Otherwise it copies on write: a fresh malloc(desired) for the bytes and a calloc for the object list, reacquireObjects(), sets cookie = 1 on kept fds so they are now owned, closes dropped fds, calls mOwner() to hand the kernel slice back, and clears mOwner.
  2. mData != nullptr (bytes already in malloc). Releases truncated objects and shrinks mObjects; then realloc(mData, desired) only if desired > mDataCapacity, otherwise it clamps mDataSize and mDataPos and keeps the capacity.
  3. Otherwise (empty owned Parcel). mData = malloc(desired), mDataCapacity = desired.

How realloc behaves depends on Scudo's size: below about 64 KiB the buffer lives in the primary allocator's size-class slots, and realloc takes a slot in a larger class, copies mDataSize bytes, and frees the old slot. At 64 KiB and above it lives in the secondary allocator as its own anonymous mmap; realloc maps a new region, copies, and unmaps the old one.

2From the Binder buffer to a Bundle that lives for hours: the kernel copy, the duplicated fd, and LazyValue

An incoming Binder call arrives in kernel-managed memory, not in malloc. Yet Parcel::appendFrom allocations in system_server can stay alive for hours. This section explains how a call that starts in kernel memory ends up in malloc. This section follows one real call to see where that memory comes from: an app calls NotificationManager.notify() with a BigPictureStyle notification, whose extras Bundle carries a 2 MB Bitmap.

What the kernel does with one notify() call

The problem. The app's Parcel holds the Bundle's bytes, a callback IBinder, and the Bitmap. The 2 MB of pixels are not in the Parcel: they sit in a memfd (a shared-memory file), and the Parcel holds only its file descriptor, say fd 23 (Figure P6). None of that is meaningful inside system_server until the kernel translates it.

The mechanism. Every process that opens /dev/binder maps a read-only Binder buffer of BINDER_VM_SIZE = 1 MiB - 2 * PAGE_SIZE (1,016 KiB with 4 KiB pages), set up in ProcessState.cpp. When the app calls transact(), the driver copies the Parcel's bytes (mData) once, straight into a slice of system_server's buffer. While copying, it walks mObjects, the list of offsets where special records sit, and rewrites each one: a local Binder object (BINDER_TYPE_BINDER) becomes a handle (BINDER_TYPE_HANDLE), and for each file descriptor record (BINDER_TYPE_FD) it opens the same file in system_server's fd table and writes the new number, here 94.

A system_server Binder thread then wakes up. In IPCThreadState.cpp, executeCommand(BR_TRANSACTION) (the handler for an incoming call) wraps the slice in a Parcel that is a local variable on the thread's stack, using ipcSetDataReference(..., freeBuffer). That Parcel borrows the bytes: it allocates nothing, and its release function is freeBuffer, which hands the slice back to the kernel (cell D in Figure 1b).

What it means for memory. The request itself costs system_server no native heap at all. Whatever shows up in malloc later was created by code that copied data out of this slice.

Details: mmap flags and ioctl names

The Binder buffer is mapped PROT_READ, MAP_PRIVATE | MAP_NORESERVE. The transfer happens inside ioctl(BINDER_WRITE_READ), and the driver places the copy inside the receiver's mVMStart range (the start of its Binder mapping). In the driver, binder_transaction() does the copy and calls fd_install() for each fd record. The fd the kernel installs is tracked in the borrowed Parcel with cookie = 0 (not owned by that Parcel).

Why a Bundle copies itself, and what appendFrom duplicates

The problem. NotificationManagerService must keep the notification's extras for as long as the notification is shown, which can be hours. But the slice they arrived in disappears at step 4 of Figure 5, and fd 94 is closed with it. The slice cannot be kept: the ~1 MiB buffer is shared by every call in flight to system_server, so holding slices would quickly fill it. For a synchronous call, IPCThreadState runs buffer.setDataSize(0), which closes the kernel-installed fds and sends BC_FREE_BUFFER, before it sends BC_REPLY. No pointer into the slice may survive onTransact().

The mechanism. So when a Bundle is read from an incoming Parcel, it does not decode anything. It reads its own length prefix and copies its whole byte range into a fresh Parcel that it owns, in BaseBundle.java:

frameworks/base/core/java/android/os/BaseBundle.java · readFromParcelInner()Parcel p = Parcel.obtain();
p.setDataPosition(0);
p.appendFrom(parcel, offset, length); // malloc(length) + memcpy + incStrong(binders) + dup(FDs)
p.adoptClassCookies(parcel);
mParcelledData = p; // State 1: mMap remains null until any key is read

Parcel::appendFrom() copies a byte range from one Parcel into another. Bytes alone are not enough, because the range contains records that stand for live things. So it copies four kinds of thing (Figure 6):

  1. The bytes: malloc(length) sized exactly to the range, then memcpy.
  2. The record list: a new mObjects array (8 bytes per record) so the copy knows where its records are.
  3. A reference on every Binder handle: incStrong(), so the callback object stays alive while the copy holds it.
  4. A new fd for every fd record: fcntl(fd, F_DUPFD_CLOEXEC, 0) turns fd 94 into fd 95, recorded with cookie = 1, meaning "this Parcel owns it and must close it".

Why it is built that way. The kernel-installed fd belongs to the transaction and is closed with it. A Bundle that outlives the transaction needs its own fd, or the Bitmap it describes would point at a closed file. That is why Parcel tracks two fd conventions: cookie = 0 for fds borrowed from the kernel, cookie = 1 for fds the Parcel duplicated and must close itself.

What it means for memory. Every Bundle that arrives over Binder costs system_server one malloc the size of the Bundle, plus one open fd per fd inside it. For our notification the heap buffer is small, but fd 95 keeps the 2 MB of pixels alive, and those pages belong to a memfd, not to the heap. Both stay until Parcel P is destroyed, which the next subsection shows can be much later than expected.

Details: copies of copies

A Bundle that has not been read yet (State 1 below) is copied by running appendFrom() again. So new Intent(orig) or new Bundle(orig) on an unread Bundle allocates a second heap buffer and duplicates every fd a second time. Each nested Bundle inside a Bundle also makes its own appendFrom() copy when the outer one is decoded.

When the copy is freed: the story of one unread entry

The problem. system_server cannot eagerly decode an app's Bundle: it lacks the app's ClassLoader for custom Parcelable classes, and running untrusted constructors in system_server would invite deserialization exploits. So a Bundle decodes only what is asked for and skips the rest. When does its heap Parcel P actually get freed?

The pointer handoff (Figure 7a). Follow our notification's extras—"android.title" (a string) and "android.picture" (the 2 MB Bitmap). On arrival (State 1), nothing is decoded and the Bundle itself strongly owns P via mParcelledData. Calling getString("android.title") decodes the title, sees that the picture is length-prefixed (L bytes), jumps over those L bytes in O(1) without loading any class, and inserts a Parcel.LazyValue placeholder into mMap (State 2b). The Bundle drops its own strong reference to weak, but LazyValue.mSource now strongly pins all of P—including the already-decoded title bytes and fd 95.

Four fates for Parcel P (Figure 7b). Eager cleanup happens only when there were no lazy entries (State 2a) or when an uncopied Bundle reads its last LazyValue (State 3, calling P.destroy() immediately). In system_server, two sticky paths dominate instead: either nobody ever reads the app's Parcelable (keeping P pinned for the holder's whole lifetime), or code clones the decoded Bundle via new Bundle(src) (State 4), which shares the LazyValue instances across both maps and marks neither Bundle allowed to destroy P—forcing cleanup to wait for GC and finalize().

What it means for memory. system_server reads simple routing keys and leaves app Parcelables untouched, so the red middle branch is the everyday case. Each such Bundle holds its full appendFrom() copy and every duplicated fd for as long as the record holding it lives (for example ActivityRecord.mIcicle or PendingIntentRecord). §3 lists the records that hold these Bundles.

Details: BaseBundle fields and lazy value types

The state is spread over five fields: mParcelledData (strong reference to P while undecoded), mMap (decoded entries and placeholders), mWeakParcelledData (weak reference to P after decoding), mLazyValues (count of placeholders not yet unwrapped), and the FLAGS_OWNS_LAZY_VALUES flag, read by ownsLazyValues().

In State 2a, when every entry was eager, BaseBundle calls parcelledData.recycle() immediately, freeing mData. Unwrapping goes through unwrapLazyValueFromMapLocked(), which runs LazyValue.apply(), sets LazyValue.mSource = null, replaces the map entry, and decrements mLazyValues. At 0, with ownsLazyValues() true, it calls mWeakParcelledData.get().destroy().

The length-prefixed (lazy) types are VAL_PARCELABLE, VAL_LIST, VAL_MAP, VAL_PARCELABLEARRAY, VAL_OBJECTARRAY, VAL_SPARSEARRAY and VAL_SERIALIZABLE. Each stores a 4-byte type tag followed by a 4-byte byte length. readLazyValue() (around Parcel.java:4858) advances mDataPos by that length and inserts new Parcel.LazyValue(sourceParcel, startPos, totalLen, type, bundle). The LazyValue's position and length cover the type tag through the end of the payload, and re-serializing it calls out.appendFrom(P, position, length). Primitives, Strings and nested Bundles are decoded eagerly.

3Who in system_server keeps an app's bytes alive, and for how long

The problem: the app is dead, but its bitmap is still in RAM

A chat app calls notify() with a big-picture notification that carries a 2 MB Bitmap. A minute later lmkd (the low-memory killer) kills the app's cached process. The notification is still on screen, so those 2 MB of pixels still exist. They are now held by system_server, not by the app.

The same thing happens to the Intent inside a PendingIntent the app gave to AlarmManager, to the saved state of an activity whose process was killed, and to the views of a home-screen widget. Each is a copy of the app's Bundle that system_server made when the call arrived (Figure P7, §2).

A native heap profile of system_server shows these bytes under the stack BaseBundle.readFromParcelInner. That stack says where the copy was made. It does not say which record still holds it, or what event will free it. To account for the memory we need both answers, and this section gives them.

How one process keeps memory alive in another

The problem. The records in Figure 8 are ordinary Java objects in system_server. The app cannot free them, and they do not become garbage just because the app died. Two kernel features decide when they can go, and a third causes the same kind of pinning inside the app itself.

1 · A Binder reference pins the object it points to. An app's PendingIntent is a BinderProxy: a handle to an object that lives in system_server (its C++ half is BpBinder, BpBinder.cpp). The proxy holds a kernel strong reference on the target (BC_ACQUIRE, the command that increments it). On the system_server side, the Java Binder object is wrapped by a C++ JavaBBinder, which holds a JNI global reference to it (NewGlobalRef, android_util_Binder.cpp) until the kernel reports that the last remote reference is gone (BR_RELEASE). A JNI global reference is a GC root. So everything reachable from that Binder, including parcelled Bundle buffers, stays alive while any client anywhere holds a proxy.

2 · A duplicated file descriptor pins shared memory. When a Bundle copies itself with Parcel::appendFrom(), it duplicates every fd listed in mObjects. system_server's copy therefore holds its own open handle on the ashmem or memfd region. The sending app can unmap its Bitmap, or die and be reaped; the pages (in RAM or zram) stay until system_server destroys its Parcel.

3 · An unrecycled reply pins the app's own Binder buffer. This one stays inside the app. A client that never calls reply.recycle() keeps a slice of its own ~1 MiB Binder buffer until the finalizer runs. Once enough slices pile up, new incoming calls fail with FAILED_TRANSACTION.

Why it is built this way. Reference counting is what lets anyone call a remote object at any time without it disappearing underneath them. Duplicating fds is what lets the receiver keep using a shared region after the sender closes its own fd (Figure P6). The price is that the last holder, in any process, decides when memory is freed.

What it means for memory. Once an app hands over a Bundle, its bytes belong to system_server: a malloc copy in its native heap, plus any shared-memory pages that copy holds an fd to. To explain that memory, you have to name the system_server record that holds the copy.

Details: Binder handles inside an unrecycled Parcel

Mechanism 1 is not limited to a live BinderProxy object. An unrecycled Parcel that contains a BINDER_TYPE_HANDLE record also holds the kernel strong reference, and so keeps the remote JavaBBinder's global reference rooted until that Parcel is freed.

Nine holders, and what each one keeps

The problem. Every one of these copies has the same allocation stack, so the heap profile cannot tell them apart. Reading frameworks/base/services shows that nine subsystems retain most app-originated Parcel and shared-memory buffers. Figure 10 lists them, with what each keeps and what kind of memory that is. The subsections below walk through the main ones with a real call; Table 1 at the end has the release rules.

A notification keeps its extras until it is cancelled

The case. The chat app's notify() sends a Notification whose extras Bundle contains the 2 MB picture under "android.picture". NotificationManagerService wraps it in a NotificationRecord, which keeps it for as long as the notification is posted.

What the record holds. NotificationRecord → StatusBarNotification → Notification (Notification.java). Three of its fields carry app bytes:

  • extras, a lazily parsed Bundle;
  • contentView and bigContentView, RemoteViews that are fully unpacked on arrival;
  • contentIntent, which pins a PendingIntentRecord (next subsection).

When the notification is enqueued, fixNotification() reads the simple keys it needs, such as booleans. It does not read the picture or the message arrays, so those stay as LazyValue placeholders. Each placeholder points back at the whole Parcel copy, so the copy and its duplicated memfd stay alive even after the app dies (Figure 9, right).

Why. SystemUI must be able to draw the notification at any moment, whether or not the app is running. So the record cannot depend on the app.

When it frees. On cancelNotification, on package removal or restart, or when the user is stopped; then Parcel.finalize() frees the native copy once the dropped record is collected. Notification history is cheaper: entries in the Archive are made with cloneLight(), which calls lightenPayload() to strip Parcelable and array entries.

For memory. One posted notification can cost its full Bundle copy in system_server's native heap plus its Bitmap pages, for as long as it is on screen. Sources: NotificationRecord.java, NotificationManagerService.java.

A PendingIntent keeps its Intent while anyone holds the token

The case. An app builds an Intent with, say, 64 KiB of extras, wraps it with PendingIntent.getBroadcast() and passes it to AlarmManager.set(). The app now holds only a token. The Intent itself lives in system_server.

Where the Intent lives. The app's PendingIntent wraps an IIntentSender, a Binder token. The real Intent and its mExtras sit in system_server inside PendingIntentRecord.Key, in the fields requestIntent, allIntents and creatorOptions. When the record is created, system_server copies the incoming Intent with new Intent(intent). That makes a fresh appendFrom() buffer on the heap, which stays parcelled because nothing reads it until the intent is sent.

What keeps it alive. Three kinds of holder, matching Figure 9 (left):

  • any process that holds a proxy for the token, through JavaBBinder's global reference;
  • an Alarm that stores it as its operation;
  • a NotificationRecord that stores it as contentIntent.

The record does not watch for the creator's death (no DeathRecipient). The controller's own lookup map holds it only weakly, so it does not count.

Why. The point of a PendingIntent is that it can fire after its creator is gone. An alarm set by a killed app must still wake it up.

When it frees. On explicit cancel, on package removal or force-stop, or when the last holder lets go. In that last case it also has to wait for a GC in system_server and two finalizer passes.

For memory. The release time depends on other processes and on GC timing, so it is not predictable from the app's lifetime. Sources: PendingIntentRecord.java, PendingIntentController.java.

Details: how the record is created and found

In ActivityManagerService.java, getIntentSenderWithFeatureAsApp() checks intent.hasFileDescriptors() directly on mParcelledData (the still-serialized bytes) without unparcelling, and then clones with new Intent(intent). PendingIntentController indexes records in mIntentSenderRecords, which stores only a WeakReference to each PendingIntentRecord.

Saved activity state is kept so a killed app can come back

When a user presses Home, the stopped activity sends its onSaveInstanceState() Bundle to system_server so Android can kill the cached process and still restore the screen later (Figure 11). activityStopped() verifies !icicle.hasFileDescriptors() on the raw bytes without unparcelling—refusing FDs because the state must stay valid without the app—and stores the 100% parcelled buffer in ActivityRecord.mIcicle until activityResumedLocked() clears it or the activity finishes. Sources: ActivityRecord.java, ActivityClientController.java.

Widgets unpack Bitmaps eagerly instead of pinning a Parcel

A launcher must be able to redraw a home-screen widget after the weather app that provides it has been killed, so AppWidgetServiceImpl.Widget retains views, maskedViews, and options. Unlike a Bundle, RemoteViews unpacks its actions and BitmapCache on arrival (Figure 11b): Bitmaps above 12 KiB live in memfd tracked by NativeAllocationRegistry (capped at 6 * screenWidth * screenHeight bytes), leaving only widget options and BUNDLE reflection actions as lazy Parcel copies. Sources: RemoteViews.java, Widget.java, AppWidgetServiceImpl.java.

When each of the nine holders lets go

The remaining five subsystems—JobStatus, Alarm, StickyBroadcast, ClipboardService, and MediaSessionRecord—complete the picture. Grouping all nine by what event frees them (Figure 11c) shows why app process death rarely reclaims system_server Parcel memory: eight of the nine outlive the sender by design, and only holders registered with kernel linkToDeath (MediaSessionRecord's onSessionDied and direct IAlarmListener callbacks, unlike PendingIntent alarms) drop their payloads when the app dies.

Part II · How Parcel's Accounting Evolved

4History: how Parcel gained, then lost, native memory accounting (2009–2021)

Two odd facts about Parcel.java—an unused 8-byte private long mNativeSize field on every instance, and zero native buffer bytes reported to ART's GC—come from four locally reasonable changes colliding between 2012 and 2021 (Figure 12a, Figure 12b).

Steps 1 & 2 (2012–2020): JNI speedups force return-value accounting that skips malloc. Switching Parcel's JNI methods to static in 2012 (~3× faster writeInt()) and marking primitive writers @CriticalNative in 2019–2020 stripped thiz and JNIEnv* from C++ calls. When unrecycled notification Bundles leaked shared memory in 2015, five FD-bearing JNI calls worked around that constraint by returning parcel->getOpenAshmemSize() to Java's updateNativeSize()—fixing the ashmem leak while leaving mData and mObjects heap buffers completely uncounted:

Parcel.java, Oct 2015 (0450565d9a6d) to Sep 2020 (c20809950691)private long mNativeSize; // only this line survived the 2020 removal

public final void appendFrom(Parcel parcel, int offset, int length) {
    // nativeAppendFrom returned parcel->getOpenAshmemSize() (never mDataCapacity):
    updateNativeSize(nativeAppendFrom(mNativePtr, parcel.mNativePtr, offset, length));
}

private void updateNativeSize(long newNativeSize) {
    if (mOwnsNativeParcelObject) {
        if (newNativeSize > Integer.MAX_VALUE) newNativeSize = Integer.MAX_VALUE;
        if (newNativeSize != mNativeSize) {
            int delta = (int) (newNativeSize - mNativeSize);
            if (delta > 0) VMRuntime.getRuntime().registerNativeAllocation(delta);
            else           VMRuntime.getRuntime().registerNativeFree(-delta);
            mNativeSize = newNativeSize;
        }
    }
}

Steps 3 & 4 (Sep 2020 – 2021): removing accounting right before LazyValue pins Parcels. In September 2020 (Android 12), updateNativeSize() was deleted for a ~3% ParcelObtainPerfTest gain under the assumption that variable-sized Parcels are explicitly recycle()d before GC matters—accidentally leaving private long mNativeSize declared on every instance. One year later (Android 13), item-wise Parcel.LazyValue unparcelling broke that assumption in system_server: reading one primitive key from a Bundle leaves LazyValue.mSource pinning the entire heap Parcel and its duplicated FDs for hours.

Where that leaves things. In AOSP today, a Java heap dump still shows a retained Bundle copy as a 48-byte Parcel shell (Figure P3). Its bytes appear only in native heap profiles under BaseBundle.readFromParcelInner → Parcel::appendFrom, which shows where the copy was made—not which system_server record in §3 still holds it.
