How Parcel holds native memory: its buffers, the copy a Binder call makes, and what keeps that copy alive in system_server

Android runs each app in an isolated process with no shared heap, so cross-process calls serialize arguments into a Parcel and pass them through the Binder kernel driver. A normal synchronous call copies the payload once into a read-only kernel mapping in the receiver and frees that slice before replying.

When the call carries a Bundle, system_server cannot deserialize custom app classes eagerly or keep the shared kernel slice past the reply, so BaseBundle allocates a native-heap buffer via malloc and copies the bytes out. This note traces how Parcel manages both buffer modes, how LazyValue and system_server retain app payloads, and how Parcel native-memory accounting evolved.

Checked against AOSP as of Android 17 (frameworks/base, frameworks/native/libs/binder, libcore) and the Android common kernel’s Binder driver.

At a glance

  • A normal Binder call copies once and retains zero bytes after replying. The caller writes arguments into a malloc-allocated buffer on its native heap; /dev/binder copies those bytes once into a shared read-only mapping in the receiver, and the receiver reads them in place before returning the slice to the driver.
  • Java Parcel pools do not pool payload buffers. Calling recycle() frees the C++ byte buffer and object-offset table back to the native heap immediately. The 32-slot Java pool caches only the small Java wrapper and its empty 120-byte C++ Parcel header.
  • Every lazy Bundle read from Binder allocates a native-heap copy via malloc. Because the incoming /dev/binder slice is reclaimed before the reply goes out, BaseBundle.readFromParcelInner() copies its byte range into a fresh heap-backed Parcel, duplicating every file descriptor and incrementing every Binder strong reference.
  • One unread LazyValue pins the entire copied Bundle buffer. Reading a primitive or string key unparcels the map lazily: length-prefixed entries (such as custom app Parcelables or notification Bitmaps) stay wrapped in Parcel.LazyValue placeholders whose strong references keep the whole backing Parcel and its duplicated shared-memory descriptors alive.
  • Unrecycled Parcels rely on finalize() and report zero bytes to the GC. ART’s garbage collector and Java heap dumps see only the small Java wrapper, not the native buffer bytes it owns. From 2015 to 2020 Parcel reported open ashmem FD sizes to the GC (never its heap buffers) before that reporting was removed (§5).

Terms.

  • Binder (/dev/binder): Android's kernel inter-process communication (IPC) driver. It moves messages between processes with a single copy and translates object handles and file descriptors along the way.
  • Owned Parcel: a C++ android::Parcel (mOwner == nullptr) whose mData byte buffer and mObjects offset array live on the native heap, allocated with malloc and realloc.
  • Borrowed Parcel: a C++ Parcel initialized via ipcSetDataReference() (mOwner != nullptr) whose pointers address the process's read-only ~1 MiB /dev/binder kernel mapping, released with BC_FREE_BUFFER rather than free().
  • ClassLoader: the Java loader that resolves class bytecode from a specific APK; system_server does not load untrusted app APKs into its own process.
  • LazyValue: a placeholder stored in BaseBundle.mMap during partial unparcelling for length-prefixed values (Parcelable, List, Map, arrays, Serializable); its mSource reference keeps the backing Parcel alive until that entry is read.
  • NativeAllocationRegistry (NAR): a libcore helper that frees a Java object's native memory through a Cleaner once the Java object becomes unreachable, and records a native size that heap dumps can attribute to it.
  • Scudo: Android's default native heap allocator, implementing malloc, realloc, and free in bionic.
  • ashmem / memfd: kernel shared-memory files. A process passes one by sending its file descriptor (FD); the underlying RAM pages stay allocated while any process holds an open FD.
  • flat_binder_object and cookie: the 24-byte record a Parcel writes for each Binder object or FD. For an FD, Parcel uses cookie = 1 to mean “this heap Parcel owns the FD and must close it”.
  • BC_* / BR_*: Binder driver commands. User space sends BC_ commands (for example BC_FREE_BUFFER, BC_REPLY) and the driver returns BR_ commands (for example BR_TRANSACTION).
  • Unparcel: deserialize the bytes of a Bundle back into Java key-value entries in its map.
Part I · How Parcel Allocates, Copies, and Stays Alive Across Processes

1A normal Binder call copies once, until a Bundle has to outlive it

Before looking at C++ struct fields or wrapper pools, it helps to trace what a Parcel is built to do on an ordinary cross-process call, and why carrying a Bundle into system_server forces a different memory path.

Why Parcel carries both flat bytes and a kernel object table

Android isolates each app in its own Linux UID and virtual address space with no shared heap. Starting an activity, posting a notification, registering a PendingIntent, or binding a service all cross a process boundary into system_server or another app.

A plain byte serializer such as JSON or Protocol Buffers over a socket can copy numbers and strings, but Android calls routinely pass live kernel capabilities too: remote IBinder object references (callbacks, tokens, service handles) and open file descriptors (such as shared-memory Bitmap buffers). A raw pointer or FD integer from one process has no meaning in another unless the kernel translates it and updates reference counts.

Parcel is the container designed around that split. It pairs a contiguous, aligned byte stream (mData) for primitive data with an out-of-band offset array (mObjects) pointing to every embedded Binder handle or FD inside the byte stream, so the /dev/binder driver can rewrite those slots in flight.

How a synchronous Binder call gets away with a single copy

Conventional user-space IPC over a pipe or UNIX socket copies every message twice: from the caller's buffer into kernel memory on write(), and from kernel memory into the receiver's heap buffer on read(). Binder cuts that to a single copy by pre-mapping a read-only window of /dev/binder pages (about 1 MiB per process) into every process's address space at startup (Figure 1a):

  1. Caller serializes onto its native heap. Generated AIDL stub code calls Parcel.obtain(), writes method arguments into a growable malloc-allocated buffer on the caller's native heap, and passes the Parcel to IBinder.transact().
  2. Kernel driver copies once into the receiver's mapping. Inside ioctl(BINDER_WRITE_READ), the driver carves a slice out of the receiver's shared ~1 MiB /dev/binder mapping, copies the caller's byte buffer directly into those physical pages once, rewrites any Binder handles and FDs recorded in the offset table, and wakes a Binder thread in the receiver.
  3. Receiver reads in place with zero heap allocation. On the woken Binder thread, IPCThreadState wraps that read-only kernel slice in a temporary, borrowed Parcel that allocates zero bytes on the native heap. The service's AIDL stub reads integers, strings, and known framework types directly out of the kernel-mapped slice, runs the method, and writes results into a reply Parcel.
  4. Both sides release their buffers immediately. Because all concurrent incoming calls to a process share that ~1 MiB /dev/binder window, no call can hold onto its slice. Before sending BC_REPLY, IPCThreadState closes any transient FDs in the request buffer and sends BC_FREE_BUFFER so the driver reclaims the slice at once; back in the caller, recycle() frees the request's native-heap buffer and releases the reply's kernel slice.

Why Bundle breaks single-copy IPC and copies onto the native heap

That single-copy flow works whenever the receiver knows every parameter's concrete type at compile time and finishes reading before onTransact() returns. Carrying a Bundle into system_server breaks both assumptions at once (Figure 1b):

  • system_server cannot safely or eagerly instantiate app classes. An Intent's extras or a Notification's extras map is an open key-value Bundle into which an app can pack custom Parcelable subclasses alongside framework keys. system_server does not have the sending app's APK ClassLoader, cannot run untrusted app CREATOR code inside the system process, and has no reason to spend CPU deserializing keys it is only forwarding to another app.
  • Stored payloads outlive the Binder call. Registering a PendingIntent, posting a notification, saving stopped activity state (mIcicle), or sending a sticky broadcast parks the Bundle inside system_server long after onTransact() returns and BC_FREE_BUFFER hands the shared /dev/binder slice back to the kernel.

To satisfy both constraints, BaseBundle escapes the transient kernel buffer without deserializing its entries: it obtains a heap-backed Parcel, allocates a buffer on the native heap via malloc, copies its byte slice out with Parcel::appendFrom(), and duplicates every FD in that slice. If system_server later reads a framework key, Parcel.LazyValue skips length-prefixed Parcelable entries in constant time while keeping a strong reference to that copied Parcel.

Supporting both halves of Figure 1 — zero-allocation borrowed slices for every incoming Binder call, and self-owned, growable heap buffers for outgoing requests and retained Bundles — is why a single Parcel class carries two wrapper pools and two C++ buffer-ownership modes.

2Inside a Parcel: ownership modes, pools, wire layout, and buffer resize paths

Because one Parcel class backs both borrowed kernel slices and heap-allocated buffers, its implementation across Parcel.java, Parcel.h, and Parcel.cpp branches on three independent choices:

  • Who owns the C++ object (Java side). A Java Parcel either owns a heap-allocated android::Parcel or temporarily wraps a stack-allocated C++ Parcel during an incoming Binder call.
  • Who owns the bytes (C++ side). Its data pointer addresses either a malloc-allocated buffer on the native heap or the read-only /dev/binder kernel mapping.
  • Which transport. Its object table is either kernel Binder (KernelFields) or socket-based RPC Binder (RpcFields), held in one std::variant.

Most methods in Parcel.cpp check these state variables before reading or mutating buffers.

Two Java pools and two C++ buffer ownership modes

One Java flag and one C++ callback pointer determine who owns the C++ struct and who owns the payload buffers (Figure 2):

  • Java wrapper ownership (mOwnsNativeParcelObject): In Parcel.java, each instance holds mNativePtr (the android::Parcel*) and mOwnsNativeParcelObject. Two static singly-linked lists guarded by sPoolSync cache up to POOL_SIZE = 32 wrappers each:
    • sOwnedPool backs public Parcel.obtain(): mOwnsNativeParcelObject = true, pointing to a 120-byte heap new Parcel() allocated via nativeCreate() in android_os_Parcel.cpp.
    • sHolderPool backs the hidden protected static Parcel.obtain(long ptr) called by Binder.java during execTransact(): mOwnsNativeParcelObject = false, temporarily wrapping the C++ Parcel buffer and Parcel reply variables on the Binder thread's stack inside IPCThreadState::executeCommand().
  • C++ buffer ownership (Parcel::mOwner): In Parcel.cpp, mOwner == nullptr means the Parcel owns its heap buffers (allocated with malloc/realloc and released with free()). When mOwner != nullptr, mOwner is a release_func callback (IPCThreadState::freeBuffer) and mData and mObjects point directly into the read-only ~1 MiB /dev/binder kernel mapping, allocating zero bytes on the native heap.

When caller code invokes parcel.recycle() on an owned Parcel, Java calls freeBuffer() → nativeFreeBuffer() → Parcel::freeData() before returning the wrapper to sOwnedPool. Because occasional transactions grow to tens or hundreds of kilobytes, keeping mData attached across 32 pool slots in every process would strand megabytes of idle native heap.

Freeing mData and mObjects immediately lets Scudo's thread caches reuse small blocks across the whole process while pooling still saves a Java allocation and a 120-byte new Parcel() struct on every RPC. If sOwnedPool is already full or a Parcel is dropped without recycle(), cleanup waits for Parcel.finalize() → destroy() → delete parcel.

frameworks/base/core/java/android/os/Parcel.java · recycle() & finalize()public final void recycle() {

Byte-level struct layout (120 B) and how mObjects indexes into mData

Parcel serializes primitive values and kernel handles inline into the same mData buffer, then tracks the byte offsets of kernel handles in a separate array so the Binder driver can rewrite them during IPC. On 64-bit Android, sizeof(android::Parcel) is fixed at 120 bytes by a static_assert in Parcel.cpp. Figure 3 shows that header and the two buffers it manages:

  1. mData (mDataCapacity bytes, word-aligned stream): Every primitive write widens smaller values (bool, byte, char16_t) to 4 bytes and pads strings and byte arrays with trailing zeroes to a 4-byte boundary so kernel structures stay aligned and uninitialized heap padding never leaks across processes. Three cursors track the stream: mDataPos (read/write cursor), mDataSize (high-water mark of valid bytes, updated whenever mDataPos advances past it), and mDataCapacity (allocated buffer length).
  2. KernelFields::mObjects (mObjectsCapacity * 8 bytes): Writing an IBinder or FD via writeObject() places a 24-byte flat_binder_object inline in mData at mDataPos and appends that offset to mObjects[]:
    • Overwrite protection (validateReadData): Checks mObjects[] (via mNextObjectHint) so primitive reads or writes never straddle or forge a flat_binder_object.
    • Reference counting & FD ownership: acquire_object() calls IBinder::incStrong and tags owned FDs with fdsan (FdTag); teardown walks mObjects[] in reverse calling release_object() (decStrong and FdTagClose when flat.cookie != 0).
  3. Out-of-line shared memory descriptors: Parcel::writeBlob() writes byte arrays up to BLOB_INPLACE_LIMIT = 16 KiB inline inside mData; above that limit it allocates an ashmem region ("Parcel Blob") and writes a BINDER_TYPE_FD record into mData + mObjects. Likewise, Bitmap.cpp writes pixel buffers up to 12 KiB inline and places larger Bitmaps into a sealed memfd file descriptor stored in mObjects.

Buffer growth, truncation, and reset: growData, continueWrite, restartWrite, and appendFrom

Parcel.cpp splits buffer resizing across four helpers because sequential writes, slice copies, truncation, and full buffer replacement treat mDataCapacity and mObjects differently (Figures 4 and 5):

  • Sequential writes (writeInt32, writeString16, writeInplace) call growData(len): computes newSize = ((mDataSize + len) * 3) / 2 (1.5x geometric growth) and calls continueWrite(max(newSize, 128)), enforcing a 128 B floor.
  • appendFrom() uses the same growth rule: if mDataPos + len exceeds mDataCapacity, it calls growData(len). Even the first copy into an empty Parcel — the path BaseBundle.readFromParcelInner() takes — allocates max(len * 3 / 2, 128) bytes, so a long-lived Bundle copy can carry up to a third more capacity than its payload. Growth of mObjects inside appendFrom() also scales by 1.5x.
  • Only restartWrite(desired), freeData(), and ~Parcel() shrink or release mData: restartWrite() (called by the C++ Parcel::setData()) releases all objects right away and calls realloc(mData, desired) even when desired < mDataCapacity. Meanwhile, dumpsys meminfo's Parcel memory counter (gParcelGlobalAllocSize) tracks only owned mDataCapacity, ignoring the 120-byte struct, mObjects, borrowed Binder mmap pages, and ashmem/memfd regions.

All other write and truncation calls funnel into continueWrite(desired). If desired < mDataSize, it first sorts mObjects and identifies any objects past desired so their references and FDs can be released, then branches on buffer ownership:

  1. mOwner != nullptr (borrowed kernel mmap): if desired == 0, calls freeData(); otherwise performs copy-on-write takeover into a fresh malloc(desired) buffer and calloc object array, calls reacquireObjects(), flips kept FD cookies to 1, closes dropped FDs, invokes mOwner() to release the kernel buffer, and clears mOwner = nullptr.
  2. mData != nullptr (already heap-owned): releases any truncated objects and shrinks mObjects via realloc, then if desired > mDataCapacity runs realloc(mData, desired); if desired <= mDataCapacity (such as setDataSize(0)), it clamps mDataSize and mDataPos without shrinking mDataCapacity.
  3. mData == nullptr (first allocation on an owned Parcel): runs malloc(desired).

3Kernel Binder translation, appendFrom FD duplication, and the BaseBundle + LazyValue state machine

Section 1 outlined why a Bundle cannot stay inside the incoming /dev/binder slice and instead ends with a native-heap copy allocated via malloc inside Parcel::appendFrom. Tracing one transaction from the kernel driver into android.os.BaseBundle shows where each buffer copy, strong reference, and duplicated file descriptor is created.

Across the Binder call: one kernel copy, FD installation, and pre-reply free

When a process opens /dev/binder, ProcessState.cpp maps BINDER_VM_SIZE = 1 MiB - 2 * PAGE_SIZE as PROT_READ, MAP_PRIVATE | MAP_NORESERVE—1,016 KiB on 4 KiB-page builds.

On 16 KiB-page builds that window is 992 KiB. During ioctl(BINDER_WRITE_READ), the kernel driver copies the sender's user-space mData buffer once into pages inside the receiver's mVMStart range, walking mObjects[] to translate local BINDER_TYPE_BINDER pointers into remote BINDER_TYPE_HANDLE descriptors and taking a reference on the file behind every BINDER_TYPE_FD entry for installation on read (Figure 6).

In IPCThreadState.cpp, executeCommand(BR_TRANSACTION) wraps that kernel slice in a stack Parcel buffer via ipcSetDataReference(..., freeBuffer). Because all concurrent incoming transactions share that ~1 MiB mapping, system_server cannot retain pointers into mVMStart after onTransact returns; for synchronous calls, IPCThreadState runs buffer.setDataSize(0), closing the buffer's FDs and queueing BC_FREE_BUFFER ahead of BC_REPLY.

When BaseBundle copies its slice via appendFrom() (Figure 6), appendFrom() calls fcntl(fd, F_DUPFD_CLOEXEC, 0) to create a second FD (with cookie = 1) owned by the heap Parcel. When IPCThreadState closes the transient kernel-installed FD at transaction teardown, that duplicate FD keeps the shared memfd or ashmem inode open in system_server.

BaseBundle.readFromParcelInner and the four-state LazyValue lifecycle

Apps pass custom Parcelable classes inside Intent extras, notification extras, and saved-state bundles. Because system_server lacks the app's APK ClassLoader—and running untrusted app Parcelable constructors inside system_server would open deserialization exploits—BaseBundle.java defers deserialization by copying the raw bytes into an owned heap Parcel during readFromParcelInner():

frameworks/base/core/java/android/os/BaseBundle.java · readFromParcelInner()Parcel p = Parcel.obtain();
p.setDataPosition(0);
p.appendFrom(parcel, offset, length); // malloc(max(length * 3/2, 128)) + memcpy + incStrong(binders) + dup(FDs)
p.adoptClassCookies(parcel);
mParcelledData = p; // State 1: mMap remains null until any key is read

From that initial copy, a BaseBundle moves through a four-state machine governed by mParcelledData, mMap, mWeakParcelledData, mLazyValues, and mOwnsLazyValues (Figures 7 and 8):

  1. State 1 — Fully parcelled (mParcelledData != null, mMap == null): Zero keys have been read yet (for example, ActivityRecord.mIcicle or PendingIntentRecord.Key.requestIntent.mExtras). Calling bundle.hasFileDescriptors() scans mParcelledData directly in C++ without unparcelling. Cloning via new Intent(orig) or new Bundle(orig) calls appendFrom() again, allocating a second native-heap buffer and duplicating every FD a second time.
  2. State 2a — Unparcelled with zero lazy items (numLazyValues == 0): When code reads any key (e.g. extras.getBoolean(...)), initializeFromParcelLocked() runs Parcel.readArrayMap(). Primitives, Strings, and nested Bundles are materialized eagerly (each nested Bundle makes its own appendFrom() copy). If every entry was eager, BaseBundle calls parcelledData.recycle() immediately, freeing mData.

  3. State 2b — Partially unparcelled with LazyValue entries (mLazyValues > 0): Length-prefixed values—VAL_PARCELABLE, VAL_LIST, VAL_MAP, VAL_PARCELABLEARRAY, VAL_OBJECTARRAY, VAL_SPARSEARRAY, and VAL_SERIALIZABLE—store a 4-byte length header right after their type tag in mData (Figure 8, bottom).

    Parcel.readLazyValue() reads type and length, advances mDataPos by length bytes in constant time without loading any ClassLoader, and inserts new Parcel.LazyValue(sourceParcel, startPos, totalLen, type, bundle) into mMap. BaseBundle then clears mParcelledData = null and stores mWeakParcelledData = new WeakReference<>(parcelledData); each LazyValue.mSource strong reference keeps the entire backing Parcel—including already-parsed string bytes and duplicated FDs—allocated.

  4. State 3 vs State 4 — Early destroy() vs shared LazyValue copies: Calling getParcelable(key) invokes unwrapLazyValueFromMapLocked(), which runs LazyValue.apply() (deserializing the slice and setting LazyValue.mSource = null), replaces the map entry with the materialized object, and decrements mLazyValues.

    When mOwnsLazyValues is true and mLazyValues reaches 0, BaseBundle calls mWeakParcelledData.get().destroy() immediately. If code copies an already-unparcelled Bundle via new Bundle(unparcelledSrc), the copy constructor shares the same LazyValue objects across both ArrayMaps and sets mOwnsLazyValues = false on both bundles, skipping eager parcel.destroy() so the native buffer remains allocated until GC and finalization.

4Cross-process retention and system_server holders

Three kernel mechanisms allow a Parcel or Binder token in one process to keep memory allocated in another (Figure 9):

  1. Remote BpBinder → local JavaBBinderExt JNI global ref. When an app holds a BinderProxy (or an unrecycled Parcel containing BINDER_TYPE_HANDLE), BpBinder.cpp holds a kernel strong reference (BC_ACQUIRE) on the target binder node. In the owning process, android_util_Binder.cpp keeps a JNI NewGlobalRef inside JavaBBinderExt until the kernel delivers BR_RELEASE. Any Java fields reachable from that Binder subclass—including parcelled Bundle buffers—cannot be garbage-collected while any client proxy lives.
  2. Duplicated ashmem and memfd descriptors. Because Parcel::appendFrom() duplicates every file descriptor in mObjects, system_server's copy of a Bundle holds its own open file description on the underlying anonymous shared memory inode. Even if the sending app unmaps its Bitmap or dies and gets reaped, those physical RAM or zram pages persist until system_server destroys its Parcel.
  3. Unreleased Binder mmap slices. A client that forgets to call reply.recycle() pins a slice of its own ~1 MiB Binder mmap until finalization; if enough slices accumulate, subsequent incoming calls fail with FAILED_TRANSACTION.

System_server subsystems that retain app Parcel memory

Native allocation stacks point at BaseBundle.readFromParcelInner, which records where buffers are allocated rather than which Java objects retain them. Across frameworks/base/services, nine subsystems retain most app-originated Parcel and shared-memory buffers (Table 2):

  • PendingIntentRecord (PendingIntentRecord.java, PendingIntentController.java). A client's PendingIntent wraps only an IIntentSender Binder token; the actual Intent and its mExtras live in system_server inside PendingIntentRecord.Key (requestIntent, allIntents, options).

    In ActivityManagerService.java, getIntentSenderWithFeatureAsApp() checks intent.hasFileDescriptors() directly on mParcelledData without unparcelling, then clones via new Intent(intent), producing a fresh appendFrom() heap buffer that sits parcelled. The controller's map (mIntentSenderRecords) stores only a WeakReference; what keeps the record alive is JavaBBinderExt's JNI global ref while any client process holds a proxy, or local references from alarms and notifications. No DeathRecipient is used.

  • NotificationRecord (NotificationRecord.java, NotificationManagerService.java). Holds StatusBarNotification → Notification.java, including extras (lazy Bundle), contentView/bigContentView (eager RemoteViews), and contentIntent (pinning a PendingIntentRecord). Enqueueing runs fixNotification(), and for non-system senders Notification.visitUris() unwraps message lists, people, and most icon extras; "android.picture" and unknown app keys stay LazyValue entries pinning the Parcel and duplicated memfds past app death (unless replaced by a flagged Android 17 content-URI icon, or stripped for Archive via cloneLight() → lightenPayload()).
  • AppWidgetServiceImpl.Widget (AppWidgetServiceImpl.java, where Widget is a nested class). Stores views, maskedViews (RemoteViews.java), and options (lazy Bundle), alongside Provider.generatedPreviews. Unlike Bundle, RemoteViews(Parcel) unparcels its action list and BitmapCache eagerly on receipt (capped by AppWidgetServiceImpl's mMaxWidgetBitmapMemory at 6 * screenWidth * screenHeight bytes, with Bitmaps above 12 KiB backed by memfd), except reflection actions of type BUNDLE, which retain lazy Parcel copies.
  • ActivityRecord saved state (ActivityRecord.java, ActivityClientController.java). When a backgrounded activity stops, activityStopped() verifies !icicle.hasFileDescriptors() without unparcelling and stores mIcicle completely parcelled in system_server alongside ActivityRecord.intent. If lmkd (the low-memory killer daemon) kills the cached app, mIcicle stays on system_server's native heap so Android can recreate the activity later, releasing only when the activity resumes (setSavedState(null)) or finishes.
  • JobStatus, Alarm, StickyBroadcast, ClipboardService, and MediaSessionRecord. JobInfo.java holds lazy extras (PersistableBundle) and transientExtras (Bundle, which can carry arbitrary Parcelables and IBinders); Alarm.java pins PendingIntentRecord via operation; BroadcastController.java retains cloned StickyBroadcast.intent extras across sender death; ClipboardService.java retains per-user primaryClip extras; and MediaSessionRecord.java unparcels string URIs in mMetadata while leaving album-art Bitmaps as LazyValue entries until session close or binderDied().

5How Parcel has reported its native memory, 2009–2021

Two opposing pressures shaped Parcel.java and android_os_Parcel.cpp between Android 1.5 and Android 17 (Table 3). Every synchronous Binder call marshals and unmarshals Parcels on the critical IPC path, pushing JNI downcalls toward static raw-pointer methods and @FastNative / @CriticalNative transitions that pass no Java object reference into C++.

Pulling the other way is garbage-collector visibility: whenever an unrecycled Bundle retains a Parcel, ART sees only a 56-byte Java wrapper unless Java tracks its native bytes. Android 7.0 started reporting open ashmem FD sizes to the GC, though never heap mData or mObjects.

Android 12 removed that accounting on the assumption that callers free variable-sized buffers via recycle() before GC runs. A release later, Android 13 introduced Parcel.LazyValue, keeping Bundle copies unrecycled for as long as an unread length-prefixed entry remains (§3).

Table 3. Changes to how Parcel reports native memory. Commit IDs are in AOSP frameworks/base.

Stores private int mObject and private int mOwnObject; every JNI method is an instance call that looks up gParcelOffsets.mObject via parcelForJavaObject(env, obj); caches 6 instances in Parcel[6] arrays; uses finalize() -> destroy(). 0 B reported to the Dalvik GC; finalize() is the only fallback for unrecycled Parcels.
Mar 2012
Android 4.1 (Jelly Bean)		 047238ced42e "Switch Parcel to static JNI calls, pass pointer." Replaces instance JNI calls with static JNI methods taking an explicit int nativePtr (~3x faster writeInt()). Renames mObject → mNativePtr and mOwnObject → boolean mOwnsNativeParcelObject. From here on, the C++ side of each JNI call receives only the native pointer, not the Java Parcel object.
Jan 2014
Android 5.0 (Lollipop)		 8ab665dda40a 64-bit ARM (arm64-v8a) transition widens mNativePtr and all JNI pointer parameters from int to long. mNativePtr widens from 4 to 8 bytes on LP64.
Oct 2015
Android 7.0 (Nougat)		 0450565d9a6d Parcel starts reporting ashmem sizes to the GC ("Track ashmem memory usage in Parcel"). Unrecycled Bundles could hold Parcels with duplicated ashmem FDs while ART saw only small Java objects. The change makes 5 JNI downcalls (nativeSetDataSize, nativeWriteFileDescriptor, nativeFreeBuffer, nativeUnmarshall, nativeAppendFrom) return jlong (parcel->getOpenAshmemSize()) instead of void, and adds updateNativeSize(long), which passes the change in size to VMRuntime.registerNativeAllocation(delta) / registerNativeFree(-delta). Reports open ashmem FD bytes to the ART GC, but never mData or mObjects heap buffers.
Oct 2019 – Jun 2020
Android 11 / 12		 012ab8e9faf8
bfac2652b0f4		 Marks non-primitive marshalling methods @FastNative (~80 ns faster per call) and converts nativeWrite{Int,Long,Float,Double} to @CriticalNative returning int (status_t) instead of throwing exceptions from C++. Primitive writers no longer receive JNIEnv* or leave the Runnable state.
Sep 2020
Android 12 (S)		 c20809950691 The ashmem size reporting is removed. Deletes updateNativeSize() and import dalvik.system.VMRuntime, and turns the 5 JNI methods back to void, for a ~3% ParcelObtainPerfTest improvement. The reasoning is that variable-sized allocations are already freed by explicit recycle() before GC runs. (The linked-list pool had replaced the 6-slot arrays in an earlier, separate change.) 9293dca91c5a		 Android 13 adds item-wise Parcel.LazyValue unparcelling to BaseBundle.java. Unread length-prefixed entries stay wrapped in LazyValue instances whose mSource field holds a strong reference to the backing Parcel. These two follow-up commits make LazyValue.writeToParcel() use appendFrom and synchronize LazyValue.get(). In system_server, reading one primitive key from a Bundle leaves mSource unrecycled for as long as any unread length-prefixed key remains in the map.
Oct 2021

Sources

All paths are in AOSP as of Android 17, except the Binder driver, which is in the Android common kernel.

  • Parcel and Binder, Java and JNI: frameworks/base/core/java/android/os/Parcel.java (pools, recycle(), LazyValue), frameworks/base/core/java/android/os/Binder.java (execTransact()), frameworks/base/core/jni/android_os_Parcel.cpp (JNI methods), frameworks/base/core/jni/android_util_Binder.cpp (JavaBBinderExt global references).
  • Parcel and Binder, C++: frameworks/native/libs/binder/Parcel.cpp and frameworks/native/libs/binder/include/binder/Parcel.h (layout, buffer growth, object tracking), frameworks/native/libs/binder/IPCThreadState.cpp (incoming transactions, freeBuffer), frameworks/native/libs/binder/ProcessState.cpp (the Binder mmap), frameworks/native/libs/binder/BpBinder.cpp (remote references).
  • Kernel: drivers/android/binder.c in the Android common kernel (transaction copy, handle and FD translation).
  • Bundle and Bitmap: frameworks/base/core/java/android/os/BaseBundle.java, frameworks/base/core/java/android/os/Bundle.java, frameworks/base/libs/hwui/jni/Bitmap.cpp (inline vs memfd pixels), frameworks/base/core/java/android/widget/RemoteViews.java, frameworks/base/core/java/android/app/Notification.java.
  • system_server holders: frameworks/base/services/core/java/com/android/server/am/ (PendingIntentRecord.java, PendingIntentController.java, ActivityManagerService.java, BroadcastController.java), frameworks/base/services/core/java/com/android/server/notification/ (NotificationRecord.java, NotificationManagerService.java), frameworks/base/services/appwidget/java/com/android/server/appwidget/ (AppWidgetServiceImpl.java, including the nested Widget class), frameworks/base/services/core/java/com/android/server/wm/ (ActivityRecord.java, ActivityClientController.java), frameworks/base/apex/jobscheduler/framework/java/android/app/job/JobInfo.java, frameworks/base/apex/jobscheduler/service/java/com/android/server/alarm/Alarm.java, frameworks/base/services/core/java/com/android/server/clipboard/ClipboardService.java, frameworks/base/services/core/java/com/android/server/media/MediaSessionRecord.java.
