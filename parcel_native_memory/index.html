How Parcel holds native memory: its buffers, the copy a Binder call makes, and what keeps that copy alive in system_server

An incoming Binder transaction starts in a buffer the kernel maps into the receiving process. Reading a Bundle out of it copies the bytes into malloc, and that copy can stay allocated in system_server behind a PendingIntent, a notification, saved activity state, a queued broadcast, or an app widget. This note follows that path. It covers how a Parcel lays out and grows its buffers, how the Binder driver and BaseBundle copy them, which system_server structures hold on to app payloads, and how the Java Parcel class has reported its native memory over the years.

Checked against AOSP as of Android 17 (frameworks/base, frameworks/native/libs/binder, libcore) and the Android common kernel’s Binder driver.

At a glance

  • Java Parcel pools do not pool data buffers. Calling recycle() invokes Parcel::freeData() immediately, freeing mData and mObjects back to Scudo. The 32-entry sOwnedPool caches only the Java object and its empty 120-byte C++ Parcel header.
  • Every lazy Bundle read from Binder copies into malloc. Incoming transactions use a shared ~1 MiB driver mmap that IPCThreadState frees before sending the reply. BaseBundle.readFromParcelInner() copies its byte range into a heap Parcel via appendFrom(), duplicating every file descriptor and incrementing every embedded Binder strong reference.
  • One unread LazyValue retains the entire Bundle buffer. When system_server reads a primitive or string key from a Bundle, top-level unparcelling leaves length-prefixed Parcelable entries (such as notification Bitmaps) wrapped in Parcel.LazyValue. Each LazyValue.mSource holds a strong reference to the whole copied Parcel and its duplicated ashmem or memfd descriptors.
  • Parcel is freed by finalize(). An unrecycled Parcel is cleaned up only when its Java object is finalized. ART’s garbage collector and Java heap dumps see the small Java object, not the native buffer bytes it owns.
  • The Java class once reported some native memory to the GC. From 2015 to 2020, Parcel told ART about the size of open ashmem file descriptors (never mData or mObjects). That reporting was removed in 2020 (§4).

Terms.

  • Owned Parcel: a C++ android::Parcel with mOwner == nullptr whose mData byte buffer and mObjects offset array live on the native heap (Scudo malloc).
  • Borrowed Parcel: a C++ Parcel initialized via ipcSetDataReference() with mOwner != nullptr whose pointers address the process's read-only ~1 MiB /dev/binder kernel mapping, released with BC_FREE_BUFFER rather than free().
  • LazyValue: a placeholder stored in BaseBundle.mMap during partial unparcelling for length-prefixed values (Parcelable, List, Map, arrays, Serializable); its mSource reference keeps the backing Parcel alive until that entry is read.
  • NativeAllocationRegistry (NAR): a libcore helper that frees a Java object's native memory through a Cleaner once the Java object becomes unreachable, and records a native size that heap dumps can attribute to it.
  • Scudo: Android's default native allocator, the code behind malloc, realloc and free.
  • ashmem / memfd: kernel shared-memory files. A process passes one by sending its file descriptor (FD); the memory stays allocated while any process holds an open FD.
  • flat_binder_object and cookie: the 24-byte record a Parcel writes for each Binder object or FD. For an FD, Parcel uses cookie = 1 to mean “this Parcel owns the FD and must close it”.
  • BC_* / BR_*: Binder driver commands. User space sends BC_ commands (for example BC_FREE_BUFFER, BC_REPLY) and the driver returns BR_ commands (for example BR_TRANSACTION).
  • Unparcel: turn the bytes of a Bundle back into Java objects in its map.
Part I · How Parcel Allocates, Copies, and Stays Alive Across Processes

1Inside a Parcel: ownership modes, pools, wire layout, and buffer resize paths

One Parcel class name covers several configurations, spread across Parcel.java, Parcel.h, and Parcel.cpp. Three independent choices define them:

  • Who owns the C++ object (Java side). A Java Parcel either owns a heap-allocated android::Parcel or temporarily wraps a stack-allocated C++ Parcel during an incoming Binder call.
  • Who owns the bytes (C++ side). Its data pointer addresses either Scudo's malloc heap or the read-only /dev/binder kernel mapping.
  • Which transport. Its object table is either kernel Binder (KernelFields) or socket-based RPC Binder (RpcFields), held in one std::variant.

Most methods in Parcel.cpp branch on these three state variables before reading or writing bytes.

Two Java pools and two C++ buffer ownership modes

One Java flag and one C++ callback pointer determine who owns the C++ struct and who owns the payload buffers (Figure 1):

  • Java wrapper ownership (mOwnsNativeParcelObject): In Parcel.java, each instance holds mNativePtr (the android::Parcel*) and mOwnsNativeParcelObject. Two static singly-linked lists guarded by sPoolSync cache up to POOL_SIZE = 32 wrappers each:
    • sOwnedPool backs public Parcel.obtain(): mOwnsNativeParcelObject = true, pointing to a 120-byte heap new Parcel() allocated via nativeCreate() in android_os_Parcel.cpp.
    • sHolderPool backs the hidden protected static Parcel.obtain(long ptr) called by Binder.java during execTransact(): mOwnsNativeParcelObject = false, temporarily wrapping the C++ Parcel buffer and Parcel reply variables on the Binder thread's stack inside IPCThreadState::executeCommand().
  • C++ buffer ownership (Parcel::mOwner): In Parcel.cpp, mOwner == nullptr means the Parcel owns its heap buffers (allocated with malloc/realloc and released with free()). When mOwner != nullptr, mOwner is a release_func callback (IPCThreadState::freeBuffer) and mData and mObjects point directly into the read-only ~1 MiB /dev/binder kernel mapping; zero bytes come from malloc.

When caller code invokes parcel.recycle() on an owned Parcel, Java calls freeBuffer() → nativeFreeBuffer() → Parcel::freeData() before returning the wrapper to sOwnedPool. That immediately frees mData and mObjects back to Scudo and resets capacities to zero; pooling saves only one Java object allocation and one 120-byte new Parcel() struct allocation. If sOwnedPool is full (32 entries) or a Parcel is dropped without recycle(), cleanup waits for Parcel.finalize() → destroy() → delete parcel.

frameworks/base/core/java/android/os/Parcel.java · recycle() & finalize()public final void recycle() {
    mRecycled = true;
    freeBuffer(); // if (mOwnsNativeParcelObject) nativeFreeBuffer(mNativePtr) -> free(mData)
    if (mOwnsNativeParcelObject) {
        synchronized (sPoolSync) {
            if (sOwnedPoolSize < POOL_SIZE) { // POOL_SIZE = 32; keeps 120 B C++ shell only
                mPoolNext = sOwnedPool; sOwnedPool = this; sOwnedPoolSize++;
            }
        }
    } else {
        mNativePtr = 0; // holder wrapper detaches from IPCThreadState stack Parcel
        synchronized (sPoolSync) { if (sHolderPoolSize < POOL_SIZE) { ... } }
    }
}
protected void finalize() throws Throwable { destroy(); } // no NativeAllocationRegistry

Byte-level struct layout (120 B) and how mObjects indexes into mData

Parcel serializes primitive values and kernel handles inline into the same mData buffer, then tracks the byte offsets of kernel handles in a separate array so the Binder driver can rewrite them during IPC. On 64-bit Android, sizeof(android::Parcel) is fixed at 120 bytes by a static_assert in Parcel.cpp. Figure 2 shows the 120-byte header and the two buffers it manages:

  1. mData (mDataCapacity bytes, 4-byte aligned stream): Every primitive write widens sub-32-bit values (bool, byte, char16_t) to 4 bytes and pads strings and byte arrays with trailing zeroes to a 4-byte boundary so kernel structures stay aligned and uninitialized heap padding never leaks across processes. Three cursors track the stream: mDataPos (read/write cursor), mDataSize (high-water mark of valid bytes, updated whenever mDataPos advances past it), and mDataCapacity (allocated buffer length).
  2. KernelFields::mObjects (mObjectsCapacity * 8 bytes): Whenever code writes an IBinder or file descriptor, writeObject() writes a 24-byte flat_binder_object directly into mData at the current mDataPos, and appends that byte offset into the separate mObjects[] side-table. Two details in Parcel.cpp exist solely because of this dual structure:
    • Overwrite protection (validateReadData): Before reading primitives or appending bytes, Parcel checks mObjects[] (using mNextObjectHint) to ensure sequential primitive reads or writes do not straddle or forge a flat_binder_object slot.
    • Reference counting & FD ownership: Writing an object calls acquire_object() (IBinder::incStrong, plus fdsan FdTag on owned FDs); freeing or truncating walks mObjects[] in reverse calling release_object() (decStrong and FdTagClose when flat.cookie != 0).
  3. Out-of-line shared memory descriptors: Parcel::writeBlob() writes byte arrays up to BLOB_INPLACE_LIMIT = 16 KiB inline inside mData; above 16 KiB it allocates an ashmem region ("Parcel Blob") and writes a BINDER_TYPE_FD record into mData + mObjects. Likewise, Bitmap.cpp writes pixel buffers up to 12 KiB inline and places larger Bitmaps into a sealed memfd file descriptor stored in mObjects.

Buffer growth, truncation, and reset: growData, continueWrite, restartWrite, and appendFrom

Parcel.cpp splits buffer resizing across four helpers because sequential writes, slice copies, truncation, and full buffer replacement treat mDataCapacity and mObjects differently (Figures 3 and 4):

  • Sequential writes (writeInt32, writeString16, writeInplace) call growData(len): computes newSize = ((mDataSize + len) * 3) / 2 (1.5x geometric growth) and calls continueWrite(max(newSize, 128)), so the minimum is 128 B.
  • appendFrom() uses the same growth rule: if mDataPos + len exceeds mDataCapacity, it calls growData(len). Even the first copy into an empty Parcel, which is the path BaseBundle.readFromParcelInner() takes, allocates max(len * 3 / 2, 128) bytes, so a long-lived Bundle copy can carry up to a third more capacity than its payload. Growth of mObjects inside appendFrom() also scales by 1.5x.
  • continueWrite(desired) is a three-way state machine: first, if desired < mDataSize, it sorts mObjects and identifies any objects sitting past desired so their references and FDs can be released. Then it branches on buffer state:
    1. mOwner != nullptr (borrowed kernel mmap): if desired == 0, calls freeData(); otherwise performs copy-on-write takeover into fresh malloc(desired) + calloc object array, calls reacquireObjects(), flips kept FD cookies to 1, closes dropped FDs, invokes mOwner() to release the kernel buffer, and clears mOwner = nullptr.
    2. mData != nullptr (already heap-owned): releases any truncated objects and shrinks mObjects via realloc, then if desired > mDataCapacity runs realloc(mData, desired); if desired <= mDataCapacity (such as setDataSize(0)), it clamps mDataSize and mDataPos without shrinking mDataCapacity.
    3. mData == nullptr (first allocation on an owned Parcel): runs malloc(desired).
  • Only restartWrite(desired), freeData(), and ~Parcel() shrink or release mData: restartWrite() (called by the C++ Parcel::setData()) releases all objects right away and calls realloc(mData, desired) even when desired < mDataCapacity. Meanwhile, dumpsys meminfo's Parcel memory counter (gParcelGlobalAllocSize) tracks only owned mDataCapacity, ignoring the 120-byte struct, mObjects, borrowed Binder mmap pages, and ashmem/memfd regions.

2Kernel Binder translation, appendFrom FD duplication, and the BaseBundle + LazyValue state machine

Incoming Binder transactions arrive in kernel-mapped memory, yet reading a Bundle from one in system_server ends with a malloc copy made by Parcel::appendFrom. Following one transaction from the kernel driver into android.os.BaseBundle shows where each buffer copy, strong reference, and duplicated file descriptor is created.

Across the Binder call: one kernel copy, FD installation, and pre-reply free

When a process opens /dev/binder, ProcessState.cpp maps BINDER_VM_SIZE = 1 MiB - 2 * PAGE_SIZE (1,016 KiB with 4 KiB pages, 992 KiB with 16 KiB pages) as PROT_READ, MAP_PRIVATE | MAP_NORESERVE. During ioctl(BINDER_WRITE_READ), the kernel driver copies the sender's user-space mData buffer once into pages mapped inside the receiver's mVMStart range. While copying, it walks mObjects[] to translate local BINDER_TYPE_BINDER pointers into remote BINDER_TYPE_HANDLE descriptors and takes a reference on the file behind every BINDER_TYPE_FD entry. The receiving thread installs those files in its own FD table when it reads the transaction (Figure 5).

In IPCThreadState.cpp, executeCommand(BR_TRANSACTION) wraps that kernel slice in a stack Parcel buffer via ipcSetDataReference(..., freeBuffer). Because all concurrent incoming transactions share that ~1 MiB mapping, system_server cannot retain pointers into mVMStart after onTransact returns; for synchronous transactions, IPCThreadState runs buffer.setDataSize(0), which closes the buffer's FDs and queues BC_FREE_BUFFER so it goes to the driver ahead of BC_REPLY. When BaseBundle copies its slice via appendFrom() (Figure 5), appendFrom() calls fcntl(fd, F_DUPFD_CLOEXEC, 0) to create a second FD (with cookie = 1) owned by the heap Parcel. When IPCThreadState closes the transient kernel-installed FD at transaction teardown, the duplicate FD keeps the shared memfd or ashmem inode open in system_server.

BaseBundle.readFromParcelInner and the four-state LazyValue lifecycle

Apps pass custom Parcelable classes inside Intent extras, notification extras, and saved-state bundles. Because system_server lacks the app's APK ClassLoader—and running untrusted app Parcelable constructors inside system_server would open deserialization exploits—BaseBundle.java defers deserialization by copying the raw bytes into an owned heap Parcel during readFromParcelInner():

frameworks/base/core/java/android/os/BaseBundle.java · readFromParcelInner()Parcel p = Parcel.obtain();
p.setDataPosition(0);
p.appendFrom(parcel, offset, length); // malloc(max(length * 3/2, 128)) + memcpy + incStrong(binders) + dup(FDs)
p.adoptClassCookies(parcel);
mParcelledData = p; // State 1: mMap remains null until any key is read

From that initial copy, a BaseBundle moves through a four-state machine governed by mParcelledData, mMap, mWeakParcelledData, mLazyValues, and mOwnsLazyValues (Figures 6 and 7):

  1. State 1 — Fully parcelled (mParcelledData != null, mMap == null): Zero keys have been read yet (for example, ActivityRecord.mIcicle or PendingIntentRecord.Key.requestIntent.mExtras). Calling bundle.hasFileDescriptors() scans mParcelledData directly in C++ without unparcelling. Cloning via new Intent(orig) or new Bundle(orig) calls appendFrom() again, allocating a second heap buffer and duplicating every FD a second time.
  2. State 2a — Unparcelled with zero lazy items (numLazyValues == 0): When code reads any key (e.g. extras.getBoolean(...)), initializeFromParcelLocked() runs Parcel.readArrayMap(). Primitives, Strings, and nested Bundles are materialized eagerly (each nested Bundle makes its own appendFrom() copy). If every entry was eager, BaseBundle calls parcelledData.recycle() immediately, freeing mData.
  3. State 2b — Partially unparcelled with LazyValue entries (mLazyValues > 0): Length-prefixed values—VAL_PARCELABLE, VAL_LIST, VAL_MAP, VAL_PARCELABLEARRAY, VAL_OBJECTARRAY, VAL_SPARSEARRAY, and VAL_SERIALIZABLE—store a 4-byte byte-length header right after their 4-byte type tag in mData (Figure 7b). Parcel.readLazyValue() reads type and length, advances mDataPos by length bytes in O(1) without loading any ClassLoader, and inserts new Parcel.LazyValue(sourceParcel, startPos, totalLen, type, bundle) into mMap. BaseBundle clears mParcelledData = null and stores mWeakParcelledData = new WeakReference<>(parcelledData); each LazyValue.mSource strong reference keeps the entire backing Parcel—including already-parsed string bytes and duplicated FDs—allocated.
  4. State 3 vs State 4 — Early destroy() vs shared LazyValue copies: Calling getParcelable(key) invokes unwrapLazyValueFromMapLocked(), which runs LazyValue.apply() (deserializing the slice and setting LazyValue.mSource = null), replaces the map entry with the materialized object, and decrements mLazyValues. When mOwnsLazyValues is true and mLazyValues reaches 0, BaseBundle calls mWeakParcelledData.get().destroy() immediately. If code copies an already-unparcelled Bundle via new Bundle(unparcelledSrc), the copy constructor shares the same LazyValue objects across both ArrayMaps and sets mOwnsLazyValues = false on both bundles, skipping eager parcel.destroy() so the native buffer remains allocated until GC and finalization.

3Cross-process retention and system_server holders

Three kernel mechanisms allow a Parcel or Binder token in one process to keep memory allocated in another:

  1. Remote BpBinder → local JavaBBinderExt JNI global ref. When an app holds a BinderProxy (or an unrecycled Parcel containing BINDER_TYPE_HANDLE), BpBinder.cpp holds a kernel strong reference (BC_ACQUIRE) on the target binder node. In the owning process, android_util_Binder.cpp keeps a JNI NewGlobalRef inside JavaBBinderExt until the kernel delivers BR_RELEASE. Any Java fields reachable from that Binder subclass—including parcelled Bundle buffers—cannot be garbage-collected while any client proxy lives.
  2. Duplicated ashmem and memfd descriptors. Because Parcel::appendFrom() duplicates every file descriptor in mObjects, system_server's copy of a Bundle holds its own open file description on the underlying anonymous shared memory inode. Even if the sending app unmaps its Bitmap or dies and gets reaped, those physical RAM or zram pages persist until system_server destroys its Parcel.
  3. Unreleased Binder mmap slices. A client that forgets to call reply.recycle() pins a slice of its own ~1 MiB Binder mmap until finalization; if enough slices accumulate, subsequent incoming calls fail with FAILED_TRANSACTION.

System_server subsystems that retain app Parcel memory

Native allocation stacks point at BaseBundle.readFromParcelInner, which records where buffers are allocated rather than which Java objects retain them. Across frameworks/base/services, nine subsystems retain most app-originated Parcel and shared-memory buffers (Table 2):

  • PendingIntentRecord (PendingIntentRecord.java, PendingIntentController.java). A client's PendingIntent wraps only an IIntentSender Binder token; the actual Intent and its mExtras live in system_server inside PendingIntentRecord.Key (requestIntent, allIntents, options). In ActivityManagerService.java, getIntentSenderWithFeatureAsApp() checks intent.hasFileDescriptors() directly on mParcelledData without unparcelling, then clones via new Intent(intent), producing a fresh appendFrom() heap buffer that sits parcelled. The controller's map (mIntentSenderRecords) stores only a WeakReference; what keeps the record alive is JavaBBinderExt's JNI global ref while any client process holds a proxy, or local references from alarms and notifications. No DeathRecipient is used.
  • NotificationRecord (NotificationRecord.java, NotificationManagerService.java). Holds StatusBarNotification → Notification.java, including extras (lazy Bundle), contentView/bigContentView (eager RemoteViews), and contentIntent (pinning a PendingIntentRecord). Enqueueing runs fixNotification(). For senders other than the system, the NotificationRecord constructor also walks every URI in the notification (Notification.visitUris()), which unwraps message lists, people and most icon extras. The big picture ("android.picture") and keys the system does not know stay LazyValue entries that pin the Parcel buffer and its duplicated memfd descriptors even after the posting app dies. Behind a feature flag, Android 17 can instead replace the big picture with a content-URI icon. Historical Archive entries call cloneLight() → lightenPayload() to strip Parcelable and array entries.
  • AppWidgetServiceImpl.Widget (AppWidgetServiceImpl.java, where Widget is a nested class). Stores views, maskedViews (RemoteViews.java), and options (lazy Bundle), alongside Provider.generatedPreviews. Unlike Bundle, RemoteViews(Parcel) unparcels its action list and BitmapCache eagerly on receipt (capped by AppWidgetServiceImpl's mMaxWidgetBitmapMemory at 6 * screenWidth * screenHeight bytes, with Bitmaps above 12 KiB backed by memfd), except reflection actions of type BUNDLE, which retain lazy Parcel copies.
  • ActivityRecord saved state (ActivityRecord.java, ActivityClientController.java). When a backgrounded activity stops, activityStopped() verifies !icicle.hasFileDescriptors() without unparcelling and stores mIcicle completely parcelled in system_server alongside ActivityRecord.intent. If lmkd (the low-memory killer daemon) kills the cached app, mIcicle stays in system_server's native heap so Android can recreate the activity later, releasing only when the activity resumes (setSavedState(null)) or finishes.
  • JobStatus, Alarm, StickyBroadcast, ClipboardService, and MediaSessionRecord. JobInfo.java holds lazy extras (PersistableBundle) and transientExtras (Bundle, which can carry arbitrary Parcelables and IBinders); Alarm.java pins PendingIntentRecord via operation; BroadcastController.java retains cloned StickyBroadcast.intent extras across sender death; ClipboardService.java retains per-user primaryClip extras; and MediaSessionRecord.java unparcels string URIs in mMetadata while leaving album-art Bitmaps as LazyValue entries until session close or binderDied().

Part II · History

4How Parcel has reported its native memory, 2009–2021

The history of Parcel.java and android_os_Parcel.cpp from Android 1.5 to Android 17 explains why Parcel uses static JNI methods, why it started reporting ashmem sizes to the GC in 2015, and why that reporting was removed in 2020 (Table 3). The 2020 change assumed that callers free a Parcel's buffers with recycle() before it is garbage-collected. That holds for short request and reply parcels, but the Parcel.LazyValue mechanism added in Android 13 keeps Bundle copies unrecycled for as long as an unread entry remains (§2).

  • Parcel and Binder, C++: frameworks/native/libs/binder/Parcel.cpp and frameworks/native/libs/binder/include/binder/Parcel.h (layout, buffer growth, object tracking), frameworks/native/libs/binder/IPCThreadState.cpp (incoming transactions, freeBuffer), frameworks/native/libs/binder/ProcessState.cpp (the Binder mmap), frameworks/native/libs/binder/BpBinder.cpp (remote references).
  • Kernel: drivers/android/binder.c in the Android common kernel (transaction copy, handle and FD translation).
  • Bundle and Bitmap: frameworks/base/core/java/android/os/BaseBundle.java, frameworks/base/core/java/android/os/Bundle.java, frameworks/base/libs/hwui/jni/Bitmap.cpp (inline vs memfd pixels), frameworks/base/core/java/android/widget/RemoteViews.java, frameworks/base/core/java/android/app/Notification.java.
  • system_server holders: frameworks/base/services/core/java/com/android/server/am/ (PendingIntentRecord.java, PendingIntentController.java, ActivityManagerService.java, BroadcastController.java), frameworks/base/services/core/java/com/android/server/notification/ (NotificationRecord.java, NotificationManagerService.java), frameworks/base/services/appwidget/java/com/android/server/appwidget/ (AppWidgetServiceImpl.java, including the nested Widget class), frameworks/base/services/core/java/com/android/server/wm/ (ActivityRecord.java, ActivityClientController.java), frameworks/base/apex/jobscheduler/framework/java/android/app/job/JobInfo.java, frameworks/base/apex/jobscheduler/service/java/com/android/server/alarm/Alarm.java, frameworks/base/services/core/java/com/android/server/clipboard/ClipboardService.java, frameworks/base/services/core/java/com/android/server/media/MediaSessionRecord.java.
  • Runtime and allocator: libcore/luni/src/main/java/libcore/util/NativeAllocationRegistry.java, external/scudo/standalone/combined.h (primary and secondary allocators).
