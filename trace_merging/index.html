Trace merging lines up files from different machines well, but two files from one phone need care

Perfetto’s Trace Processor can load several trace files as one trace, on one timeline. Files from different machines line up through a measured offset or their wall clocks. Two files from the same phone can merge wrongly, and most of these failures load without any error.

Code excerpts are from the upstream Perfetto repository at commit 9843f023eb (8 October 2026). Paths are relative to src/trace_processor/ unless stated. Excerpts marked shape are simplified. The rest are quoted with comments trimmed. Symbols are given instead of line numbers.

At a glance

  • What merging does. It puts several files on one timeline and in one set of SQL tables, and keeps each event tied to its machine.
  • Across machines. Machines recorded together are aligned by a measured offset. Machines recorded apart are aligned through their wall clocks.
  • On one phone. Two files share thread identity, so they join. But scheduler data that both recorded is stored twice, and a reboot between them misplaces the second file.
  • Usually silent. Most of these failures load without an error. The queries in Section 17 catch them.
  • What to do. Merge one phone’s files onto one machine only if they share a boot and do not record the same kind of data. Otherwise give each file its own machine name.

Terms. Trace time is the one shared clock that every event is placed on. A machine is one device or VM as Trace Processor models it. Each file is assigned to one machine. An archive is a TAR or ZIP file whose members are the traces. A manifest is an optional JSON member of the archive that names each file’s machine and relates clocks. The primary file is the first file read on a machine. Later files on that machine are secondary. A proto trace is a trace in Perfetto’s own protobuf format, such as a .pftrace file. A data source is one kind of data a trace records, such as kernel scheduler events or stack samples. traced is Perfetto’s tracing service, and traced_relay forwards a guest machine’s (VM’s) trace data to the host’s traced.

Merging puts several files on one timeline and one set of tables

One trace is often not enough, so Trace Processor can merge several. A host and its VM, two phones talking to each other, or one phone recorded by two tracing sessions each produce their own file. Trace Processor is Perfetto’s engine that imports traces into SQL tables. Merging lets you follow cause and effect across the files.

Merging has three jobs:

  • Place every event on trace time.
  • Keep every event tied to its machine, so that pid 1500 on a phone and on a VM stay different processes.
  • Keep state that belongs to one file inside that file. Examples are clocks private to one writer (Section 1) and interned strings: strings sent once with a short id that later packets refer to.
What works

Different machines. A host and guest recorded live through traced_relay are aligned by a measured offset (Section 3). Separately recorded devices with their own machine names are aligned through their wall clocks (Section 4). One phone, one boot, with different data in each file also merges well. Both files share thread ids, so they join.

What breaks on one device

Files on one machine share thread and CPU identity but keep separate bookkeeping. If both recorded the same scheduler events, every scheduling row is stored twice and some stay open (Sections 11 and 12). A reboot between the files puts the second one at the wrong time (Section 14). A few manifest and packet-order cases drop data or fail the load (Sections 9 and 13).

What to do instead

Merge one phone’s files onto one machine only when their data sources do not overlap and they come from one boot. Otherwise decompress them and give each file its own machine name in a manifest. Joins between the files then go through the kernel thread id instead of a shared thread row. Run the checks in Section 17 before trusting any join.

Trace Processor takes a single input, so you merge by handing it one archive. The archive can also hold a manifest. The manifest is recognised by its content. By convention it is named perfetto_manifest.json.

The other way in is one proto trace recorded through traced_relay. That one trace already holds several machines and their measured clock offsets.

Part I · Clocks

1A timestamp means nothing until you know its clock and its machine

Two files can share a timeline only once you know what their timestamps mean. A timestamp is a reading of some clock, and the number alone does not say which clock or which machine. Trace Processor calls each distinct clock it tracks a clock domain: one clock on one machine. For the private clocks in the table, the domain is also limited to one file or one sequence.

Timestamps in the same domain compare directly. Timestamps in different domains cannot be compared until something relates them. Linux exposes several clocks, and Perfetto names them in BuiltinClock (protos/perfetto/common/builtin_clock.proto):

ClockIdWhat it counts
BOOTTIME6Nanoseconds since boot, including time in suspend, the low-power sleep where the CPUs stop and the screen is off. Perfetto’s default trace clock on Android and Linux.
MONOTONIC3Nanoseconds since boot, but it stops while the device is suspended.
REALTIME1Wall-clock time since 1970. It jumps forwards or backwards when the user sets the time or on an NTP step: a jump to the correct time made by NTP, the Network Time Protocol daemon that keeps the wall clock in line with a time server.
Sequence-scoped clocks64–127Defined by one trace writer for its own packets, often as deltas, where each timestamp counts from the previous one. TrackEvent, Perfetto’s in-app instrumentation API, uses them.
TRACE_FILE11A private timeline for one file. Used for formats with no absolute clock, such as Chrome JSON.

A sequence is the stream of packets from one writer, usually one thread of one producer. A producer is a process that writes trace data. The trace identifies each sequence by trusted_packet_sequence_id.

Converting a timestamp from one clock to another means adding an offset: clock B minus clock A at the same instant. On one device, the offset between two clocks is constant most of the time. BOOTTIME − MONOTONIC changes only across a suspend. REALTIME − BOOTTIME changes only when the wall clock is stepped (Figure 2).

Across devices, BOOTTIME values are unrelated, because each device booted at a different instant. REALTIME values are close only if both devices synchronised their wall clocks. Even then the offset slowly changes, because two crystals never tick at exactly the same rate. That slow change is drift.

What it means for you Two files from the same boot of the same device can share BOOTTIME directly. Two devices, or two boots, cannot. BOOTTIME means something different on each, and only a measured offset or the wall clock can relate them.

2Clock snapshots link clocks into a graph that can convert any timestamp

Because offsets change, a trace records them as it goes, in clock snapshots. A clock snapshot is a set of clocks read back to back, close enough to count as the same instant. Each one says “when clock A read X, clock B read Y”. That gives the offset between A and B at that moment.

traced takes a snapshot when a session starts and writes it first in every trace. It also takes periodic snapshots into a small ring, a fixed-size buffer where each new entry replaces the oldest. It keeps a new one only if some clock drifted by at least 10 ms against BOOTTIME since the last one. Section 18 lists the code behind each of these rules.

Trace Processor keeps every snapshot in one ClockSynchronizer (util/clock_synchronizer.h). It models them as a clock graph (Figure 3):

  • Nodes are clocks. Each node keeps a time series of (snapshot id, timestamp) pairs. Snapshots that read the same clocks share a series, grouped by a snapshot hash of their clock ids.
  • Edges join every pair of clocks that one snapshot read, in both directions.
  • Conversion follows a path of at most four edges, found by breadth-first search. On each hop it takes the latest snapshot at or before the timestamp and adds that snapshot’s offset.
util/clock_synchronizer.cc · ConvertSlowpath, one hop (trimmed)auto it = std::upper_bound(ts_vec.begin(), ts_vec.end(), ns);
if (it != ts_vec.begin())
  --it;                         // latest snapshot ≤ ns (or the first one)
uint32_t snapshot_id = cur_snap.snapshot_ids[index];
// ... look up the same snapshot_id in the next clock's series ...
const int64_t hop_translation_ns = next_timestamp_ns - *it;
ns += hop_translation_ns;

Two more rules matter for merging:

  • A clock that goes backwards loses its outgoing edges. This happens to REALTIME after a backwards step. Conversions can still go into REALTIME but no longer out of it. A REALTIME instant that happened twice cannot be mapped back to one BOOTTIME value, but BOOTTIME → REALTIME stays well defined. If the clock that goes backwards is trace time itself, adding the snapshot fails with “the trace clock … is not monotonic”.
  • The graph ignores time. Once any snapshot connects two clocks, they count as connected for the whole trace, even for timestamps long before or after that snapshot.
What it means for you Between snapshots the offset is assumed constant. That is exact for BOOTTIME ↔ REALTIME until a wall-clock step. It is wrong for MONOTONIC across a suspend until the next snapshot (Section 15).

3Machines recorded together are aligned by timing a round trip

Machines recorded together through traced_relay are aligned by timing messages between them. Two machines cannot read each other’s clocks at one instant, because any message takes an unknown time to arrive. NTP solves this by timing a round trip: send a message, get the reply, and note both send and receive times. It assumes both directions take equally long, so the remote reading belongs at the midpoint.

traced_relay does this with four timestamps per round, and each timestamp is a full clock snapshot (Figure 5). The client is the guest machine running traced_relay. The host runs traced.

  1. The client takes a snapshot and sends PING (t1c).
  2. The host takes a snapshot when the ping arrives (t1h) and replies.
  3. The client takes another snapshot and sends UPDATE (t2c).
  4. The host takes a snapshot when that arrives (t2h).

A new round starts every 30 seconds. The host keeps only the most recent exchanges, about two rounds’ worth. traced writes them once per session into one RemoteClockSync packet per machine. That packet holds (client snapshot, host snapshot) pairs. Section 18 gives the exact limits and code.

Trace Processor turns the packet into one fixed offset per clock. It pairs adjacent entries that belong to one round, computes both offsets, and averages all offsets in the packet into one number per clock:

importers/proto/proto_trace_reader.cc · CalculateClockOffsetsint64_t offset1 =
    (static_cast<int64_t>(t1c + t2c) / 2) - static_cast<int64_t>(t1h);
int64_t offset2 =
    static_cast<int64_t>(t2c) - (static_cast<int64_t>(t1h + t2h) / 2);
raw_clock_offsets[clock_id].push_back(offset1);
raw_clock_offsets[clock_id].push_back(offset2);
// ... then, per clock:
int64_t avg_offset = std::accumulate(offsets.begin(), offsets.end(), 0LL) /
                     static_cast<int64_t>(offsets.size());

It then adds one edge per clock between the host and the client. The host end sits at the last host reading of that clock, and the client end at that reading plus the offset. The client’s own snapshots from each round are also added on the client machine. They relate its other clocks to its BOOTTIME.

What it means for you A relay-recorded trace aligns machines by one constant offset. It is averaged over the last minute or so of sync rounds before traced first wrote the trace out. Drift between the machines is not modelled, so in a long recording the error grows with distance from those rounds.

4Files nothing measured are placed by the wall clock or by assuming one boot

A file with no measured link to trace time gets a fallback link: the wall clock if it is on another machine and both sides have one, otherwise a same-boot guess. Most merges are like this: two files recorded separately, with no RemoteClockSync between them.

Trace Processor plans the fallback when it opens the file. It registers a deferred clock sync: a reminder to link the clock the format’s timestamps use, which is BOOTTIME for proto, to trace time later. The link is added only at the file’s first timestamp conversion, and only if nothing better relates the two clocks by then. At that point Trace Processor tries four things in order (Figure 6). Step 2, the REALTIME rendezvous, joins the two machines’ wall clocks and assumes they agree.

    Convert(global_realtime, 0, trace_time)) {

What it means for you Two separately recorded devices line up through their wall clocks, as accurately as NTP kept them. A file on the trace-time machine never takes Step 2, because its REALTIME is already that machine’s REALTIME. A second proto file there is tied BOOTTIME to BOOTTIME at zero offset (Section 9). A file with a private clock is tied by Step 3. Both cases assume the files share one boot.

6File type and name, not archive order, decide which file anchors the others

Trace Processor reads archive members sorted by file type first and name second, not in the order they sit in the archive. Order matters for two reasons. The manifest must be read before the files it configures. And the first trace read on a machine becomes its anchor: the file whose clocks the others are tied to (Section 7).

So TarTraceReader first reads the whole archive. It skips hidden members, where any part of the path starts with a dot, such as macOS ._foo files. It records each other member, guesses its format from the first bytes and sorts it. At the end of the input it walks the sorted list. Each member is parsed completely before the next one starts. The sort key is (priority, name, position):

importers/archive/archive_entry.ccbool ArchiveEntry::operator<(const ArchiveEntry& rhs) const {
  return std::tie(priority, name, index) <
         std::tie(rhs.priority, rhs.name, rhs.index);
}

Each importer sets its own priority in TraceTypeDescriptor::archive_priority (util/trace_type.h). Lower runs first:

archive_priorityImportersWhy there
-1perfetto_manifestConfigures every later file. ForwardingTraceParser::Init rejects a manifest that is not first.
0protoCarries ClockSnapshots that other files may need.
1gzip, zstd, tar, zipContainers. A .pftrace.gz sorts here, not with proto.
2everything else (JSON, systrace, ctrace, perf, …)Default.
3symbols (a proto whose first packet is ModuleSymbols)Symbolizes data already imported.

A compressed member is only a container, so it gets no context of its own. Trace Processor decompresses it and reads the contents as a new, nested file. That inner file has an empty name. Its row in the trace_file table, not the compressed member’s, is the trace id the events are attributed to.

What it means for you To pick the anchor file, give all trace members the same compression and prefix their names (00_, 01_). Mixing a raw .pftrace with .pftrace.gz members makes the raw one primary whatever it is called.

7Each clock is keyed by machine and file, and the first file to claim trace time sets it

All clocks of all files live in one graph, so each clock node needs a name that cannot collide. That name, ClockId, has four fields:

util/clock_synchronizer.h · ClockId (trimmed)struct ClockId {
  uint32_t clock_id = 0;       // BuiltinClock, or 64..127 for sequence clocks
  uint32_t seq_id = 0;         // trusted_packet_sequence_id, sequence clocks only
  uint32_t trace_file_id = 0;  // isolates files on the same machine
  uint32_t machine_id = 0;     // MachineTable row id; 0 is the host

  static constexpr ClockId Qualify(ClockId c, uint32_t machine,
                                   uint32_t file_tag) {
    c.machine_id = machine;
    if (c.seq_id == 0 && c.trace_file_id == 0)
      c.trace_file_id = file_tag;
    return c;
  }
};

The trace_file_id field holds the file’s trace file id from the Overview. Code and the stats table call it trace_id, and this page says “trace id”. Sequence clocks already include the trace id, so they are private to one file.

Builtin clocks get a file tag from the file’s clock tracker. Tag zero means the machine’s canonical nodes, shared by every file on that machine. A non-zero tag is the file’s own id and means nodes private to that file.

How a file gets a machine

A file lands on machine zero unless a manifest or its own packets say otherwise (Figure 8).

  • Default. ForwardingTraceParser::Init puts every trace file on raw machine id 0, unless a manifest entry gives it one.
  • Embedded ids. When a proto packet carries a non-zero machine_id, the file adopts it: the file’s own machine row is relabelled with that id instead of the host’s. This happens only if the host machine is still unused and no manifest remaps the file. Otherwise Trace Processor starts a separate reader for that machine’s packets and adds a deferred BOOTTIME sync.
  • Manifest names. Each distinct name gets a synthetic raw id, and its machine row is created up front in manifest order.

A machine therefore has two ids. Its raw id is the one the input uses: 0 for the host, a packet’s machine_id, or a synthetic id for a manifest name. Its row id is its row in the machine table, assigned in creation order. In clock ids and in SQL, machine_id is the row id. The docs note that this id is not stable across versions. In queries, use machine.raw_id or machine.name instead.

Who owns trace time

Exactly one clock domain can be trace time, and the first file to claim it wins. Trace time starts as a placeholder TRACE_FILE clock. After the first claim, later claims are ignored (TraceTimeState::TrySetClock). Claims happen at different moments:

  • A manifest trace_time entry claims it before any trace is read.
  • Non-proto formats claim their source clock when the file is opened.
  • Proto claims at its first ClockSnapshot. It uses primary_trace_clock, a snapshot field naming the clock the trace wants as its timeline. Without it, proto uses BOOTTIME if the snapshot has BOOTTIME and no TRACE_FILE.

The claimed node is always the machine’s canonical one, with file tag zero.

Primary and secondary files

The first file on a machine is its primary file, and it always uses the canonical clock nodes. Every later file on that machine is secondary. A secondary file starts on the canonical nodes too. So a file without snapshots, such as JSON or systrace, converts through the primary’s snapshots. When a secondary file adds its own snapshot, it switches to its own private nodes (Section 9). Figure 9 shows both kinds of node.

8Files on one machine share thread identity but keep separate bookkeeping

Two files on one machine share who each thread and CPU is, but each keeps its own record of what is in progress. That split decides what merges and what gets duplicated. Clocks are only half of merging. The other half is which importer state two files share.

Trace Processor turns parsed events into rows through trackers. Each tracker owns one kind of data and remembers state between events. For example, the process tracker maps a pid to a thread row. The slice tracker keeps the stack of open slices, the named, nestable intervals that trace sections become. Whether two files get the same tracker or separate ones is the tracker’s scope.

Two shared identities matter below:

  • A utid is a thread’s row id in the thread table. It is unique across the whole trace, even when thread ids are reused.
  • A ucpu is a CPU’s row id in the cpu table. CPU 0 on two machines gets two ucpus.

Most of Part III is about scheduler data. ftrace is the Linux kernel’s built-in event tracer, which Perfetto reads for kernel events. Its sched_switch event fires every time a CPU stops running one thread and starts another. From sched_switch and wakeup events, Trace Processor builds two tables:

  • sched: one row per stretch a thread ran on a CPU.
  • thread_state: each thread’s state over time, such as running, runnable or sleeping.

Every trace file is parsed with its own context, its set of trackers. When Trace Processor creates it, it shares global state, then either creates or reuses each other kind of state:

9A second file on one machine gets private clocks, and an early timestamp can cut it off

A secondary file moves to private clock nodes at its first snapshot, so that it cannot change how the primary file converts. Both files carry clock snapshots. If the second file’s snapshots went into the shared canonical nodes, they could shift the first file’s timestamps. The code comment gives the example of an in-app trace next to a system trace.

The switch happens in ClockTracker::AddSnapshot, on the highlighted line:

The usual order works

traced writes its first clock snapshot as the first packet of every trace. So in a normal secondary file the snapshot arrives first and moves the file to its private tag, k. The first converted timestamp then adds BOOTTIME(tf k) ↔ BOOTTIME(tf 0) at zero offset. Every later conversion goes through that edge. For two files of one boot this is exact, because BOOTTIME is the same clock.

A conversion before the snapshot cuts the file off

If the secondary file converts any timestamp before its first snapshot, the order inverts and the file loses its link to trace time (Figure 11):

  1. The deferred sync runs while the file is still on tag zero. With tag zero, the file’s “private” node is the canonical node itself, so the sync adds no edge, and it is used up.
  2. The snapshot then moves the file to tag k.
  3. From then on, the private BOOTTIME links only to the file’s own MONOTONIC and REALTIME. REALTIME is not bridged on the trace-time machine (Step 2 of Section 4 applies only to other machines). Nothing connects the file to trace time.

Few packets count as an early conversion, so files written by traced are normally safe. A proto packet is converted only if it names a clock: on the packet, in its sequence’s defaults, or as a trace-wide default. Proto sets no trace-wide default until its first snapshot. So a timestamped packet with no clock id before that passes through unconverted and does no harm.

Two kinds of packet do convert:

  • Ftrace bundles, packets holding a batch of ftrace events from one CPU, always convert. They use BOOTTIME or the bundle’s own ftrace clock.
  • traced’s own service packets name BOOTTIME explicitly, but they come after the first snapshot.

A secondary file produced some other way can hit this. Examples are a converter, a tool that rewrites or reorders packets, or a writer that emits timestamped packets with explicit clock ids before any snapshot.

When it happens, the stats table records it, and ftrace can fail the whole import:

  • clock_sync_mixed_clock_sources is logged first, with num_conversions_using_primary.
  • clock_sync_failure_no_path is logged for every failed conversion.
  • Proto packets are retried at the end of the file, then counted in clock_sync_failure_undeferrable_packet_loss.
  • Ftrace events get no retry. Bundles from newer Perfetto can carry a per-CPU start timestamp. If that value fails to convert, the import fails with “Failed to convert timestamp to trace time”.
What it means for you If a secondary file loses everything after its first snapshot, look for clock_sync_mixed_clock_sources on that trace id. Giving the file its own machine name in a manifest avoids the problem. It then becomes primary on its machine and stays on the canonical nodes.
Part III · Where same-machine merging breaks

10Joining traces with cat makes unrelated writers share state

Gluing two trace files together with cat gives a file that loads, but it is still one trace, and the two halves mix up their writers. This part lists where merging gives wrong or missing results when the files come from one device. Skipping the archive is the first trap.

A Perfetto proto trace is a sequence of length-prefixed packets, so cat a.pftrace b.pftrace parses. But it has one context, one reader and one table of per-sequence state, keyed by sequence id. traced numbers sequences per session: 1 for the service, then counting up for writers in the order they appear. So the two halves reuse the same ids for unrelated writers (Figure 12).

Sharing sequence ids causes four problems:

  • Interned data is only partly protected. Each writer’s first packet normally sets a flag saying later packets will not refer to interned data sent before it. So the second half’s writer starts with a clean interning table instead of reusing the first half’s strings. Anything else keyed by sequence id is shared between the halves.
  • Private clocks collide. Both halves feed the same sequence-scoped clock node. If the second half’s values are lower, the clock goes backwards and loses its outgoing edges (Section 2).
  • Snapshots can be rejected. If the second half was recorded before the first, its snapshots go backwards in trace time and are rejected.
  • Metadata is overwritten. Single-value metadata, such as trace_uuid and trace_config_pbtxt, has one row per key, machine and trace. Both halves share one trace id, so the second half’s value replaces the first’s.

An archive avoids all of this, because each member gets its own trace id, reader and sequence state.

What it means for you Never merge Perfetto traces with cat. Pack them into a TAR instead, for example with trace_processor util merge (Section 5).

11The same thread recorded by two files gets two tracks

When two files on one machine record slices for the same thread, Trace Processor creates two tracks for it, and the slices never nest. A track is a timeline that events hang off: a row in the track table that slices or counter values point to, drawn as one lane in the UI. The two files’ slices should share one track so that they nest and line up.

They do not, because each file creates its own tracks. The track tracker creates each track once and reuses it. It looks tracks up in its own map, keyed by a hash of the track’s blueprint and its dimensions. The blueprint is the track’s type, such as “thread execution”. A dimension is a key such as the utid:

importers/common/track_tracker.h · InternTrackInneruint64_t hash = tracks::HashFromBlueprintAndDimensions(bp, dims);
auto [it, inserted] = tracks_.Insert(hash, {});
if (inserted) {
  *it = CreateTrack(bp, dims, name, args, unit);   // new row in the track table
}
return *it;

Each file has its own track tracker, so each map starts empty. If both files emit slices on one thread’s main track, each creates a row with the same type and the same utid (Figure 13). Each file’s slice tracker also keeps its own stacks, so the two sets of slices never nest in each other.

Counters behave the same way. The same counter recorded by both files becomes two counter tracks. A query that groups counter values by name rather than by track sees two interleaved series instead of one.

What it means for you If both files on one machine trace the same thread or counter, expect two tracks for it. Query by track id, or check for duplicates with the Section 17 query before aggregating.

12Scheduler data recorded by both files is stored twice

If both files recorded scheduler events for the same time, every scheduling row in that time is stored twice. Most CPU and latency analyses start from the sched and thread_state tables. Both tables assume one row per thread or CPU at any instant.

Each file’s ftrace scheduler tracker handles its own copy of the same kernel events. Each tracker remembers, per CPU, which slice is open and which pid was switched in. But both look up CPUs and threads in the shared per-machine trackers. So both write into the one sched table, with the same ucpu:

importers/ftrace/ftrace_sched_event_tracker.cc · PushSchedSwitch (shape)auto* pending_sched = sched_event_state_.GetPendingSchedInfoForCpu(cpu);  // per file
if (prev_pid == pending_sched->last_pid)
  context_->sched_event_tracker->ClosePendingSlice(pending_slice_idx, ts, ...);
auto new_slice_idx = context_->sched_event_tracker->AddStartSlice(
    cpu, ts, next_utid, next_prio);        // dur = -1 until closed
ThreadStateTracker::GetOrCreate(context_)->PushSchedSwitchEvent(...);       // per file

Nothing in the import flags this, so queries silently give wrong answers. Any query that assumes intervals do not overlap per CPU or per thread is affected. Interval intersection keyed by ucpu or utid is one example. The duplication does not raise mismatched_sched_switch_tids, the stat counted when a switch’s outgoing thread is not the one last switched in on that CPU. Each tracker sees its own file’s consistent stream, so it never sees such a mismatch.

What it means for you Merge two files onto one machine only when their data sources do not overlap. For example, one has scheduler data and the other only stack samples. If both have ftrace, give them separate machines, or crop one so the time ranges do not overlap.

13Two common manifest uses fail on files from one device

A manifest clock pin between two files on one machine either fails the load or misses the file it was meant for. Compressed members cannot be configured at all. The manifest is how you override the defaults of Part II: which machine a file belongs to, which clock is trace time, and fixed clock relations.

A clocks entry relates one of this file’s clocks to a clock of another file. At a common instant, the other file’s clock reads this file’s value plus offset_ns. This page calls any such entry a pin. The reference doc reserves “pin” for the form without a clock, used for files with no clocks of their own.

The layout below follows the manifest reference in Perfetto’s docs (docs/reference/perfetto-manifest.md). It is the recommended layout for two traces from one device when both record ftrace or a reboot separates them (Sections 12 and 14):

perfetto_manifest.json (shape){
  "perfetto_manifest": {
    "version": 1,
    "files": [
      {"path": "system.pftrace", "machine": {"name": "phone-system"}},
      {"path": "sampling.pftrace", "machine": {"name": "phone-sampling"},
       "clocks": {"clock": "BOOTTIME",
                  "sync_to": {"file": "system.pftrace", "clock": "BOOTTIME"},
                  "offset_ns": 0}}
    ]
  }
}

Two other uses of a pin go wrong when both files are on one machine.

A BOOTTIME-to-BOOTTIME pin on one machine fails the load

If neither file names a machine, a BOOTTIME-to-BOOTTIME pin joins a clock to itself, and the import fails (Figure 15). The manifest reader resolves both ends of a pin to machine rows. It then builds the edge from each machine’s canonical clocks:

plugins/perfetto_manifest/perfetto_manifest_reader.cc · ApplyManifest (shape: TraceFile branches omitted)uint32_t source_row = EnsureMachineRow(context_, source_raw);
uint32_t ref_row = EnsureMachineRow(context_, ref_raw);
ClockId source = ClockId::Machine(source_row, *co.source_clock);
ClockId ref = ClockId::Machine(ref_row, *co.ref_clock);
int64_t source_ts = co.offset_ns < 0 ? -co.offset_ns : 0;
int64_t ref_ts = co.offset_ns > 0 ? co.offset_ns : 0;
std::vector<ClockTimestamp> clocks = {{source, source_ts}, {ref, ref_ts}};
ASSIGN_OR_RETURN(uint32_t id, context_->clock_sync->AddSnapshot(clocks));

Both files resolve to raw machine 0 and the same row. With BOOTTIME on both sides, the two ends are the same clock id. Adding a snapshot with the same clock twice returns “Clock sync error: duplicate clock domain with id=6 at snapshot N.”, and the import fails. The device1/device2 example in the manifest reference has this shape, so it needs distinct machine names on the two files.

A pin between different clocks on one machine is accepted, but it may not reach the file it was meant for. Take this file’s MONOTONIC pinned to the other’s BOOTTIME. The edge lands on the canonical nodes, which belong to the primary file. A secondary file with its own snapshots converts through its private nodes and the identity edge of Section 9, so the offset does not apply to it. The pin also adds a second MONOTONIC ↔ BOOTTIME relation next to the primary’s own snapshots. The primary file’s conversions can then go through either one.

Overrides are rejected on compressed members

A manifest cannot assign a machine or clocks to a compressed member, so decompress members first. The manifest matches entries by exact member path. A .pftrace.gz or .zst member is only a container, and Trace Processor refuses a machine or clocks override on it. The error is “perfetto_manifest: overrides are not supported for trace files which are themselves archives or perfetto_manifest files”. The decompressed inner file has an empty name, so it cannot be targeted either.

What it means for you To relate two proto traces from one device by hand, give each its own machine name, store them uncompressed, and pin one to the other. Each is then primary on its machine, so the edge lands on the clocks it actually uses. The cost is that the two files no longer share a process tracker. The same thread gets two utids, and cross-file joins must go through tid and machine instead.

14A reboot between two files puts the second one at the wrong time

Two traces from one phone with a reboot between them still land on the same machine by default, and the second one lands at the wrong time. A reboot restarts BOOTTIME and MONOTONIC from zero and starts every process again with fresh pids.

The second trace is a secondary file on the trace-time machine. So it is placed by the BOOTTIME identity edge, never by REALTIME. Its BOOTTIME values count from the new boot, so it lands in the wrong place (Figure 16). It lands before the first trace if it was recorded soon after boot. It lands on top of it if both were taken at similar uptimes, the time since boot.

Both files also share one process tracker. So a pid reused after the reboot can resolve to a thread or process from before the reboot, unless the trace records the new process starting.

In the trace model, two boots are two machines. Give each boot its own manifest machine name. Each file is then primary on its machine, and each gets its own process tracker. The second file reaches trace time through the REALTIME rendezvous (Section 4, Step 2).

What it means for you Before merging two traces from one phone, compute REALTIME − BOOTTIME from each trace’s first clock snapshot. Within one boot it stays the same, apart from NTP steps. If the two values differ by more than a few seconds, a reboot happened in between, so use separate machine names.

15Ring-buffer trace pairs are useful only inside the scheduler window and without suspend

When you pair a long ring-buffer trace with another trace from the same phone, the overlap that matters is where scheduler data survives, and suspend can shift MONOTONIC events. A useful same-device merge pairs two kinds of trace:

  • A long ring-buffer system trace comes from a long-running session that keeps recent system activity, including scheduler data, in ring buffers and saves it when a trigger fires.
  • A stack-sampling trace comes from a separate session that records periodic and event-triggered call-stack samples.

The scheduler window is much shorter than the trace

A ring-buffer trace keeps the most recent data per buffer. High-rate ftrace wraps quickly, so scheduler data covers only the tail of a trace whose other buffers span much longer. Overlap computed on the full start-to-end range mostly finds pairs that overlap where scheduler data was already overwritten (Figure 17).

So compute overlap against a sched window instead: the last stretch of the trace, as long as the time its scheduler data covers. Section 18 gives the formula.

MONOTONIC events after a suspend are shifted earlier

A MONOTONIC timestamp after a suspend is placed too early, by the length of the suspend. Conversion uses the latest snapshot at or before the timestamp (Section 2). MONOTONIC does not advance during suspend, so a timestamp after resume still falls in the pre-suspend snapshot’s range. The error lasts until the next snapshot that traced keeps. BOOTTIME events are not affected.

What it means for you When pairing ring-buffer traces, compute overlap against the ring-buffer trace’s sched window, not its full range. Skip ring-buffer traces that recorded a suspend if any of your data uses MONOTONIC timestamps.
Part IV · Practice

16A short checklist and one recipe per kind of merge cover the rules above

Parts I to III reduce to a few checks for building a set of traces from one device, and one recipe for each kind of merge. Before putting several files from one phone onto one machine:

  • Compute overlap against the sched window, not the full trace range (Section 15).
  • Skip traces that recorded a suspend if any of your data uses MONOTONIC timestamps (Section 15).
  • Skip traces that report data loss or import errors.
  • Choose the anchor file: give every member the same compression and prefix the names (00_, 01_) (Section 6).
  • Make sure all files come from one boot (Section 14). A shared device, build and overlapping wall-clock windows make one boot likely, but do not prove it.
  • Make sure only one file records scheduler data (Section 12). For a stack-sampling trace this depends on its config.

For each kind of merge, the table gives the recipe:

One device, one boot, disjoint data sourcesArchive, no manifest. Prefix names so the anchor is first. Same compression for all.Shared utid/ucpu makes cross-file joins work.

17Six queries catch the failures that load without an error

Most of Part III produces no error: the trace loads and the numbers are wrong. Run these queries after loading to check each failure mode.

-- Files in processing order, with their parent container.
SELECT id, parent_id, name, trace_type, processing_order, size
FROM __intrinsic_trace_file ORDER BY processing_order;

-- Machines and how much each owns.
SELECT m.id, m.raw_id, m.name,
  (SELECT COUNT(*) FROM thread t WHERE t.machine_id = m.id) AS threads
FROM machine m;

-- Clock problems, per file.
SELECT name, value, machine_id, trace_id FROM stats
WHERE value > 0 AND (name GLOB 'clock_sync*' OR name = 'invalid_clock_snapshots'
  OR name = 'trace_sorter_negative_timestamp_dropped');

-- Every edge in the clock graph, including bridges and manifest edges.
SELECT snapshot_id, machine_id, clock_name, clock_value, ts FROM clock_snapshot
ORDER BY snapshot_id;

-- Duplicate main-thread tracks (Section 11).
SELECT utid, COUNT(*) AS n, GROUP_CONCAT(id) AS track_ids
FROM thread_track WHERE type = 'thread_execution'
GROUP BY utid HAVING n > 1;

-- Duplicate sched rows (Section 12): two slices starting at the same instant on one CPU.
SELECT ucpu, ts, COUNT(*) AS n FROM sched
GROUP BY ucpu, ts HAVING n > 1 LIMIT 20;

Every edge added to the clock graph is written to the clock_snapshot table, including fallback links and manifest pins (ClockTracker::AddSnapshotToTable). So a fallback link you did not expect shows up there as a snapshot with zero-offset values.
