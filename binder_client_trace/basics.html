Binder from scratch: how a call crosses processes, and how both ends get a name in the trace

An app asks system_server a question: "is a monkey driving this phone?" (IActivityManager.isUserAMonkey()). The two programs share no memory. Yet the call looks like an ordinary method call in the app's code, and with the change in the companion report, a trace labels both ends with the same name. This note follows that one call from start to finish and introduces each piece only when the call needs it.

1Two processes, one wall

Every Android app and every system service runs in its own process. A process gets its own private address space: the app's address 0x7f00… and system_server's 0x7f00… are completely different bytes. So the app cannot just jump into system_server's code, or hand it a pointer. There's a wall between them.

Only the kernel can see both sides. Binder is the kernel driver Android uses to pass a request through that wall. It does something unusual: it moves a thread's attention, not just bytes. The calling thread goes to sleep, a thread in the other process wakes up with the request, runs the method, sends back a reply, and the caller wakes up holding the answer. From the caller's point of view, it called a function and it returned.

Two questions follow immediately. What goes through the wall? And how does the app say which object, and which method, it means?

2The envelope: Parcel

Whatever goes through has to be flat bytes, because pointers mean nothing on the other side. The container for those bytes is a Parcel. Think of an envelope with a long strip of paper inside and a pen that writes left to right. writeInt32(7) writes four bytes and moves the pen. On the other side, a reader with its own finger reads the same strip left to right: readInt32() returns 7 and moves the finger. That finger is the Parcel's read position, and it will matter later.

Here is the strip for our call. isUserAMonkey() takes no arguments, so all that's written is a short header:

Notice what the envelope does not say: the method name. The method is identified by a plain number, the transaction code, which the kernel carries next to the Parcel. AIDL numbers methods in the order they're declared: the first method is code 1, the second is code 2, and so on. The string "isUserAMonkey" never crosses the wall. Keep that in mind; it's the whole puzzle of this note. The next section shows the exact bytes.

3On the wire: the actual bytes

"Envelope" is a metaphor. Here's what is really in memory, and what the kernel is really handed.

The Parcel bytes

Our call's Parcel is 76 bytes. Integers are 4 bytes, little-endian (least significant byte first). Strings are UTF-16: 2 bytes per character, NUL-terminated, padded to a multiple of 4.

Where does the strict-mode word come from? It's how StrictMode policies follow a call into the server. The low bits carry the thread's policy, which is 0 here. Treat it as bookkeeping; for this note, the important thing is that the token always sits at byte 12.

What the kernel is handed

The Parcel doesn't go to the kernel on its own. libbinder wraps it in a small command and makes one system call, ioctl(fd, BINDER_WRITE_READ, …), on the binder device. The command is BC_TRANSACTION ("binder command: transaction"), followed by this struct:

Two details here pay off later. First, the kernel itself writes sender_pid and sender_euid, so the server knows who's calling, and the caller can't lie about it. Second, the kernel moves bytes and translates handles, but it never parses the Parcel. It doesn't know which interface or method this is. Those meanings exist only in user space, in the code on each end.

4Phone numbers and people: BpBinder, BBinder

Next: who is the envelope addressed to? system_server hosts hundreds of objects. The answer is libbinder's central abstraction, IBinder: "something you can send a transaction to". Its one important method is:

status_t transact(uint32_t code, const Parcel& data, Parcel* reply, uint32_t flags);

There are two kinds of IBinder, and the difference between them is the heart of this note:

  • BBinder ("binder") is the real object. It lives in the process that implements the service, here system_server. When a transaction arrives, its transact() runs the actual code.
  • BpBinder ("binder proxy") is a stand-in for an object that lives in another process. It contains almost nothing: mainly a small integer handle. Its transact() just asks the kernel to deliver the envelope to whatever object that handle refers to.

A good picture: a BBinder is a person; a BpBinder is that person's phone number. You can call a phone number, but you can't ask it a question about the person without making a call.

On the server, a few binder threads wait inside the kernel. When an envelope arrives for one of its BBinders, the kernel wakes one of them, and it calls that BBinder's transact() with the code and the Parcel.

6Java wears a native costume

Our app and system_server are written in Java. Does Java have its own binder? No: every Java binder object is a thin wrapper around a native one, connected through JNI, the bridge between Java and C++.

That last asymmetry is worth slowing down for. The server's JavaBBinder keeps a reference to the Java Stub, the object that implements the interface. So native code on the server can always ask it a question. The client's BpBinder is wrapped by a BinderProxy, but BinderProxy is one generic class for every interface. The generated Stub.Proxy points at the BinderProxy, not the other way round. From native code on the client, there's nobody to ask.

7All together: three sequence diagrams

Time to put every piece on one page. Read each diagram top to bottom: time flows down, each column is one layer, and each arrow is one call between layers. The two colored bars are trace slices: blue on the client, green on the server. Each diagram is one call, from start to finish, with tracing on.

Three things to notice across the diagrams:

  • The client slice always contains the server slice. The client starts waiting before the server starts working, and stops after the server is done. The gap between them is the two kernel trips: copying the Parcel and waking threads.
  • Exactly one layer emits each slice. For Java and cpp clients it's BpBinder. For Rust and NDK clients it's libbinder_ndk, so BpBinder stays quiet for them and you never get two client slices for one call.
  • Generated code never emits a slice in this design. It only provides the names. Section 9 explains why.

8What a trace slice is

Now the tracing side. A slice in Perfetto is just a labeled bar on a thread's timeline: it starts at one moment and ends at another. The mechanism is old and simple, called atrace. To start a slice, the thread writes a line like B|1234|AIDL::java::android.app.IActivityManager::isUserAMonkey::server into a special kernel file (trace_marker). To end it, it writes E|1234. The kernel timestamps both lines, and Perfetto draws the bar.

Writing those lines isn't free (each is a system call), so tracing is grouped into categories, and code checks a bit before doing any work. Binder's category is aidl (ATRACE_TAG_AIDL). When nobody is tracing aidl, the check is one load and one bit test, and nothing else happens.

if (atrace_enabled_tags & ATRACE_TAG_AIDL) {     // nearly free when off
    trace_begin(ATRACE_TAG_AIDL, name);          // writes "B|pid|name"
}
... do the work ...
trace_end(ATRACE_TAG_AIDL);                        // writes "E|pid"

9Who should emit the slice: generated code or libbinder?

There are two places you could put the trace_begin/trace_end pair, and Android has tried both.

Option A: in the generated code. The AIDL compiler has a switch for this, gen_trace. When it's on, every generated method gets a trace line baked in. For the cpp backend it looks like this:

generated with gen_trace = true (cpp)Status BpFoo::doFoo() {
  ScopedTrace _aidl_trace(ATRACE_TAG_AIDL, "AIDL::cpp::IFoo::doFoo::cppClient");
  ...
}
status_t BnFoo::onTransact(...) {
  case TRANSACTION_doFoo: {
    ScopedTrace _aidl_trace(ATRACE_TAG_AIDL, "AIDL::cpp::IFoo::doFoo::cppServer");
    ...

It works, but count the cost: two trace sites per method, each with its own string literal, compiled into every library that uses the interface, for every interface in the system. There are thousands of methods. And only interfaces built with the switch on get it.

Option B: once, in libbinder. Every call passes through BBinder::transact (server) and BpBinder::transact (client) no matter which interface it is. Put one trace site in each, and let generated code supply only the names, which it generates anyway. One copy of the tracing code serves the whole system, and every interface is covered.

So the CL isn't inventing a new place to trace. It finishes a move Android had already started: tracing happens in libbinder, and generated code provides the names. The only open question was how the client end gets hold of those names, which is the next three sections. All of it is behind a read-only flag that is off by default.

10How the server names its slice

libbinder already wraps every incoming call in a slice. It happens in BBinder::transact(), the box on the server side of the diagram in §5. To build the name AIDL::<backend>::<descriptor>::<method>::server, it needs two strings:

  • The descriptor. Easy: the BBinder is the object, so it simply knows its own interface name (getInterfaceDescriptor(), a local call).
  • The method name. It has the code (42), not the name, so it has to look it up:
    • cpp and NDK services: the generated constructor handed the BBinder a pointer to the names table (setTransactionCodeMap(&IFoo_data)), so it reads names[code − 1].
    • Java services: the BBinder is a JavaBBinder, which holds the Java Stub. libbinder calls JavaBBinder::getFunctionName(code), which calls the Stub's generated getTransactionName(code) through JNI.

Result: AIDL::java::android.app.IActivityManager::isUserAMonkey::server on system_server's binder thread. This part was already working before this change.

11Why the client was blind

Now stand on the client side, inside BpBinder::transact(), at the moment our call goes out. What do you have?

  • A handle: 7. A phone number.
  • A code: 42. A number.
  • A Parcel: the envelope.

To name the slice you'd want android.app.IActivityManager and isUserAMonkey. Neither is in your hands:

  • Ask the remote for its descriptor? BpBinder::getInterfaceDescriptor() exists, but on a phone number, asking a question means making a call. It sends a separate INTERFACE_TRANSACTION through the kernel. A second binder call, inside the slice for the first, just to label it, is exactly what tracing must never do.
  • Look up the method name? The names live in generated code. libbinder has no access to it, and the generic BinderProxy doesn't know which interface it's serving (§6).

So the client end showed nothing: the app's thread sat blocked in the kernel with no label saying who it was waiting on. The rest of this note covers how the change gets those two strings without making any extra call.

12Fix 1: hand the proxy a cheat sheet

For cpp clients the answer is pleasingly symmetric. The generated code already has the names table, the one it gives the server. So let the generated client constructor hand the same table to its BpBinder:

generated BpFoo constructor (cpp)BpFoo::BpFoo(const sp<IBinder>& impl) : BpInterface<IFoo>(impl) {
  if (BpBinder* bp = impl->remoteBinder()) bp->setTransactionCodeMap(&IFoo_data);
}

Now the phone number carries a sticky note. It's one pointer to a table that already exists, with the descriptor and all method names on it. BpBinder::transact() reads names[code − 1], the same way the server does. The pointer even fits into padding the BpBinder object already had, so the object doesn't grow.

13Fix 2: Java proxies register their Stub

Java clients have no static native table to hand over, and BpBinder can't reach any Java object (§6). But the generated Stub.Proxy knows both facts: the interface name (DESCRIPTOR) and its own Stub class, which has the method names. So the Proxy hands them down once, when it is built:

generated IActivityManager.Stub.Proxy constructor (Java, aidl --proxy_transaction_names)Proxy(android.os.IBinder remote) {
  mRemote = remote;
  android.os.BinderProxy.setTransactionNames(remote, DESCRIPTOR, Stub.class);
}

JNI turns that into a per-interface table and attaches it to the BpBinder, the same hook cpp uses. The table has no names array. Instead it has a function, resolveName, that asks the Stub class for a name the first time a code is traced, then caches it.

So, to answer both halves directly:

  • "Didn't the client already know the interface name?" Yes: DESCRIPTOR is a constant in the generated Proxy. The slice is emitted one layer down, in BpBinder, which per call is handed only (code, parcel). So the Proxy passes the name down once, at construction, instead of on every call. BinderProxy.transact keeps its signature.
  • "Where does the method name come from?" From a function the AIDL compiler already generates into every framework Stub, getDefaultTransactionName(int code). The Proxy passes the Stub class, so JNI calls it directly. No class is looked up by name.

What is getDefaultTransactionName, and is it going away?

It is not leftover tracing code, and nothing plans to remove it. It's a small lookup table written as a switch, one case per method:

generated into IActivityManager.Stub (framework.jar)public static String getDefaultTransactionName(int transactionCode) {
  switch (transactionCode) {
    case TRANSACTION_isUserAMonkey: return "isUserAMonkey";
    case TRANSACTION_getRunningAppProcesses: return "getRunningAppProcesses";
    ...
    default: return null;
  }
}

Where it comes from: frameworks/base/Android.bp sets aidl: { generate_get_transaction_name: true } for the framework, so the build runs the AIDL compiler with --transaction_names. That flag only emits this name lookup; it adds no tracing code. (aidl_interface modules get the same function when their Java backend sets gen_trace, which defaults to on for platform interfaces.)

The registration line in the Proxy constructor comes from a separate AIDL option, --proxy_transaction_names. It is on for framework.jar's interfaces (framework-minus-apex), and for aidl_interface Java backends with gen_trace, platform APIs and no sdk_version, because BinderProxy.setTransactionNames is a hidden API.

And it already has three users today. This change adds a fourth:

Both ends get names from generated code; only the route differs

libbinder has no method names of its own, on either side. The server's slice names come from AIDL-generated code too. The only difference is how libbinder reaches that code, because the server holds the object and the client holds only a handle:

Registration and lookup, step by step

Two moments matter: when the Proxy is built (once per proxy object), and when a traced call goes out (every call, but Java runs only the first time per code).

  1. IActivityManager.Stub.asInterface(binder) builds a Stub.Proxy. Its constructor calls BinderProxy.setTransactionNames(remote, "android.app.IActivityManager", IActivityManager.Stub.class).
  2. JNI (@FastNative) returns at once if the flag is off, the binder is not a BpBinder, or the BpBinder already has a table. That last case is the common one: one pointer check.
  3. Otherwise it gets or creates the table for that descriptor and calls bp->setTransactionCodeMap(&table->data).
  4. On a traced call, BpBinder sees a table without names and calls resolveName(table, 42). The first time, that is one JNI call to Stub.getDefaultTransactionName(42) through the cached jmethodID. The string is copied into native memory and cached.
  5. BpBinder builds AIDL::java::android.app.IActivityManager::isUserAMonkey::client from the table's descriptor and that name.

If the Stub has no name for a code, resolveName returns nothing and the slice shows #42, which is also what the server shows. A Java proxy built without --proxy_transaction_names never registers, so its calls get no client slice.

Alternative: Option B, reflection in BinderProxy (its own read-write flag, off by default; land A or B, not both)

  • How: BinderProxy.transact() opens the slice in Java and closes it in finally when the code is a user code, its flag is on and the aidl tag is on. One file.
  • Cache: the same scheme the server-side Binder.getTransactionTraceName() used: a static map from descriptor to an array of finished slice names, plus a volatile reference on each BinderProxy. A traced call after the first is one field read and one array read.
  • Descriptor: read once per BinderProxy from the start of the Parcel (the interface token the Proxy just wrote).
  • Method name: the generated Stub.Proxy is on the calling stack; its enclosing class is the Stub. getDefaultTransactionName(code) is found once per interface and called once per code. No match → #<code>.
  • Trade-off: it covers every Java proxy, including mainline modules and apps, without touching AIDL or JNI. But the Stub is matched by name against the descriptor (true for generated AIDL, not a contract), it is Java-only, and it adds a flag read and a tag check to every BinderProxy.transact.

Here's the satisfying part. The client name and the server name are built from the same strings: the descriptor constant the proxy registered (the same one it writes into every Parcel and the server checks), and the method name from the same generated switch. So they match exactly.

(Rust and NDK clients don't need any of this: their generated code registers a names table with libbinder_ndk, which already emits the client slice. See the report's "Where names come from" table.)

14What you see now

On the test device, a 12 s whole-system trace while opening Settings showed Java client slices in system_server (460), permissioncontroller (716), Settings (194), SystemUI (152), the keyboard, the launcher and phone. It had 255 distinct Java client names, none numeric; 251 of them also appeared with an identical ::server name. 1635 of 1923 Java server slices (85%) had a matching client slice. The rest came from proxies not built with --proxy_transaction_names (mainline modules such as ISafetyCenterManager, framework-location's ILocationManager) and from hand-written native clients.

15How the costs were measured

"It's cheap" is a claim; here's how each number was actually produced, so you can judge it, or rerun it. Everything ran on one cuttlefish VM: x86_64, 4 virtual CPUs, Android userdebug, idle. On that build libbinder.so is really libcore_bundle.so, so that's the library that was rebuilt.

Rule 1: compare two builds that differ only by the change

The baseline library was built from the same source tree with the change removed. Its md5 matched the library already on the device, so "baseline" really is "what the phone runs today". Test programs loaded one library or the other via LD_LIBRARY_PATH, so nothing else on the device changed between runs.

Memory: read it out of the binary

  • Object size. new BpBinder(...) compiles to operator new(SIZE) with a constant. Disassembling BpBinder::create shows movl $0xa0, %edi in both builds: 160 bytes. Appending the pointer naively would give $0xa8, 168 bytes. Android's allocator (scudo) adds a 16-byte header and rounds up to a fixed size class: 176 fits exactly, but 184 rounds up to 192. So the naive version would cost 16 real bytes per proxy. Moving one 4-byte field into a gap avoids it.
  • Library size. llvm-size -A on both libraries, section by section. .text grew by 1.4 KB (shared, clean, read from the file). .data.rel.ro, which each process gets a private copy of, grew 16 bytes and needed no new page.

CPU with tracing off: count instructions, then confirm with a stopwatch

A few nanoseconds is far below what a stopwatch can resolve on a 40 µs operation. So the primary evidence is the machine code: llvm-objdump of BpBinder::transact in both builds, diffed. The diff is about 9 instructions: load the tag word, test bit 24, branch, and store/reload a flag. Then a benchmark checks that nothing else changed:

  • Native: binderClientTraceBenchmark forks a server and makes empty synchronous calls to it. The same binary was run against both libraries, alternating baseline and patched, 8 rounds × 5 repetitions × ≥2 s each.
  • Java: a small Java program run with app_process calls isUserAMonkey, isSafeMode and isInteractive on system_server through their real generated proxies: 500 warm-up calls, then 30,000 timed. Again alternated stock vs patched, 8 rounds.

Why alternate instead of running all baseline runs, then all patched runs? Because the machine drifts (thermal state, other work, cache state). Running the two back to back and looking at their difference cancels most of the drift:

CPU with tracing on: measure the parts, then the whole

  • Parts: two microbenchmarks in a tight loop. BM_formatName is the same snprintf that builds the name: 118 ns. BM_traceBeginEnd is one atrace_begin + atrace_end, i.e. two writes to trace_marker: 887 ns.
  • Whole, native: the benchmark has two services in the same server process: one proxy with a table, one without. With the aidl tag on, both pay for the server's slice; only one pays for the client's. The difference between them is the client slice: +2.35 µs (n = 15 runs each, standard error 0.65 µs).
  • Whole, Java: not cleanly measured. With the tag on, the server slices turn on too, and on this VM the end-to-end Java numbers were too noisy to isolate the client part. By construction, a traced Java call does the native work plus, after the first call per code, one mutex and one hash lookup in resolveName. With tracing off, Java adds nothing per call; registration costs one JNI pointer check per Proxy construction.

Trace size: let the kernel count

The ftrace buffer keeps per-CPU statistics, including how many bytes it holds. The measurement:

  1. Enlarge the buffer to 32 MiB per CPU, so nothing gets overwritten.
  2. Clear it, and run exactly 10,000 calls without a table. Read the bytes: 1,221,512. Those are the server's slices.
  3. Clear it, and run exactly 10,000 calls with a table. Read the bytes: 2,421,964. That's the server's slices plus the client's.
  4. Check: overruns 0, and 10,000 client slices counted in the text.

The difference divided by 10,000 is 120.0 bytes per client slice.

Correctness: count slices, match names

A cost is only interesting if the feature works. Every trace run was checked with SQL over the trace (trace_processor):

  • Counts: N calls must give exactly N client slices. 2000 calls gave 2000 slices; 800 gave 800.
  • Names: client and server names must match. In the Java end-to-end test (800 calls each to isUserAMonkey, isSafeMode, isInteractive) client and server names were identical. Across the whole-device trace, of 255 distinct Java client names (none numeric), 251 had an identical server name in the same trace.
  • No duplicates from libbinder: no call got two libbinder client slices. NDK and Rust proxies have no BpBinder table, so BpBinder doesn't add a second slice to the one libbinder_ndk already emits. The only doubled names come from interfaces that still bake in gen_trace slices (…::cppClient, §9).

The raw numbers, benchmark JSON and trace files are linked from the report.
