Client-side AIDL slices from BpBinder

libbinder already emits AIDL::<backend>::<descriptor>::<method>::server for every incoming AIDL call. This proposal makes BpBinder::transact() emit the matching ::client slice, with the same name, through the existing aidl atrace category. Everything sits behind a flag that is off by default.

This is a design proposal for AOSP's libbinder, frameworks/base and the AIDL compiler.

New to binder? Binder from scratch walks through Parcels, BpBinder/BBinder, generated code and how each end gets its name.

TL;DR

  • Problem: libbinder names the server end of every AIDL call (AIDL::<backend>::<descriptor>::<method>::server), but for cpp and Java clients the calling thread only shows that it is blocked in binder.
  • Proposal: give each proxy's BpBinder one pointer to its interface's TransactionCodeData. With the aidl atrace tag on, BpBinder::transact() wraps user calls in …::client, with the same name as the server slice.
  • cpp: the generated BpFoo constructor attaches the static table AIDL already generates for the server.
  • Java, option A: the generated Stub.Proxy constructor calls BinderProxy.setTransactionNames(remote, DESCRIPTOR, Stub.class). The method names come from that Stub's generated getDefaultTransactionName(), fetched once per method and cached. There is no reflection and no guessing.
  • Java, option B: a self-contained change to BinderProxy.java that finds the Stub by reflection and caches names the way the old server-side Binder.getTransactionTraceName() did. It is smaller and covers more proxies, but matching the Stub to the descriptor by name is a convention, not a contract. Pick one, not both.
  • NDK/Rust: already traced by libbinder_ndk; no change.
  • Cost: sizeof(BpBinder) is unchanged. With tracing off, a few instructions per call. Everything is behind a flag that is off by default.

    const char* descriptor;                                                   // new

  • First table wins. Every interface_cast / asInterface builds a new proxy object around the same cached BpBinder, so "already set" is the common case. It costs one load and compare.
  • No table, no slice. NDK/Rust proxies already trace themselves in AIBinder_transact, and are not traced twice.
  • Hot path: the name is built in a 512-byte stack buffer. No allocation (checked by binderAllocationLimits).

2 · Java: two options

The Java server can name calls because JavaBBinder holds the Stub object. The Java client's BpBinder holds nothing, so something has to tell it which interface it speaks.

Option A: the Proxy registers its Stub

IFoo.java, generated with --proxy_transaction_namesprivate static class Proxy implements IFoo {
  Proxy(android.os.IBinder remote) {
    mRemote = remote;
    android.os.BinderProxy.setTransactionNames(remote, DESCRIPTOR, Stub.class);   // new
  }
}
  • Where the name comes from: getDefaultTransactionName is generated by aidl -t / --transaction_names. The server's getTransactionName returns the same strings. It is a current API, not legacy tracing.
  • Tables are never freed (BpBinders keep raw pointers), with one per interface per process, capped at 4096. A per-table mutex guards only the name map; the JNI call runs outside it.
  • Opt-in per build rule, because BinderProxy.setTransactionNames is hidden API. It is on for framework-minus-apex, and for aidl_interface Java backends with gen_trace, platform_apis and no sdk_version.

Option B: reflection in BinderProxy

Everything happens in BinderProxy.transact(), in Java. The cache uses the same scheme as the server-side cache that Binder.getTransactionTraceName() used before Java binder tracing moved to libbinder: a static map from descriptor to an array of finished slice names, and a per-object reference to that array so later calls skip the map.

private volatile AidlTraceNames mAidlTraceNames;      // like Binder's old mTransactionTraceNames
private String getAidlTraceName(Parcel data, int code) {
    AidlTraceNames names = mAidlTraceNames;
    if (names == null) mAidlTraceNames = names = AidlTraceNames.forParcel(data);   // peek + computeIfAbsent

}

3 · Flag

android.os.binder.flags.bpbinder_client_trace lives in libs/binder/flags.aconfig, next to binder_stats_v3 (namespace system_performance). It is off by default and fixed read-only, like every flag in that package (libbinder runs before /metadata is mounted). That makes it a constexpr: when off, setTransactionCodeMap() returns immediately, the check in transact() compiles away, and BinderProxy.setTransactionNames returns at once. The Java and AIDL change have no flag of their own; everything they do goes through the libbinder flag.

5 · Open questions

  • Coverage (A): proxies built outside opted-in rules get no Java client slice. That covers mainline modules, framework-location and apps. Extending it means turning on --proxy_transaction_names in more rules; module SDK builds would need a non-hidden API. Option B does not have this gap.
  • Hidden API (A): a non-platform-signed app linking a platform_apis AIDL library calls @hide setTransactionNames. To be checked.
  • Lifetime: a cpp table pointer dangles if its library is dlclosed while a proxy holds it. Java tables are never freed.
  • Duplicates: interfaces that still set cpp gen_trace also emit …::cppClient. Remove cpp gen_trace after this lands.
  • Measurement: benchmark both Java options on arm64 hardware before choosing.
