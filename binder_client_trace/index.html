Client-side AIDL slices from BpBinder

libbinder already emits AIDL::<backend>::<descriptor>::<method>::server for every incoming AIDL call. This change makes BpBinder::transact() emit the matching ::client slice, with the same name, through the existing aidl atrace category. Everything sits behind a flag that is off by default.

Status: a prototype of changes to AOSP's libbinder, frameworks/base and the AIDL compiler, not merged. Numbers are from a Cuttlefish x86_64 userdebug build.

New to binder? Binder from scratch walks through Parcels, BpBinder/BBinder, generated code and how each end gets its name.

TL;DR

  • Mechanism: a proxy's BpBinder gets one pointer to its interface's TransactionCodeData. With the aidl tag on, transact() wraps user calls in AIDL::<backend>::<descriptor>::<method>::client.
  • cpp: the generated BpFoo constructor attaches the static table AIDL already generates for the server.
  • Java (Option A): the generated Stub.Proxy constructor calls BinderProxy.setTransactionNames(remote, DESCRIPTOR, Stub.class). Method names come from that Stub's generated getDefaultTransactionName(), fetched once per method and cached. No reflection, no guessing.
  • Java (Option B, separate CL): one file, BinderProxy.java. Its cache uses the same scheme as the old server-side Binder.getTransactionTraceName(): a static map from descriptor to a name array, plus a volatile reference on each proxy. A traced call costs one field read and one array read; the tracing-off check costs 6 ns. The Stub is found by name from the Stub.Proxy frame on the stack. It covers more proxies (97–98% vs 77–85% of Java server slices paired), but matching the Stub to the descriptor by name is a convention, not a contract. Land A or B, not both.
  • NDK/Rust: already traced by libbinder_ndk; no change.
  • Cost: sizeof(BpBinder) unchanged. With tracing off, about 9 instructions per call and no measurable difference. With tracing on, +2.35 µs per native call and about 57 + strlen(name) bytes per slice.
  • Verified, both options, on device: Java client names are identical to the server names, and no client is numeric where the server has a name. Share of Java server slices with a matching client slice: A 77–85% (misses proxies not built with the new option), B 97–98%.

TransactionCodeData (Binder.h): two fields appended, read only if totalSize covers themstruct TransactionCodeData {
    size_t totalSize; const char* backendType; const char* const* names; size_t count;
    const char* descriptor;                                                   // new
    const char* (*resolveName)(const TransactionCodeData* table, uint32_t code); // new: names known only at runtime (Java)
};
  • First table wins. Every interface_cast / asInterface builds a new proxy object around the same cached BpBinder, so "already set" is the common case. It costs one load and compare.
  • No table, no slice. NDK/Rust proxies already trace themselves in AIBinder_transact, and are not traced twice.
  • Hot path: the name is built in a 512-byte stack buffer. No allocation (checked by binderAllocationLimits).

2 · Java: two options

The Java server can name calls because JavaBBinder holds the Stub object. The Java client's BpBinder holds nothing, so something has to tell it which interface it speaks.

Option A: the Proxy registers its Stub

IFoo.java, generated with --proxy_transaction_namesprivate static class Proxy implements IFoo {
  Proxy(android.os.IBinder remote) {
    mRemote = remote;
    android.os.BinderProxy.setTransactionNames(remote, DESCRIPTOR, Stub.class);   // new
  }
}
  • Where the name comes from: getDefaultTransactionName is generated by aidl -t / --transaction_names. The server's getTransactionName returns the same strings. It is a current API, not legacy tracing.
  • Tables are never freed (BpBinders keep raw pointers), with one per interface per process, capped at 4096. A per-table mutex guards only the name map; the JNI call runs outside it.
  • Opt-in per build rule, because BinderProxy.setTransactionNames is hidden API. It is on for framework-minus-apex, and for aidl_interface Java backends with gen_trace, platform_apis and no sdk_version.

Option B: reflection in BinderProxy (separate CL)

Everything happens in BinderProxy.transact(), in Java. The cache uses the same scheme as the server-side cache that Binder.getTransactionTraceName() used before Java binder tracing moved to libbinder: a static map from descriptor to an array of finished slice names, and a per-object reference to that array so later calls skip the map.

BinderProxy.javafinal boolean aidlTraced = code >= FIRST_CALL_TRANSACTION && code <= LAST_CALL_TRANSACTION

try { … existing transact … } finally { if (aidlTraced) Trace.traceEnd(Trace.TRACE_TAG_AIDL); }

private volatile AidlTraceNames mAidlTraceNames;      // like Binder's old mTransactionTraceNames
private String getAidlTraceName(Parcel data, int code) {
    AidlTraceNames names = mAidlTraceNames;
    if (names == null) mAidlTraceNames = names = AidlTraceNames.forParcel(data);   // peek + computeIfAbsent
    return names.get(code);                           // getAcquire; on miss build once, setRelease
}

Tested on its own (flag on via aflags, Option A not installed):
  • Java e2e: 800/800 client slices per method, with names identical to the server.
  • Whole device: 276 distinct Java client names. The 22 #<code> ones are #<code> on the server too (no generated names, e.g. ILauncherProxy, IContentProvider). 97–98% of Java server slices have a matching client slice.
  • A hand-written nested interface (test.LoaderTest.IFoo), called with a null context class loader, is named through the Stub.Proxy frame. Option A gives it no slice, because it is not registered.
  • Cost: 6 ns per call with tracing off (0 with the flag off); +2.3 µs median per traced call, the same as native libbinder.

3 · Flag

android.os.binder.flags.bpbinder_client_trace lives in libs/binder/flags.aconfig, next to binder_stats_v3 (namespace system_performance). It is off by default and fixed read-only, like every flag in that package (libbinder runs before /metadata is mounted). That makes it a constexpr: when off, setTransactionCodeMap() returns immediately, the check in transact() compiles away, and BinderProxy.setTransactionNames returns at once. The Java and AIDL CLs have no flag of their own; everything they do goes through the libbinder flag.

6 · Open issues

  • Coverage (A): proxies built outside opted-in rules get no Java client slice. That covers mainline modules, framework-location and apps. Extending it means turning on --proxy_transaction_names in more rules; module SDK builds would need a non-hidden API. Option B does not have this gap.
  • Hidden API (A): a non-platform-signed app linking a platform_apis AIDL library calls @hide setTransactionNames. Untested.
  • Lifetime: a cpp table pointer dangles if its library is dlclosed while a proxy holds it. Java tables are never freed.
  • Duplicates: interfaces that still set cpp gen_trace also emit …::cppClient. Remove cpp gen_trace after this lands.
  • Measurement: isolate the traced Java cost and rerun the benchmarks on arm64.
