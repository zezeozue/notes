Zero-copy Java to native on ART: a non-movable byte[] removes a copy and keeps Java writes fast

High-throughput Android code often builds structured binary payloads in Java or Kotlin and hands them to C without crossing JNI per field or copying the buffer twice. Perfetto’s tracing SDK hits this boundary head-on: Java code encodes typed protocol-buffer fields at sub-microsecond cost, and C code writes the packet into a shared-memory ring buffer. Standard arrays, JNI helpers, DirectByteBuffer and Unsafe each sacrifice either zero-copy hand-off or Java compiler optimizations; an ART non-movable byte[] keeps both.

Runtime and compiler excerpts are from art/ and libcore/ in AOSP as of Android 17. SDK excerpts are from the development branch of the Java SDK rewrite in the open-source Perfetto repository (“the branch” below). Instruction sequences marked shape are simplified. The proposal in Section 4 is a design sketch that has not been built.

At a glance

  • Why trace in user space. Android’s classic Trace.beginSection(String) writes a flat text string through JNI and a kernel write() into ftrace. Perfetto’s TrackEvent SDK instead writes typed protobuf fields into a user-space shared-memory ring buffer (SMB) at sub-microsecond overhead, with no syscall on the fast path.
  • Why encode in Java, once. Crossing JNI once per field would pay thread-state transitions on every field and block ART’s inliner (Where the costs are in ART). Encoding the whole event in Java and calling JNI once at emit() avoids that, leaving the encoded bytes in a Java buffer that C code must copy into the SMB.
  • The runtime tension. ART’s moving garbage collectors relocate normal byte[] arrays to keep allocation a fast pointer bump and prevent fragmentation, whereas C code wants a stable uint8_t* pointer. Standard JNI copies the bytes a second time (GetByteArrayRegion) or touches pages and stalls GC flips (GetPrimitiveArrayCritical).
  • Why DirectByteBuffer and Unsafe lose in Java. On ART a direct buffer sits on the same non-movable heap memory, yet every put(byte) writes through a raw-address intrinsic (AllWrites) that forces the compiler to reload buffer state from memory on every byte.
  • How a non-movable byte[] gets both. Allocating the scratch buffer with VMRuntime.newNonMovableArray and reading VMRuntime.addressOf once gives Java an ordinary byte[] (bounds-check elimination, register-held write cursor) and gives C a fixed address, provided a strong reference keeps the array alive across the call.

Terms. ART is the Android Runtime for Java and Kotlin bytecode, GC is its garbage collector, and JNI (Java Native Interface) bridges managed code and C/C++. atrace is Android’s legacy user-space tracing API (android.os.Trace), which writes text markers into the kernel’s ftrace buffer.

A TrackEvent is Perfetto’s structured trace packet, serialized as protocol-buffer bytes into a per-process SMB (shared memory buffer) mapped with the traced daemon by Perfetto’s C SDK. A non-movable array is a primitive Java array allocated in a heap space the GC never compacts, and a direct buffer is a java.nio.DirectByteBuffer.

Part I · Getting the bytes out

1Today each event is copied once more than it needs to be

To see why this path exists, start with android.os.Trace.beginSection(String). It formats a plain text marker (B|pid|name, capped at 127 characters) and writes it through JNI and a kernel write() into ftrace. Every slice pays a syscall, and attaching structured debug arguments forces string concatenation on hot threads. Perfetto’s TrackEvent pipeline writes binary protobuf fields straight into a user-space shared memory buffer (SMB) with no syscall on the fast path.

Exposing TrackEvent to Java and Kotlin raises a boundary choice: make one JNI call per protobuf field, or serialize the event in Java first? Per-field JNI calls lose because each regular call swaps thread state twice and blocks ART’s inliner (Where the costs are in ART).

The Perfetto Java SDK rewrite therefore batches encoding in Java: on the branch, a per-thread ProtoWriter writes the entire TrackEvent protobuf body into a reusable byte[] (mBuf), and PerfettoTrackEventBuilder.emit() crosses JNI once via native_emit.

That single crossing eliminates per-field JNI overhead, yet the encoded bytes still have to move from the Java byte[] into the SMB, and today they are copied twice when only the final copy into the SMB is required. In _emit, the JNI layer first copies mBuf into a native RawBody std::vector using GetByteArrayRegion. That vector backs raw_, a PERFETTO_TE_HL_PROTO_TYPE_RAW descriptor holding a pointer and a length, which Perfetto’s C SDK then copies unchanged into the SMB chunk.

The second copy is the point of the exercise, because the event has to end up in the SMB. The first copy exists only because native code cannot be handed a pointer into a normal Java array and keep using it.

2JNI copies because the GC moves normal arrays

Why can’t C code simply take the address of mBuf[0] and read from it? ART’s garbage collectors are moving collectors. Freeing dead objects in place would scatter holes across the heap, wasting RAM to fragmentation and forcing allocations onto free lists. Compacting survivors together leaves contiguous free memory so normal Java allocation stays a lock-free pointer bump (Where the costs are in ART).

When Concurrent Mark-Compact (CMC, the default collector in AOSP builds) slides live objects down, or Concurrent Copying (CC) copies them into fresh regions, ART rewrites every Java reference on thread stacks and inside heap objects. A raw uint8_t* in C is an untyped integer outside ART’s view, so the collector cannot find or update it.

Because objects differ in size and pinning needs, ART splits the heap into spaces. A normal new byte[n] lands in the moving space, where any GC cycle can relocate it. The non-moving space uses mark-sweep and a free list so live objects never move, and the large object space (LOS) maps primitive arrays and strings of 12 KB or more in whole OS pages without moving them either. Sizes and thresholds are in Numbers and method.

So native code gets a jbyteArray instead of a pointer. It is an opaque handle that the runtime resolves to the array’s current location on each call. Each JNI array function then has a choice. It can copy the data out, or it can pin the array, which stops the GC from moving it until native code says it is done.

The critical call is how JNI pins. The thread flip is the short pause in which CC or CMC switches every thread over to the moved objects. While any thread holds a critical array, the flip waits. So the array cannot move, and a long critical section delays the next GC.

For movable and non-movable arrays alike, the critical call also runs EnsureObjectUserfaulted before returning. Userfaultfd is the Linux kernel mechanism CMC uses during concurrent compaction to catch user-space accesses to heap pages it has not compacted yet and compact them on the spot. If C code passed an uncompacted heap pointer straight into a kernel system call such as write(), the kernel access could not run ART’s user-space fault handler, so JNI touches every page of the array up front.

What it means for you If the array never moves, Get<T>ArrayElements and GetPrimitiveArrayCritical hand out a direct pointer instead of a copy. Get<T>ArrayRegion still copies, by definition. addressOf goes one step further. It turns the array into a plain long once, so the per-event JNI call needs no array handle at all.

3Two runtime calls give you an array that never moves, and its address

A per-thread encoding buffer has the opposite profile from ordinary short-lived Java objects: it is allocated once, grown rarely, and read across thousands of JNI calls. Paying a free-list allocation once so the buffer’s address never changes is an easy win. Two methods on dalvik.system.VMRuntime expose ART’s non-moving space directly: one allocates a primitive array there, and the other returns the native address of its first element.

Platform and mainline module code can call both, because both are @SystemApi(client = MODULE_LIBRARIES). They are not public SDK, and apps see them only as hidden API (both carry @UnsupportedAppUsage). Both are also @FastNative, a JNI binding that skips the usual thread-state change but still passes a JNIEnv.

libcore/libart/src/main/java/dalvik/system/VMRuntime.javapublic native Object newNonMovableArray(Class<?> componentType, int length);
public native long   addressOf(Object array);   // "Returns the address of array[0]"

newNonMovableArray

  • Throws NegativeArraySizeException for a negative length and NullPointerException for a null component type.
  • Allocates through the normal mirror::Array::Alloc, but with the non-moving allocator (heap->GetCurrentNonMovingAllocator()) instead of the TLAB allocator. A TLAB is a per-thread chunk of the moving space that a thread allocates from without locking.
  • An array at or above the large-object threshold still lands in the large object space, like any large primitive array. That space never moves objects either, so the address stays valid.
  • To Java it is an ordinary byte[]: normal header, normal a[i], collected when unreachable.

addressOf

  • Returns 0 for null. It throws for non-arrays, object arrays, and arrays the heap considers movable (Heap::IsMovableObject). That check only looks at the moving and non-moving spaces, so a plain new byte[1 MB] in the large object space is accepted too. Only newNonMovableArray is documented to give a non-movable array, so don’t rely on that.
  • Returns the address of element 0, just past the array header (GetRawData(componentSize, 0)).
  • The address is valid only while the array is reachable. Nothing pins it, so Java must keep a strong reference (Section 8).
  • Its doc comment notes the difference from JNI. Under CheckJNI’s forcecopy mode, a debug mode that hands out copies to catch misuse, JNI may return a copy. addressOf never does.

DirectByteBuffer is the same memory

In standard Java, the portable way to give native code a stable buffer address without internal APIs is ByteBuffer.allocateDirect. On OpenJDK/HotSpot, that allocates off-heap native memory and registers a Cleaner to free it. ART does something simpler: ByteBuffer.allocateDirect does not call malloc at all. Its MemoryRef allocates a non-movable byte[] on the managed heap and takes its address the exact same way:

libcore/ojluni/src/main/java/java/nio/DirectByteBuffer.java · MemoryRef(int capacity)VMRuntime runtime = VMRuntime.getRuntime();
buffer = (byte[]) runtime.newNonMovableArray(byte.class, capacity + 7);
allocatedAddress = runtime.addressOf(buffer);
// Offset is set to handle the alignment
offset = (int) (((allocatedAddress + 7) & ~(long) 7) - allocatedAddress);

Because the backing store is an ordinary managed array, nothing has to free it explicitly. Buffers that wrap memory outside the GC’s control (such as file mappings) attach a Cleaner (sun.misc.Cleaner), a phantom-reference callback that unmaps the region once the buffer becomes unreachable. On ART only the file-mapped constructor creates one. The allocateDirect path sets cleaner = null, with the comment “no need for a cleaner since the GC will do all the work”.

The Android framework already uses this exact pattern in performance-sensitive graphics code. android.graphics.PathIterator allocates its scratch point buffer with newNonMovableArray and records addressOf once in the constructor. It passes that long address to a @CriticalNative method, the lowest-overhead JNI binding, restricted to static methods with primitive arguments and no JNIEnv. It also keeps a standard array fallback for host JVMs (IS_DALVIK checks "Dalvik".equals(System.getProperty("java.vm.name")), a historical property value ART kept for compatibility):

What it means for you A direct buffer and a non-movable byte[] give native code the same zero-copy pointer. The difference that matters for speed is how Java writes the bytes, which is what Part II is about.

4The SDK needs two small changes

The encoder must write into a non-movable array, and native code must receive that array’s address instead of the array.

Rules

  1. Pass the address on every call, and never keep it in native code after the call returns.
  2. Read the address after encoding finishes. ensureCapacity may have replaced the array, and a new array has a new address.
  3. Keep the array strongly reachable across the call. It is a field of the ProtoWriter that the thread-local builder holds, so this already holds (Section 8).

Tradeoffs

  • Space. The non-moving space has a fixed default size and is never compacted, so it fragments. Use small, reused buffers that grow geometrically. The branch starts at 512 bytes. The default size is in Numbers and method.
  • Allocation cost. A @FastNative call plus a free-list allocation, instead of the TLAB bump. It happens once per thread and per growth, not per event.
  • Host and Ravenwood. Host JVMs have no VMRuntime. Ravenwood, the platform’s host-side test runtime, has a fake one. Its newNonMovableArray returns a plain array, and its addressOf returns a made-up id, not a memory address. Keep the GetByteArrayRegion path as a fallback, as PathIterator does.

A smaller variant keeps the array parameter and swaps GetByteArrayRegion for GetPrimitiveArrayCritical. For a non-movable array, that also returns a direct pointer without touching the GC (Section 2). It still pays to decode the handle and check types on every event, and it rules out the next step.

Next step: @CriticalNative native_emit is @FastNative because it takes the event name as a String, which native code decodes through JNIEnv. A @CriticalNative method must be static and take only primitives, and it gets no JNIEnv. If the name is also encoded in Java, into the same buffer or as an interned id (a small integer standing for a string registered once), every argument becomes a long or int. Then the emit can be @CriticalNative, which skips the JNI frame and local-reference setup entirely.
Part II · Writing the bytes in Java

5One direct-buffer put() wraps a single store in a chain of loads and checks

Part I showed that on ART a DirectByteBuffer and a non-movable byte[] sit on the exact same heap memory, and both emit a single byte-store instruction for the payload itself. Why, then, is encoding protobuf varints and fixed-width integers byte-by-byte into a DirectByteBuffer so much slower than writing into a byte[]? Look at the state checks and mutable field updates that DirectByteBuffer.put(byte) runs around each byte:

libcore/ojluni/src/main/java/java/nio/DirectByteBuffer.javapublic final ByteBuffer put(byte x) {
    if (!memoryRef.isAccessible) {
        throw new IllegalStateException("buffer is inaccessible");
    }
    if (isReadOnly) {
        throw new ReadOnlyBufferException();
    }
    put(ix(nextPutIndex()), x);   // ix(i) = address + i
    return this;
}
private ByteBuffer put(long a, byte x) {
    Memory.pokeByte(a, x);
    return this;
}
// Buffer.nextPutIndex(): int p = position; if (p >= limit) throw ...; position = p + 1; return p;

Memory.pokeByte is an intrinsic: ART’s compiler recognizes the signature and emits a single arm64 strb (store byte) instead of a JNI call (Where the costs are in ART). Its destination, however, is an untyped 64-bit long that could point anywhere in memory, so the intrinsic is declared kWriteSideEffects (SideEffects::AllWrites(), Section 7). Nothing after the poke keeps the buffer alive explicitly; the method relies on ART keeping this live until it returns (Section 8).

Bulk put is worse put(byte[], off, len) goes through Memory.pokeByteArray, which is registered with plain NATIVE_METHOD: a regular JNI method that pays the full thread-state change. It is not an intrinsic, and not even @FastNative. Its body is a GetByteArrayRegion into the destination address. So every region put is a full JNI transition plus a copy, a poor fit for the short fields protobuf encoding produces.
What about Unsafe? Unsafe does not help either. Its raw-address putByte(long, byte) is a @FastNative JNI call on every byte. This holds for both sun.misc.Unsafe and jdk.internal.misc.Unsafe. Only the object-and-offset putByte(Object, long, byte) form is compiled inline, and it is declared kAllSideEffects: it may read and write any memory, an even broader side effect than pokeByte’s. It drops the buffer checks but not the side-effect problem, and a wrong address corrupts memory silently.

6The compiler can delete array bounds checks, but not a buffer’s

Java enforces memory safety on every indexed write: writing past the end of an array or buffer must throw an exception rather than corrupting adjacent memory. Checking 0 <= pos < bound on every byte of an 8-byte integer would emit eight compare-and-branch pairs around eight byte stores. To avoid that tax, an optimizing compiler tries to hoist or collapse repeated checks into a single guard ahead of the writes, which requires knowing that the bound cannot change mid-sequence.

In ART’s optimizing compiler, a method’s intermediate representation (IR) is a graph of typed nodes whose class names start with H. An array store a[i] = v lowers to HArraySet guarded by HBoundsCheck(i, a.length), where HArrayLength has SideEffects::None() because array length never changes.

DirectByteBuffer.put() instead runs a plain Java if (p >= limit) branch inside nextPutIndex, comparing two mutable int fields. Bounds-check elimination (BCE) folds or hoists redundant HBoundsCheck nodes, so that structural difference decides whether checks disappear.

BCE tracks value ranges relative to the array length and deletes bounds checks it can prove are in range. When it cannot prove it up front, it can still add one compare before the accesses that deoptimizes, dropping to the interpreter, if it fails. Then it removes the individual checks. It does this for loops, and for groups of accesses like a[pos]…a[pos + 7] in one block (AddComparesWithDeoptimization). The group must be big enough; the thresholds are in Numbers and method.

The DirectByteBuffer test is not a bounds-check node, so BCE never looks at it. It could only fold away if load/store elimination first proved that position and limit are unchanged since the previous put(). The poke in between prevents that proof (Section 7).

ProtoWriter.java · putLongLeNoCheck (branch)byte[] buf = mBuf;    // fields hoisted into locals
int pos = mPos;
buf[pos] = (byte) value;
buf[pos + 1] = (byte) (value >> 8);
// ... pos + 2 .. pos + 6 ...
buf[pos + 7] = (byte) (value >> 56);
mPos = pos + 8;         // one write-back

This is the shape BCE handles best: one base index, constant offsets, and a length that cannot change. Each public write* on the branch checks capacity once, for the worst-case size, and then writes through these *NoCheck helpers. Each helper loads and stores the position field once. So the field traffic is a couple of loads and stores per field, not per byte.

What it means for you Write into a byte[] with the position in a local, and check capacity once per field rather than once per byte. That gives the compiler an immutable bound to reason about and nothing to reload.

7A raw-address write makes the compiler forget every field it loaded

Why couldn’t the compiler at least keep buf.position, buf.limit and buf.address in registers across consecutive DirectByteBuffer.put() calls? The obstacle is pointer aliasing: keeping a heap field in a CPU register across a store is only legal if the compiler can prove that the store did not overwrite that same memory location. In strongly typed Java, memory is partitioned cleanly by type: writing to a byte[] element can never overwrite an object’s int or long fields, because arrays and object fields occupy disjoint layouts.

To check aliasing fast without expensive whole-program pointer analysis, ART’s compiler tags every IR instruction with a compact side-effects bitset listing which categories of heap memory (field types and array element types) it may read or write. As soon as code steps outside Java’s type system and passes a raw 64-bit integer address to Memory.pokeByte(addr, v), that partitioning collapses: as far as the compiler knows, addr could point straight at buf.position itself.

ART marks pokeByte and reachabilityFence as able to write any memory (AllWrites), and the inline Unsafe byte stores as able to read and write any memory (AllExceptGCDependency).

“Cached” means kept in a register

Reading buf.position is a load from the heap. “Caching” it means the compiler keeps the loaded value in a CPU register and reuses it. It has nothing to do with the L1 cache. A register read is free. A load is an instruction whose result the next instruction waits for.

LSE, GVN and LICM all lose to the poke

In a normal Java method, ART relies on three complementary optimization passes to strip away redundant heap loads and stores: one tracks memory values along paths through a method, one deduplicates identical computations, and one hoists unchanging loads out of loops. All three consult the instruction’s side-effects bitset before reusing a heap value. Because Memory.pokeByte stays in the IR graph as an HInvoke (ART’s call node) tagged with AllWrites, it defeats every one of them:

PassWhat it removesMemory.pokeByte (an HInvoke with AllWrites)
LSE · load/store eliminationReloads of a known value; stores that are overwritten before being read.HandleInvoke: every heap value that might be shared (anything but a fresh, non-escaping allocation, i.e. an object created in this method that no other code can see) becomes unknown, and pending stores must be kept.
GVN · global value numberingRecomputing an identical value, including loads.set->Kill(current->GetSideEffects()) drops every load of a written type
LICM · loop-invariant code motionWork that gives the same result on every iteration.loop effects include AllWrites, so no field load is hoisted

So inside put() the poke forces every reload. A byte[] loop with pos in a local is unaffected, because an array store only writes array elements of its type.

What it means for you Avoid raw-address writes in a hot loop. Each one ends every “this field has not changed” proof. So all the buffer state around it is loaded and stored again for every byte.
Part III · Keeping it alive

8Something must keep the array alive while native code uses its address

Even when an array never moves, turning it into a raw long address introduces a lifetime hazard. A tracing collector finds live objects solely by following typed references from GC roots (thread stacks, static fields, and JNI local or global reference tables). An untyped long holding addressOf(buf) is invisible to the GC: once code stops reading the Java reference buf, a concurrent GC could reclaim the array and reuse its non-moving slot mid-call.

Under the Java Language Specification, an object may become unreachable immediately after the last expression that reads its reference, even before the enclosing method returns. On Android, a long-standing implementation choice in ART masked many bugs of this kind. Three runtime concepts explain how:

  • A safepoint is a point in compiled code, such as a method call or a loop back-edge (the jump back to the top of a loop), where a thread is allowed to pause for GC.
  • A stack map is metadata emitted at each safepoint telling the GC which CPU registers and stack slots currently hold live object references.
  • The method’s environment is the mapping from dex bytecode’s virtual registers to machine registers or stack slots recorded at each safepoint (used for deoptimization as well as root scanning).

By default, ART includes every reference still occupying a dex virtual register in the safepoint’s stack map, even after the code’s last lexical read of that variable. SsaLivenessAnalysis::ShouldBeLiveForEnvironment returns true for every reference unless the method’s graph is marked dead-reference safe, meaning the compiler is allowed to drop dead references right after their last use so large object graphs are not pinned unnecessarily across long methods.

Today ART prunes dead references only in platform classes annotated @DeadReferenceSafe, and disables pruning for methods touching a @ReachabilitySensitive field or cleanup method. The @DeadReferenceSafe javadoc describes the classic failure, where a finalized wrapper frees its native struct while a method still dereferences the copied pointer, and notes: “Historically, ART has avoided this by keeping ‘this’ reachable until m() completes.”

When a local variable is the sole reference to an object whose raw address is in use, Reference.reachabilityFence(obj) gives a portable guarantee instead of relying on ART’s default. The fence stays in the IR as an HInvoke intrinsic that extends obj’s live range past preceding safepoints; kWriteSideEffects prevents dead-code elimination while arm64’s VisitReachabilityFence emits zero instructions.

The fence costs no instructions, but it blocks some optimizations

KindCost
Instructions (compiled)None. The arm64 code generator emits nothing.
Instructions (not intrinsified)The Java body runs: a volatile store to SinkHolder.sink, then a volatile read and (normally) a second store that clears it. ART inlines methods with try/catch (kInlineTryCatches), except at call sites that are themselves inside a try block, or that were devirtualized through CHA (class hierarchy analysis, which proves only one implementation is loaded) or an inline cache (the receiver classes recorded at that call site at run time).

Per byte in a hot write loop, those costs would add up; DirectByteBuffer.put omits the fence and relies on ART’s default column in Figure 8. Once per event around a JNI call, the cost vanishes because the call is already opaque to the optimizer, and in the SDK design mBuf stays strongly reachable through the thread-local builder’s ProtoWriter anyway.

What it means for you Whenever you turn an object into a raw address, something else has to keep it alive. Prefer a strong field the GC can see. Use reachabilityFence after the last raw access when the only reference is a local.

What it means for you A non-movable byte[] keeps the fast path for Java writes and gives native code a zero-copy pointer. The only copy left is the one into the SMB.

Numbers and method

This page is an explainer. Its figures are constants read from the AOSP and Perfetto sources listed below, not measurements. The proposal in Section 4 has not been built or measured.

Exact figures and code names behind the text.

TopicExact figure or code detailSource
Non-moving space64 MB by default (kDefaultNonMovingSpaceCapacity), managed with a free list, never compacted. Heap::IsMovableObject returns false for every object there. It only inspects continuous spaces (single address ranges such as the moving and non-moving spaces), so it also returns false for anything in the large object space.heap.h, heap.cc, dalvik_system_VMRuntime.cc
Large object spacePrimitive arrays and strings of 12 KB and more (kMinLargeObjectThreshold), in a separate page-granular region. A free list by default (FreeListSpace, kDefaultLargeObjectSpaceType).heap.h, heap-inl.h
Array header and JNI pinning12-byte array header; addressOf returns the address just past it (GetRawData(componentSize, 0)). For movable arrays, Get<T>ArrayElements allocates new uint64_t[] and calls memcpy; GetPrimitiveArrayCritical calls IncrementDisableThreadFlip under CC/CMC or IncrementDisableMovingGC on other collectors.dalvik_system_VMRuntime.cc, jni_internal.cc
