Zero-copy Java to native on ART: a non-movable byte[] removes a copy and keeps Java writes fast

The Perfetto Java SDK rewrite encodes each trace event in Java and then hands the bytes to native code. That hand-off copies the bytes today. This page explains why, and how an array that never moves removes the copy. It also explains why a plain array is faster to write from Java than a direct buffer, even though on ART both are the same kind of memory.

Runtime and compiler excerpts are from art/ and libcore/ in AOSP as of Android 17. SDK excerpts are from the development branch of the Java SDK rewrite in the open-source Perfetto repository (“the branch” below). Instruction sequences marked shape are simplified. The proposal in Section 4 is a design sketch that has not been built.

At a glance

  • What happens. Each event’s bytes are copied twice on the way out: once into a native buffer, then into the tracing buffer.
  • Why. The garbage collector moves normal Java arrays, so native code cannot keep a pointer into one.
  • The fix. Allocate the encoding buffer as an array that never moves, and pass native code its address. Only the needed copy is left.
  • Why not a direct buffer. It uses the same memory, but every byte written through it makes the compiler reload the buffer’s state.
  • The catch. Something must keep the array alive while native code reads it. In the SDK, a field already does.

Terms. ART is the Android runtime that runs Java code, and the GC is its garbage collector. JNI is the bridge between Java and C code. The SMB (shared memory buffer) is the memory the tracing service reads events from. The C SDK is Perfetto’s C tracing API, which the JNI layer calls. A non-movable array is a Java array allocated where the GC never moves it. A direct buffer is a java.nio DirectByteBuffer, whose bytes native code can address directly.

Part I · Getting the bytes out

1Today each event is copied once more than it needs to be

The event body is copied twice on its way to the tracing buffer, and only the second copy is needed. On the branch, ProtoWriter encodes the TrackEvent body (the event’s protobuf payload) into its mBuf, an ordinary Java array. PerfettoTrackEventBuilder.emit() then makes one JNI call, native_emit, that passes the array and its length.

The native side copies the bytes into a RawBody vector with GetByteArrayRegion. That vector backs the raw_ field, a PERFETTO_TE_HL_PROTO_TYPE_RAW proto field that is just a pointer and a length. The C SDK, built as a shared library, then appends those bytes unchanged to the event in the SMB.

  uint8_t* dst = raw_body->reserve_body(static_cast<size_t>(body_len));   // grows buf_ if needed
  env->GetByteArrayRegion(body, 0, body_len, reinterpret_cast<jbyte*>(dst)); // copy 1
}

The second copy is the point of the exercise, because the event has to end up in the SMB. The first copy exists only because native code cannot be handed a pointer into a normal Java array and keep using it.

2JNI copies because the GC moves normal arrays

A raw pointer into a Java object is only safe while the object stays put, and on ART it usually does not. ART’s collectors are moving collectors. To keep the heap compact, they relocate live objects and update every Java reference to the new copy. CMC (concurrent mark-compact, the default collector in AOSP builds) slides live objects down within the moving space. CC (concurrent copying) copies them to fresh regions. A pointer held by native code is not a Java reference, so the GC cannot update it.

The heap is split into spaces with different rules. A normal new byte[n] goes into the moving space, so its address can change at any GC. The non-moving space is a separate region managed with a free list: dead objects leave holes, and live ones stay put. The large object space (LOS) holds big primitive arrays and strings in whole pages, and never moves them either. Sizes and thresholds are in Numbers and method.

So native code gets a jbyteArray instead of a pointer. It is an opaque handle that the runtime resolves to the array’s current location on each call. Each JNI array function then has a choice. It can copy the data out, or it can pin the array, which stops the GC from moving it until native code says it is done.

Table 1 shows what art/runtime/jni/jni_internal.cc does for each way of reading a primitive array, depending on whether the array may move (Heap::IsMovableObject). The last row, VMRuntime.addressOf (Section 3), is not JNI and is there for comparison.

The critical call is how JNI pins. The thread flip is the short pause in which CC or CMC switches every thread over to the moved objects. While any thread holds a critical array, the flip waits. So the array cannot move, and a long critical section delays the next GC.

For movable and non-movable arrays alike, the critical call also runs EnsureObjectUserfaulted before returning. Userfaultfd is the kernel mechanism CMC uses to catch accesses to pages it has not compacted yet. Touching the array’s pages up front means a kernel call handed the pointer never hits one of those faults.

What it means for you If the array never moves, Get<T>ArrayElements and GetPrimitiveArrayCritical hand out a direct pointer instead of a copy. Get<T>ArrayRegion still copies, by definition. addressOf goes one step further. It turns the array into a plain long once, so the per-event JNI call needs no array handle at all.

3Two runtime calls give you an array that never moves, and its address

To give native code a pointer it can keep using, the array has to live where the GC never moves it. Two calls in dalvik.system.VMRuntime do that. One allocates such an array, and the other returns its address.

Platform and mainline module code can call both, because both are @SystemApi(client = MODULE_LIBRARIES). They are not public SDK, and apps see them only as hidden API (both carry @UnsupportedAppUsage). Both are also @FastNative, a JNI binding that skips the usual thread-state change but still passes a JNIEnv.

libcore/libart/src/main/java/dalvik/system/VMRuntime.javapublic native Object newNonMovableArray(Class<?> componentType, int length);
public native long   addressOf(Object array);   // "Returns the address of array[0]"

newNonMovableArray

  • Throws NegativeArraySizeException for a negative length and NullPointerException for a null component type.
  • Allocates through the normal mirror::Array::Alloc, but with the non-moving allocator (heap->GetCurrentNonMovingAllocator()) instead of the TLAB allocator. A TLAB is a per-thread chunk of the moving space that a thread allocates from without locking.
  • An array at or above the large-object threshold still lands in the large object space, like any large primitive array. That space never moves objects either, so the address stays valid.
  • To Java it is an ordinary byte[]: normal header, normal a[i], collected when unreachable.

addressOf

  • Returns 0 for null. It throws for non-arrays, object arrays, and arrays the heap considers movable (Heap::IsMovableObject). That check only looks at the moving and non-moving spaces, so a plain new byte[1 MB] in the large object space is accepted too. Only newNonMovableArray is documented to give a non-movable array, so don’t rely on that.
  • Returns the address of element 0, just past the array header (GetRawData(componentSize, 0)).
  • The address is valid only while the array is reachable. Nothing pins it, so Java must keep a strong reference (Section 8).
  • Its doc comment notes the difference from JNI. Under CheckJNI’s forcecopy mode, a debug mode that hands out copies to catch misuse, JNI may return a copy. addressOf never does.

DirectByteBuffer is the same memory

The usual Java answer to “give native code a stable pointer” is a direct buffer, so it is worth knowing what one is on ART. ByteBuffer.allocateDirect does not call malloc. Its MemoryRef allocates a non-movable array and takes its address the same way as above:

libcore/ojluni/src/main/java/java/nio/DirectByteBuffer.java · MemoryRef(int capacity)VMRuntime runtime = VMRuntime.getRuntime();
buffer = (byte[]) runtime.newNonMovableArray(byte.class, capacity + 7);
allocatedAddress = runtime.addressOf(buffer);
// Offset is set to handle the alignment
offset = (int) (((allocatedAddress + 7) & ~(long) 7) - allocatedAddress);

Because the memory is a Java array, nothing has to free it explicitly. Buffers that own memory the GC does not manage use a Cleaner (sun.misc.Cleaner), a callback that runs once its referent becomes unreachable. For those buffers it unmaps the memory. On ART only the file-mapped constructor creates one. The allocateDirect path sets cleaner = null, with the comment “no need for a cleaner since the GC will do all the work”.

The framework already uses the pattern this page proposes. android.graphics.PathIterator allocates its point buffer with newNonMovableArray and takes addressOf once in the constructor. It passes the address to a @CriticalNative method, the cheapest JNI binding: static, primitive arguments only, and no JNIEnv. It also keeps a fallback for runtimes that are not ART:

What it means for you A direct buffer and a non-movable byte[] give native code the same zero-copy pointer. The difference that matters for speed is how Java writes the bytes, which is what Part II is about.

4The SDK needs two small changes

The encoder must write into a non-movable array, and native code must receive that array’s address instead of the array.

Where: the Perfetto Java SDK rewrite (in development).
Change: allocate the encoding buffer with newNonMovableArray and pass addressOf to native_emit as a long.
Effect: the raw proto field points straight at the Java array, so the only copy left is the one into the SMB.

Design sketch, simplified. It has not been built or measured. The current ensureCapacity on the branch is shown for reference.

ProtoWriter.java · ensureCapacity (branch, today)private void ensureCapacity(int needed) {
  if (mPos + needed <= mBuf.length) {
    return;
  }
  int newSize = Math.max(mBuf.length * 2, mPos + needed);
  byte[] newBuf = new byte[newSize];
  System.arraycopy(mBuf, 0, newBuf, 0, mPos);
  mBuf = newBuf;
}

  VMRuntime rt = VMRuntime.getRuntime();

  raw_.len = n;
}

Rules

  1. Pass the address on every call, and never keep it in native code after the call returns.
  2. Read the address after encoding finishes. ensureCapacity may have replaced the array, and a new array has a new address.
  3. Keep the array strongly reachable across the call. It is a field of the ProtoWriter that the thread-local builder holds, so this already holds (Section 8).

Tradeoffs

  • Space. The non-moving space has a fixed default size and is never compacted, so it fragments. Use small, reused buffers that grow geometrically. The branch starts at 512 bytes. The default size is in Numbers and method.
  • Allocation cost. A @FastNative call plus a free-list allocation, instead of the TLAB bump. It happens once per thread and per growth, not per event.
  • Host and Ravenwood. Host JVMs have no VMRuntime. Ravenwood, the platform’s host-side test runtime, has a fake one. Its newNonMovableArray returns a plain array, and its addressOf returns a made-up id, not a memory address. Keep the GetByteArrayRegion path as a fallback, as PathIterator does.

A smaller variant keeps the array parameter and swaps GetByteArrayRegion for GetPrimitiveArrayCritical. For a non-movable array, that also returns a direct pointer without touching the GC (Section 2). It still pays to decode the handle and check types on every event, and it rules out the next step.

Next step: @CriticalNative native_emit is @FastNative because it takes the event name as a String, which native code decodes through JNIEnv. A @CriticalNative method must be static and take only primitives, and it gets no JNIEnv. If the name is also encoded in Java, into the same buffer or as an interned id (a small integer standing for a string registered once), every argument becomes a long or int. Then the emit can be @CriticalNative, which skips the JNI frame and local-reference setup entirely.
Part II · Writing the bytes in Java

5One direct-buffer put() wraps a single store in a chain of loads and checks

If a direct buffer gives native code the same pointer, why not encode into a DirectByteBuffer? Because of what each put(byte) does on the Java side:

libcore/ojluni/src/main/java/java/nio/DirectByteBuffer.javapublic final ByteBuffer put(byte x) {
    if (!memoryRef.isAccessible) {
        throw new IllegalStateException("buffer is inaccessible");
    }
    if (isReadOnly) {
        throw new ReadOnlyBufferException();
    }
    put(ix(nextPutIndex()), x);   // ix(i) = address + i
    return this;
}
private ByteBuffer put(long a, byte x) {
    Memory.pokeByte(a, x);
    return this;
}
// Buffer.nextPutIndex(): int p = position; if (p >= limit) throw ...; position = p + 1; return p;

Memory.pokeByte is an intrinsic. The compiler recognizes the call and replaces it with inline machine code, here a single arm64 strb (store byte). So the call overhead disappears. What remains is that the compiler must record which memory the store may touch, and for a raw address the answer is “any”. The intrinsic is declared kWriteSideEffects, which the compiler records as SideEffects::AllWrites(). Section 7 explains the consequences. Nothing after the poke keeps the buffer alive explicitly. The method relies on ART keeping this live until it returns (Section 8).

Bulk put is worse put(byte[], off, len) goes through Memory.pokeByteArray, which is registered with plain NATIVE_METHOD: a regular JNI method that pays the full thread-state change. It is not an intrinsic, and not even @FastNative. Its body is a GetByteArrayRegion into the destination address. So every region put is a full JNI transition plus a copy, a poor fit for the short fields protobuf encoding produces.
What about Unsafe? Unsafe does not help either. Its raw-address putByte(long, byte) is a @FastNative JNI call on every byte. This holds for both sun.misc.Unsafe and jdk.internal.misc.Unsafe. Only the object-and-offset putByte(Object, long, byte) form is compiled inline, and it is declared kAllSideEffects: it may read and write any memory, an even broader side effect than pokeByte’s. It drops the buffer checks but not the side-effect problem, and a wrong address corrupts memory silently.

6The compiler can delete array bounds checks, but not a buffer’s

Java requires every array access and every buffer put() to be checked against its bound. A compare and branch per byte is a large overhead next to a one-instruction store. So what matters is which checks the compiler can delete.

ART’s optimizing compiler represents a method as a graph of instructions whose class names start with H. a[i] = v becomes an HArraySet guarded by an HBoundsCheck(i, a.length). put() instead runs an explicit p >= limit test in nextPutIndex, which is ordinary Java code. Bounds-check elimination (BCE) is the pass that deletes bounds checks it can prove redundant. Whether it can depends on where the bound lives.

BCE tracks value ranges relative to the array length and deletes bounds checks it can prove are in range. When it cannot prove it up front, it can still add one compare before the accesses that deoptimizes, dropping to the interpreter, if it fails. Then it removes the individual checks. It does this for loops, and for groups of accesses like a[pos]…a[pos + 7] in one block (AddComparesWithDeoptimization). The group must be big enough; the thresholds are in Numbers and method.

The DirectByteBuffer test is not a bounds-check node, so BCE never looks at it. It could only fold away if load/store elimination first proved that position and limit are unchanged since the previous put(). The poke in between prevents that proof (Section 7).

ProtoWriter.java · putLongLeNoCheck (branch)byte[] buf = mBuf;    // fields hoisted into locals
int pos = mPos;
buf[pos] = (byte) value;
buf[pos + 1] = (byte) (value >> 8);
// ... pos + 2 .. pos + 6 ...
buf[pos + 7] = (byte) (value >> 56);
mPos = pos + 8;         // one write-back

This is the shape BCE handles best: one base index, constant offsets, and a length that cannot change. Each public write* on the branch checks capacity once, for the worst-case size, and then writes through these *NoCheck helpers. Each helper loads and stores the position field once. So the field traffic is a couple of loads and stores per field, not per byte.

What it means for you Write into a byte[] with the position in a local, and check capacity once per field rather than once per byte. That gives the compiler an immutable bound to reason about and nothing to reload.

7A raw-address write makes the compiler forget every field it loaded

Section 5 showed the buffer’s fields being reloaded around every poke. That comes from how the compiler decides whether a value it loaded earlier is still valid. Two memory accesses alias if they may touch the same location. A loaded value can only be reused if nothing in between may alias it.

To answer that cheaply, the optimizing compiler records side effects for every instruction: which kinds of memory it may read and write. Fields are tracked by type, and arrays by element type. That set decides what the compiler may keep in a register across the instruction.

ART marks pokeByte and reachabilityFence as able to write any memory (AllWrites), and the inline Unsafe byte stores as able to read and write any memory (AllExceptGCDependency).

“Cached” means kept in a register

Reading buf.position is a load from the heap. “Caching” it means the compiler keeps the loaded value in a CPU register and reuses it. It has nothing to do with the L1 cache. A register read is free. A load is an instruction whose result the next instruction waits for.

; compiler can keep the register (shape)
ldr  w1, [x0, #position]   ; load once
strb a,  [base, w1]
add  w1, w1, #1
strb b,  [base, w1]
add  w1, w1, #1
str  w1, [x0, #position]   ; store once
; poke between the puts (shape)
ldr  w1, [x0, #position]
strb a,  [base, w1]
add  w1, w1, #1
str  w1, [x0, #position]   ; must store first
<AllWrites: anything may have changed>
ldr  w1, [x0, #position]   ; must reload
strb b,  [base, w1]
add  w1, w1, #1
str  w1, [x0, #position]

LSE, GVN and LICM all lose to the poke

Three passes remove redundant memory traffic, and each needs a proof that nothing in between wrote the value. The poke in put() is an intrinsic call, which the compiler still represents as an HInvoke (its node for a method call), with AllWrites. Each pass handles it like this:

PassWhat it removesMemory.pokeByte (an HInvoke with AllWrites)
LSE · load/store eliminationReloads of a known value; stores that are overwritten before being read.HandleInvoke: every heap value that might be shared (anything but a fresh, non-escaping allocation, i.e. an object created in this method that no other code can see) becomes unknown, and pending stores must be kept.
GVN · global value numberingRecomputing an identical value, including loads.set->Kill(current->GetSideEffects()) drops every load of a written type
LICM · loop-invariant code motionWork that gives the same result on every iteration.loop effects include AllWrites, so no field load is hoisted

So inside put() the poke forces every reload. A byte[] loop with pos in a local is unaffected, because an array store only writes array elements of its type.

What it means for you Avoid raw-address writes in a hot loop. Each one ends every “this field has not changed” proof. So all the buffer state around it is loaded and stored again for every byte.
Part III · Keeping it alive

8Something must keep the array alive while native code uses its address

The GC frees an object once it is no longer reachable, meaning no chain of references from a GC root leads to it. Roots are things like a thread’s stack, a static field or a JNI global reference. A long holding the object’s address is not a reference. So once code works only with the address, the object’s survival depends on how long the compiler keeps the original reference visible to the GC.

The Java language rules let an object become unreachable after its last use, even while a method that used it is still running. ART has historically been more conservative. To see how, three terms are needed:

  • A safepoint is a place in compiled code, such as a call or a loop back-edge (the jump back to the top of a loop), where the thread may stop for GC.
  • A stack map tells the GC which stack slots and registers hold live references at that safepoint.
  • The method’s environment is the set of values recorded at each safepoint.

By default ART keeps every reference in the environment live. SsaLivenessAnalysis::ShouldBeLiveForEnvironment returns true for every reference unless the graph is dead-reference safe, meaning the compiler may drop a reference after its last use.

That only happens for classes annotated @DeadReferenceSafe. It does not happen for methods that touch a @ReachabilitySensitive member, which is a field, usually a native pointer, whose owner must stay alive while it is used. The @DeadReferenceSafe documentation describes the risk: an object is finalized and its native memory freed while a method is still using a pointer copied out of it. It then says: “Historically, ART has avoided this by keeping ‘this’ reachable until m() completes.”

Reference.reachabilityFence(obj) is that artificial use. The compiler treats it as an intrinsic. The call stays in the graph as an HInvoke whose argument keeps the reference live up to that point, so the reference is in the stack maps of the safepoints before it. It is declared with write side effects, so dead-code elimination cannot remove it, and the arm64 intrinsic code generator’s VisitReachabilityFence is empty.

The fence costs no instructions, but it blocks some optimizations

KindCost
Instructions (compiled)None. The arm64 code generator emits nothing.
Instructions (not intrinsified)The Java body runs: a volatile store to SinkHolder.sink, then a volatile read and (normally) a second store that clears it. Its comment says this path runs only when ART executes the method without the intrinsic, for example in tests run under the access-checks interpreter.
OptimizerAllWrites: blocks LSE, GVN and LICM like any other call (Section 7).

ART inlines methods with try/catch (kInlineTryCatches), except at call sites that are themselves inside a try block, or that were devirtualized through CHA (class hierarchy analysis, which proves only one implementation is loaded) or an inline cache (the receiver classes recorded at that call site at run time).

Per byte, in a hot write loop, these costs would add up. DirectByteBuffer.put has no fence at all: it relies on the “ART default” column of Figure 8. Once per event, around a JNI call, they are negligible, because the call is already an opaque point for every pass. In the SDK design a fence is likely unnecessary anyway. mBuf stays reachable through the ProtoWriter that the thread-local builder holds. And because the array is non-movable, a GC during the native call cannot relocate it either.

What it means for you Whenever you turn an object into a raw address, something else has to keep it alive. Prefer a strong field the GC can see. Use reachabilityFence after the last raw access when the only reference is a local.
